# 2026-07-26

## `canonical_compute_required` now decides something

The field was set on all eleven capability rows and read by nobody:
`grep -rn canonical_compute_required --include=*.rs` matched only the struct
definition and the rows themselves.

Chose to enforce it rather than delete it, because "genuinely dead weight" was
close to true but not true. The contract it describes — a backend accepting
`-os` keeps emitting the canonical block `compute`, empty, so the ordinary DSP
interface stays satisfied — *is* checked today, by four hand-written
per-backend tests in `crates/compiler/tests/execution_options.rs`. But those
tests name their signatures directly and never consult the table, so the
dependency ran the wrong way: `fir` accepts `-os` and had no such test at all,
and a new row could claim `canonical_compute_required: true` and get zero
coverage.

So the new test is driven by the table. `all_backend_execution_caps()` exposes
the rows; the loop visits every one whose `one_sample` is supported, and
`compute_probe` panics on a backend it does not recognise — a new row claiming
`-os` support cannot reach the assertion without someone stating what its
canonical `compute` looks like. Six rows are visited: c, cpp, rust, fir, asc,
and codebox as the single negative case.

Each probe carries two signature fragments, not one. `block_compute` alone
cannot distinguish a backend that correctly omits the canonical entry point
from a probe that is simply looking for the wrong string — both read as
"absent". So `per_sample` is asserted present on every backend, which makes a
mis-typed probe fail loudly instead of quietly agreeing with a
`canonical_compute_required: false` row. This is the same failure mode the C4
`iadd` mutation exposed: a test that passes for a reason unrelated to what it
claims to check is indistinguishable from one that works.

Scope kept deliberate: the new test checks presence versus absence against the
row. That the entry point is present *and empty* stays with the four
per-backend tests, which pin exact signatures — recorded in the doc comment so
the division of labour is on record rather than an oversight.

Four rejecting mutations:

| Mutation | Result |
| --- | --- |
| codebox row → `canonical_compute_required: true` | fails, naming the row and the missing fragment |
| cpp row → `false` | fails, in the other direction |
| new row (`cmajor`) accepting `-os`, no probe | panics with the fail-closed message |
| drop the empty canonical `compute` from FIR lowering under `-os` | fails, together with 3 of the 4 hand-written tests |

The fourth is the one that matters: it is the actual defect the field claims to
guard, and before today nothing tied that guard to the table.

One honest limit. Codebox's `block_compute` fragment is `count`, on the
reasoning that a block entry point must take a sample count and nothing else in
the emitted file mentions one. That its absence is noticed is proven by the
first mutation; that it would be *present* if codebox ever grew a block entry
point cannot be proven without writing that code.

Plan: `porting/external-control-one-sample-port-plan-2026-07-23-en.md` §4.2.

Validation: `cargo test --workspace`; `cargo clippy --workspace --all-targets
-- -D warnings`; `cargo fmt --all --check`; `xtask cli-transcript-check`.

## Codebox C5: wire the CLI, and settle what an execution option means when the backend has no choice

The last phase of the codebox port. `-lang codebox` and `-lang codebox-test`
now reach the backend, the facade has its six entry points, and the capability
table has a codebox row.

The open question from the plan was the capability model. Codebox *requires*
external control and one-sample and *forbids* `-vec`, and the table was built
for flags that are opt-in per backend. The plan proposed either a new "forced"
state or a lowering path that imposes the modes itself.

Neither, quite: `ExecutionCapability::Intrinsic` already said the right thing —
"the backend's native contract already has a tick/control split; the flag is
accepted as an output-invariant compatibility alias". RNBO calls the generated
code once per sample and sets controls through `@param` identifiers, so those
two modes are what codebox *is*. The row is `Intrinsic` on both, and
`lower_signals_to_codebox` forces them into the lowering context before
validating. That override is what makes the "output-invariant" half true rather
than merely claimed, and a test asserts all four execution shapes emit
byte-identical text — plus that the shared text really is the one-sample shape,
so the assertion is not four copies of block code.

`-vec` could not be absorbed that way, so the table grew a `vector` column.
Reusing the existing `OneSampleWithVectorMode` was tempting and wrong: its
message blames `-os`, which someone writing `-lang codebox -vec` never typed.
`FRS-EXEC-VEC-BACKEND` names the backend instead. All ten pre-existing rows are
`Explicit`, preserving their behaviour exactly; the doc says plainly that this
means only "validation does not reject `-vec` here", not that the emitter has a
certified vector lane. Validation now checks that column *before* the `-ec`/
`-os` early return, because a backend can refuse `-vec` with neither flag in
play, and the CLI guard was widened to match.

`codebox-test` is a second `-lang` value rather than a modifier flag, as in C++
Faust. It therefore needed `cli_backend_id` split out from `cli_lang_name`:
looking a capability row up under `codebox-test` fails closed and would reject
a perfectly valid command line.

Three rejecting mutations: dropping the two forcing assignments, flipping the
codebox row to `vector: Explicit`, and making `cli_backend_id` fall through for
`CodeboxTest` — each fails the tests that claim to cover it.

## Document the `CompilerError` fields and lock the `missing_docs` gate

`cargo rustdoc -p compiler --lib -- -D missing-docs` reported 48 errors, every
one a struct field of a `CompilerError` variant, while the sibling `transform`
crate has enforced that exact gate for a while.

Documented all 48, but not by restating "the source", "the error", "the
diagnostics" thirteen times. The non-obvious facts belong to the enum as a
whole and are stated once there: `source` is provenance for messages only — a
display path for the file-based entry points, the caller-supplied logical name
for the in-memory ones, not a key and not necessarily a file that exists;
`diagnostics` is *derived from* `error`, so the two can never describe
different failures, which is why the variants whose bundle takes real work
expose a constructor (`CompilerError::import`, `missing_root`, `codegen_wasm`)
that callers should prefer over building the variant by hand.

`#![warn(missing_docs)]` now sits in `lib.rs` as it does in `transform`. Since
the workspace CI gate runs `cargo clippy --workspace --all-targets -- -D
warnings`, an undocumented public item is a hard failure from here on rather
than a number someone has to remember to re-measure.

Plan: `porting/compiler-cleanup-plan-2026-07-26-en.md` (phase P1).

Validation: `cargo rustdoc -p compiler --lib -- -D missing-docs` exits 0;
`cargo clippy -p compiler --all-targets -- -D warnings`; `cargo test -p
compiler`. Behavioral freeze checked by a new CLI transcript differential (148
modes: every `--lang`, every `--dump-*`, the argument-validation errors, and
the FIR-fixture ladder over all 7 built-in fixtures, capturing stdout, stderr
and exit status) — identical before and after, as a documentation-only change
must be.

Harness note, recorded because it produced a false positive first: the DSP
inputs must live at a path of *fixed length*, not inside the per-run output
directory. The source path is embedded in the wasm module's JSON, so a
directory named `before` versus `after` shifts two LEB128 length prefixes by
one byte — and text normalization of the path hides the cause while leaving the
binary difference visible. A differential whose own scaffolding varies between
runs reports changes that are not there.

Public API mapping: documentation only. No signature, behavior, or output
change.

## Split `run_main()` into named phases

`run_main()` in `crates/compiler/src/cli/runner.rs` was 1 356 lines — the
single worst obstacle to reading this crate. Its shape only becomes visible
after scrolling: an argument-validation prologue, then the `--fir-fixture`
mode, then the DSP-source mode, the last two being parallel per-backend
emission ladders that answer the same question ("which backend did the user
ask for?") from two different starting points.

Extracted, as a pure move, into `handle_early_exit_modes`,
`spawn_timeout_watchdog`, `handle_fixture_listing`, `validate_cli_arguments`,
`run_fir_fixture_mode` and `run_source_mode`. `run_main()` is now 24 lines and
reads as a table of contents.

Two details the extraction had to make explicit rather than preserve blindly:

- the validation block contained a bare `return` (the "no output mode and no
  input file" case prints the scaffold banner and stops). Once extracted, that
  is no longer "return from `run_main`", so `validate_cli_arguments` returns
  `Option<usize>`: `None` means the run is already over, `Some(0)` means "no
  explicit mode" and the caller falls back to default C++ emission;
- the fixture ladder reads `mode_count`, which the prologue computes, so it
  becomes a parameter instead of an ambient local.

The doc comment on `validate_cli_arguments` records the property that makes
this function fragile to reorder: every rejection exits with status 2, so the
*order* of the checks decides which message a doubly-invalid command line
reports.

Validation: CLI transcript differential over 148 modes (every `--lang`, every
`--dump-*`, the argument-validation errors, and the FIR-fixture ladder across

before and after. Plus `cargo fmt --all --check`, `cargo clippy -p compiler
--all-targets -- -D warnings`, and `cargo test -p compiler` (31 suites green).

## Finish P3: drop the redundant import-dir branches, share the fixture JSON companion, and land the transcript harness

Three cleanups that the earlier phases made visible and safe.

**The 17 `if cli.import_dir.is_empty()` branches were provably redundant.**
Every `*_default*` entry point is literally `*(path, &[])` — for example
`compile_file_default(path)` is `self.compile_file(path, &[])` and
`compile_file_default_to_cpp_with_lane(p, o, l)` is
`compile_file_to_cpp_with_lane(p, &[], o, l)`. Since `&cli.import_dir` on an
empty `Vec` *is* `&[]`, both arms of every one of those `if`/`else` blocks
called the same function with the same arguments. Replaced by the single call:
`source_mode.rs` drops from 756 to 644 lines, and the reader stops looking for
a difference that was never there. The `*_default*` family stays in the facade
— it is a legitimate convenience for library callers; it is the CLI that had no
use for the distinction. The one *negated* check (`--import-dir is not
supported with --golden`) is a real rejection and stays.

**Nine of the fixture ladder's JSON-companion blocks were identical.** The
source ladder already had `emit_cli_json_companion_for_backend`; the fixture
ladder open-coded the same three statements nine times, differing only in the
backend name. Now one `emit_fixture_json_companion` helper. Two companion sites
deliberately stay out of it and the helper's doc says why: the WASM branch
emits the module and its matched JSON together, and the standalone `--json`
branch already holds the rendered text. (The first attempt at this assumed ten
identical blocks; the pattern-match found nine, which is what stopped the
change from folding the two genuinely different sites into the helper.)

**The transcript differential is now part of the repo.** It had lived as a
throwaway script for four commits. It is now `xtask cli-transcript-gen` /
`cli-transcript-check` with the snapshot in `tests/cli-transcripts/` (132
modes: every `--lang`, every `--dump-*`, the option combinations, the
argument-validation errors, and the fixture ladder over all 7 built-in
fixtures — stdout, stderr and exit status each). Its module doc records the two
traps it is built around: inputs must sit at a path of *fixed length* (the
source path is embedded in the wasm JSON, so a directory named `before` versus
`after` shifts LEB128 length prefixes and text normalization then hides the
cause), and only genuinely unstable fields may be normalized (the Cranelift
runtime `compute_entry_addr`, nothing else).

Checked as a real guard, twice. Changing one letter of the Cranelift report
header produces 9 findings. A first attempt mutated the "JSON fixture
generation failed" message instead and the check stayed green — correctly, since
that path only runs when JSON generation fails, which the matrix never
provokes. Recorded because it is the useful lesson: a rejecting mutation only
proves anything if it lands on a line the matrix actually executes.

Also fixed in the harness itself before it could mislead anyone: the
normalization loop as first written never terminated (it replaced
`compute_entry_addr: 0x<hex>` with text that still contains the search key, so
every pass matched again and the string grew). It now scans forward into a
fresh string.

## Share one validation prologue across the backend dispatchers

The six `lower_signals_to_{cpp,c,julia,asc,rust,interp}` dispatchers in
`signal_lowering.rs` were 16 lines each and identical except for four tokens:
the options type, the error envelope, the backend name, and the fast-lane
function called. They now delegate to one `lower_signals_with_validation`,
generic over the options and error types, with `?` lifting an execution-option
rejection through three new `From<ExecutionOptionsError>` impls (one blanket
one for `LowerError<E>`, one each for the bespoke interp and FIR envelopes).

Honest accounting: the file grew from 759 to 804 lines. `rustfmt` expands a
six-argument call to one argument per line, and the shared function, the `From`
impls and the documentation below all cost lines. The gain is not volume — it
is that the execution-option check now exists in exactly one place, so the six
backends cannot drift apart, and each wrapper body is three lines of pure
delegation instead of five lines mixing validation with delegation.

**A hidden fact surfaced.** Each dispatcher contained `let _ = ctx.lane;`. That
statement was load-bearing: it silenced a dead-field warning, because
`SignalLoweringContext::lane` is read *nowhere*. Removing the six copies made
`clippy` say so immediately. The field is kept — the public entry points do take
a lane, and recording it here is what makes a second lane a change to the
lowering rather than to every signature — but it now carries an explicit
`#[allow(dead_code)]` and a doc comment stating that nothing reads it, instead
of six scattered no-ops hiding the same thing in six places.

Also repaired while there: the insertion initially landed between
`#[allow(clippy::too_many_arguments)]` and the `lower_signals_to_fir` it
annotates, orphaning the attribute and its explanatory comment. Caught by

## One generic error mapper behind a `BackendCodegenError` trait

The five `lower_{cpp,c,julia,asc,rust}_error_to_compiler` functions were 17
lines each and identical except for the backend name and the
`CompilerError::Codegen*` variant they built. What blocked a generic version
was not the variant — a constructor closure handles that — but the accessors:
five backend error types expose `code()` / `message()` as **methods**, while the
interpreter and Cranelift ones expose `code` / `message` as **public fields**, so
no single expression could read both.

`codegen::backend_error::BackendCodegenError` is that missing common surface,
with `code_str()` / `message_str()` and seven small impls generated by two local
macros (one per accessor shape). It abstracts nothing else: emission, options
and failure kinds genuinely differ per backend, and unifying them would hide
real differences. A unit test asserts both accessor shapes reach the same
strings, so a generic consumer cannot tell a method-based backend from a
field-based one.

With that in place, `lower_error_to_compiler` holds the three shared arms once
and takes `backend` plus a `wrap` closure for the fourth. The five mappers are
now four lines each. `CompilerError` keeps its eight per-backend `Codegen*`
variants (decision recorded: the naming regularity was the real irritant, and
collapsing them would cost the typed error a caller can match on), so `wrap` is
what preserves that choice while removing the duplication.

`cranelift` and `interp` keep hand-written mappers, and their doc comments now
say why: neither envelope is a `LowerError<E>` — Cranelift folds two fallible
backend steps into one `Codegen` variant, and the interpreter has an extra
`Serialize` arm.

**A detached doc comment fixed, of my own making.** The `LowerToInterpError`
doc block sat above `lower_cranelift_error_to_compiler`, and
`lower_interp_error_to_compiler` had none at all: `fbe0f0b3` inserted the
Cranelift mapper between the interp doc and the interp function — the exact
hazard `cf2d8808` had documented two commits earlier. Both now carry their own
comment. Worth recording that the first attempt at this change reproduced the
same class of defect three more times through regex-based deletion spanning doc
comments; the fix was to locate each function block by walking back over its
`///` lines instead.

## Numeric impulse tests for `-ec` / `-os`, on a self-contained architecture

The execution-options port claimed runtime equivalence — `control(); frame()xN`
bit-exact against `compute(N)` — and verified it with an external harness that
was never committed. In-tree, only
`crates/compiler/tests/execution_options.rs` guarded it, and that inspects
emitted *signatures*, not numbers. `tests/impulse-tests` now covers the numbers.

Nine new targets, for the three backends whose capability table marks the
options Explicit and that have a runnable impulse target: `make {cpp,c,rust}-ec`
/ `-os` / `-ec-os`, plus `make all-execopts`. `interp`, `cranelift`, `wasm`,
`wast` and `julia` are Unsupported; `fir` is a text dump with no runtime.

Each shape is compared against the same classic `reference/*.ir` as every other
target, on the scalar prefix. That is the property worth checking: selecting an
execution option must not move the impulse response by one bit. Result: 131 of
133 DSPs pass in all nine shapes.

That figure comes from a strictly sequential run. A first full pass reported the
same numbers while an earlier pass was still running against the same `build/`
and `ir/` directories — two makes writing one output tree can let a comparison
read a partially written `.ir` and pass for the wrong reason, so that result was
discarded and the whole matrix replayed one target at a time.

**Why a new architecture was needed.** The reference 4-pass architecture only
ever calls `compute(count, ...)`. Under `-ec` the block-rate work lives in
`control()`, so a host that never calls it reads uninitialized slow values;
under `-os` the canonical `compute` is deliberately *empty* and the sample body
sits in `frame()`, so the same host measures silence. Either way the test would
fail for the harness's reason and look like a compiler bug.

**And why it is self-contained.** `archs/faust_minimal.h` and
`archs/faust_minimal_cglue.h` are faust-rs-owned reimplementations of the
architecture surface the generated scalar code needs — `dsp`, `UI`, `Meta`, the
`Soundfile` layout, the suite's synthetic soundfile fixture, and the
`UIGlue`/`MetaGlue` layouts the C backend emits calls against. Not copies of the
C++ Faust headers. Verified by building these targets with `FAUST_ARCH` and
`CPP_TESTS` pointed at nonexistent paths. Producing `reference/*.ir` still needs
the C++ oracle, exactly as for every other target.

Structure: `archs/impulseexecopts_driver.h` holds the driver once;
`impulseexecopts.cpp` (C++ backend, the generated class is used directly) and
`impulseexecopts_c.cpp` (C backend, a wrapper class forwards to the generated C
functions) are thin front-ends — the same split the reference makes between
`impulsearch.cpp` and `impulsearch2.cpp`. `archs/impulserust.rs` gained
`--cfg impulse_ec` / `--cfg impulse_os` call sites rather than a second copy;
its classic output is byte-identical to before the change.

`known.mk` learned the new suffixes: `base_backend` now strips `-ec-os` before
`-ec`/`-os` (longest first, or `cpp-ec-os` would become `cpp-ec`), so each shape
inherits its base backend's known failures.

**Two DSPs excluded, for different reasons.** `subcontainer1` is the existing
global compile gap. `bs` is not a divergence at all: it reads the foreign
variable `count`, which the execution options forbid on purpose
(`FRS-SFIR-0009`). It is excluded from the gate rather than silenced, so
`make ir/cpp-ec/bs.ir` still shows the refusal.

**Three harness bugs found by their own failures, worth recording because each
looked like a compiler bug:**

1. *Pressing check buttons.* The driver set every button *and* check-button
   zone. The reference's `FUI::addButton` registers its zone for `setButtons()`
   while `FUI::addCheckButton` does not, so a check button keeps its
   `instanceResetUserInterface()` value. `UITester.dsp` differed by a constant 1.
2. *A 512-frame block.* `kFrames` must match the reference's 64: the block size
   decides how long the buttons stay pressed, so a larger block held them longer
   and `UITester.dsp` diverged from frame 64 onward. `archs/impulserust.rs`
   already had `BLOCK_SIZE = 64`.
3. *`FAUSTFLOAT` left at `float`.* `-double` selects double for the DSP *core*;
   the interface type is architecture-controlled, and `impulsearch.cpp` sets it
   to `double` on its very first line. Leaving the generated default cost
   precision at the I/O boundary — a 4e-6 absolute divergence on
   `downsampling_06_multi_branch`, past the 2e-6 tolerance, while every
   small-signal DSP still passed. Diagnosed by checking whether the *classic*
   shape of the new driver also diverged (it did) and whether the official `cpp`
   target passed the same DSP (it did), which located the fault in the harness
   rather than in `-ec`.

The `-ec` driver was also checked for sensitivity: compiling `-ec` output
*without* `-DIMPULSE_EC`, so `control()` is never called, makes the output
differ. Without that check the target could have passed by not exercising the
contract at all.

Public API mapping: test harness only. No compiler, CLI or generated-code
change.

## Codebox backend port plan, with the manual RNBO validation as an explicit hand-off

Analysed the C++ `codebox` backend (1 009 lines under
`compiler/generator/codebox/`) and wrote
`porting/codebox-backend-port-plan-2026-07-26-en.md`: six phases (C0–C5), the
emitted module shape, and a three-layer test strategy.

**The structural finding that shrinks the port.** The C++ container relies on
`gExtControl` for a separate `control()` function and calls
`generateOneSample()` for the body — which is `ControlRateMode::External` plus
`ProcessingApi::OneSample` here. So codebox is a text emitter over a lowering
faust-rs already has, not a new lowering, and it inherits the execution-options
correctness work instead of duplicating it. Two pieces genuinely missing:
shortnames (our JSON `shortname` field is currently just the label, which is a
defect independent of codebox) and the `codebox-test` label convention.

**Testing, and the hand-off.** Upstream tests codebox through an RNBO export
(proprietary Cycling '74 tooling) plus `rnbo-dsp.h`; its only in-tree check is
that compilation succeeds, not that the output is correct. The plan therefore
proposes a textual differential against the pinned C++ compiler as the primary
oracle, a small codebox evaluator for numeric coverage against the existing
impulse `reference/*.ir`, and — as agreed — the manual RNBO round-trip run by
Stéphane in the C++ architecture *after* the backend and the differential are
delivered. That step is written up as an attempt whose outcome gets journalled
either way: a failure would mean our text passes the differential while RNBO
still rejects it, which points at something the reference does implicitly and we
reproduce only in appearance.

Specifying that hand-off promoted one item from optional to required:
`-lang codebox-test` must ship in phase C2, because `rnbo-dsp.h` recovers the
Faust UI purely by prefix-matching `RB_button_` / `RB_hslider_` / … on RNBO
parameter names, and from nothing else. Without it the manual run would produce
a DSP with zero controls and prove nothing.

**Everything asserted about the reference was measured against `faust 2.84.3`,
which corrected five drafting errors.** Recorded because each would have become
a wrong instruction to a future implementer:

1. `-double` is *accepted*, not rejected; it only changes the float-literal
   suffix (`0.5f` → `0.5`), so the differential must cover both precisions.
2. Arrays are declared *untyped* and constructed:
   `@state fVec0SE_cb = new FixedFloatArray(2);`.
3. The compile-options header reports `-ec` but *not* `-os`, so our provenance
   string will differ unless the flag list is filtered — and that string is part
   of the text being compared.
4. `@param` range literals are formatted inconsistently on purpose: sliders print
   `0.0f` / `1.0f` through `checkReal()`, buttons and checkboxes print `0.` / `1.`
   from a hardcoded range. The asymmetry has to be reproduced.
5. Bargraphs emit *no* `@param` at all — only an extra audio channel — while
   `rnbo-dsp.h` looks for `RB_vbargraph_*` parameters. The missing link is
   patch-level `snapshot~`/`change` wiring, done by hand in RNBO. A first manual
   validation should use a DSP without bargraphs.

The shortname algorithm was measured too (`a_gain` / `b_gain` disambiguation by
enclosing group, plus a codebox-only `cb_` prefix for digit-initial labels), and
one case found where the backend emits duplicate `@param` identifiers for
path-colliding widgets that the JSON path check rejects outright — left as an
explicit decision for phase C2 rather than settled silently by the differential.

Public API mapping: documentation only — no code change.

## Codebox port C0: shared short-name computation

First phase of `porting/codebox-backend-port-plan-2026-07-26-en.md`. Codebox
needs short, unique identifiers for its `@param` names, because codebox
parameters *are* identifiers rather than pointers to zones. The JSON description
needs the same thing for its `shortname` field — and was getting it wrong:
`shortname` was simply the label (`json.rs:859`), so any two widgets sharing a
label reported the same short name.

`crates/codegen/src/shortname.rs` ports `PathBuilder::computeShortNames`: turn
each address into a unique path prefixed `/P<index>`, then raise the "keep the
last N slash-parts" level of every colliding pair until none agree. Wired into
`build_json_description_from_fir` as a second pass over the finished UI tree,
because a short name cannot be decided widget by widget — it is the shortest
suffix no other widget shares, so all addresses must be known first (the C++
visitor likewise computes the mapping only when the enclosing box closes).

Verified against the pinned C++ compiler on
`vgroup("a", hslider("gain",…)) + vgroup("b", hslider("gain",…)) +
hslider("0freq",…)`: both now report `a_gain`, `b_gain`, `0freq`.

**Three things the tests caught, each worth recording.**

1. *A real bug in my first version.* The collision list was a `Vec` where C++
   uses a `std::set`. With three or more colliding paths the middle one is
   reported twice, so it was raised twice and skipped a level: `/d/{a,b,c}/g`
   gave `a_g`, `d_b_g`, `c_g` instead of `a_g`, `b_g`, `c_g`.
2. *Two of my expectations were wrong, not the code.* I assumed `str2ID` dropped
   a leading run of non-identifier characters. It does not — the underscore is
   emitted before the next kept character, so `" gain"` would give `_gain`. The
   reason that never appears is upstream: Faust trims labels and `buildPath`
   substitutes space/`#`/`*`/`,`/`?`/brackets/parens *before* `str2ID` runs, so
   `hslider(" gain")` arrives as the address `/dsp/gain`. Measured, not
   reasoned: the C++ JSON for that DSP shows `"label": "gain"`. The function's
   real behaviour is now asserted so it stays on record.
3. *An API limit worth stating rather than papering over.* The result is keyed by
   address, so two identical addresses collapse to one entry. That is sound only
   because Faust rejects duplicate addresses earlier
   (`ERROR : path '/dsp/g' is already used`, observed) — so the test asserts
   what actually matters, that the loop terminates, and the doc comment says why
   the collapse is acceptable.

Coverage note: no golden case contains a `shortname` field, so the golden suite
does not observe this fix; the unit tests are what cover it.

Validation: `cargo test -p codegen` (311 passed, 9 of them new);
`cargo clippy --workspace --all-targets -- -D warnings`; `golden-check` 197 OK;
`cli-transcript-check` 132 modes identical.

Public API mapping: `codegen::shortname::compute_short_names` is additive. The
JSON `shortname` field changes value where disambiguation is required — a
`preserved` fix, since it now matches the C++ compiler where it previously did
not.

## Codebox plan correction: byte parity with the C++ compiler is unreachable

Found while starting phase C1, before writing any emitter code. The plan's test
strategy rested on an assumption I never checked when writing it: that our FIR
lowering produces the same structure as the C++ one, so that a textual
differential against `faust -lang codebox` could serve as the primary oracle.

It does not, and it does not have to — the contract with C++ Faust has always
been *numerical* equivalence, which is what the impulse suite checks. Measured
on `process = + ~ *(0.5);`:

| | emitted loop body |
|---|---|
| C++ | `fVec0SE[0] = fTemp0SE; … fVec0SE[1] = fVec0SE[0];` (two-element shift buffer) |
| faust-rs | `fRec36 = fRecCur36;` (single scalar) |

Both are correct; the text is structurally different. And the divergence is not
confined to state: on `(_,_:+),(_,_:*)`, which has none, C++ emits
`static_cast<float>(x)` where we emit `((float)(x))`.

Consequences, applied to the plan:

- **Layer 1 is demoted** from "textual differential against C++ (primary
  oracle)" to "self-snapshot of our own output (regression detection only)",
  with the limit stated in the plan itself: a snapshot of a wrong output is a
  green snapshot, so it catches change, never wrongness.
- **Layer 2 — the codebox evaluator run against the existing impulse
  `reference/*.ir` — is promoted to primary oracle.** It is no longer
  "recommended"; it is the only layer that can show the backend is correct.
- **Layer 3, the manual RNBO round-trip, gains weight** as the only end-to-end
  check of the real chain.
- The C++ reference output kept in §7 is relabelled: it is a *language
  specification read by a human* — where the syntax of `@state`, `@param`,
  `iadd`/`imod`, `trunc` and the literal formatting come from — not a target
  compared by a machine. Spot-comparing by eye during C1–C4 stays worthwhile;
  wiring that comparison into a gate does not.
- Four residual mentions of the differential as a gate were rewritten, and the
  per-phase verification lines now say which properties *are* still comparable
  against C++ (parameter names, from the `preserved` shortname algorithm of C0;
  output count and order for bargraphs) and which are not (everything
  structural).

Recorded as its own entry rather than folded into a later commit because the
error was in the plan, not in code, and the useful part is why it survived
review: the plan asserted a property of *our* compiler while every other claim
in it had been measured against the reference. "Our FIR matches theirs" reads
like a premise, not a claim, which is exactly how it escaped being checked.

Public API mapping: documentation only.

## Codebox port C1: emitter skeleton, no UI

`crates/codegen/src/backends/codebox/mod.rs` replaces the scaffold with a real
emitter: header, `@state`/`let` declarations with the `_cb` suffix, `dspsetup`,
`control`, an `update` skeleton, the one-sample `compute`, and the file-scope
wiring. UI, bargraphs and the language quirks stay for C2–C4.

The backend consumes a FIR module lowered with external control and the
one-sample processing API, which is what makes it small: `control` supplies
codebox's `control()` and `frame` supplies the body of `compute()`. Selecting
that lowering is the caller's job, so the tests build it through
`compile_source_to_fir_with_lane` rather than waiting for the CLI wiring of C5.

Two bridges the FIR shape needs. The one-sample `inputs[]`/`outputs[]` function
arguments do not exist in codebox, so `inputs[0]` is rewritten to the `input0_cb`
local declared at the top of `compute` and the subscript disappears; the field
pass skips FIR's own `input`/`output` declarations for the same reason. And
`dspsetup` folds `classInit`, `instanceResetUserInterface`, `instanceClear` and
`instanceConstants` in the C++ container's order, with literal array contents
written first — arrays are declared constructed-but-empty
(`new FixedFloatArray(n)`), so their contents can only be written there.

Checked by eye against the reference, which is all §5.2 allows: for
`process = _;` our output is identical to `faust -lang codebox` apart from the
header line. For `process = + ~ *(0.5);` it is *correctly* different — we emit
`@state fRec36_cb` where C++ emits an `IOTA0` + `fVec0SE` ring buffer, which is
the lowering divergence that made byte parity unreachable in the first place.

Ten tests, checking properties rather than text: section order, one-sample
`compute` arity and return list, that the I/O arrays never leak into the body,
that no emitted identifier ends with a digit (codebox rejects those, and every
Faust name is `fRec0`/`IOTA0`/`fSlow1`), that `@state` scalars always carry an
initialiser, that `sample_rate` reads through `samplerate()` rather than a
field, that `-double` changes literal spelling and nothing else (asserted as
`single.replace("0.5f", "0.5") == double`), and that soundfiles are rejected
with `FRS-CGEN-CBOX-0002` rather than mis-emitted.

Two drafting errors the tests caught, both mine: `ma.SR` needs an `import`, and
`fconstant` is not supported by our lowering (`FRS-SFIR-0004`) — the sample-rate
test now uses the `fSampleRate` field every module already carries.

The `codegen` README consistency test then failed, correctly: codebox was still
listed as scaffolded. Moved to bring-up with its entry point named. That test
exists for exactly this and it worked.

Validation: `cargo test -p codegen -p compiler`; `cargo clippy --workspace
--all-targets -- -D warnings`; `cli-transcript-check` 132 modes identical;
`structure-check` clean.

Public API mapping: additive — `codegen::backends::codebox::{CodeboxOptions,
CodegenError, CodegenErrorCode, generate_codebox_module, codebox_var_name}`.
No CLI surface yet; that is C5.

## Codebox evaluator: the numeric oracle the port actually needs

Plan §5.2 layer 2, promoted to primary oracle by the correction in `a02b965e`.
Text cannot arbitrate codebox output — our lowering legitimately differs from
C++'s — and a snapshot of our own output only detects change. This runs the
emitted code.

`crates/codegen/src/backends/codebox/eval.rs` parses and evaluates exactly the
subset the emitter produces: `@state`/`let` declarations, `new
FixedFloatArray(n)`, assignment to a variable or array element, `if`/`for`/
`while`, parenthesised operators, function definitions and calls, the integer
helpers (`iadd`/`isub`/`imul`/`imod`, wrapping at 32 bits), the math names
codebox exposes, `samplerate()` and `return [a, b]`. Anything outside that is a
hard error: an evaluator that guessed would report a green test for code RNBO
would reject.

**It executes the emitted file's own top level**, rather than calling `update`
and `compute` directly. That is where `outputs = compute(in1, …)` and
`out1 = outputs[0]` live, so running it is what checks the *wiring* — including
channel order, which is how C3 will append bargraphs after the real outputs.
Driving the functions directly would assume the wiring instead of verifying it.
Clippy is what surfaced this: it reported the parsed top level as a never-read
field, which was true and was the design flaw.

The oracle is the **interpreter**, in-process: both backends consume the same
FIR module, so a disagreement isolates the codebox emission from the lowering,
and the interpreter is itself validated against the genuine C++ reference by the
impulse suite. Four numeric tests — passthrough, arithmetic, a recursion over
256 samples, a 7-sample delay — compare sample for sample at 1e-9.

Checked as a real oracle, not a decorative one. Flipping `FirBinOp::Sub` to
emit `+` fails the arithmetic and delay tests; changing the evaluator's `trunc`
to `floor` fails its own rounding test. That second mutation matters because
`trunc` versus `floor` is precisely the C4 quirk, and it differs only on
negative values — a text comparison would never see it.

**Two real bugs the tests caught, both mine.**

1. *`ForLoop` was unhandled.* Only `SimpleForLoop` was, so a `@(7)` delay hit
   `FRS-CGEN-CBOX-0002`. Added, with the reverse form and the `iadd` step
   spelling codebox requires.
2. *File-scope declarations re-ran every sample.* `@state x = 0;` was kept in
   the per-sample top level as well as registering state, so it wiped whatever
   `dspsetup` had initialised — the sample-rate test read 0 instead of 48000.
   A declaration now runs once; only bare statements are per-sample wiring.

And one thing the change exposed about the tests themselves: the evaluator's
unit fixtures had no file-scope wiring at all, so they were exercising a
fiction. They now carry the real `update(); outputs = compute(in1);
out1 = outputs[0];` tail.

Validation: `cargo test -p codegen -p compiler`; `cargo clippy --workspace
--all-targets -- -D warnings`.

Public API mapping: additive — `codegen::backends::codebox::eval::{Program,
EvalError}`.

## Codebox port C2: params, control, update, and the `codebox-test` convention

`@param` declarations from the UI, `update()` with its dirty-check protocol,
and both label conventions. `control()` already carried the externalizable
statements from C1; C2 gives it something to compute.

Parameters come from walking `buildUserInterface`, with short names from C0.
The two-pass shape is forced: a short name is the shortest address suffix no
other widget shares, so no widget can be named until every address is known.

**The range asymmetry is reproduced, not normalised.** Sliders and numeric
entries carry their real range through the float formatter (`{min: 0.0f, max:
1.0f}`); buttons and checkboxes carry a hardcoded one spelled differently
(`{min: 0., max: 1.}`), because the C++ visitor writes those literals directly.
Normalising would cost nothing functionally and would make a by-eye comparison
against the reference noisier for no gain.

**`codebox-test` ships here, as the plan required.** `rnbo-dsp.h` rebuilds the
Faust UI purely by prefix-matching `RB_button_` / `RB_hslider_` / … on RNBO
parameter names and by nothing else, so without this the manual round-trip
would produce a patch with zero controls.

**The colliding-address decision, recorded.** Two controls sharing an address
would share a `@param` identifier, and `update` would declare the same argument
twice — not valid codebox. The C++ backend does not check and emits the
duplicate; we refuse with `FRS-CGEN-CBOX-0002`. A deliberate divergence: Faust
rejects duplicate addresses upstream anyway, so the only way to reach this is a
path the reference itself mishandles.

**Two quality fixes the reference comparison exposed.**

1. *Float literals were unreadable.* FIR carries constants as `f64` even for a
   single-precision DSP, so `0.3` printed as `0.30000001192092896f`. Narrowing
   to `f32` *before* formatting gives `0.3f`, since `f32`'s Display yields the
   shortest text that round-trips at that width. My first attempt narrowed after
   formatting and changed nothing, which is worth remembering: the order is the
   whole trick.
2. *The evaluator ignored `@param` defaults.* It parsed the declarations as
   ordinary statements, so every parameter read 0 instead of its declared
   value. Parameters are now registered with their default, and passing an empty
   slice to `compute` leaves them there — what a host that has written nothing
   would do.

**A precision artefact worth stating rather than tolerating.** The numeric test
now runs both sides in double precision, because codebox has a single `number`
type and it is a double. Against a single-precision DSP a `0.3f` constant is
`0.30000001192092896` in the DSP and exactly `0.3` in codebox, a ~1e-8
disagreement that no emitter change can remove — measuring it would have meant
loosening the tolerance until the test stopped meaning anything.

Nine new tests: the range asymmetry, `control()` running once per update rather
than once per parameter that moved, agreement between the `@param` names, the
`update` signature and the top-level call (a mismatch makes the file
unparseable), the `RB_` prefixes present in test mode and absent otherwise,
`a_gain`/`b_gain` disambiguation, the `cb_` prefix for digit-initial labels, and
a numeric run of the full UI DSP against the interpreter.

Validation: `cargo test -p codegen -p compiler` (22 codebox tests);
`cargo clippy --workspace --all-targets -- -D warnings`.

Public API mapping: `CodeboxOptions` gains `test_labels`. Additive otherwise.

## Codebox port C3 and C4: bargraphs as audio channels, and the language quirks

**C3.** Codebox cannot send a value back to the host as control data, so a
bargraph becomes an extra audio output appended after the real ones, for the
RNBO patch to sample with `snapshot~`/`change`. Collected in UI declaration
order and threaded through both `compute`'s return list and the `outN` wiring.
Bargraphs are deliberately absent from the `@param` list: they are meters, and a
host must not write to them.

**C4.** The four quirks that make emitted codebox correct rather than
plausible:

- **Integer casts emit `trunc()`.** Codebox's own `int()` *floors*, so
  `int(-1.5)` would give -2 where C gives -1.
- **Integer `+`, `*` and `%` go through `iadd`/`imul`/`imod`**, which wrap at 32
  bits; codebox's infix operators work on `number` and would not. Only those
  three, matching the C++ `iop` table — `-` and the bitwise operators stay
  infix.
- **`fmod` becomes `safemod`**, which returns 0 rather than NaN for a zero
  divisor.
- **Math names lose their precision suffix** (`sqrtf` → `sqrt`), via the port of
  `gPolyMathLibTable`.

On the quirk DSP our output is now line-for-line identical to the reference —
`output0_cb = (0.5f * trunc((3.0f * input0_cb)));`, `safemod(input1_cb, 2.5f)`,
`sqrt(abs(input2_cb))` — which is expected for a DSP with no state, since the
lowering divergence that blocks byte parity lives in how state is represented.

**Bargraphs are compared by value, not by count.** They are control zones for
the interpreter and audio channels for codebox, so the numeric harness reads the
interpreter's zones through `ui_instructions()` and appends them to the expected
channel list in the same order the emitter appends them. Asserting only the
count would have accepted a permutation, which is exactly the failure an RNBO
patch would show as plausible values on the wrong meter.

**Three rejecting mutations, and the one that did not reject.**

- `trunc` → `floor`: 2 tests fail. ✓
- bargraphs emitted before the audio outputs: 1 test fails. ✓
- dropping the `Add` → `iadd` mapping: **every test still passed.**

That third result was the useful one. The mapping was not covered at all: my
integer-arithmetic test used a delay, whose ring counter produces integer
arithmetic only inside *loop headers* — and the emitter writes those directly,
never consulting the operator mapping. The test asserted `iadd(` *or* `imod(`
and passed on the loop header alone.

Fixed by testing what actually reaches the mapping: `process = _ : int : +(3) :
*(2) : %(5);` emits `imod(imul(2, iadd(trunc(input0_cb), 3)), 5)`, and the test
now requires all three helpers by name plus a numeric run. The mutation is
rejected. Recorded because the failure mode is general: a test that passes
because a *different* code path happens to emit the same token is
indistinguishable from a test that works.

Validation: `cargo test -p codegen -p compiler` (36 codebox tests);
`cargo clippy --workspace --all-targets -- -D warnings`.

Public API mapping: none beyond C2 — internal emission only.
