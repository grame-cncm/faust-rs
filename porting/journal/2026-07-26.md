# 2026-07-26

## Document the `CompilerError` fields and lock the `missing_docs` gate

`cargo rustdoc -p compiler --lib -- -D missing-docs` reported 48 errors, every
one a struct field of a `CompilerError` variant, while the sibling `transform`
crate has enforced that exact gate for a while.

Documented all 48, but not by restating "the source", "the error", "the
diagnostics" thirteen times. The non-obvious facts belong to the enum as a
whole and are stated once there: `source` is provenance for messages only — a
display path for the file-based entry points, the caller-supplied logical name
for the in-memory ones, not a key and not necessarily a file that exists;
`diagnostics` is *derived from* `error`, so the two can never describe
different failures, which is why the variants whose bundle takes real work
expose a constructor (`CompilerError::import`, `missing_root`, `codegen_wasm`)
that callers should prefer over building the variant by hand.

`#![warn(missing_docs)]` now sits in `lib.rs` as it does in `transform`. Since
the workspace CI gate runs `cargo clippy --workspace --all-targets -- -D
warnings`, an undocumented public item is a hard failure from here on rather
than a number someone has to remember to re-measure.

Plan: `porting/compiler-cleanup-plan-2026-07-26-en.md` (phase P1).

Validation: `cargo rustdoc -p compiler --lib -- -D missing-docs` exits 0;
`cargo clippy -p compiler --all-targets -- -D warnings`; `cargo test -p
compiler`. Behavioral freeze checked by a new CLI transcript differential (148
modes: every `--lang`, every `--dump-*`, the argument-validation errors, and
the FIR-fixture ladder over all 7 built-in fixtures, capturing stdout, stderr
and exit status) — identical before and after, as a documentation-only change
must be.

Harness note, recorded because it produced a false positive first: the DSP
inputs must live at a path of *fixed length*, not inside the per-run output
directory. The source path is embedded in the wasm module's JSON, so a
directory named `before` versus `after` shifts two LEB128 length prefixes by
one byte — and text normalization of the path hides the cause while leaving the
binary difference visible. A differential whose own scaffolding varies between
runs reports changes that are not there.

Public API mapping: documentation only. No signature, behavior, or output
change.

## Split `run_main()` into named phases

`run_main()` in `crates/compiler/src/cli/runner.rs` was 1 356 lines — the
single worst obstacle to reading this crate. Its shape only becomes visible
after scrolling: an argument-validation prologue, then the `--fir-fixture`
mode, then the DSP-source mode, the last two being parallel per-backend
emission ladders that answer the same question ("which backend did the user
ask for?") from two different starting points.

Extracted, as a pure move, into `handle_early_exit_modes`,
`spawn_timeout_watchdog`, `handle_fixture_listing`, `validate_cli_arguments`,
`run_fir_fixture_mode` and `run_source_mode`. `run_main()` is now 24 lines and
reads as a table of contents.

Two details the extraction had to make explicit rather than preserve blindly:

- the validation block contained a bare `return` (the "no output mode and no
  input file" case prints the scaffold banner and stops). Once extracted, that
  is no longer "return from `run_main`", so `validate_cli_arguments` returns
  `Option<usize>`: `None` means the run is already over, `Some(0)` means "no
  explicit mode" and the caller falls back to default C++ emission;
- the fixture ladder reads `mode_count`, which the prologue computes, so it
  becomes a parameter instead of an ambient local.

The doc comment on `validate_cli_arguments` records the property that makes
this function fragile to reorder: every rejection exits with status 2, so the
*order* of the checks decides which message a doubly-invalid command line
reports.

Validation: CLI transcript differential over 148 modes (every `--lang`, every
`--dump-*`, the argument-validation errors, and the FIR-fixture ladder across
all 7 built-in fixtures, capturing stdout, stderr and exit status) — identical
before and after. Plus `cargo fmt --all --check`, `cargo clippy -p compiler
--all-targets -- -D warnings`, and `cargo test -p compiler` (31 suites green).

Plan: `porting/compiler-cleanup-plan-2026-07-26-en.md` (phase P2, first half —
the move into separate modules is a follow-up commit).

Public API mapping: none. `run_main` keeps its signature; every extracted
function is private to the binary.

## Move the CLI modes into their own modules

Follow-up to the `run_main()` split: the three extracted phases now live in
`crates/compiler/src/cli/{validate,fixture_mode,source_mode}.rs` instead of
trailing behind the helpers in `runner.rs`.

| file | before | after |
|------|--------|-------|
| `cli/runner.rs` | 1 953 | 615 |
| `cli/source_mode.rs` | — | 762 |
| `cli/fixture_mode.rs` | — | 404 |
| `cli/validate.rs` | — | 265 |

`runner.rs` keeps what its name promises: process-level orchestration
(`run_main`) plus the shared helpers the modes call (`emit_output`,
`compiler_from_cli`, the `selected_*` mappers, `report_pipeline_failure`). The
two emission ladders are now side by side as sibling modules, each documented
as the counterpart of the other, which is the fact the old layout hid.

`report_pipeline_failure` and `emit_check_success` became `pub(crate)`, and the
mode entry points `pub(crate)`, since they now cross a module boundary. Nothing
became `pub`: the CLI surface of the binary is unchanged.

Validation: same 148-mode CLI transcript differential — identical; `cargo fmt

`cargo test -p compiler`.

## Split `lib.rs`, then extend `structure-check` to `crates/compiler`

`lib.rs` was 2 804 lines, well past the repo's own 2 000-line review
threshold. Two self-contained blocks came out, each as one `impl Compiler`
block in its own module:

| file | lines |
|------|-------|
| `src/lib.rs` | 2 804 → 1 483 |
| `src/emitters.rs` | 1 040 (every `compile_*_to_<backend>` entry point) |
| `src/service.rs` | 297 (`getInfos`, `expandDSP`, `generateAuxFiles`) |

The backend grouping and its convention note travel with the emitters, so the
regularity established in `055ddbe7` survives the move. `service.rs` carries
the reason it exists as a module doc: those entry points mirror the C++ helper
APIs rather than the compile ones, and report through `FaustwasmServiceError`
rather than `CompilerError`, because their callers are host bindings that
propagate a code plus a message.

With every production file under the threshold, the guard is now worth
arming: `xtask structure-check` walks `crates/compiler/src` in addition to
`crates/transform/src`. Only the line check applies there — the other rules
(legacy `vector_*` paths, producer/checker separation) are transform-specific
and cannot match outside `signal_fir/vector/`, which the module doc now states.

Checked as a real guard, not a decorative one: padding `lib.rs` past 2 000
lines makes `structure-check` report it, and removing the padding clears it.
Without that mutation the check could have been scanning nothing and still
printing OK.

Pre-existing and untouched: `structure-check` still reports
`crates/transform/src/signal_fir/vector/lower/signal.rs` at 2 100 lines,
recorded in the 2026-07-24 journal.

Validation: public `pub fn` surface identical before and after the split; the
148-mode CLI transcript differential unchanged; `cargo fmt --all --check`;
`cargo clippy --workspace --all-targets -- -D warnings`; `cargo test -p

## Finish P3: drop the redundant import-dir branches, share the fixture JSON companion, and land the transcript harness

Three cleanups that the earlier phases made visible and safe.

**The 17 `if cli.import_dir.is_empty()` branches were provably redundant.**
Every `*_default*` entry point is literally `*(path, &[])` — for example
`compile_file_default(path)` is `self.compile_file(path, &[])` and
`compile_file_default_to_cpp_with_lane(p, o, l)` is
`compile_file_to_cpp_with_lane(p, &[], o, l)`. Since `&cli.import_dir` on an
empty `Vec` *is* `&[]`, both arms of every one of those `if`/`else` blocks
called the same function with the same arguments. Replaced by the single call:
`source_mode.rs` drops from 756 to 644 lines, and the reader stops looking for
a difference that was never there. The `*_default*` family stays in the facade
— it is a legitimate convenience for library callers; it is the CLI that had no
use for the distinction. The one *negated* check (`--import-dir is not
supported with --golden`) is a real rejection and stays.

**Nine of the fixture ladder's JSON-companion blocks were identical.** The
source ladder already had `emit_cli_json_companion_for_backend`; the fixture
ladder open-coded the same three statements nine times, differing only in the
backend name. Now one `emit_fixture_json_companion` helper. Two companion sites
deliberately stay out of it and the helper's doc says why: the WASM branch
emits the module and its matched JSON together, and the standalone `--json`
branch already holds the rendered text. (The first attempt at this assumed ten
identical blocks; the pattern-match found nine, which is what stopped the
change from folding the two genuinely different sites into the helper.)

**The transcript differential is now part of the repo.** It had lived as a
throwaway script for four commits. It is now `xtask cli-transcript-gen` /
`cli-transcript-check` with the snapshot in `tests/cli-transcripts/` (132
modes: every `--lang`, every `--dump-*`, the option combinations, the
argument-validation errors, and the fixture ladder over all 7 built-in
fixtures — stdout, stderr and exit status each). Its module doc records the two
traps it is built around: inputs must sit at a path of *fixed length* (the
source path is embedded in the wasm JSON, so a directory named `before` versus
`after` shifts LEB128 length prefixes and text normalization then hides the
cause), and only genuinely unstable fields may be normalized (the Cranelift
runtime `compute_entry_addr`, nothing else).

Checked as a real guard, twice. Changing one letter of the Cranelift report
header produces 9 findings. A first attempt mutated the "JSON fixture
generation failed" message instead and the check stayed green — correctly, since
that path only runs when JSON generation fails, which the matrix never
provokes. Recorded because it is the useful lesson: a rejecting mutation only
proves anything if it lands on a line the matrix actually executes.

Also fixed in the harness itself before it could mislead anyone: the
normalization loop as first written never terminated (it replaced
`compute_entry_addr: 0x<hex>` with text that still contains the search key, so
every pass matched again and the string grew). It now scans forward into a
fresh string.

Validation: `cargo run -p xtask -- cli-transcript-check` OK (132 modes);
`cargo fmt --all --check`; `cargo clippy --workspace --all-targets -- -D
warnings`; `cargo test -p compiler`; `xtask structure-check` reports nothing
for `crates/compiler`.

Plan: `porting/compiler-cleanup-plan-2026-07-26-en.md` (phase P3 and §3).

Public API mapping: none.

## Share one validation prologue across the backend dispatchers

The six `lower_signals_to_{cpp,c,julia,asc,rust,interp}` dispatchers in
`signal_lowering.rs` were 16 lines each and identical except for four tokens:
the options type, the error envelope, the backend name, and the fast-lane
function called. They now delegate to one `lower_signals_with_validation`,
generic over the options and error types, with `?` lifting an execution-option
rejection through three new `From<ExecutionOptionsError>` impls (one blanket
one for `LowerError<E>`, one each for the bespoke interp and FIR envelopes).

Honest accounting: the file grew from 759 to 804 lines. `rustfmt` expands a
six-argument call to one argument per line, and the shared function, the `From`
impls and the documentation below all cost lines. The gain is not volume — it
is that the execution-option check now exists in exactly one place, so the six
backends cannot drift apart, and each wrapper body is three lines of pure
delegation instead of five lines mixing validation with delegation.

**A hidden fact surfaced.** Each dispatcher contained `let _ = ctx.lane;`. That
statement was load-bearing: it silenced a dead-field warning, because
`SignalLoweringContext::lane` is read *nowhere*. Removing the six copies made
`clippy` say so immediately. The field is kept — the public entry points do take
a lane, and recording it here is what makes a second lane a change to the
lowering rather than to every signature — but it now carries an explicit
`#[allow(dead_code)]` and a doc comment stating that nothing reads it, instead
of six scattered no-ops hiding the same thing in six places.

Also repaired while there: the insertion initially landed between
`#[allow(clippy::too_many_arguments)]` and the `lower_signals_to_fir` it
annotates, orphaning the attribute and its explanatory comment. Caught by
clippy, moved back.

Validation: `cargo run -p xtask -- cli-transcript-check` OK (132 modes);
`cargo clippy -p compiler --all-targets -- -D warnings`; `cargo test -p
compiler`.

Public API mapping: none — every changed item is `pub(crate)`.
