## faustprobe: bargraphs are read, named, and never written

Commit date: 2026-09-17

Source commit: this commit

`faustprobe` discovered bargraphs (a `ControlKind::Bargraph` with its zone)
and did nothing else with them. Found from faust-diff-jot, whose preset
program shows the selected preset's parameters on bargraphs so that they can
be copied into another program: nothing could read them, `--list-params`
printed them like sliders (a step of zero the only sign), and `--set
T60_at_dc=5` or `--sweep gain=1,2` on one ran to completion, exit code 0,
the sweep printing identical rows that look like a measurement. Three
changes. `--list-params` has a `kind` column (`ControlKind::label`, and
`Display`), scalar and polyphonic. Writing a bargraph is an error:
`Probe::set` refuses one, and `Probe::check_writable` validates every path
of `--set`, `--sweep` and `--at` before any render, which also makes an
unknown `--at` path an error where the render loop used to drop it (`let _ =
self.set(..)`); `--train` already refused. And they are read:
`Probe::bargraphs` returns every bargraph's current value by path
(`get_zone`, at the factory's width); the statistics block gains `# bargraph
PATH=VALUE` lines and every JSON run a `bargraphs` object (absent without
bargraphs, schema version unchanged); `--bargraphs` adds one column per
bargraph to the per-frame CSV and to a sweep's rows, and is refused with
`--format ir`, `--train`, the impulse-test protocol and `--nvoices`. A
bargraph's zone holds the last sample of the last `compute` call, so the
per-frame column is block-rate, which the guide says. Tests in
`tests/bargraph_probe.rs`, at the library level (read-back in both widths,
the last block's value around a scheduled step, the refusal, the kinds) and
through the binary (the listing, the three refusals and the unknown `--at`
path, the statistics and the JSON, the columns and the flag's conflicts).
Three hand-applied mutations are each caught: `bargraphs()` returning the
declared init, `Probe::set` without its guard, the `--at` paths left
unchecked. User guide: section 5 and a new "Bargraphs" subsection.

## FFI: the complete text of a compile error, and faustprobe prints it

Commit date: 2026-09-17

Source commit: this commit and the two before it

`faustprobe` answered a syntax error with "parse failed for x.dsp: errors=1,
recoveries=0, diagnostics=1": that there is an error, not where. The probe is
not the cause. It compiles through the Cranelift C API, and both FFI backends
flattened a `CompilerError` with `.map_err(|e| e.to_string())`: the one-line
`Display` went to `error_msg` and the `DiagnosticBundle` (location, snippet,
notes, fixes) was dropped, for every host of that API. Putting the rendered
bundle in `error_msg` is not available in general: the buffer is allocated by
the caller and its size is never passed, 4096 bytes by the libfaust contract
(our own C++ wrappers declare a `char [4096]` seventeen times), so writing more
is a stack overflow in an existing host, and an undefined-symbol diagnostic,
which lists the visible scope three times, passes 4096 bytes with two hundred
definitions. So the buffer keeps receiving exactly what it received, and each
backend adds one entry point, `getCCompleteCraneliftDSPFactoryError` and
`getCCompleteInterpreterDSPFactoryError` (the interpreter's symbols all spell
`Interpreter`): the message the buffer got, then the rendered diagnostics,
whole, from per-thread storage the library owns, the `dlerror` convention:
null while the thread reported no error, valid until its next one, not reset
by a success. Three commits. (1) `xtask libfaust-export-check` was already
failing: its prefix filter had no `set`, so `setCCraneliftMemoryManager`,
exported since the mem0 work, was reported as a missing header export; prefix
added, parsing test extended, baseline line added. (2) The terminal renderer
moves from the binary (`cli/human.rs`) to the library
(`compiler::diagnostics_human`, with `ErrorVerbosity` and
`DiagnosticPathStyle`, which the CLI re-exports; the binary's output is
unchanged, its 80 tests pass), `CompilerError` and `FaustwasmServiceError`
get `rendered_diagnostics()`; `ffi_common::CompleteError` holds the record,
`attach` where a typed error is flattened and `report` in each backend's
`write_error` funnel, the diagnostics going to the message that carries their
summary and to no other; compile, expand and auxiliary-file failures attach
theirs; headers, header smoke test, export baseline (398 exports), parity
matrix. Tests: five on the record, six end to end per backend (a located
syntax error, a text over 4096 bytes kept whole, an error without diagnostics
inheriting none, no reset on success and null on another thread, expansion
failures); four mutations rejected (report ignoring the attachment, the
attachment given to whatever error comes next, a funnel that does not
publish, service errors attaching nothing). (3) `faustprobe` reads the
complete text when a factory creation fails, and takes it only if it extends
the summary of that failure, since a success does not reset it;
`tests/compile_error_probe.rs` (library and binary) and a unit test of that
guard, two mutations rejected; user guide, "When the program does not
compile". Not done: the C++ wrappers (`cranelift-dsp.h`,
`interpreter-dsp.h`), whose `std::string& error_msg` has no size limit, still
copy the 4096-byte buffer, and `libfaust-ffi` has no such entry point.

## C++ wrappers: `std::string& error_msg` gets the complete compile error

Source commit: this commit

`std::string` that has no such limit. `cranelift-dsp.h` and
`interpreter-dsp.h` now declare `getCComplete{Cranelift,Interpreter}DSPFactoryError`

failure (create from file and string, bitcode readers, expand, auxiliary

## faustprobe: feedback quality, analysis and plan

Commit date: 2026-09-17

Source commit: this commit

`porting/faustprobe-feedback-quality-analysis-and-plan-2026-09-17-en.md`. After
three changes that each removed a place where the probe answered without
informing (`--set` with `--train`, bargraphs, compile errors), the question of
what remains of that kind. The analysis applies the principle of the design
document's §6 (an instrument that silently misreports is worse than none) and
every claim about the present tool was run on the release binary. Four defects:
an out-of-range value is clamped in silence, so `--sweep gain=0.5,1,7,100` on a
0..1 slider prints rows labelled 7 and 100 equal to the row of 1, the bargraph
sweep defect one step further; "full precision" is `{:.9}`, which keeps two
significant digits of a sample of 3.3e-8 in either width and is the only reason
the `faust-diff-jot` tolerances are 1e-7, while `--list-params` prints an `f32`
step as `0.0010000000474974513`; a non-finite render discards the frame it knew;
an exactly silent render says nothing of the button at 0 that explains it. Then
what costs Python today: comparing two renders (the first differing frame is the
information a maximum does not give), the invariants the guide states and
nothing checks (block size, reset, width, determinism; a `rad` program is a
genuine positive for the first, its gradient lanes differing between `--block
64` and `256` at frame 100 while its loss lane does not), and questions about a
sub-expression, which cost a file each although the `environment{}` wrap of the
polyphonic engine is the mechanism needed. Also the host loop (a control ending
on a bound, no gradient magnitude, grid-then-descent refused as one command),
cost (compile and render times known and unreported, subnormals uncounted) and
the typed diagnostics channel. What stays out is argued from independence, not
only from the scalar/vector line of the guide's §9: a domain analysis inside the
tool, checked by a test that calls the tool, compares it with itself; the one
exception, a frequency response with a linearity check, is the design's own
§7.1. Plan in five phases, F1 corrective (range errors with `--clamp`,
round-trip numbers with `--precision 9` as the escape hatch and `--out`
npy/wav, first non-finite frame with controls and last event and
`--fail-above`, silence notes), F2 `--compare`/`--ref` and `--check`, F3
`--eval EXPR` in a file's scope with the file's line numbers kept, F4 host-loop
feedback, `--time`, subnormals, `--error-format json`, F5 `--freqresp`. Each
behaviour has its check and a mutation it must reject; where a Faust fixture
cannot exist (`--check reset` would take a compiler bug) the mutation is in the
probe. F1 changes two defaults and therefore has a qualification gate: the
crate's suite, the impulse-test byte identity, the guide's quoted outputs, and
the four sibling suites. Five open questions, the first being whether D1 should
be an error or a notice by default. Nothing is implemented.

## faustprobe F3: `--eval`, an expression in a file's scope

Phase F3 of the feedback-quality plan. A question about a sub-expression cost a
`.dsp` with an `import` and a `process` (`faust-diff-jot` keeps a 150-output
`jot_coefs.dsp` for nothing else), and a `.lib` could not be given to the probe.
`--eval EXPR`, repeatable, wraps the file the way the polyphonic engine wraps an
instrument to reach its `effect`: `__faustprobe_env = environment{ <file> ...
}`, the expressions defined inside it and therefore evaluated in the file's own
scope, a library's functions unprefixed, `process` taking them side by side; the
file's own `process` is simply not the one evaluated. `probe/eval.rs`
(`EvalProgram`): the opener shares the file's first line so that the file keeps
its line numbers; each expression is alone on a line, so a diagnostic about it
has exact columns and the expression as its source line, and `explain` renames
that location `<eval k>:1:COL` and says which expression it is. With several
expressions the columns are attributed by their numbers of outputs, computed by
a second one-frame program (`outputs(E)`), rather than assumed to be one each.
The source is named by the file's path: what diagnostics cite, what gives the
controls the paths they have in the file, and what the compiler resolves
relative imports against; code that also added the file's directory to the
import path was removed when the mutation deleting it survived. An expression
sees top-level definitions only: a `with`-local one fails, often unlocated
since the name also occurs in the file, so an unlocated undefined symbol is
attributed to the expressions that use it, with the rule. Header fields with a
comma are quoted; a `# eval outN = EXPR` legend goes with the statistics and
before a sweep's rows; JSON has an `eval` array; `--set`, `--sweep`,
`--list-params`, `--out`, `--train` apply unchanged; `--nvoices` and the
impulse-test protocol refuse it. `Factory::compile_from_string_with_args`
carries `-bra-tape` to a source string. Exit criterion: the 150 outputs of
`jot_coefs.dsp` from `jot.lib` alone, thirteen `--eval`, 126 identical text for
text and 24 within three units in the last place, which is not the wrapper: the
file computes from sliders at run time, the expressions had literals folded at
compile time, and with sliders as arguments `--eval` gives the file's digits.
Tests: `tests/eval_probe.rs` (10, the independent route being the hand-written
program that states the same expressions) and 6 unit tests; six mutations
rejected. Found on the way and handed to a separate task: `process = 2.0 / 0;`
panics the compiler and aborts a host through the FFI. User guide: "Evaluating
an expression: `--eval`". 264 tests in the crate.

## faustprobe `--eval`: what a constant checks, and what it does not

Commit date: 2026-09-17

Source commit: this commit

A correction to the entry above and to the plan's §3.3, written the same day.
The plan said a `.lib` could be compile-checked with `--eval '0'`, the first
version of the guide repeated it, and a `make check` line was added to
`faust-diff-jot` on its strength. Tried on a library broken on purpose, it
passed: Faust evaluates lazily, so only what an expression uses is evaluated,
and `--eval 0` checks that a library parses and that its imports resolve, not
that its functions are sound. `gamma(t60) = oops + ...` passes `--eval 0` and
fails under `--eval 'gamma(2.0)'`, at `jot.lib:81:14`, the library's own line.
The guide now states the rule with that example, the plan records the
correction, the test that asserted the wrong claim is replaced by one that holds
both halves (a constant passes on an unsound library, the unsound function
fails when evaluated and is cited at its line, a library that does not parse
fails under a constant), and the `faust-diff-jot` change was withdrawn: the
programs that import the library already parse it, so the line added no check
and suggested one.

## A constant division by zero is a diagnostic, not a panic

Commit date: 2026-09-17

Source commit: this commit

`process = 2.0 / 0;` panicked the compiler (`compiler thread panicked: Any {
.. }`, exit 101) and, through the Cranelift FFI, aborted the host ("panic in a
function that cannot unwind"): found from `faustprobe --eval` on
`faust-diff-jot`'s `jot.lib`, where `householder_coef(N, i, j) = float(i == j)
- 2.0 / N` had been given `N = 0`. The mechanism was there and deliberate: the
term normalizer reports `x / 0` by unwinding with a typed `DivisionByZero`
payload, the analogue of the `faustexception` of C++ `mterm::operator/=`, and
`normalform::simplify_signals_fastlane` catches it; a quiet panic hook keeps it
silent, which is why the launcher had nothing to print but `Any`. The evaluator
calls the same simplifier, `simplify_const`, at four places to fold constant
sub-expressions, and none of them was under a catch. Reference behaviour,
measured with Faust 2.89 on some thirty programs: every constant division by
zero is an error with exit status 1, `ERROR : division by 0 in 2 / 0`, reals
included (no infinity is folded), and it is raised where the evaluator folds a
numeric sequence (`eval.cpp`, `isBoxSeq`). The fix follows it.
`normalize::try_simplify_const` returns the `DivisionByZero` and lets any other
payload keep unwinding. `try_fold_seq_numeric`, the port of that C++ branch,
returns it, and `eval_seq_value` raises the new `EvalError::DivisionByZero`,
code `FRS-EVAL-0007`, located on the sequence, with the folded division in the
message and in a `computed:` note next to the `expr=(2 / n)` the diagnostics
already gave: `par(i, 2, 1.0 / i)`, a count `par(i, 4 / 0, _)`, a route size, a
label `%N`, a pattern argument `f(1 / 0)` all report it, as the reference does.
The three other sites see a division only when the divisor is constant without
being a numerical tuple (`z = 0 <: _, !`): `eval_box_to_i32`/`f64`, which need
the constant, report it (an iteration count and a route size had discarded the
error for "not an int node" and "invalid integer value"); the pattern and box
simplifications, for which the fold is an optimization, give up, and the typing
stage reports the division (`FRS-COMP-0004`) if its value is used. One
divergence remains and is pinned by a test: an unused late-zero division in a
pattern argument compiles here and fails in the reference, which simplifies
eagerly. The sweep of the sibling operators found three more defects. `0 / 0`
and `0.0 / 0.0` compiled to a silent 0, the left-absorbing rule `0 / x = 0`
running before the divisor was looked at; `0 % 0` likewise through `x % x = 0`;
the reference rejects all three, and the two rules now except the constant zero
divisor. `(-2147483647 - 1) % -1` panicked in `fold_binop` (`i32::MIN % -1`
overflows in Rust, is 0 in C++): `wrapping_rem`; `div_nums` had the same
overflow, unreached, and uses checked operations. Shifts by 40, -1 and 32,
`i32::MIN / -1`, additive and multiplicative wrap-around, `7 % -2`, `pow(0,
-1)` already agreed with the reference. Two differences were seen and left
alone, neither a panic: `log(0)` is a domain error here and an infinity there,
`abs(i32::MIN)` is a real here and wraps there. The launcher now prints a
panic payload by its message instead of `Any { .. }`. Tests:
`crates/compiler/tests/diagnostic_errors.rs` (six, including the values of
eleven neighbouring folds and the pinned divergence), unit tests in `normalize`
(the returned division, zero over zero, zero modulo zero, the two overflows,
and that another panic keeps unwinding), three corpus fixtures `err_18` to
`err_20`, which the diagnostics-v2 sweep picks up. Ten mutations rejected; an
eleventh survived a first version of the "other panics keep unwinding" test,
which did not go through the function it claimed to test, and the filter was
made a generic helper so that it could be. `FRS-EVAL-0007` is in the registry,
the frozen table and both guides; the table's counts were already off by one
(`FRS-COMP-*` is four codes) and are corrected.
