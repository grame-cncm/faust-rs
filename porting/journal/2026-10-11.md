## Integer runtime pow: port C++ eb21fccc (#1340)

Commit date: 2026-10-11

Source commit: this commit (parent `e7c320f093a2240789a858b9aab3ce500852f858`);
C++ provenance `eb21fcccff1ead7fe286f35614a464bea70a5fe2`.

Deliverable/pass criteria: preserve C++ integer pow typing, emit double
pow/rint before int32 conversion on both production FIR paths, and run the
250^1 / 25^6 / (-3)^3 runtime-exponent regressions at both native precisions,
scalar/vector, with and without fast math. Small constant powers must retain
int32 wrap; mixed integer/real programs must have coherent math signatures.

Phase 0 scope: the established production preparation -> scalar/checked vector
FIR -> backend flow is used. No global-state, arena, ownership/lifecycle,
recursion representation, or scheduling architecture changes. Existing Phase 0
pipeline, differential protocol, gGlobal decomposition, and arena validation

`sigtype` had forced pow to Real and the promoter had cast both arguments to
Real, so adding a backend branch alone could never reach integer pow. Typing
now preserves the union of operand natures (C++ `powprim.hh::inferSigType`),
promotion keeps integer pairs, and positive constant integer folding uses
wrapping power. The shared leaf emitter handles both lowerers: small
nonnegative constant exponents multiply in int32, runtime exponents use
Float64 pow -> Float64 rint -> Int32. Single pow/rint use `powf`/`rintf`, separate
from the double prototypes; RAD formula emission uses the same names. Rust's
single-precision prologue supplies the double rint bridge too. The compile-time
table-generator interpreter uses the prepared nature for the same rounding and
wrapping decisions; its negative runtime exponent and wrapping regressions
prevent table-init=const from silently changing initialization values.

The vector artifact keeps its public math-op inventory complete, while owning
its sample-precision declarations and double-power requirement together.
Cranelift still resolves explicit C `powf`/`rintf` symbols to their fixed
single-precision host signature, including when a foreign declaration widens
the returned value; C++ likewise keeps those names rather than selecting a
double overload of std::pow/std::rint. The new FIR aliases must not change
those bindings, and both emitters have precision-preservation regressions.
The existing FIR CSE materializes a nontrivial base before repeated integer
multiplication; a foreign-base test guards evaluating it only once.

Public API mapping: `FirMathOp::from_symbol` additionally recognizes `powf`
and `rintf` (`adapted` spelling coverage, same signature); signal pow nature
is restored to `1:1` with C++. The host `FaustDsp`/F32/F64/ParamIndex contract
is unchanged and generated Rust is built/run inside the repository's host
architecture surface. Prototype bookkeeping is not a value memo; no memo
key, lifetime, invalidation, or cache site changes.

Compatibility registry: DIFF-BEH-020 records the numerical correction beyond
the pinned C++ reference and the shared single-precision FBC limitation.
The interpreter stores all reals in the factory precision, as C++ does;
this port does not introduce a new FBC ABI/opcode. Double FBC passes the
runtime cases at optimization levels 0/max. A manual single-FBC run retains
an error of -1 for `pow(25, 6) - 244140625`, confirming the precision limit.
The local C++ build has no interpreter backend, so that limitation is checked
against its CastInst/opcode source rather than claimed as a runtime differential.
Constant negative powers are
normalized to reciprocals by both compilers; variable integer negative
exponents retain C++ rint/cast behavior, including ties to even.

## W7: foreign-call barriers are ordered through their transitive reduction

Commit date: 2026-10-11

Source commit: this commit

What remained of the recursive foreign chain (`stage = + ~ w`, 12.2 s at
N = 2048 after the previous entry) was `fir-effect-orientation`, 9.8 s, ×5
per doubling. Every `ffunction` call is an ordering barrier (purity
`Unknown`), ordered against every effect node it is not already ordered
with. The incremental walks that made this quadratic rather than cubic kept
the pairwise reference's edges exactly, and a chain has about N² of them: a
call reaches the state reads upstream, not the state writes of the other
stages.

- `orient_effect_conflicts`: the transitive reduction of those orders. The
  effect nodes in baseline order, the barriers chained, each other effect
  node after the barrier before it and before the one after it: every
  barrier is ordered against every effect node as before, through O(E)
  edges, each along the baseline, so no cycle. `predecessor_lists`,
  `extend_forward` and `extend_backward` go.
- The edges differ, so a schedule may. Generated C++ against the previous
  compiler's, in scalar and `-vec -lv 1` mode: 2 of the 2 227
  `faustlibraries` tests (`ja_processor_stereo_test`,
  `ja_processor_stereo_ui_test`) and the corpus's `math.dsp` are
  reordered, in scalar mode only; built and run over 48 000 samples, their
  outputs are bitwise identical, and the two tests within `1e-5` of their
  references.
- `ffun_rec` at 2048: 12.2 s → 2.2 s (C++ 55.2 s); in `ondemand` 14.4 s →
  3.3 s. `fir-effect-orientation`: 0.22 s.

Tests: `barrier_orientation_equals_the_pairwise_reference` becomes
`barrier_orientation_keeps_the_pairwise_orders_with_linear_edges`: every pair
of effect nodes ordered as the pairwise reference orders it, every barrier
against every effect node, at most three edges per barrier.
`a_chain_of_foreign_recursions_is_ordered_with_linear_edges`: 40 stages,
199 edges, where the reference adds at least N²/4.

## W7: a chain of recursions no longer types in its square

Commit date: 2026-10-11

Source commit: this commit

The recursive chains of the W7 measurements (`chain(n) = chain(n-1) : stage`,
`stage = + ~ sin` or `+ ~ w`) were quadratic in both compilers. The `sin`
control spent 4.0 s of 4.2 s at 1024 in `fir-prepare-normalize`, in the
recursive groups' type fixpoint (`sigtype::TypeAnnotator`), which the
preparation runs six times. It is C++ `typeAnnotation`: `updateRecTypes` over
every group, each reading the previous iteration's approximations (a Jacobi
iteration), until none changes; in a chain a change crosses one group per
iteration, N + 1 iterations over N groups (counted: 65 for 64 groups, 257 for
256).

- `solve_recursive_groups`: the same iteration, recomputing only the groups
  one of whose read approximations changed in the previous iteration
  (`GroupCones`: a body's inference stops at `SYMREC` nodes and `SYMREF`
  variables, the seeds), clearing only their part of the memo. A group none
  of whose inputs changed would compute its approximation again.
- `==` on types ignores `lsb` and `res`, as in C++. The first version tracked
  changes by `==` and kept stale `lsb` seeds, which changed the bounds of 65
  nodes of `dm.springreverb_demo`; the full iteration assigns every new
  approximation. The end is now decided by `==` and a change of any field
  reaches the readers.
- `solve_recursive_groups_jacobi` stays, test-only, as the reference;
  `merge_rec_approximation` is shared by both.

Checked with both solvers on every annotation, compared field for field: the
corpus (4 918 annotations, 610 files) and the 2 227 `faustlibraries` tests
(18 547), whose generated C++ is also byte-identical to the previous
compiler's in scalar and `-vec -lv 1` mode. Times at N = 2048: `+ ~ sin`
14.1 s → 2.6 s (C++ 51.1 s), `+ ~ w` 23.7 s → 12.2 s (C++ 55.2 s), whose
remainder is the foreign-call barriers of `fir-effect-orientation`. A
feedback whose `lsb` falls at every iteration (`+ ~ *(0.5)`) still changes
through the whole chain, and is recomputed as the full iteration does it,
half its body inferences.

Tests: `the_incremental_fixpoint_gives_the_jacobi_types` (seven chains:
halving or `sin` feedback, nested recursions, a component ignoring the
recursion, two outputs; every field and the warnings);
`a_chain_of_recursions_infers_each_body_a_bounded_number_of_times` (200
groups: 5 646 body inferences, 30N − 354 from N = 50 to 800, against at
least N² for the reference).

## W1: the functions of `maths.lib` the backends lacked come from the C math library

Commit date: 2026-10-11

Source commit: this commit

`maths.lib` declares, as `ffunction`s of `<math.h>`, functions neither
Cranelift (`HOST_MATH`) nor the interpreter (its opcodes) implement: `cbrt`,
`hypot`, `erf`, `erfc`, `tgamma` (`ma.gamma`), `lgamma`, `logb`, `ilogb`,
`ldexp`, `scalbn` (`ma.scalb`), `nextafter` and the Bessel functions `j0`,
`j1`, `jn`, `y0`, `y1`, `yn`. Both failed on them ("no Cranelift
implementation", `UnknownMathFunction`) unless a host registered each. The C++
LLVM JIT finds them among the process's symbols, in the C math library.
Rust's standard library has `cbrt` and `hypot` only, stable; the user chose
the system's library over the `libm` crate, for the results the C and C++
code generated on the same machine computes.

- `foreign-call`: the 28 C symbols, `float` and `double` variants, declared
  `safe` in an `unsafe extern "C"` block (`-lm` outside Apple), with a typed
  table, `libm_functions()`. `ldexpf` and `scalbnf`, inline in MSVC's
  header, go through `ldexp` and `scalbn`, which is exact. The Bessel
  functions are `double` only, `_j0`... under MSVC. Nothing on wasm32.
- `TypedFunction` (moved from the Cranelift backend, where it was
  `HostMathFn`, with three new shapes: `float(float, int)`,
  `double(double, int)`, `double(int, double)`) and `NamedFunction` now live
  in `foreign-call`, so `HOST_MATH` and the C math library table are typed
  the same way.
- Order, both backends: the backend's own math functions, then host
  registrations, then the C math library, which a host may so replace. A
  call follows the rule of the typed registrations: arguments and result
  convert (`float j0(float)` calls `j0` on a `double`), another shape is
  refused naming "the C math library function `double j0(double)`".
- Cranelift registers the table as JIT symbols; the interpreter compiles the
  call as a typed one and the executor finds the address in the table when
  no host registered the name.

Checked: `ma.cbrt`, `ma.hypot`, `ma.ldexp`, `ma.scalb`, `ma.logb`,
`ma.ilogb`, `ma.erf`, `ma.erfc`, `ma.gamma`, `ma.lgamma`, `ma.J0` to
`ma.Yn` and `ma.nextafter` from this repository's `maths.lib`, rendered by
`faustprobe` in both precisions, give the values a C program calling the
same functions prints.

Tests: `foreign-call` calls each kind of function through `invoke`
(`ldexpf` at the edges of `float` included) and checks the symbols are
unique; `a_c_math_library_function_is_called_from_its_maths_lib_declaration`
and `a_host_registration_replaces_a_c_math_library_function`
(`math_signature_probe.rs`, Cranelift, both precisions, opt levels 0 and 3);
`a_c_math_library_function_is_called_by_the_interpreter` (interp-ffi, a
refused shape and a host replacement included);
`a_c_math_library_function_resolves_after_the_registrations` (codegen).

Also fixed: the journal index counts. Updating them by the text
"(N entries)" changed the first line with that count, so the four previous
commits left 2026-02-23 at 27 instead of 26, 2026-02-24 at 26 instead of 23,
and 2026-10-10 at 23 instead of 27. The two February lines are back to their
