## Let `make bench`/`compile-bench` run against any DSP corpus, not just `dsp/`

Commit date: 2026-08-19

Source commit: this commit

`tests/impulse-tests/Make.bench` already exposed `dspdir` as a knob (every
other lane — `Make.gcc`, `Make.interp`, `Make.mem0` — takes it), but the
throughput/compile-time benchmark ignored it: `allnames := $(dspfiles:dsp/%.dsp=%)`
and every path reconstruction (`dsp="dsp/$$name.dsp"`, `-I dsp`) hardcoded
the literal `dsp/` prefix instead of `$(dspdir)`. Passing `dspdir=` silently
did nothing.

**Fixed, and extended to nested corpora in the same pass**, motivated by
wanting to bench against the C++ Faust `examples/` tree (297 DSPs, all one
level down in per-category subdirectories — `misc/tester.dsp`,
`physicalModeling/faust-stk/piano.dsp`, none at the top level, so a
non-recursive listing would find nothing there). `dspfiles` is recomputed
with `find $(dspdir) -name '*.dsp' | sort` instead of `common.mk`'s
single-level `wildcard`; every `dsp/%.dsp=%` substitution and hardcoded
`-I dsp` became `$(dspdir)`-relative; log paths get `mkdir -p
"$$(dirname "$$log")"` so a DSP named `misc/tester` lands at
`build/bench/logs/misc/tester.*.log` instead of failing to open.

**`vec-bench` deliberately untouched.** It draws its DSP list from
`../vector-coverage/certified-dspfiles.txt`, the float/double × `-lv` × `-ss`
retention matrix certified for the internal corpus specifically — there is
no equivalent certification for an arbitrary external corpus, so
generalizing it would mean silently running against an empty list rather
than a meaningful comparison.

Verified end-to-end, not just by inspection: `make -n bench
dspdir=/Users/letz/faust/examples` resolves all 297 names with correct
per-DSP paths; a real `make bench`/`compile-bench` run against a synthetic
nested corpus (`probe/misc/tester.dsp`) produced correct CSVs and created
`logs/misc/tester.*.log`; the unmodified internal `dsp/` corpus still
produces the same 94 filtered test names as before the change (`wildcard`
vs. `find | sort` are a no-op difference on a flat directory).

Documented in `README.md`'s Performance Bench section and the `Make.bench`
header comment.

## Add a Rust effective-vs-test line-count report, `scripts/loc_report.py`

Commit date: 2026-08-19

Source commit: this commit

A standalone `cloc`-backed script, not an `xtask` subcommand, since it needs
no compilation and the ask was a quick, rerunnable report rather than a
repository-maintenance workflow. `python3 scripts/loc_report.py --by-crate`
prints totals and a per-crate effective/test breakdown for everything under
`crates/`.

**Classifying "test" required four rules, not one.** Files under a `tests/`
directory and inline `#[cfg(test)] mod name { ... }` blocks are the obvious
cases. Two more turned out to matter in this codebase: a file whose stem is
`tests`/`test` (the `mod tests;` → sibling `tests.rs` pattern used
throughout, e.g. `crates/fir/src/checker/tests.rs`), and a file reached
transitively through `#[cfg(test)] mod name;` pointing at an
arbitrarily-named sibling (`crates/cranelift-ffi/src/diff.rs`, pulled in via
`#[cfg(test)] mod diff;` in `lib.rs`). Missing the last two undercounted
test code by roughly 26,000 lines on the first pass — most of it from the
`mod tests;`-to-`tests.rs` pattern, which `grep`-based spot checks alone
would not have caught. `resolve_mod_file` follows Rust's own module lookup
rules (root/`mod.rs` files resolve siblings in the same directory,
non-root files resolve into a subdirectory named after their own stem) and
walks the reachable set transitively (a `tests.rs` file can itself declare
further `mod foo;` files, all inheriting the parent's `cfg(test)`).

**Deliberately does not look at `tests/impulse-tests/build/`.** Those
189 `.rs` files (132,923 `cloc` lines) are Rust emitted by the Faust
compiler for the numeric-parity corpus — generated output, not hand-written
source or test code. Scoping the walk to `crates/` only sidesteps the
question rather than filtering it out after the fact.

**Result on `crates/`: 143,590 effective / 69,554 test / 213,144 total**,
about 33% test code overall — `transform` and `codegen` are the largest
crates by far, and `compiler` is the one crate with more test than
effective code (11,536 / 18,208). Cross-checked against a plain
`cloc --include-lang=Rust crates` (212,931): a 0.1% gap, attributable to
doc comments straddling a test-block boundary, small enough not to chase
further.

Usage documented in `docs/developer-workflows-en.md` §8 alongside the other
`xtask`/build workflows.
