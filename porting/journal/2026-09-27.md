## Structure gates green again on `rust-facade`: `faust` is a distribution crate, `dispatch_ui_runtime` under 200 lines

Commit date: 2026-09-27

Source commit: this commit

Two of the five structure gates CI runs had been failing on this branch, and
no journal entry said so.

- `ffi-boundary-check`, since `ae8cd278` (the first commit of the `faust`
  crate): `faust` was in no layer list, so the check took it for a core crate
  depending rightward on `interp-ffi`, `cranelift-ffi` and `ffi-common`, and
  opting into `unsafe` outside the FFI boundary (four findings). It is now a
  distribution crate, next to `faust-ffi` (`libfaust-rs`, from C and C++) and
  `wasm-ffi` (from `faustwasm`): what a host links, here from Rust, over the
  adapters. It joins the `unsafe` allowlist, since its safe surface is built
  over the adapters' raw pointers. The layer test pins `faust` to the right of
  `interp-ffi` and `cranelift-ffi`.
- `structure-check`, since `72c6be24` (P2): `dispatch_ui_runtime`
  (`crates/cranelift-ffi/src/instance.rs`) grew from 194 to 206 lines, over the
  200-line function threshold. The three slider-shaped callbacks, the two
  bargraphs, the two buttons and the three box openers each go through one
  helper (`add_slider`, `add_bargraph`, `add_button`, `open_box`), with the
  same skips as before (null callback, label with an interior NUL, zone that
  does not resolve). Not listed in `OVERSIZED_FUNCTIONS`: the repetition was
  the length.

Tests: `cranelift-ffi` and `faust` (429, the `faustprobe` output snapshots
included, which walk this UI), `xtask` layer tests; the five structure gates
pass.

## `interp-ffi`: the factory JSON in the C++ format (F2)

Commit date: 2026-09-27

Source commit: this commit

Follow-up F2 of `porting/rust-facade-embedder-feedback-plan-2026-09-27-en.md`,
found during P2: `getCInterpreterDSPFactoryJSON` returned a list of UI opcodes
with heap offsets and no ranges, not the Faust JSON the C++
`interpreter_dsp_factory::getJSON` returns (a flat `JSONUI` built by
`buildUserInterface` and `metadata`).

`interp-ffi/src/json.rs` rebuilds the `JSONUI` description from the factory's
UI and metadata instructions: the group tree with group and widget
`declare`s, `PathBuilder::buildPath` addresses, short names through
`codegen::json::assign_short_names` (made public), rendered flat by
`JsonDescription::render_flat`. The shared renderer now also writes
`varname` only when known, and a group's or widget's `meta` as `[{` like
`JSONUI::addMeta`. It still writes an empty top-level `meta`, which `JSONUI`
omits: the WASM JSON shares the renderer and its runtime may expect the key.

Compared with the C++ libfaust 2.89.2 on three programs in single and double
precision: byte-identical except the top-level `meta` (`[]`) and `filename`
(empty), which depend on program metadata faust-rs does not yet carry in the
FIR.
`crates/interp-ffi/tests/factory_json.rs` pins three of the references
(fails on the previous commit).

## Interpreter and facade: a compute call allocates nothing (F1)

Commit date: 2026-09-27

Source commit: this commit

Follow-up F1 of `porting/rust-facade-embedder-feedback-plan-2026-09-27-en.md`,
measured during P1: every block the interpreter executed allocated its three
evaluation stacks (`Vec::with_capacity` in `try_execute_block_io_inner`),
twice per `compute`, 10 304 bytes per call in single precision and 14 464 in
double, in the audio thread. The C++ interpreter keeps them in local arrays.

- `FbcExecutor` keeps its stacks (`ExecStacks`) across runs, emptied and
  reserved to the C++ capacities at the start of each; they leave the
  executor for the run and come back after it (a panic drops them, and the
  next run allocates them again).
- The channel slice lists of `interp-ffi` (`compute_with`, `run_converted`)
  and the channel pointer arrays of the facade (`run_channels`) are gathered
  on the stack up to 64 channels.

Tests: `crates/interp-ffi/tests/compute_allocation.rs` and
`crates/faust/tests/allocation.rs` assert zero bytes after the first block,
through the C entry point, `compute_f64` and the facade, both backends and
precisions; the first fails on the previous commit.

## `interp-ffi`: no `&mut` on a shared factory at instantiation (F3)

Commit date: 2026-09-27

Source commit: this commit

Follow-up F3 of `porting/rust-facade-embedder-feedback-plan-2026-09-27-en.md`.
`createCInterpreterDSPInstance` called `optimize` through `&mut` on the
factory at every instantiation, while another instance of that factory could
be computing on another thread with a `&` on it. After the first call
`optimize` only reads its flag, so nothing was written, but the two
references coexisted, which Rust's aliasing rules forbid. The flag is now
read through `&` (`FbcDspFactoryAny::is_optimized`), and `&mut` is taken only
by the first instantiation, before any instance exists. The facade also
serialises `Factory::json` with the lifecycle calls, since building the JSON
may instantiate the program.

Test: none can fail on the previous code (no concurrent write for
ThreadSanitizer to see; only Miri would flag it). The stress test
`instances_are_created_while_another_one_computes` covers the path and runs
clean under ThreadSanitizer.

## `faust`: controls in the order of the user interface

Commit date: 2026-09-27

Source commit: this commit

Step P5 of `porting/rust-facade-embedder-feedback-plan-2026-09-27-en.md`.
`Dsp::controls()` was in path order (a `BTreeMap`); `py-faust-rs` asked for
the order of the UI tree, which its previous binding followed. The control
map is now a `Vec` in `buildUserInterface` order with a path index. That
order is Faust's: a group's widgets sorted by label, `[n]` prefixes
included, so `[2]alpha`, `[1]beta` list as `beta`, `alpha`.

The planned test of two widgets sharing a path cannot be written: the
compiler refuses such a program. The map keeps the C++ `MapUI` rule (the
later zone replaces the earlier) as an untested guard.

Test: `controls_come_in_the_order_of_the_user_interface` (both backends;
fails on `0f240664`).

## `faust`: `Control::label`; `Control` and `ErrorKind` non-exhaustive

Commit date: 2026-09-27

Source commit: this commit

Step P4 of `porting/rust-facade-embedder-feedback-plan-2026-09-27-en.md`.
The path of a control replaces space, `#`, `/`, brackets and parentheses by
`_`, as the C++ `PathBuilder::buildPath` does, so `py-faust-rs` could not get
`"my gain"` back and used the last path segment. `Control::label` is the
label the UI builder passes: as written, without its `[key:value]` metadata,
which the compiler strips on both backends.

`Control` and `ErrorKind` are now `#[non_exhaustive]`, decided before the
surface is declared stable: fields and error kinds can be added without a
breaking change. `ControlKind` stays exhaustive on purpose.

Test: `a_control_keeps_its_label_as_the_program_wrote_it` (both backends;
does not compile on `0f240664`).

## `faust`: `Dsp` is `Sync`

Commit date: 2026-09-27

Source commit: this commit

Step P3 of `porting/rust-facade-embedder-feedback-plan-2026-09-27-en.md`.
PyO3 0.29 requires `Send + Sync` on a `#[pyclass]`; `Dsp` was `Send` only, so
`py-faust-rs` wrapped it in a `Mutex`.

Audit of the C entries reached from `&self`: both `getSampleRate` entries
read the instance, both `metadata` entries read the factory into a sink local
to the call; `get` reads one zone; everything that writes (`compute_*`,
`set`, the initialisations, `clear`, `reset_controls`) already takes
`&mut self`. `unsafe impl Sync for Dsp` carries that list as its `SAFETY`,
with the rule that a new `&self` method keeps to reads. `Dsp`, `lib.rs` and
`README.md` say `Send + Sync`.

The audit found one issue outside `Dsp`'s `&self` paths, recorded as
follow-up F3: `createCInterpreterDSPInstance` takes `&mut` on the factory to
call `optimize` on every instantiation, while another instance may hold a `&`
on it in `compute`; after the first call nothing is written, but the two
references coexist.

Tests: `dsp_and_factory_are_send_and_sync` (does not compile on
`0f240664`, E0277 as PyO3 reported) and
`one_dsp_can_be_read_from_several_threads_at_once` (both backends), both
also run under ThreadSanitizer without a report:

```sh
RUSTFLAGS="-Zsanitizer=thread" cargo +nightly test -Zbuild-std \
  --target aarch64-apple-darwin -p faust --test api -- one_dsp_can_be_read dsp_and_factory
```

## `faust`: control ranges at the compiled precision

Commit date: 2026-09-27

Source commit: this commit

Step P2 of `porting/rust-facade-embedder-feedback-plan-2026-09-27-en.md`. For a
`-double` program, `Control::init`, `min`, `max` and `step` arrived rounded to
`f32` (`hslider("x", 0.1, ...)` reported `init = 0.10000000149011612`), since
the `UIGlue` callbacks take `float`; `get` right after `reset_controls` read
`0.1` and disagreed with `init`.

The plan meant to read the ranges from `Factory::json`. Its first check
failed: the interpreter's JSON is not the C++ one (no ranges, a flat list of
UI opcodes; follow-up F2), and the C++ format would round to six digits
anyway. Both backends keep the ranges at full precision in the compiled
program, so each FFI crate gains a Rust-only `control_ranges(dsp)`, returning
`ffi_common::ControlRange` values keyed by the zone `buildUserInterface`
passes: from `FbcUiInstruction<R>` in the interpreter, from `RuntimeUiItem`
in Cranelift, whose ranges are now kept in `f64` and narrowed only at the C
callback. The facade overlays them on the controls after the `UIGlue` walk.
The C callbacks and the C header are unchanged.

Tests: `control_ranges_are_those_of_the_compiled_precision` (facade, both
backends and precisions; fails on `0f240664`), `tests/control_ranges.rs` in
`interp-ffi` and `cranelift-ffi`. `public-api-baseline.txt` gains
`ffi_common::ControlRange` and `FbcDspFactoryAny::control_ranges`.

Noted for P5: `buildUserInterface` sorts a group's widgets by label, as the
C++ compiler does; that is the order `controls()` should follow.

## `faust`: a `-double` interpreter program exchanges `f64` samples

Commit date: 2026-09-27

Source commit: this commit

Step P1 of `porting/rust-facade-embedder-feedback-plan-2026-09-27-en.md`, the
one regression `py-faust-rs` reported on issue #17: through the `faust`
crate, a `-double` interpreter program had its samples rounded to `f32`
(`process = _;` returned `1.0` for `1.0 + 2^-40`, `process = 16777217.0;`
output `16777216`), since `Dsp::exchanged` answered `f32` for the
interpreter and the C entry point narrows, as the C++ `interpreter_dsp` does
with the default `FAUSTFLOAT`.

- `interp-ffi`: `instance::compute_f64`, a Rust-only entry over `f64`
  buffers, with no C symbol and no header change; it and
  `computeCInterpreterDSPInstance` share one body (`compute_with`: the frame
  count, the control block, the DSP block). `FbcDspFactoryAny` gains
  `execute_block_io_f64`, native on a double program, converting on a single
  one.
- Both conversion paths go through `IoScratch`, buffers the instance keeps:
  the C entry point used to allocate one `f64` vector per channel on every
  call of a double program, 276 704 bytes per call for a 2-in 2-out
  8192-frame block; it now allocates nothing that depends on the frame
  count.
- `faust`: `RawInstance::compute` is generic over a crate-private `Sample`
  (`f32`, `f64`) and sends the interpreter's `f64` channels to
  `compute_f64`; both backends exchange the compiled precision.
  `lib.rs`, `README.md` and the `interp-ffi` README say so.

Measured on the way: every executed block allocates the executor's
evaluation stacks (`FbcExecutor::execute_block*`), 10 304 bytes per compute
call in single precision and 14 464 in double, whatever the block size. Not
touched here; follow-up F1 in the plan.

Tests: `a_double_program_exchanges_f64_samples_exactly_on_both_backends` and
`f64_buffers_on_a_single_precision_program_are_converted`
(`crates/faust/tests/api.rs`), `crates/interp-ffi/tests/compute_io.rs`,
`crates/interp-ffi/tests/compute_allocation.rs` (a counting allocator, its
own test binary); the first and the last checked to fail on `0f240664`.
`public-api-baseline.txt` gains `execute_block_io_f64` and `IoScratch`.

## Plan for the first embedder feedback on the `faust` crate

Source commit: this commit

`py-faust-rs` has been ported onto the `faust` crate by its author
(shakfu/faust-rs@py-facade, `99e9419a` on top of `0f240664`) and the report
