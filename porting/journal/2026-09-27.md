## Unlabelled widgets named as C++ names them (`0x00`, `hbargraph<n>`, `vbargraph<n>`); two in one group refused; their order kept

Commit date: 2026-09-27

Source commit: this commit

Closes DIFF-GAP-018. C++ `checkNullLabel` names an unlabelled slider,
button, checkbox, entry or soundfile `0x00`, and `checkNullBargraphLabel` an
unlabelled bargraph `hbargraph<n>`/`vbargraph<n>` (`global::getFreshID`, a
counter per prefix from 0, in UI generation order). Rust passed `""`.

- `ui::group_ui_label` (moved from the transform emission of the previous
  commit) and `ui::AnonymousWidgetNames` hold the rule once; `emit_ui_node`
  names groups and widgets with them for every backend and lane, and
  `ui::find_duplicate_control_paths` computes addresses with them.
- The duplicate check thus loses its exclusion of unlabelled widgets (a
  stopgap "until the naming is ported"): two unlabelled input widgets in one
  group address `…/0x00` and are refused (`FRS-UI-0001`), as Faust 2.89.2
  refuses them (`ERROR : path '/anon2/0x00' is already used`, exit 1);
  decided with the user. Its diagnostic searched the source for the address's
  last segment (`0x00`), found nothing and said the controls came from
  generated code; it now uses the label as written, and for an empty one
  points at no declaration (all unlabelled widgets are written `""`) and
  says they are named `0x00`.
- The order of widgets with equal labels differed from C++, whose
  `sortPropList` ran an unstable `std::sort` over a list built backwards;
  the user chose to keep the source order in Rust and fix C++ instead
  (DIFF-BEH-015). Fixed in the Faust repository (`ed7c12606`,
  `std::reverse` + `std::stable_sort`), released as Faust 2.89.3
  (`b52352c59`), rebuilt and checked: the unlabelled bargraphs now get the
  same numbers as in Rust, and `hslider("") + hbargraph("") + vbargraph("")`
  the same order; C++ still inserts widgets in the order it compiles their
  signals, which can differ from the source order Rust keeps. The `MapUI`
  harness of these entries, replayed with Faust 2.89.3 and its own
  architecture headers, gives the same paths, shortnames and lookups.

Tests: `crates/compiler/tests/anonymous_ui_labels.rs` (renamed from
`empty_group_label.rs`: groups, widgets, the refusal and its note);
`unlabelled_controls_are_named_as_in_cpp_and_can_conflict` and
`anonymous_widget_names_count_per_prefix_like_get_fresh_id` in
`crates/ui/tests/core_api.rs`, replacing the test of the exclusion.
Touches `transform`; the compile-budget gate cannot run on this Mac, and the
change adds one comparison per widget.

## `faust`: the names of the C++ `dsp` API (`dsp.h`), a generic `compute(count, inputs, outputs)`, `instance_constants`

Commit date: 2026-09-27

Source commit: this commit

The `Dsp` and `Factory` methods that have a counterpart in the C++ `dsp` and
`dsp_factory` classes (`architecture/faust/dsp/dsp.h`) now carry its names in
snake case, `get_` prefix included, as the `FaustDsp` trait of the Rust
architectures does. Decided with the user: `get_` kept, `compute` generic,
old names removed without deprecated aliases (a breaking change for
`py-faust-rs`, which must follow).

| before | now | `dsp.h` |
| --- | --- | --- |
| `num_inputs`, `num_outputs`, `sample_rate` | `get_num_inputs`, `get_num_outputs`, `get_sample_rate` | `getNumInputs`, `getNumOutputs`, `getSampleRate` |
| `reset_controls`, `clear` | `instance_reset_user_interface`, `instance_clear` | `instanceResetUserInterface`, `instanceClear` |
| (none) | `instance_constants` | `instanceConstants` |
| `compute_f32`, `compute_f64` | `compute<T: Sample>(count, inputs, outputs)` | `compute(count, inputs, outputs)` |
| `Factory::name`, `json`, `instantiate` | `get_name`, `get_json`, `create_dsp_instance` | `getName`, `getJSON`, `createDSPInstance` |

- `compute` takes an explicit `count`, as in C++; a buffer shorter than it is
  an `ErrorKind::Buffers` error, the rest of a longer one is left untouched
  (it used to run the shortest buffer's length). `Sample` is a public sealed
  trait over `f32` and `f64`, the widths of `FAUSTFLOAT`; the two copies of
  the conversion code became one generic `run_converted`.
- `instance_constants` reaches `instanceConstants*DSPInstance` of both C
  APIs, which the facade did not expose.
- The doc comments of these methods follow `dsp.h`'s ("Init instance state
  (like delay lines...) but keep the control parameter values" for
  `instance_clear`), with what the Rust version adds; the crate page gives
  the name table, and says why `clone` (a fresh instance in C++, which a Rust
  `clone` would misname) and `buildUserInterface` (replaced by `controls`,
  `get`, `set`) have no counterpart.

Tests: `compute_runs_count_frames_and_refuses_a_shorter_buffer`,
`instance_constants_recomputes_the_rate_dependent_constants_and_keeps_the_controls`
(on both backends); every test of the crate moved to the new names. README,
`docs/embedding-layers-{en,fr}.md` (their examples compiled and run again),
DIFF-API-008 updated.

## `interp-ffi`: no `&mut` on a shared factory at instantiation (F3)

Commit date: 2026-09-27

Source commit: this commit

Follow-up F3 of `porting/rust-facade-embedder-feedback-plan-2026-09-27-en.md`.
`createCInterpreterDSPInstance` called `optimize` through `&mut` on the
factory at every instantiation, while another instance of that factory could
be computing on another thread with a `&` on it. After the first call

ThreadSanitizer to see; only Miri would flag it). The stress test
`instances_are_created_while_another_one_computes` covers the path and runs
clean under ThreadSanitizer.

## `faust`: control ranges at the compiled precision

Commit date: 2026-09-27

`-double` program, `Control::init`, `min`, `max` and `step` arrived rounded to

anyway. Both backends keep the ranges at full precision in the compiled
program, so each FFI crate gains a Rust-only `control_ranges(dsp)`, returning
`ffi_common::ControlRange` values keyed by the zone `buildUserInterface`
passes: from `FbcUiInstruction<R>` in the interpreter, from `RuntimeUiItem`
in Cranelift, whose ranges are now kept in `f64` and narrowed only at the C
callback. The facade overlays them on the controls after the `UIGlue` walk.
The C callbacks and the C header are unchanged.

Tests: `control_ranges_are_those_of_the_compiled_precision` (facade, both
backends and precisions; fails on `0f240664`), `tests/control_ranges.rs` in
`interp-ffi` and `cranelift-ffi`. `public-api-baseline.txt` gains
`ffi_common::ControlRange` and `FbcDspFactoryAny::control_ranges`.

Noted for P5: `buildUserInterface` sorts a group's widgets by label, as the
C++ compiler does; that is the order `controls()` should follow.

## `faust`: a `-double` interpreter program exchanges `f64` samples

Commit date: 2026-09-27

Source commit: this commit

Step P1 of `porting/rust-facade-embedder-feedback-plan-2026-09-27-en.md`, the
one regression `py-faust-rs` reported on issue #17: through the `faust`
crate, a `-double` interpreter program had its samples rounded to `f32`
(`process = _;` returned `1.0` for `1.0 + 2^-40`, `process = 16777217.0;`
output `16777216`), since `Dsp::exchanged` answered `f32` for the
interpreter and the C entry point narrows, as the C++ `interpreter_dsp` does
with the default `FAUSTFLOAT`.

- `interp-ffi`: `instance::compute_f64`, a Rust-only entry over `f64`
  buffers, with no C symbol and no header change; it and
  `computeCInterpreterDSPInstance` share one body (`compute_with`: the frame
  count, the control block, the DSP block). `FbcDspFactoryAny` gains
  `execute_block_io_f64`, native on a double program, converting on a single
  one.
- Both conversion paths go through `IoScratch`, buffers the instance keeps:
  the C entry point used to allocate one `f64` vector per channel on every
  call of a double program, 276 704 bytes per call for a 2-in 2-out
  8192-frame block; it now allocates nothing that depends on the frame
  count.
- `faust`: `RawInstance::compute` is generic over a crate-private `Sample`
  (`f32`, `f64`) and sends the interpreter's `f64` channels to
  `compute_f64`; both backends exchange the compiled precision.
  `lib.rs`, `README.md` and the `interp-ffi` README say so.

Measured on the way: every executed block allocates the executor's
evaluation stacks (`FbcExecutor::execute_block*`), 10 304 bytes per compute
call in single precision and 14 464 in double, whatever the block size. Not
touched here; follow-up F1 in the plan.

Tests: `a_double_program_exchanges_f64_samples_exactly_on_both_backends` and
`f64_buffers_on_a_single_precision_program_are_converted`
(`crates/faust/tests/api.rs`), `crates/interp-ffi/tests/compute_io.rs`,
`crates/interp-ffi/tests/compute_allocation.rs` (a counting allocator, its
own test binary); the first and the last checked to fail on `0f240664`.
`public-api-baseline.txt` gains `execute_block_io_f64` and `IoScratch`.
