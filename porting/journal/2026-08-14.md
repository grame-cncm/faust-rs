## Correction: `createCCraneliftDSPFactoryFromString` rejects `import`, not the standard library

Commit date: 2026-08-14

Source commit: this commit

The P4 entry below claimed the string factory "does not resolve the standard
library". That was an inference from a failure, not a diagnosis, and it was
wrong. Narrowed properly:

| Source compiled from a string | Result |
|---|---|
| `import("stdfaust.lib"); process = _;` | `malformed definition node 2` |
| `import("maths.lib"); process = _;` | `malformed definition node 2` |
| `import("no_such_lib_xyz.lib"); process = _;` | `malformed definition node 2` |
| same, with `-I /usr/local/share/faust` | `malformed definition node 2` |
| `ma = library("maths.lib"); process = _;` | **compiles** |
| `process = _; import("maths.lib");` | `malformed definition node 8` |

A library that does not exist fails identically to one that does, an explicit
`-I` changes nothing, and the `library(...)` form works. So the fault is not
path resolution: `createCCraneliftDSPFactoryFromString` does not handle the
`import(...)` *statement*. The node number tracks the statement's position in
the definition list, which is consistent with the import node itself being
what the evaluator rejects.

The same source compiles through `createCCraneliftDSPFactoryFromFile`, so this
is a divergence between the two entry points of one backend, and a candidate
for the compatibility-difference registry (AGENTS.md section 5) rather than a
footnote in a tool's journal entry. Not filed here: whether it is a Cranelift
factory bug or shared front-end behaviour has not been established, and
guessing at the layer would put a wrong claim in the registry — which is the
mistake this entry exists to correct in the first place.

Corrected in the P4 entry and in the doc comment of
`crates/cranelift-ffi/tests/poly_probe.rs`. The P4 commit message still carries
the original wording; it is left alone rather than rewritten, since the history
is linear and the correction is auditable from here.

## `faust-probe` P5: scheduled events — `--at`, `--note`, `--chord`

Commit date: 2026-08-14

Source commit: this commit

The last phase of the design. `probe/schedule.rs` carries frame-scheduled
parameter changes and note on/off; both render loops apply them and the CLI
exposes `--at FRAME PATH=VALUE`, `--note PITCH[:VEL]@ON[..OFF]` and
`--chord P1,P2,...[:VEL]@ON[..OFF]`.

Exit criterion met, and comfortably: a DSP with `en.asr` at a 0.5 s release,
driven by `--note 69@0..24000` at 48 kHz, decays below -60 dB **0.4995 s**
after note-off — a 0.1 % error against the 5 % the design asked for.

This is the measurement the tool existed to recover. Before P5 the probe could
hold a gate for exactly one block (64 samples, the reference protocol), which
made every envelope longer than about a millisecond unmeasurable; the bespoke
C++ harness this tool replaces did it with a scripted gate, and now so does
this.

**Timing is sample-exact, not block-aligned.** The render loop shortens its
block so a boundary always falls on the next scheduled frame. The alternative
— rounding events to the block grid — still renders something plausible, but
bakes an error of up to one block into every measurement taken from it. At
block 64 that is 63 frames: negligible against a 0.5 s release, and a third of
a 5 ms one. Verified directly: `--at 1000 g=0.25` with `--block 64` shows 1.0
at frame 999 and 0.25 at frame 1000, and an integration test asserts the same
render comes out of block sizes 1, 64 and 256.

Details worth recording:

- Velocity defaults to 100, matching the reference `Key2Midi` helper.
- `..OFF` may be omitted, holding the note to the end of the render — an
  attack should be measurable without inventing a release that gets in the way.
- A reversed span (`60@200..100`) is rejected rather than silently swapped: a
  quietly reordered note would measure something the caller did not ask for.
- Events at one frame keep insertion order, so a note-off and a note-on for the
  same pitch at the same frame resolve in the order written rather than
  cancelling each other.
- `--at` is rejected alongside `--sweep`: each sweep point resets the instance,
  so a schedule would replay identically per point while the swept value moved
  underneath. Representable, but almost certainly not what anyone means.
- `--note`/`--chord` require `--nvoices > 0`, and all three are rejected under
  `--protocol impulse-test` with the other perturbing flags.

Verification: 133/133 corpus DSPs still byte-identical; 117 unit tests plus 17
integration tests across three files; clippy, fmt and the four structure gates
clean.

With this the design's P0–P5 are complete. The open questions in its section 8
— whether the tool should replace the two existing runners now that
`--protocol impulse-test` is byte-exact, and whether `-vec`/scheduling flags
belong here — are untouched and still open.

## `faust-probe` P4: polyphonic wrapper

Commit date: 2026-08-14

Source commit: this commit

`probe/poly.rs` ports the voice model of
`architecture/faust/dsp/poly-dsp.h`: control discovery by path suffix, voice
states, allocation, stealing, retrigger, and reclamation below the stop level.
`engine.rs` gains a shared `Factory` so N voices come from one JIT, plus
`PolyProbe` driving them and an optional effect on the mix. The CLI gains
`--nvoices`, `--effect` and `--voice-stop-level`.

The design asked for `-n/--nvoices`. `-n` already names `--render` (frames),
including inside this tool's own regression check against `impulse_cranelift`,
so the short form was dropped rather than silently repurposed.

Verification: 133/133 corpus DSPs still byte-identical to `impulse_cranelift`;
103 unit tests plus 7 new integration tests; clippy, fmt and the four structure
gates clean.

Three things worth recording.

**A control broadcast is not a voice control.** The first version of
`PolyProbe::set_all` required an exact path, while scalar `--set` accepts a
trailing fragment. That would have made `--set gain=0.5` work at `--nvoices 0`
and fail at `--nvoices 4` — a trap, not a safety feature. Voices are identical
instances of the same DSP, so a fragment unambiguous on one is unambiguous on
all: `set_all` now resolves once against voice 0 and applies the resulting
exact path everywhere, while the effect, being a different DSP, gets its own
resolution.

**The string factory rejects `import`.** A source containing
`import("stdfaust.lib")` compiles from a `.dsp` on disk but fails from a string
with `evaluation failed: malformed definition node 2`. The poly fixture is
therefore built from primitives only — `fconstant`, `floor`, `sin`, and a
one-pole follower standing in for `en.ar`.

*(Corrected after this entry was first written: the original text blamed
standard-library resolution. That was an inference from the failure, not a
diagnosis, and it was wrong. See the correction entry above for what the
failure actually is.)*

**A test premise that was wrong.** The broadcast test first set `gain` to zero
and expected silence; sound came out anyway. Correctly: `gain` is one of the
voice controls, so `key_on` overwrites it from the note velocity. The test now
broadcasts a separate `level` parameter. The failure was the wrapper doing its
job, and confusing a voice control with a patch parameter is precisely the
mistake the suffix-discovery table exists to prevent.

Deliberately out of scope, per the design: no MIDI file input, no real-time
thread, no soundfile playback beyond the existing fixture, and no
`--note`/`--chord`/`--at` scheduling — those are P5. Until then the polyphonic
engine is driven at the library level (`PolyProbe::key_on`/`key_off`), so a
poly render from the command line alone is silence: every voice starts free and
nothing gates it.

## `faust-probe` P3: parameter sweeps, reductions, JSON output

Commit date: 2026-08-14

Source commit: this commit

`--sweep PATH=V1,V2,...` (repeatable, cartesian, last axis fastest),
`--reduce rms|peak|energy|dc|f0`, and a versioned JSON document carrying one
row per point.

This is the phase that justifies building on Cranelift at all. A shell loop
re-runs the binary and re-JITs the DSP; a sweep amortises one JIT across every
configuration. Measured: five points at 96 000 frames each, one process,
**0.071 s total**. The design's estimate for 30 points was ~1.2 s and looks
conservative.

The measurement it replaces is the one from the port this tool came from:

```
faust-probe moog.dsp -I lib --sr 48000 -n 96000 --skip 48000 --in sine:1000 \
    --sweep cutoff=250,500,1000,2000,4000 --reduce rms --format json
```

At cutoff 1000 that reports rms 0.176777, i.e. |H| = 0.25 — the analytic value
for a 4-pole TPT ladder at its cutoff, exactly.

**State between points is the correctness question, not the sweep itself.**
Each point resets the user interface to declared defaults and clears the
instance state, then re-applies the fixed `--set` values and the point's own.
Without the clear a resonant filter carries its ringing into the next
configuration and every measurement after the first silently describes its
predecessor as much as itself. Verified by sweeping ascending and descending at
resonance 0.9 — the worst case — and getting bit-identical values per cutoff in
both directions.

**A regression the corpus caught.** After P3 the byte-comparison against
`impulse_cranelift` dropped to 132/133, on `sound.dsp`. The output was in fact
byte-identical; the exit code had changed. P3 moved the non-finite check ahead
of the format branch, and `sound.dsp` legitimately produces NaN at frames 41
and 845 — the *reference* `.ir` contains them. The check now applies to the
free path only: a non-finite sample invalidates a measurement, but the `.ir` is
an artifact `filesCompare` judges, and the exit code says whether the render was
produced, not whether the DSP diverged. `impulse_cranelift` exits 0 there and
the probe has to match. Back to 133/133.

`f0` needed a transform; a compact radix-2 FFT lives in `probe/spectrum.rs`
rather than a new workspace dependency, checked against a direct DFT. Its
docs state the bin-resolution caveat, since a 440 Hz sine reported at 439.45 Hz
is the nearest bin and not an error.

Sweeps require `--format json`: CSV and `.ir` describe a single render and
would concatenate points into something unreadable. `--protocol impulse-test`
rejects `--sweep` and `--reduce` along with the other perturbing flags.
Non-finite reductions serialize as `null`, since `serde_json` cannot represent
them and dropping the point would hide exactly the runs worth looking at.

## `faust-probe` P2: reference impulse-test protocol and `.ir` output

Commit date: 2026-08-14

Source commit: this commit

`--protocol impulse-test` pins every rendering condition to the reference
values and emits the `.ir` text format, so the probe subsumes
`impulse_cranelift` instead of competing with it.

Exit criterion met: **133/133 DSPs of `tests/impulse-tests/dsp` byte-identical**
to `impulse_cranelift` output.

Getting there required two things beyond formatting.

**Buttons must be driven.** `FUI::setButtons` holds every `button` zone at 1.0
for the first block and releases it after — buttons only, not checkboxes or
sliders. Without it an instrument renders pure silence because nothing gates a
voice. `RenderSpec::drive_buttons` carries this, and it is set only by the
protocol.

**Soundfiles must be installed, or the probe segfaults.** The first corpus run
crashed on `sound.dsp`. A DSP declaring `soundfile(...)` gets a pointer the
host is expected to fill; leaving `add_soundfile: None` leaves it null and the
first `compute` dereferences it. That is a crash, not a diagnostic, so it had
to be fixed rather than documented as a limitation.

`impulse_cranelift` already had the in-memory fixture the C++ suite uses, as a
95-line block private to the binary. Copying it into the probe would have
duplicated a numerically load-bearing fixture — buffer sizes and the
channel-sharing layout — with two copies free to drift. It now lives in
`probe/soundfile.rs`, used by both binaries, with its two tests moved alongside
the type they cover. The corpus comparison was re-run after the refactor and
still reports 133/133.

The `.ir` path writes nothing but the artifact, not even statistics on stderr,
since the output is compared byte for byte.

Conflicting flags are rejected rather than overridden: `--protocol
impulse-test` combined with `--sr`, `--block`, `--in`, `--skip`, `--every`,
`--set` or a non-`ir` `--format` is an error. A protocol run whose sample rate
was silently ignored would produce a plausible-looking `.ir` that compares
wrong.

One note on method: two unit tests asserting the exact `.ir` line format failed
after being written, each expecting one space too many. The 133-DSP byte
comparison had already established the real behaviour, so the tests were wrong
and the code was right — a useful reminder that a hand-written expectation is
weaker evidence than a differential against a known-good implementation.

## `faust-probe` P1: control discovery, control setting, offline render

Commit date: 2026-08-14

Source commit: this commit

First phase of the design committed earlier today. `faust-probe` can now
compile a DSP through Cranelift, discover its controls, set any of them, render
offline with a chosen excitation, and report per-frame CSV plus statistics.

Exit criterion met: it reproduces, in one command and with no build step, the
measurement that previously required a bespoke `faust -a` architecture file
plus a `c++ -O2` compile. A 4-pole ZDF ladder at 1 kHz with resonance 0 matches
its analytic magnitude response to six significant figures at 1, 2, 4 and
8 kHz (0.25, 0.0394523, 0.00318736, 0.000161896 against 0.25, 0.0394522,
0.00318736, 0.000161896).

Three things the implementation settled.

**Where it lives.** The design left this open between a `crates/faust-probe`
and a binary beside `impulse_cranelift`. `ffi-boundary-check` answered it: a
first attempt as its own crate produced four findings, the substantive one
being `core crate faust-probe depends rightward on adapter crate cranelift-ffi`.
`impulse-runner` gets away with being its own crate because the interpreter it
drives is safe Rust reachable from the compiler core; instantiating and calling
Cranelift-compiled code is not, and needs this crate's factory/instance handles
and `UIGlue` table. The probe therefore lives in `crates/cranelift-ffi/src/probe/`
with its binary in `src/bin/faust_probe.rs`, and no layering contract had to be
relaxed to accommodate it.

**Path building must copy C++ exactly.** The first version joined group labels
with `/` and emitted `/TIMBRE/amp_env/attack_s`, where a C++ host reports
`/TIMBRE/amp_env_attack_s`. `PathBuilder::buildPath`
(`architecture/faust/gui/PathBuilder.h:212`) replaces `/` *inside a label* with
`_` before joining, then sanitizes the assembled path a second time for
` # * , ? [ ] { } ( )`. Without step one, a DSP that names a control
`osc0/volume` silently acquires a group, and every address a user holds from
another tool fails to resolve. Both passes are now reproduced, with tests.

**Statistics honour the render window.** `--skip` applies to the reductions as
well as the dump, and the window is printed alongside the values. This is the
failure recorded in design §7.2: the bespoke harness computed RMS over the
whole buffer while `-skip` affected only printing, so on a strongly attenuated
signal the startup transient dominated and produced a 5x "discrepancy" against
theory that cost an hour of suspecting the filter.

Non-finite samples are reported even when they occur before the window, since a
DSP that diverged and recovered is still a DSP that diverged; the binary exits
non-zero in that case.

23 unit tests, `cargo fmt` / `cargo clippy --workspace --all-targets -D warnings`
/ `cargo test --workspace --all-targets` (101 suites) and the four structure
gates all clean.

## Design `faust-probe`, a generic DSP probing tool (Cranelift, polyphonic)

Commit date: 2026-08-14

Source commit: this commit

Both existing runners — `impulse-runner` (interpreter) and `impulse_cranelift`
— answer one question: *did the behaviour change?* They render a fixed
protocol (SR 44100, block 64, impulse on frame 0, buttons held for the first
block only, sliders at their defaults) and emit `.ir` for `filesCompare -part`
against the C++ oracle. The protocol is fixed by construction: regression
testing requires that nothing varies.

Neither answers *is the behaviour correct?*, which needs the opposite —
varying exactly the thing under test.

The gap was hit concretely while porting a C++ synthesizer engine to Faust in
a separate repository. Verification there needed a bespoke `faust -a`
architecture file plus a `c++ -O2` compile per DSP variant, 3-5 s each,
because no faust-rs tool can set a parameter. Four of that port's eight
validation properties were unreachable with `impulse-runner`: envelope release
timing (its gate lasts 64 samples, 44 000 were needed), delay ping-pong and
M/S width collapse (its impulse goes to *every* input channel, so one channel
cannot be excited alone), and anything requiring a specific operating point.

Measured before committing to a backend, same DSP and same output:

| Frames | Interpreter | Cranelift |
|---|---|---|
| 15 000 | 0.07 s | 0.06 s |
| 96 000 | 0.11 s | 0.04 s |
| 2 000 000 | 1.96 s | 0.41 s |

Subtracting the ~0.05 s JIT/front-end baseline, Cranelift renders ~5.3x faster
(1.91 s against 0.36 s). At 15 000 frames the two are indistinguishable
because compilation dominates, which is why the existing runners show no
reason to prefer either backend.

That ratio is what makes parameter sweeps the point of the design rather than
a convenience: a 30-point sweep at 96 000 frames costs one JIT plus 30 renders
— ~1.2 s under Cranelift, ~3.3 s under the interpreter, and ~150 s under the
compile-per-variant scheme a bespoke harness forces. The build step is what
shapes a test tool; removing it is what lets one process explore a parameter
space.

Two things must be built on top of the runtime path `impulse_cranelift`
already establishes:

1. A path→zone map, by accumulating the box stack while walking the `UIGlue`
   callbacks (`crates/ffi-common/src/abi.rs:111`) — the `PathBuilder.h` /
   `MapUI.h` algorithm. `getCCraneliftDSPFactoryJSON` carries addresses and
   ranges but not zone pointers, so it can serve a richer `--list-params` and
   nothing else.
2. A polyphonic wrapper, since the Cranelift runtime has no poly/MIDI wrapper
   any more than the interpreter does. Ported from
   `architecture/faust/dsp/poly-dsp.h`: control discovery by path suffix
   (`/gate`, `/freq` vs `/key`, `/gain` vs `/vel` — the distinction selects the
   conversion function), voice states `kFreeVoice -1` … `kNoVoice -4`,
   first-free-then-steal-oldest-releasing-then-oldest-playing allocation with
   the stolen voice entering `kLegatoVoice`, retrigger onto the oldest voice
   playing the pitch, and voice reclamation below `VOICE_STOP_LEVEL`
   (0.00003162, -90 dB).

`--protocol impulse-test` pins the reference protocol exactly, so the tool
subsumes both existing runners rather than competing with them, and stays
usable against the existing corpus.

Design: [`porting/faust-probe-generic-test-tool-design-2026-08-14-en.md`](../faust-probe-generic-test-tool-design-2026-08-14-en.md).
Phases P1-P5 with exit criteria there; P1 and P2 are independently useful and
P4 (poly) should not gate them.

## Document `sr_index` as a declared Rust extension (`G5-W4`, `DIFF-BACK-005`)

Commit date: 2026-08-14

Source commit: this commit

Asked to explain `G5-W4` from the inventory below, then to fix it. No code
changed — `sr_index` was already correct on the Rust side; only the registry
was missing the entry that says so.

Rust's WASM companion JSON always fills `sr_index` with the byte offset of
`fSampleRate` in the module's memory layout
(`crates/codegen/src/backends/wasm/mod.rs:674`,
`WasmMemoryLayout::field_offsets`). The pinned C++ WASM backend never does:
`WASMCodeContainer::generateJSON()` constructs its `JSONInstVisitor` with
`sr_index = -1`, and the schema's shared serializer
(`architecture/faust/gui/JSONUI.h:645`) omits the key whenever the value is
`-1`. The field is not a Rust invention — it is part of the general Faust JSON
schema and has a real host-side reader,
`architecture/faust/gui/JSONUIDecoder.h:224` and `:295`, which reads the
sample rate straight out of WASM linear memory at that offset, the same
mechanism widget `index` values already use for parameters. C++ simply never
populates it for this one backend, plausibly because a single
`getSampleRate()` call is cheap enough that the per-widget-count argument for
avoiding exports (many widgets vs. one export call) does not apply to a
single scalar.

Registered as `DIFF-BACK-005` in
[`faust-rs-vs-faust-cpp-differences-en.md`](../faust-rs-vs-faust-cpp-differences-en.md)
§6 (Additional backends and delivery forms), next to the other WASM-family
entries. Status `extension`: additive, not narrower — no C++-documented
consumer breaks on the extra key, and nothing the C++ JSON promises is absent
from Rust's. `G5-W4` is closed in
[`wasm-julia-maturity-diff-gap-005-analysis-and-plan-2026-08-14-en.md`](../wasm-julia-maturity-diff-gap-005-analysis-and-plan-2026-08-14-en.md)
and the top-level `DIFF-GAP-005` entry updated to reflect it.

## WASM companion JSON: inject the compiler-synthesized identity `meta` entries (`G5-W2`)

Commit date: 2026-08-14

Source commit: this commit

The WASM half of `DIFF-GAP-005`'s inventory (see the entry below) was scoped
out of the previous change on request. Asked to pick it up specifically for
`G5-W2`; since that item names the WASM emitter directly and directly
contradicts the earlier "leave WASM alone" instruction from the same session,
confirmed the scope change with the user before touching the backend.

`G5-W2`: the WASM companion JSON `meta` array carried only source `declare`s
(or nothing, for a DSP without any) — C++ always injects `compile_options`,
`filename`, and `name` into `meta` too, from `gGlobal->gMetaDataSet`, which
records them before the DSP is even parsed. `build_wasm_json_description`
(`crates/codegen/src/backends/wasm/mod.rs`) now runs the same
`c_family::ordered_compilation_metadata` helper the C/C++/Julia emitters
share, so all four backends declare identity in the same C++ key order from
the same transport. Verified against C++ on `s2.dsp` (no `declare`) and
`s3.dsp` (`declare name/author/version`): key set, values, and order match
exactly (the `compile_options` *value* still differs — `DIFF-CLI-006`,
pre-existing and out of scope).

One correctness trap surfaced during implementation, not by the earlier audit:
`build_json_description_from_fir` appends the FIR module's own `metadata`
function body *after* the injected identity set, without deduplicating across
the two. Production DSPs never populate that body — `signal_fir` lowering
always emits it empty and carries source `declare`s through
`WasmJsonContext::top_level_meta` instead, the same split the Julia fix relied
on — but the codegen-level fixture `build_gain_bias_ui_meta_test_module` hand-
builds a real declaring `metadata` body to test FIR-driven replay directly,
bypassing the compiler facade entirely. Unconditional injection would have
doubled `name`/`filename` for that fixture. `wasm_meta_with_identity_entries`
skips injection whenever the FIR module already declares a non-empty
`metadata` body — the same mutual-exclusion rule `has_metadata` already
enforces in the C-family emitters and `is_empty_metadata_body` enforces in
Julia, now applied to JSON `meta` construction too. No existing test needed to
change.

Validation: `make -f Make.wasm -j8` runs 94 comparisons against genuine C++
references and all 94 pass. Workspace tests, clippy, golden-check, and a
re-recorded `cli-transcript-check` are green; the changed transcripts
(`*_lang_wasm`, `*_lang_wast`) show only the intended `meta` addition —
confirming the fix reaches both `-lang wasm` and `-lang wast`, since both route

## Julia backend: real `metadata!`, real `getJSON`, `@inbounds` on `compute!`

Commit date: 2026-08-14

Source commit: this commit

Audited the two backends named by `DIFF-GAP-005` ("WASM and Julia are functional
on validated paths but do not claim the complete … maturity of the C++
implementations") against the pinned C++ reference `8eebea429`, and replaced the
blanket disclaimer with an enumerated inventory in
[`wasm-julia-maturity-diff-gap-005-analysis-and-plan-2026-08-14-en.md`](../wasm-julia-maturity-diff-gap-005-analysis-and-plan-2026-08-14-en.md)
(`G5-W1`…`G5-W6`, `G5-J1`…`G5-J7`). The WASM half of the inventory is
specification only: the emitter was deliberately left untouched in this change.

Three Julia items are closed.

- `G5-J1` — `metadata!` was emitted with an **empty body in every case**. Not
  only were the compiler-synthesized `compile_options` / `filename` / `name`
  entries missing: source `declare`s were dropped too. A Julia host calling
  `metadata!` got nothing. The C-family metadata transport
  (`metadata_name` / `metadata_filename` / `metadata_entries` plus
  `c_family::ordered_compilation_metadata`) is now shared with Julia, so the
  three backends declare the same keys, in the same C++ key order, from the same
  snapshot. Verified against C++ `-lang julia` on a source with
  `declare name/author/version`: same five declarations, same order.
- `G5-J2` — `getJSON` returned the literal `"{}"`. It now returns the real
  description, built by the facade through the existing
  `build_strict_json_description` and embedded as a flat Julia string literal
  (`JsonDescription::render_flat`, the Rust counterpart of C++
  `JSON(true)` + `flattenJSON`). Agrees with the C++ payload on `name`,
  `filename`, `inputs`, `outputs`, `size`, and the whole `ui` tree.
- `G5-J3` — `compute!` is emitted as `@inbounds function compute!`, as the
  reference does. Every table and buffer access in the audio loop was paying a
  bounds check.

Two defects found while implementing, neither of them in the audit:

- The embedded description took its `name` from the FIR module, which carries
  the **class** identity (`-cn`, default `mydsp`), not the DSP name. A DSP
  compiled without `declare name` advertised `"name": "mydsp"` next to
  `"filename": "simple.dsp"`, contradicting its own `metadata!` callback. This
  is the mirror image of the `-mem0` `memory_layout` zone-naming defect fixed on
  2026-08-13. The description now takes the resolved DSP name; a regression test
  pins `-cn` against it.
- `julia_string_literal` did not escape `$`. Julia interpolates it inside a
  double-quoted literal, so any label — or any embedded JSON — containing `$`
  produced source that does not compile. Deliberate deviation from C++
  `flattenJSON`, which leaves `$` alone.

`G5-J5` was filed by the audit as a correctness defect (`REAL(...)` assigned to a
`FAUSTFLOAT` field) and is **withdrawn**: Julia's `setproperty!` converts to the
declared field type, so the store is correct whatever the host defines
`FAUSTFLOAT` to be. Only the spelling differs. `G5-J4` (internal FIR `Label`
comments reaching the generated source) turned out not to be a Julia matter
either — the labels come from the shared lowering and the Rust backend prints
them too — so it moves to the cross-backend phase with the 200 stored Rust
golden files it would re-record.

Validation: `make -f Make.julia -j8` runs 94 comparisons against genuine C++
references and all 94 pass with the new emitter, so the generated Julia still
compiles and computes identically. Workspace tests, clippy, golden-check, the
four structure gates, and a re-recorded `cli-transcript-check` are green; the two
re-recorded transcripts contain only the three intended changes.

Pre-existing and unrelated: `compile-budget-check` fails on
`reverb_designer: vector` (≈955 units against a 953.982 ceiling) on this machine.
Confirmed by re-running the gate with these changes stashed — it fails
identically on the clean tree.
