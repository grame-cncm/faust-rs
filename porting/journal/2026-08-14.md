# 2026-08-14

## Design `faust-probe`, a generic DSP probing tool (Cranelift, polyphonic)

Commit date: 2026-08-14

Source commit: this commit

Both existing runners — `impulse-runner` (interpreter) and `impulse_cranelift`
— answer one question: *did the behaviour change?* They render a fixed
protocol (SR 44100, block 64, impulse on frame 0, buttons held for the first
block only, sliders at their defaults) and emit `.ir` for `filesCompare -part`
against the C++ oracle. The protocol is fixed by construction: regression
testing requires that nothing varies.

Neither answers *is the behaviour correct?*, which needs the opposite —
varying exactly the thing under test.

The gap was hit concretely while porting a C++ synthesizer engine to Faust in
a separate repository. Verification there needed a bespoke `faust -a`
architecture file plus a `c++ -O2` compile per DSP variant, 3-5 s each,
because no faust-rs tool can set a parameter. Four of that port's eight
validation properties were unreachable with `impulse-runner`: envelope release
timing (its gate lasts 64 samples, 44 000 were needed), delay ping-pong and
M/S width collapse (its impulse goes to *every* input channel, so one channel
cannot be excited alone), and anything requiring a specific operating point.

Measured before committing to a backend, same DSP and same output:

| Frames | Interpreter | Cranelift |
|---|---|---|
| 15 000 | 0.07 s | 0.06 s |
| 96 000 | 0.11 s | 0.04 s |
| 2 000 000 | 1.96 s | 0.41 s |

Subtracting the ~0.05 s JIT/front-end baseline, Cranelift renders ~5.3x faster
(1.91 s against 0.36 s). At 15 000 frames the two are indistinguishable
because compilation dominates, which is why the existing runners show no
reason to prefer either backend.

That ratio is what makes parameter sweeps the point of the design rather than
a convenience: a 30-point sweep at 96 000 frames costs one JIT plus 30 renders
— ~1.2 s under Cranelift, ~3.3 s under the interpreter, and ~150 s under the
compile-per-variant scheme a bespoke harness forces. The build step is what
shapes a test tool; removing it is what lets one process explore a parameter
space.

Two things must be built on top of the runtime path `impulse_cranelift`
already establishes:

1. A path→zone map, by accumulating the box stack while walking the `UIGlue`
   callbacks (`crates/ffi-common/src/abi.rs:111`) — the `PathBuilder.h` /
   `MapUI.h` algorithm. `getCCraneliftDSPFactoryJSON` carries addresses and
   ranges but not zone pointers, so it can serve a richer `--list-params` and
   nothing else.
2. A polyphonic wrapper, since the Cranelift runtime has no poly/MIDI wrapper
   any more than the interpreter does. Ported from
   `architecture/faust/dsp/poly-dsp.h`: control discovery by path suffix
   (`/gate`, `/freq` vs `/key`, `/gain` vs `/vel` — the distinction selects the
   conversion function), voice states `kFreeVoice -1` … `kNoVoice -4`,
   first-free-then-steal-oldest-releasing-then-oldest-playing allocation with
   the stolen voice entering `kLegatoVoice`, retrigger onto the oldest voice
   playing the pitch, and voice reclamation below `VOICE_STOP_LEVEL`
   (0.00003162, -90 dB).

`--protocol impulse-test` pins the reference protocol exactly, so the tool
subsumes both existing runners rather than competing with them, and stays
usable against the existing corpus.

Design: [`porting/faust-probe-generic-test-tool-design-2026-08-14-en.md`](../faust-probe-generic-test-tool-design-2026-08-14-en.md).
Phases P1-P5 with exit criteria there; P1 and P2 are independently useful and
P4 (poly) should not gate them.

## Re-derive the impulse-tests status table on one corpus; close G5-J7

Commit date: 2026-08-14

Source commit: this commit

Asked to re-derive `tests/impulse-tests/README.md`'s Status table on one
consistent corpus and close `G5-J7` (Julia missing a row, blocked on that
re-derivation per the earlier P6 note — mixing Julia's 94/94 current-corpus
number with the table's stored 92/93 historical one would have been
unreadable).

Doing the re-derivation surfaced a real methodology bug, twice compounding:

1. `Make.ref`'s `FAUST_CPP ?= faust` resolves through `$PATH`. This machine has
   a second, newer Faust install (`/usr/local/bin/faust`, v2.87.4) ahead of the
   pinned dev checkout on `$PATH`. Regenerating `reference/` without pinning
   `FAUST_CPP` explicitly silently built the whole reference corpus against the
   wrong compiler.
2. Under that wrong compiler, the C++-oracle preflight reported only 94/133
   DSPs supported — the 39 `ondemand_*`/`upsampling_*`/`downsampling_*`
   clock-domain fixtures are dev-branch-only and not in a public 2.87.4
   release — matching, and therefore reinforcing rather than catching, a
   stale comment already in `known.mk` making the same claim. One DSP,
   `bells` (0 inputs, feedback gain 0.989, entirely excited through UI
   buttons), diverged outright from that wrong reference under the
   interpreter backend: not a faust-rs regression, a different compiler
   version driving button-excitation timing slightly differently and a
   near-unity-feedback resonant model amplifying the difference within a few
   samples. Two other DSPs (`modulations`, `zita_rev1`) also appeared to fail
   their native C++ reference build under that same wrong compiler's local
   install; both turned out to be an unrelated bad local build of it, fixed by
   rebuilding, and are not faust-rs issues either. None of this affects the
   133-DSP sweep below, which was always built and validated against the
   pinned `8eebea429` checkout.

Rebuilding the full 133-DSP reference corpus with `FAUST_CPP` set explicitly
to the pinned `master-dev-ocpp-od-fir-2-FIR19`@`8eebea429` build, then running
all 8 backends (`make cpp c interp cranelift wasm assemblyscript rust julia`,
each against the same 133-DSP set): **133/133, 0 mismatch, 0 compile-fail,
every backend**. `bells` matches exactly against the correct reference.

`tests/impulse-tests/README.md` §Status is now one table over the full current
133-DSP corpus (adding the Julia row that closes `G5-J7`), replacing the
historical 92/93-DSP table plus the two prose paragraphs that had validated
the clock-domain fixtures separately from it — their content (non-silent
output characterization, dedicated `ma.SR` relationship tests) is kept,
reframed as supplementary detail about cases now inside the unified sweep. The
92/93 history and the `subcontainer1` shared-compile-gap fix date
(2026-08-06) are kept as a labeled historical paragraph. Added a methodology
note inline explaining the `FAUST_CPP` trap so the next person who regenerates
`reference/` doesn't rediscover it the same way, and a one-line caution in the
Requirements section pointing there. `known.mk`'s `KNOWN_FAIL_all` comment,
which carried the same wrong "94 of the corpus's 133" claim, is corrected to
point at the same explanation instead of repeating it.

`G5-W6` (no C++ oracle exists for *vector*-mode WASM on the pinned branch,
`-vec` rejected outright there) is untouched by this change — the 133-DSP
sweep is scalar-only and doesn't bear on that claim.

`porting/wasm-julia-maturity-diff-gap-005-analysis-and-plan-2026-08-14-en.md`
(`G5-J7` row and P6) and the `DIFF-GAP-005` summary in
`porting/faust-rs-vs-faust-cpp-differences-en.md` are updated to close `G5-J7`
and record the `FAUST_CPP` finding.

## Document `sr_index` as a declared Rust extension (`G5-W4`, `DIFF-BACK-005`)

Commit date: 2026-08-14

Source commit: this commit

Asked to explain `G5-W4` from the inventory below, then to fix it. No code
changed — `sr_index` was already correct on the Rust side; only the registry
was missing the entry that says so.

Rust's WASM companion JSON always fills `sr_index` with the byte offset of
`fSampleRate` in the module's memory layout
(`crates/codegen/src/backends/wasm/mod.rs:674`,
`WasmMemoryLayout::field_offsets`). The pinned C++ WASM backend never does:
`WASMCodeContainer::generateJSON()` constructs its `JSONInstVisitor` with
`sr_index = -1`, and the schema's shared serializer
(`architecture/faust/gui/JSONUI.h:645`) omits the key whenever the value is
`-1`. The field is not a Rust invention — it is part of the general Faust JSON
schema and has a real host-side reader,
`architecture/faust/gui/JSONUIDecoder.h:224` and `:295`, which reads the
sample rate straight out of WASM linear memory at that offset, the same
mechanism widget `index` values already use for parameters. C++ simply never
populates it for this one backend, plausibly because a single
`getSampleRate()` call is cheap enough that the per-widget-count argument for
avoiding exports (many widgets vs. one export call) does not apply to a
single scalar.

Registered as `DIFF-BACK-005` in
[`faust-rs-vs-faust-cpp-differences-en.md`](../faust-rs-vs-faust-cpp-differences-en.md)
§6 (Additional backends and delivery forms), next to the other WASM-family
entries. Status `extension`: additive, not narrower — no C++-documented
consumer breaks on the extra key, and nothing the C++ JSON promises is absent
from Rust's. `G5-W4` is closed in
[`wasm-julia-maturity-diff-gap-005-analysis-and-plan-2026-08-14-en.md`](../wasm-julia-maturity-diff-gap-005-analysis-and-plan-2026-08-14-en.md)
and the top-level `DIFF-GAP-005` entry updated to reflect it.

## WASM companion JSON: inject the compiler-synthesized identity `meta` entries (`G5-W2`)

Commit date: 2026-08-14

Source commit: this commit

The WASM half of `DIFF-GAP-005`'s inventory (see the entry below) was scoped
out of the previous change on request. Asked to pick it up specifically for
`G5-W2`; since that item names the WASM emitter directly and directly
contradicts the earlier "leave WASM alone" instruction from the same session,
confirmed the scope change with the user before touching the backend.

`G5-W2`: the WASM companion JSON `meta` array carried only source `declare`s
(or nothing, for a DSP without any) — C++ always injects `compile_options`,
`filename`, and `name` into `meta` too, from `gGlobal->gMetaDataSet`, which
records them before the DSP is even parsed. `build_wasm_json_description`
(`crates/codegen/src/backends/wasm/mod.rs`) now runs the same
`c_family::ordered_compilation_metadata` helper the C/C++/Julia emitters
share, so all four backends declare identity in the same C++ key order from
the same transport. Verified against C++ on `s2.dsp` (no `declare`) and
`s3.dsp` (`declare name/author/version`): key set, values, and order match
exactly (the `compile_options` *value* still differs — `DIFF-CLI-006`,
pre-existing and out of scope).

One correctness trap surfaced during implementation, not by the earlier audit:
`build_json_description_from_fir` appends the FIR module's own `metadata`
function body *after* the injected identity set, without deduplicating across
the two. Production DSPs never populate that body — `signal_fir` lowering
always emits it empty and carries source `declare`s through
`WasmJsonContext::top_level_meta` instead, the same split the Julia fix relied
on — but the codegen-level fixture `build_gain_bias_ui_meta_test_module` hand-
builds a real declaring `metadata` body to test FIR-driven replay directly,
bypassing the compiler facade entirely. Unconditional injection would have
doubled `name`/`filename` for that fixture. `wasm_meta_with_identity_entries`
skips injection whenever the FIR module already declares a non-empty
`metadata` body — the same mutual-exclusion rule `has_metadata` already
enforces in the C-family emitters and `is_empty_metadata_body` enforces in
Julia, now applied to JSON `meta` construction too. No existing test needed to
change.

Validation: `make -f Make.wasm -j8` runs 94 comparisons against genuine C++
references and all 94 pass. Workspace tests, clippy, golden-check, and a
re-recorded `cli-transcript-check` are green; the changed transcripts
(`*_lang_wasm`, `*_lang_wast`) show only the intended `meta` addition —
confirming the fix reaches both `-lang wasm` and `-lang wast`, since both route
through the same `generate_wasm_module_with_context`. `compile-budget-check`
passed this run (947.750/953.982 on `reverb_designer: vector`), consistent
with the near-ceiling measurement noise already noted below rather than an
actual regression.

`G5-W3` (embedded base64 `code`) and `G5-W4` (declaring `sr_index` as a Rust
extension in the differences registry) remain open, tracked in
[`wasm-julia-maturity-diff-gap-005-analysis-and-plan-2026-08-14-en.md`](../wasm-julia-maturity-diff-gap-005-analysis-and-plan-2026-08-14-en.md).

## Julia backend: real `metadata!`, real `getJSON`, `@inbounds` on `compute!`

Commit date: 2026-08-14

Source commit: this commit

Audited the two backends named by `DIFF-GAP-005` ("WASM and Julia are functional
on validated paths but do not claim the complete … maturity of the C++
implementations") against the pinned C++ reference `8eebea429`, and replaced the
blanket disclaimer with an enumerated inventory in
[`wasm-julia-maturity-diff-gap-005-analysis-and-plan-2026-08-14-en.md`](../wasm-julia-maturity-diff-gap-005-analysis-and-plan-2026-08-14-en.md)
(`G5-W1`…`G5-W6`, `G5-J1`…`G5-J7`). The WASM half of the inventory is
specification only: the emitter was deliberately left untouched in this change.

Three Julia items are closed.

- `G5-J1` — `metadata!` was emitted with an **empty body in every case**. Not
  only were the compiler-synthesized `compile_options` / `filename` / `name`
  entries missing: source `declare`s were dropped too. A Julia host calling
  `metadata!` got nothing. The C-family metadata transport
  (`metadata_name` / `metadata_filename` / `metadata_entries` plus
  `c_family::ordered_compilation_metadata`) is now shared with Julia, so the
  three backends declare the same keys, in the same C++ key order, from the same
  snapshot. Verified against C++ `-lang julia` on a source with
  `declare name/author/version`: same five declarations, same order.
- `G5-J2` — `getJSON` returned the literal `"{}"`. It now returns the real
  description, built by the facade through the existing
  `build_strict_json_description` and embedded as a flat Julia string literal
  (`JsonDescription::render_flat`, the Rust counterpart of C++
  `JSON(true)` + `flattenJSON`). Agrees with the C++ payload on `name`,
  `filename`, `inputs`, `outputs`, `size`, and the whole `ui` tree.
- `G5-J3` — `compute!` is emitted as `@inbounds function compute!`, as the
  reference does. Every table and buffer access in the audio loop was paying a
  bounds check.

Two defects found while implementing, neither of them in the audit:

- The embedded description took its `name` from the FIR module, which carries
  the **class** identity (`-cn`, default `mydsp`), not the DSP name. A DSP
  compiled without `declare name` advertised `"name": "mydsp"` next to
  `"filename": "simple.dsp"`, contradicting its own `metadata!` callback. This
  is the mirror image of the `-mem0` `memory_layout` zone-naming defect fixed on
  2026-08-13. The description now takes the resolved DSP name; a regression test
  pins `-cn` against it.
- `julia_string_literal` did not escape `$`. Julia interpolates it inside a
  double-quoted literal, so any label — or any embedded JSON — containing `$`
  produced source that does not compile. Deliberate deviation from C++
  `flattenJSON`, which leaves `$` alone.

`G5-J5` was filed by the audit as a correctness defect (`REAL(...)` assigned to a
`FAUSTFLOAT` field) and is **withdrawn**: Julia's `setproperty!` converts to the
declared field type, so the store is correct whatever the host defines
`FAUSTFLOAT` to be. Only the spelling differs. `G5-J4` (internal FIR `Label`
comments reaching the generated source) turned out not to be a Julia matter
either — the labels come from the shared lowering and the Rust backend prints
them too — so it moves to the cross-backend phase with the 200 stored Rust
golden files it would re-record.

Validation: `make -f Make.julia -j8` runs 94 comparisons against genuine C++
references and all 94 pass with the new emitter, so the generated Julia still
compiles and computes identically. Workspace tests, clippy, golden-check, the
four structure gates, and a re-recorded `cli-transcript-check` are green; the two
re-recorded transcripts contain only the three intended changes.

Pre-existing and unrelated: `compile-budget-check` fails on
`reverb_designer: vector` (≈955 units against a 953.982 ceiling) on this machine.
Confirmed by re-running the gate with these changes stashed — it fails
identically on the clean tree.
