# 2026-10-12

## AD: `tan' = 1 + tan²` built on the primal, in FAD, symbolic RAD and BRA

Commit date: 2026-10-12

Source commit: this commit (parent `78bd77e`).

The `tan` derivative rule was `1 / cos²(x)` everywhere, so each
differentiated `tan` added a `cos`, a square and a division to the generated
code next to a primal `tan(x)` that is computed anyway. Reported (measurement dated 2026-10-13) from
the sibling project `faust-diff-mxr`: `mx.newton(1, rate)` (Newton slope by
`fad`) ran 32.6 ms against 27.4 ms for the same solver with the slope written
by hand as `1 + g²` (`-lang cpp -double`, clang++ -O3, 10 s at 48 kHz, +18 %,
three runs); the FAD code had one extra `std::cos` per stage.

- FAD (`crates/propagate/src/forward_ad.rs`): the `Tan` arm builds the primal
  `tan(x')` once and writes every tangent lane as `(1 + p·p) · x'` on that same
  `SigId` `p`, so no second `tan` and no `cos` is built.
- Shared RAD formula (`crates/signals/src/ad_rules.rs`,
  `rad_unary_contribution`): `y_bar · (1 + primal²)`. The callers now pass the
  forward value as `primal`: symbolic RAD (`reverse_ad.rs`) rebuilds `tan(x)`,
  which hash-conses onto the primal node; BRA (`signal_fir/module/setup.rs`)
  loads the forward `tan` output, and `collect_tape_needed_values`
  (`block_reverse_ad.rs`) tapes that output instead of the operand, as for
  `exp`, `exp10` and `sqrt`. The tape count is unchanged (one slot holds
  `tan(·)` instead of its argument) and the reverse sweep calls no
  transcendental function for `tan` any more.
- Docs: the rule tables of `forward_ad.rs` and `docs/rad-note-en.md`
  (`docs/fad-note-en.md` does not list it), the `ad_rules` formula list, and
  the BRA tape table.
- Numerics: `1 + tan²` and `1 / cos²` are the same function; near the poles
  both are large and their rounding differs by a few ulps.

Measurement. `faust-diff-mxr` is not available in the cloud session that made
the change, so its native bench could not be re-run there; a self-contained
proxy of the same shape was measured instead: four cascaded implicit stages,
each solving `v + 0.3·tan(v) = 0.5·x + 0.4·v[n-1]` by four unrolled Newton
steps per sample, slope from `fad` or written by hand as
`1 + 0.3·(1 + tan²(v))` (`-lang cpp -double`, clang++ 18 -O3, 10 s at
48 kHz, best of 7 runs, three rounds, Linux x86-64):

| Variant | `std::cos` / `std::tan` in `compute` | Time |
|---|---|---|
| `fad`, before | 16 / 16 | 278.7–280.8 ms |
| `fad`, after | 0 / 16 | 262.5–263.8 ms |
| hand-written slope | 0 / 16 | 262.6–267.2 ms |

−5.8 %, and the `fad` version now costs what the hand-written one costs; the
output checksums of the three are identical. The mxr figure (+18 % with four
extra `cos`) is to be re-measured with that project's bench.

Tests: `ad_rules_tan_contribution_matches_analytic_derivative` (the shared
formula, evaluated in `f64`, against `1 / cos²` at eight points of
`(-π/2, π/2)`), `ad_rules_tan_contribution_reuses_primal_without_cos`,
`fad_tan_tangent_reuses_primal_node_without_cos`,
`rad_tan_gradient_reuses_primal_node_without_cos`; in `rad_runtime.rs`,
`fad_tan_tangent_matches_analytic_derivative` (interpreter, six points),
`rad_vs_fad_parity_on_tan`, `rad_tan_matches_central_difference`,
`rad_tan_in_recursive_body_bra_total_grad_matches_fd` (BRA with the taped
`tan` output) and `tan_derivative_emits_no_cos_in_generated_cpp` (one
`std::tan`, no `std::cos`, in FAD, symbolic RAD and BRA C++).

A latent defect seen in passing, not fixed here: symbolic RAD
(`reverse_ad.rs::propagate_unary_math`) passes the operand as `primal` for
`exp10`, whose shared rule reads the forward value, so `rad` of `exp10` would
be `y_bar · x · ln 10`. `exp10` has no source binding, so no program reaches it
today; the BRA path loads the right value.
