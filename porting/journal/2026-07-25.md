## Complete the `generate_aux_files` option forwarding (`-double`/`-mcd`/`-dlt`/`-vec`/`-ss`)

Continuation of yesterday's PR #13 gap (faustwasm service: execution options
in the argv): that fix forwarded only `-ec`/`-os` from the hand-parsed
`generateAuxFiles` argv into the derived `Compiler`. A WIP edit to
`with_execution_options_from_argv` (`crates/compiler/src/lib.rs`) had started
adding `-double`/`-single`/`-vec`, but referenced `ComputeMode::Vectorized`, a
variant that does not exist — the real shape is `ComputeMode::Vector {
vec_size, loop_variant }` — so `cargo check -p compiler` failed outright.
`-single` is not a real Faust flag either: single precision is already the
default and only `-double` toggles it; neither the CLI surface in this
codebase (`crates/compiler/src/cli/args.rs`) nor the reference compiler
defines `-single`.

Fix. The function now mirrors the flag-to-field mapping `compiler_from_cli`
(`crates/compiler/src/cli/runner.rs`) already applies for the real CLI:
`-double`, `-mcd N`/`-dlt N`, `-vec` (+`-vs N`/`-lv N`),
`-ss N`/`--scheduling-strategy N`, alongside the existing `-ec`/`-os`. These
are plain Faust CLI flags on a raw argv string, not a dialect belonging to any
one caller of `generate_aux_files` — the Rust mirror of the C++
`generateAuxFilesFromString`/`generateAuxFilesFromFile` API, of which faustwasm
is one consumer among others.

Also fixed here: `-double` was re-parsed by hand for `WasmOptions` and missed
the `--double` spelling the same function accepts, so `--double -wasm`
compiled the DSP in double while the emitted JSON advertised `-single`. It is
now derived from the derived compiler's `real_type`, so one decode drives both.

A shared `argv_value`/`argv_value_parsed` helper lands in `json_naming.rs`
rather than a third copy of the position/get scan; `generate_asc_aux_file`'s
`-cn`/`-o` lookup drops its private closure in favour of it.

Validation: `cargo test -p compiler`. Two tests added —
`faustwasm_aux_files_honor_mcd_dlt_vec_ss_in_argv`
(`crates/compiler/tests/execution_options.rs`): `-mcd 0` forces delay-1 off
the Shift strategy (`[(fIOTA & 1)]` masking reappears), `-dlt 8` switches the
far delay line to `IfWrapping` (`fIdx` counter), `-vec -os` still rejects with
"scalar mode" (which only triggers if `-vec` actually reached
`ComputeMode::Vector` through the argv path), and all four `-ss` decode buckets
compile; and `…applies_long_double_flag_to_the_wasm_backend`
(`crates/compiler/src/tests.rs`) locks both `-double` spellings, confirmed
rejecting by restoring the hand-parse.

Public API mapping: `generate_aux_files` argv surface only — no CLI, C, C++,
ABI, or generated-code contract change; it brings the hand-parsed argv path to
parity with the `faust-rs` CLI flag set it already claimed to mirror.

## Documentation coherence and factoring pass over the compiler facade

Several doc comments in `crates/compiler/src/lib.rs` described a compiler
from two ports ago, and one described the wrong function entirely.

- **Detached doc block.** The `generate_aux_files` doc comment ("Generate
  auxiliary output files…") sat above `with_execution_options_from_argv`:
  `339ed0b7` had inserted that helper between the doc and the function it
  documents, leaving `generate_aux_files` itself with no doc at all. Split
  into two, each describing its own function, with the flag→output and
  flag→option tables where a reader looks for them.
- **Contradictory option docs.** The `compute_mode` field and
  `with_compute_mode` claimed vector mode "still emits scalar code until the
  `LoopGraph` lowering lands", and `scheduling_strategy` claimed "no compile
  path invokes `transform::schedule::schedule` yet". Both are long obsolete,
  and the same file contradicts the first through
  `FirCompileOutput::vector_effective_mode`. Verified before rewriting:
  `-vec -vs 8` emits the chunked `vindex` loop, and `-ss 0/1/2/3` emit four
  different modules for the same DSP.
- **The same obsolete claim in `--help`.** `clap` renders `cli/args.rs`'s
  `--vec` doc into `faust-rs --help`, where it stated the flag records the
  option but still emits scalar code — telling users the flag does nothing.
  Rewritten there too, along with the matching `plumbing only` notes on the
  `signal_lowering.rs` option struct and the scope comment above the `-ss`
  CLI tests (which describes what those tests cover, not what the flag does).
- **Stale `deferred` mapping status** on `AuxFileArtifact` and
  `ExpandDspRequest` ("planned"/"reserved for future support") although both
  APIs are implemented; `FaustwasmServiceError` still described itself as
  meaning "not implemented yet" when it mostly carries compile diagnostics.

Factoring, all in the aux-file surface: `AuxFileArtifact::text`/`::binary`
constructors replace six repeated struct literals;
`unsupported`/`invalid_argument` now take `impl Display`, so nine
`.map_err(|e| …::unsupported(e.to_string()))` closures become
`.map_err(FaustwasmServiceError::unsupported)`; the asc path's three
`invalid_argument` mappings join the rest of the surface on `Unsupported`
(no consumer reads the code — `wasm-ffi` propagates only the message);
`-lang asc` detection reuses `argv_value`.

One trap avoided while making the output branches uniform: `-json` cannot
simply become independent of `-wasm`. `-wasm` already emits the companion
`<stem>.json` matched to the module (`WasmArtifactBundle`'s ABI contract),
so an unconditional `-json` branch would push a second artifact at that
same path and a host writing them out in order would silently lose one.
The branch is independent but explicitly stands down under `-wasm`, and
`…never_emits_two_artifacts_at_one_path` locks the artifact-path set for
`-cpp -c -wasm -json` (confirmed rejecting: dropping the guard reproduces
a duplicated `zero.json`).

Public API mapping (CLI help text): `--vec`'s `--help` description changes
from a false "does nothing yet" to the checked-selection contract. No flag,
default, or emitted-code behavior changes.

## Group the facade emitter entry points by backend

The ~62 emitter entry points of `impl Compiler` were grouped by *input kind*
(source / file / file-default), with the backends in a different, arbitrary
order inside each group (`cpp, c, julia, c_with_lane, asc, …`). One backend's
six entry points were therefore scattered across three distant regions, and a
function's `_with_lane` twin was sometimes adjacent, sometimes 300 lines away.
`compile_file_default_to_json*` sat *after* the faustwasm service methods —
detached from both the other JSON functions and the other file-default ones —
and the whole interpreter family sat alone at the end of the impl.

Regrouped by backend: C++, C, Rust, Julia, AssemblyScript, interpreter, FIR,
WASM, JSON, then the helper service surface. Each section follows one
identical order — `compile_source_to_X`, `_with_lane`, `compile_file_to_X`,
`_with_lane`, `compile_file_default_to_X`, `_with_lane` — so once a reader
knows one backend they know them all. A note above the first section states
that convention and the three deliberate deviations (the FIR dump is
lane-only, because the lane *is* what is being dumped; the WASM and JSON
groups end with extra variants returning richer results), so the irregular
cases read as intentional rather than as leftovers.

Done by script rather than by hand, and checked as a pure move: the
function-name multiset is unchanged, every non-comment line is byte-identical
to the previous revision, and the public surface still counts 87 `pub fn` and
16 private ones. The script asserts on dropped or duplicated blocks, so an
error would have failed loudly instead of shipping.

Public API mapping: none — declaration order only.

## Rename `CompilerError::Codegen` to `CodegenCpp`

`CompilerError` carried `CodegenC`, `CodegenJulia`, `CodegenAsc`,
`CodegenRust`, `CodegenInterp`, `CodegenWasm` — and a bare `Codegen` for
C++, which read like a catch-all rather than one backend among seven. The
C++ backend's error type was likewise the only one imported unaliased,
next to `CodegenError as CCodegenError` and friends, leaving a bare
`CodegenError` in a file importing seven of them; it is now
`CppCodegenError`.

`LowerError::Codegen(E)` keeps its name deliberately: it is generic over
every backend error type, so there "codegen" is the correct, non-specific
word, and renaming it would have been the opposite of the regularity this
change is after.

Public API mapping (Rust API, source-breaking): the enum is `pub`, so any
downstream `match` naming that variant must be updated; both in-tree
matchers (`crates/xtask/src/reports.rs`,
`crates/compiler/src/error_mapping.rs`) were. No error code, message,
diagnostic bundle, or CLI output changes — the variant only takes the name
the other six backends already use.

## CI fix: `phaser_flanger.dsp` legacy library names don't resolve against the pinned faustlibraries checkout

`main-dev` CI run
(https://github.com/grame-cncm/faust-rs/actions/runs/30137107145) failed
`Lint and test` on all three OSes: `fused_serial_groups_survive_dead_pure_root_removal`
(added yesterday in `f04276d9`) errored with "library could not resolve
source file `oscillator.lib`" while compiling
`tests/impulse-tests/dsp/phaser_flanger.dsp`.

Cause. The fixture imports the legacy singular library names
`oscillator.lib`, `filter.lib`, `effect.lib` via `ol/fl/el =
library(...)`. Those names only exist under `old/` in the pinned
`faustlibraries` checkout (`ecf2fdc238148c44c18352102333a1229ca7a8d3`,
used by the `Lint and test` job's `FAUST_LIB_PATH`); the canonical
top-level names since faustlibraries' 2017 legacy-compatibility
reorganization are the plural `oscillators.lib`/`filters.lib`, and none
of `sawtooth_demo`/`flanger_demo`/`phaser2_demo`/`spectral_level_demo`
even live there anymore — they moved into `demos.lib` (prefix `dm`).
`candidate_loaded_source_paths` (`crates/eval/src/lib.rs`) does a direct
`search_path.join(target)` with no subdirectory search, so `old/` is
never consulted.

This passed on the author's machine only because a Homebrew-installed
`faust` (`/usr/local/share/faust`) happens to carry a flatter, legacy-
compatible library layout that resolves the old singular names directly
— a fallback search path entry that masked the gap locally. CI's
`Lint and test` job has no system `faust` install (only the separate
`vector_retention` job does, via `apt-get install faust`), so it hit the
real gap.

Fix. Rewrote `phaser_flanger.dsp` to `dl = library("demos.lib")` and
`dl.sawtooth_demo` / `dl.flanger_demo` / `dl.phaser2_demo` /
`dl.spectral_level_demo`, matching the pinned checkout's current layout.
Verified with `FAUST_LIB_PATH` pointed at a fresh clone of the pinned
faustlibraries commit (no system faust on `PATH`/fallback masking to
worry about, since `FAUST_LIB_PATH` is checked before the
`/usr/local/share/faust` fallback in `default_import_search_paths`):
`cargo test -p compiler --test vector_mode` — 37/37 passed.

Not fixed here (flagged, out of scope): several other impulse-tests
fixtures (`cubic_distortion.dsp`, `gate_compressor.dsp`,
`parametric_eq.dsp`, `spectral_tilt.dsp`, `vcf_wah_pedals.dsp`,
`virtual_analog_oscillators.dsp`, `carre_volterra.dsp`,
`reverb_tester.dsp`, `reverb_designer.dsp`, `thru_zero_flanger.dsp`,
`zita_rev1.dsp`) use the same legacy singular library names. They
currently only surface in jobs/tools that either don't compile them
through this eval path yet or run where a real `faust` install papers
over the gap (`vector_retention`); any future test that compiles them
through the plain git checkout will hit the identical failure.

Public API mapping: test-fixture-only change; no CLI, C, C++, ABI, or
generated-code contract change.
