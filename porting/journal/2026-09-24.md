## `controls.lib` 0.1.0 and the uses of the control-input primitives

Commit date: 2026-09-24

Source commit: this commit

`libraries/controls.lib` (prefix `ct`) packages the uses of `cinputs`,
`cinput` and the `"*"` target beyond learning, on a program left as it is.
Everything is `map(f, e)`, `par(i, N, f(i, widget_i)) : ["*": (!, _) -> e]`:
a function that reads its widget keeps the knob, one that ignores it removes
it. Readers (`count`, `widget`, `init`, `lo`, `hi`, `step`, `inits`);
rebinding (`external`, `normalized`, `cv`, `smooth`, `smoother`); rebuilt
interfaces (`relabel`, `knobs`); exploration (`morph`, `randomize`,
`offset`); testing (`sweep`, `sweep_one`, `nonfinite`); sensitivity
(`gradient_fad`, `gradient_rad`). The library imports nothing (its own
one-pole, noise, sample-and-hold, `take`), so its tests need only
`-I libraries` and never skip.

Found while writing it: `fad(e, cinputs(e))` gives each output followed by
its derivatives, `rad(e, cinputs(e))` the outputs then the gradient of their
sum, so `gradient_rad` has `outputs(e) + count(e)` outputs; a widget built
inside a lambda composed with `cinput(i, e) : \(w, v, a, b, s).(...)`
receives signals and is refused (`FRS-EVAL-0011`), the constants must be
passed by application, as `relabel` does. `docs/control-inputs-en.md` gains
the uses (section 3: the pattern, a table of uses, the limits: labels are not
values, `"*"` matches buttons, bargraph signals are out of reach, nothing
sets a knob) and the library reference (section 4).

Tests: `crates/compiler/tests/controls_lib.rs`, 8 tests on
`tests/corpus/ctl_01_reading` to `ctl_07_sensitivity` (values derived by
hand in each header, the rebuilt interface read from the JSON, random draws
on each range and grid and held between triggers, a sweep of `1 / d` whose
non-finite count is 1 exactly where `d` crosses 0) and
`ctl_all_functions.dsp`, the 23 documented `#### Test` entries, 26 outputs.
Golden: `golden-gen-rust` added the 8 Rust fingerprints; no existing
snapshot changed. No C++ snapshot: the reference stops on `undefined symbol :
cinputs` in the library, an expected divergence for the corpus classifier.
Registry: `DIFF-SRC-004` names the library.

## `cinputs`: dead widgets listed, decided and documented

Commit date: 2026-09-24

Source commit: this commit

Decision: `cinputs(e)` lists the control inputs present in `e`, read or not,
as `inputs(e)` counts the audio inputs of `e` (`inputs(_ : !)` is 1). It is
therefore a superset of the compiled interface, which prunes the widgets the
final signals no longer read (`hslider("d",…) * 0 + hslider("l",…)`: `cinputs`
lists `d` and `l`, the interface shows `l`). Counting only live widgets was
rejected: at evaluation `e` is a box, and deciding liveness would mean
propagating and simplifying it there, making the count, the `cinput` indices
and the inputs `"*"` adds depend on signal simplification rules and options.
The behaviour does not change; `docs/control-inputs-en.md` ("What is listed",
the order of the widgets the interface shows, `"*"` adding
`outputs(cinputs(e))` inputs), the analysis section 7, `DIFF-SRC-004` and the
module doc of `crates/eval/src/control_inputs.rs` now say so, where the doc
presented the list as "the order of the interface" without the caveat.

## `cinput` / `coutput`: an index that is not a constant, named and diagnosed

Commit date: 2026-09-24

Source commit: this commit

`cinput(freq1, 0)` (the arguments swapped) failed with the generic
`FRS-EVAL-0099 expression is not a compile-time numeric constant (type 0→1):
node 34`, with no source location. It is now `FRS-EVAL-0009`, whose meaning
widens from "index out of range" to "invalid control index" (the constant is
renamed `EVAL_CONTROL_INDEX_INVALID`, as `EVAL_ITERATION_INVALID` covers every
bad `par` count): the message names the index as written (`the index of
`cinput` must be a compile-time integer, and `freq1` is not`), and when the
expression is itself a constant the diagnostic says the arguments look
swapped and suggests `cinput(0, freq1)`. A division by zero in the index stays
that error, as for iteration counts. A negative index is reported as written
(it was reported as the count), and "1 control inputs" is singular. The four
control-list errors now carry their node to `eval_error_node`, so they get
the source line, the owning definition and a readable `expr=` note (the
preview renderer learns the four primitives).

Tests: fixture `tests/corpus/err_32_cinput_arguments_swapped.dsp` (the
reported program) and three tests in `crates/compiler/tests/control_inputs.rs`
(swapped arguments, a signal index without a constant expression, a negative
index). Golden: `golden-gen-rust` added the one fingerprint
`tests/golden/rust/err_32_cinput_arguments_swapped`; no existing snapshot
changed. Compile budget: only error paths changed; not measured.

## Control inputs as boxes (`cinputs`, `cinput`, `coutputs`, `coutput`) and the wildcard modulation target `"*"`

Commit date: 2026-09-24

Source commit: this commit

Implements sections 3.1 to 3.3 of
`porting/control-inputs-and-wildcard-modulation-analysis-2026-09-22-en.md`
(registry `DIFF-SRC-004`, note `docs/control-inputs-en.md`). Four keywords and
box kinds (`BOXCINPUTS`, `BOXCINPUT`, `BOXCOUTPUTS`, `BOXCOUTPUT`: builder,
matcher, printer, grammar), folded by eval like `inputs(e)`: `cinputs(e)` to
the `par` of `e`'s widget boxes, `cinput(i, e)` to
`(widget, init, min, max, step)`, the bargraph twins to `(bargraph, min, max)`.

Three decisions taken with the user, recorded in section 7 of the analysis:
the order is the interface's (the analysis claimed a depth-first walk was
the order of `buildUserInterface`; it is not, both compilers sort each
group's children by raw label and merge groups of the same label), a widget
box under several groups is one control per group (the UI builder's key, not
the `TreeId`), and `cinput` has five entries, no scale. To keep the order
from drifting, the list is the UI builder's own: `propagate::control_widgets`
builds the UI program of the lowered `e` and reads its leaves in layout
order, with an index from (widget, group-context hash) to position. This
widens `propagate`'s public API by `ControlWidget(s)`, `UiGroupContext` and
`control_widgets` (baseline regenerated), a design decision: eval needs the
list, and a second implementation of label sorting and group merging in eval
would be the drift this avoids. Eval caches the list per lowered box, since
`par(i, N, cinput(i, e))` asks N times.

The wildcard: a target whose last segment is `*` matches every control input
whose interface path has the preceding segments as a subsequence, bargraphs
never. A two-input modulator gets one fresh slot per matched control, wrapped
first-outermost so the i-th extra input drives the i-th control of `cinputs`;
a literal target keeps its one shared slot. `implant_wildcard` walks the
lowered body with `UiGroupContext`, the builder's context key, restarting at
the root for `fad`/`rad` seeds as the builder does, so a seed and the body's
use of one widget get the same slot; memoized per (box, context). No match
is `FRS-EVAL-0010`, an index out of range `FRS-EVAL-0009`.

Tests, self-contained (`crates/compiler/tests/control_inputs.rs`, 13): the
order against the program's own JSON, `cinput`'s values, the empty list, a
box under three groups, dead widgets counted, `"*"` equal to one literal
target per control to the bit and leaving the interface empty, one-input
modulators, `fad(f, cinputs(f))` equal to `fad(f, (a, b))`, a rebound `fad`
seed, both codes, `"stage*"` staying literal; plus unit tests in `boxes`,
`parser` and `propagate`. Known caveat, documented: as `fad`/`rad` seeds the
copies of one widget box under several groups resolve to one control (the
existing seed aliasing). The C++ reference has none of this, so no
differential test; `"*"` is a label it parses and matches nothing with.

## A widget parameter that is not a compile-time number is refused, like C++

Commit date: 2026-09-24

Source commit: this commit

`process = 0.5 : \(x).(hslider("a", x, 0, 1, 0.1));` compiled with an init
of 0: the lambda applied by `:` binds `x` to an input signal,
`simplify_slider_param` (`crates/eval/src/ui_widgets.rs`) kept the parameter
box when it did not fold, and the UI builder's `decode_box_scalar` read any
non-literal as 0. The C++ reference stops in `eval2double`
(`compiler/evaluate/eval.cpp`): `not a constant expression of type : (0->1)`
for a parameter box that is not `0→1`, and, through `tree2double`
(`compiler/tlib/tree.cpp`), `the parameter must be a real constant numerical
expression : SigInput[10001]` for a `0→1` signal. `simplify_slider_param` now
raises `EvalError::WidgetParameterNotConstant` (`FRS-EVAL-0011`, numbers 9 and
10 of the family being taken by the unmerged `control-inputs-wildcard`
branch) with the C++ wording, the widget, its label, the parameter and the
expression as written, located in the source; a division by zero in a
parameter stays `FRS-EVAL-0007`. It covers the four slider-family parameters
and the bargraph min and max; a bargraph whose max was a lambda argument used
to fail later with a propagation arity error.

No program relied on the silent 0: the 336 corpus programs and the 133
impulse-test programs compile as before (only the new fixture raises the
code). Tests: `tests/corpus/err_33_widget_parameter_not_constant.dsp` and
`a_widget_parameter_that_is_not_a_number_is_refused_like_the_reference` in
`crates/compiler/tests/diagnostic_errors.rs` (both C++ refusals, every
parameter kind, constant parameters still accepted). Golden: `golden-gen-rust`
added the one fingerprint; no existing snapshot changed. Registry:
`DIFF-BEH-014`. Compile budget: only the failure path of the parameter fold
changed; not measured.

## An environment passed as an argument keeps its definitions

Commit date: 2026-09-24

Source commit: this commit

`play(cfg) = os.osc(cfg.freq) * cfg.gain; low = environment { freq = 220;
gain = 0.5; }; process = play(low);` failed with `undefined symbol freq`
where the C++ compiler plays a 220 Hz sine at 0.5. Any access through a
parameter failed, lambda parameters and nested `cfg.inner.x` included;
`mk(330).freq`, `low.freq` and substitution worked. Found while writing the
Faust tutorial (faust-tutorial, chapter 13), whose example had to be checked
on the C++ compiler only.

`rev_eval_list` forces each argument to a box (`eval_box`), and the
closure path of `apply_value_list_value` re-evaluates that box in the
function's captured environment. `force_value_to_box` kept an abstraction
closure as a `boxClosure(key)` handle to the evaluator's closure store, but
returned an environment closure as its bare `environment` node: re-evaluated,
that node became a closure over the function's environment, which has no
`freq`. The C++ `revEvalList` passes the closure tree itself to `applyList`;
environment closures are now stored as handles too, and `eval_value`
resolves a handle to the stored closure, captured definitions included.
Lowering a handle with `a2sb` still yields the bare `environment` node, as
C++ `real_a2sb` returns `abstr` for `isBoxEnvironment`, so arity inference
(which lowers before measuring) is unchanged.

Tests: `tests/corpus/environment_argument.dsp` (the repro, an environment
returned from a function and accessed directly and through a call, a nested
access, a lambda parameter, a substitution on a parameter, a member function,
two environments at once; all eight outputs equal the C++ compiler's, and
the unfixed build fails on the file) with its Rust golden, and
`core_eval::eval_process_accesses_environment_passed_as_argument_like_cpp`,
which fails without the fix. Regenerating every Rust golden changed no other
snapshot. tonestacks.lib's `with {t = ts.bassman;}` pattern and a library
passed as an argument (`get(library("maths.lib"))`) match the C++ output.

## Case rules tried in textual order, as in the reference pattern matcher

Commit date: 2026-09-24

Source commit: this commit

`f(n) = 1; f(0) = 2; process = f(0);` gave 2 where the C++ compiler gives
1, and `case { (n) => 1; (0) => 2; }(0)` likewise: a general rule written
before a specific one did not hide it. Found while writing the Faust
tutorial (faust-tutorial, chapter 11), whose rule-order example had to be
checked on the C++ output only.

The automaton itself follows Gräf's construction as the C++ one does; the
divergence was in the rule lists of its states. A final state holds the
rules that reach it, and `apply_pattern_matcher` returns the first one that
survives, so the list must be in rule order. The C++ `merge_rules` calls
`std::list::merge`, which keeps it sorted by rule index; `merge_state` in
`crates/eval/src/pattern_matcher.rs` appended (`rules.extend`). In the
repro, rule 1 (`f(0)`) creates the constant branch from its own trie, then
`merge_trans_cst` merges rule 0's variable completion into it: appended,
the list reads [1, 0] and rule 1 wins. `merge_rules` now does the same
stable sorted merge as `std::list::merge` (equal indices keep the first
list's elements first). No rule is reordered by specificity anywhere else:
the tries are built per rule in source order, and `make_var_state` clones
an already sorted list.

Tests: `tests/corpus/pattern_rule_order.dsp` (twelve outputs: general rule
first in both forms, specific rule first, two arguments where all three
rules match, a variable before a structural pattern `p((a, b))`; all equal
the C++ compiler's, and the three that differed before the fix are
`f(0)`, `first_wins(0)` and `p((1, 2))`) with its Rust golden, and
`core_eval::eval_process_tries_case_rules_in_textual_order_like_cpp`,
which fails without the fix. Regenerating every Rust golden changed no
other snapshot of the corpus.
