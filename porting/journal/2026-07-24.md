## Reject dead pure FIR roots and clean vector CSE scaffolding

Commit date: 2026-07-24
Source commit: this change

Added the `FIR-D01` warning to the module verifier for `Drop` statements whose
value is side-effect-free. The conservative purity predicate now recognizes
canonical FIR math calls recursively but retains ordinary foreign calls, whose
evaluation may be observable. Final vector certification treats this specific
warning as a rejection while continuing to tolerate unrelated generic FIR
warnings.

Fixed checked vector lowering so temporary `Drop` roots remain present through
the independent body-evidence check, then are removed after output
materialization and before final module assembly. This preserves the
producer/checker boundary while preventing dead `pow`, `fmin`, `floor`, and
arithmetic evaluations from reaching generated code. The `karplus.dsp`
regression that emitted `(void)(std::pow(...))` now retains certified vector
lowering without any pure `Drop` in the final FIR.

Public API mapping: `is_obviously_side_effect_free_value` is **adapted** from
the compiler's existing FIR canonicalization policy rather than a C++ API
surface. It is public only to share one conservative classification across the
`fir` and `transform` crates; there is no CLI, C, C++, ABI, or generated-code
compatibility impact.

Validation covered focused FIR checker/canonicalization tests, vector final
materialization and certified-module tests, plus direct FIR and C++ generation
for `karplus.dsp` under `-vec -lv 1`.

Phase 2 (FIR execution contract), per plan §4.3–§4.6:

- **P2a — execution-owned sections.** `ModuleSections.control_statements`
  entries are now tagged `Externalizable` vs `ComputePreamble`. One
  interleaved list deliberately kept (not two): classic emission must
  reproduce the exact lowering-encounter order byte-for-byte; the tag is
  what splits the section by semantics. CSE re-derives tags after
  `materialize_shared_values` (surviving statements keep theirs; inserted
  shared fSlow/iSlow declarations are externalizable).
- **P2b — typed contracts.** faust_api reserves `control(dsp)` and
  `frame(dsp, FAUSTFLOAT*, FAUSTFLOAT*)`; the FIR checker records function
  bodies and adds FIR-F08 (frame declared but canonical compute not empty)
  and FIR-F09 (control/frame references `count`). `control`/`frame` stay
  out of DSP_API_FUNCTIONS so M07 does not require them.
- **P2c — external control.** `materialize_in_bucket` promotes
  `Bucket::Control` values to DSP-owned storage under
  `ControlRateMode::External` by generalizing the existing
  `konst_escapes` escape promotion (§4.4): struct field + StoreVar(Struct)
  in the externalizable section. `build_module` emits the externalizable
  statements as the body of `control(dsp)`; block plumbing stays in the
  block entry point. CSE-shared slow declarations remain stack-local
  inside `control` (their uses never leave it — confirmed by the FIR
  scope rules).
- **P2d — one-sample.** Direct `inputs[channel]` loads and
  `outputs[channel]` stores (flat FunArgs arrays), slice bodies emitted
  straight into `frame` with no loop/count/i0, canonical `compute` kept
  but empty, block aliases skipped. `-ec -os` splits control work from
  the per-sample body, which loads the promoted state.
- **P2e — structural tests** (§7.1) over an input×slider fixture for all
  four shapes: entry-point presence, slow-value storage class, direct vs
  aliased I/O, loop/count/i0 absence in `frame`, empty `compute`, and no

## Upstream finding refined: reference `-ec -os` drops state-reload statements

Minimization of the Phase 3 upstream finding (reference C++ at
`8eebea429`, version 2.84.3), correcting the earlier "state-renaming"
description:

- **Minimal reproducer**: `process = +~_;` — no controls needed.
  `faust -lang cpp -ec -os t.dsp` (same with `-lang c`).
- **`-os` alone is CORRECT**: `frame()` opens with the local state reload
  `float fVec0SE[2]; fVec0SE[1] = fVec0SEState;` and the emitted code
  compiles and runs.
- **`-ec -os` combined is broken**: those two reload statements vanish
  entirely — they are in neither `control()` nor `frame()` — so `frame()`
  references the undeclared local `fVec0SE[...]` and the generated code
  does not compile. They appear to be classified as control-rate
  declarations and routed to the external-control path, which does not
  emit them (and `control()` would be the wrong home anyway: the reload
  must run once per frame, before the sample body, because the tail of
  `frame()` writes the updated `fVec0SE[1]` back to `fVec0SEState`).
- **Both cpp and c backends affected.** Stateless DSPs are unaffected
  (bit-exact faust-rs ↔ reference parity verified there).

Why faust-rs is structurally immune (no fix was needed on our side):

1. Execution ownership is decided **at statement creation time** via the
   tagged compute-preamble list (P2a); recursive state updates never
   enter that list at all — they live in the region sample phases, which
   become the whole `frame` body. There is no post-hoc routing step where
   a statement can land on the wrong side, which is where the reference
   appears to lose the reloads.
2. faust-rs represents recursive state as a directly read/written struct
   scalar (`fRec36`), not the reference's persistent-scalar +
   locally-reloaded-array pattern — less machinery to route.
3. Defense in depth: had such a bug been introduced, the FIR verifier's
   scope rule (FIR-SC01, load of an undeclared variable) and the P2e
   structural tests ("no stack local crosses a function boundary") would
   have failed before any emission. The reference has no equivalent
   check; its bug only surfaces when someone compiles a recursive DSP's
   generated `-ec -os` output.

Verified on the exact reproducer: faust-rs `-ec -os` emits
`control()` = promoted slow store only, `frame()` = recursion body with
direct `fRec` state read/write; compiles under `g++ -Wall -O2` and is
bit-exact against faust-rs `compute(N)`.

Report drafted for upstream (GRAME) with the reproducer and both
emitted-shape comparisons.
