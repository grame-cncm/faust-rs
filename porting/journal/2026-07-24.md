## State fused-group reads as escape rules, not presence rules

Commit date: 2026-07-24
Source commit: this change

Fixed the `vector-coverage-check` regression introduced by "Reject dead pure
FIR roots" (`4abb6d37`): `echo_bug.dsp` and `phaser_flanger.dsp` lost their
certified vector structure with `Fallback(FirAssembly)` / "fused serial group 0
has an invalid FIR shape", in every one of the 16 retention modes.

Cause. `remove_pure_drop_roots` runs on the loop-region statements before
`assemble_vector_fir`, so a region root whose only anchor was its seeding
`Drop` disappears from the assembled FIR. Two of the fused-group envelope
rules in `verify_assembled_fused_serial_groups` demanded that a recorded value
be *present* inside the physical sample loop: the delayed-read definition
(echo_bug loses a `vstate_s249` read at a constant delay whose branch nothing
consumes) and the load side of a fused scalar transport (phaser_flanger loses
`transport_s22657_l300_l0`). Dead-code removal therefore read as a shape
violation.

Fix. Both rules are now stated the way the envelope property actually reads:
no delayed read and no transport load may occur *outside* the selected body. A
value that survives anywhere in the assembly but not in the body is still
rejected — that is the escape the rule exists to catch — while a value absent
from the whole assembly is accepted, because an eliminated read cannot escape.
The whole-assembly node set is built on first use only, so the common path
pays nothing. Writes keep their presence rules: they are statements, and the
pure-Drop cleanup never removes them.

Emission impact is confined to dead code. Against the pre-`4abb6d37` output,
both DSPs are line-for-line identical except for deleted `(void)(...)`
statements (2 in echo_bug, 44 in phaser_flanger) — which is exactly what
`4abb6d37` set out to remove.

Public API mapping: internal **adapted** vector-checker behavior only. No CLI,
C, C++, ABI, or generated-code contract change.

Validation: `cargo run -p xtask -- vector-coverage-check` back to OK (1,552
retained certified mode/DSP pairs, 16 modes, 133 corpus DSPs, 97 per mode);
`golden-check` (196 cases), `vector-interp-opt-check` (40 traces),
`vector-compile-budget-check`; `cargo fmt --all -- --check`;
`cargo clippy --workspace --all-targets -- -D warnings`; `cargo test
--workspace`. A rejecting mutation in the assemble checker relocates the
delayed read out of the physical body with the read still reachable from the
top level and asserts `FusedGroupShape`, so the tolerance cannot degrade into
"never checked"; a compiler-level test locks both corpus shapes at
`Certified`/`CertifiedVector` and holds echo_bug to the scalar bit-exactness
oracle across all four scheduling strategies and both loop variants.

Known unrelated break on this branch: `xtask structure-check` fails because
`crates/transform/src/signal_fir/vector/lower/signal.rs` reached 2,100 lines
in `b93bc4cc`, over the 2,000-line review threshold.

## Preserve external-control root promotion during pure-Drop cleanup

Commit date: 2026-07-24
Source commit: this change

Fixed the vector external-control (`-ec`) path after `FIR-D01` exposed
temporary pure `Drop` roots in the final module. Control roots that are not
already materialized by CSE, including constants and other non-UI values, are
now promoted deterministically to DSP struct fields and emitted as real
`StoreVar(Struct)` operations in `control`. Temporary `Drop` loads remain only
long enough for the independent body-evidence checker, then final module
assembly removes them.

This preserves the documented external-control contract that every value
crossing from `control` to block compute is DSP-owned, without weakening the
new dead-expression diagnostic. A structural regression covers trivial
control-root promotion, and the three previously failing external-control
tests now remain certified.

Public API mapping: internal **adapted** vector-lowering behavior only. There
is no CLI, C, C++, ABI, or generated-code contract change beyond restoring the
already documented `-ec` behavior.

Validation: `cargo fmt --all -- --check`;
`cargo clippy --workspace --all-targets -- -D warnings`;
`cargo test`; and `cargo run -p xtask -- golden-check` (196 cases).

## Reject dead pure FIR roots and clean vector CSE scaffolding

Commit date: 2026-07-24
Source commit: this change

Added the `FIR-D01` warning to the module verifier for `Drop` statements whose
value is side-effect-free. The conservative purity predicate now recognizes
canonical FIR math calls recursively but retains ordinary foreign calls, whose
evaluation may be observable. Final vector certification treats this specific
warning as a rejection while continuing to tolerate unrelated generic FIR
warnings.

Fixed checked vector lowering so temporary `Drop` roots remain present through
the independent body-evidence check, then are removed after output
materialization and before final module assembly. This preserves the
producer/checker boundary while preventing dead `pow`, `fmin`, `floor`, and
arithmetic evaluations from reaching generated code. The `karplus.dsp`
regression that emitted `(void)(std::pow(...))` now retains certified vector
lowering without any pure `Drop` in the final FIR.

Public API mapping: `is_obviously_side_effect_free_value` is **adapted** from
the compiler's existing FIR canonicalization policy rather than a C++ API
surface. It is public only to share one conservative classification across the
`fir` and `transform` crates; there is no CLI, C, C++, ABI, or generated-code
compatibility impact.

Validation covered focused FIR checker/canonicalization tests, vector final
materialization and certified-module tests, plus direct FIR and C++ generation
for `karplus.dsp` under `-vec -lv 1`.

## Upstream finding refined: reference `-ec -os` drops state-reload statements

Minimization of the Phase 3 upstream finding (reference C++ at
`8eebea429`, version 2.84.3), correcting the earlier "state-renaming"
description:

- **Minimal reproducer**: `process = +~_;` — no controls needed.
  `faust -lang cpp -ec -os t.dsp` (same with `-lang c`).
- **`-os` alone is CORRECT**: `frame()` opens with the local state reload
  `float fVec0SE[2]; fVec0SE[1] = fVec0SEState;` and the emitted code
  compiles and runs.
- **`-ec -os` combined is broken**: those two reload statements vanish
  entirely — they are in neither `control()` nor `frame()` — so `frame()`
  references the undeclared local `fVec0SE[...]` and the generated code
  does not compile. They appear to be classified as control-rate
  declarations and routed to the external-control path, which does not
  emit them (and `control()` would be the wrong home anyway: the reload
  must run once per frame, before the sample body, because the tail of
  `frame()` writes the updated `fVec0SE[1]` back to `fVec0SEState`).
- **Both cpp and c backends affected.** Stateless DSPs are unaffected
  (bit-exact faust-rs ↔ reference parity verified there).

Why faust-rs is structurally immune (no fix was needed on our side):

1. Execution ownership is decided **at statement creation time** via the
   tagged compute-preamble list (P2a); recursive state updates never
   enter that list at all — they live in the region sample phases, which
   become the whole `frame` body. There is no post-hoc routing step where
   a statement can land on the wrong side, which is where the reference
   appears to lose the reloads.
2. faust-rs represents recursive state as a directly read/written struct
   scalar (`fRec36`), not the reference's persistent-scalar +
   locally-reloaded-array pattern — less machinery to route.
3. Defense in depth: had such a bug been introduced, the FIR verifier's
   scope rule (FIR-SC01, load of an undeclared variable) and the P2e
   structural tests ("no stack local crosses a function boundary") would
   have failed before any emission. The reference has no equivalent
   check; its bug only surfaces when someone compiles a recursive DSP's
   generated `-ec -os` output.

Verified on the exact reproducer: faust-rs `-ec -os` emits
`control()` = promoted slow store only, `frame()` = recursion body with
direct `fRec` state read/write; compiles under `g++ -Wall -O2` and is
bit-exact against faust-rs `compute(N)`.

Reported upstream: https://github.com/grame-cncm/faust/issues/1277
(with the reproducer and both emitted-shape comparisons).

## Execution-options port — Phase 5: vector external control

Producer (P5a):

- UI zone reads under `-ec` go through promoted snapshot fields
  (`fSlowN = cast(zone)` stored in `control`); compute never observes
  host-mutated zones (§2.4 semantics).
- Shared control-root temporaries (`fVecControlTemp*`) are
  struct-promoted through a new Struct mode of the CSE materializer (top
  scope only) — the konst-escape reasoning of §4.4 generalized: their
  stores move to `control` while vector transport fills in `compute`
  read them across the function boundary.
- The externalizable section (snapshots, promoted root stores,
  control-scope UI stores) becomes `control(dsp)`; input aliases stay in
  the compute preamble. Classic mode is byte-identical (single
  interleaved list, stack temporaries).

Checker (P5b):

- `verify_final_module` gains external-control rules: `control` must be
  absent in classic mode; under `-ec` it must contain EXACTLY the
  externalized statement list, and every promoted field must be declared
  in the struct, stored exactly once and only in `control`, never
  written by `compute`.
- BuiltVectorModule carries the evidence; the corruption test verifies
  the exact lists pass while a missing event, a duplicated event, and a
  misattributed field are each rejected. Non-UI control values
  (control-region constants) externalize too; a pure passthrough
  externalizes nothing and emits no `control`.
- Coherence guard in the wrapper: classic mode must not carry
  external-control evidence.

Gate lifted: `-ec -vec` accepted for fir/cpp/c/rust; `-os -vec` remains
a stable early error.

Reference note: the pinned dev-branch reference disables `-vec`
unconditionally ("'-vec' is not yet supported with 'ondemand' primitive"
even for programs without ondemand), so the recorded behavioral oracle
for `-ec -vec` is stable Faust 2.83.1. Runtime differential (recursive
feedback DSP, fixed controls, 256 samples): our `-ec -vec` output is
bit-identical to our classic vector, to our scalar, and to the stable
