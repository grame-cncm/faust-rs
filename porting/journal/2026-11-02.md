# 2026-11-02

## diagnostics: a feedback, a library and an operator, told the way out

Commit date: 2026-11-02

Source commit: this commit

A local model (Qwen 27B, with a Faust primer and library search) in `dsp-language-eval` failed its
Faust runs mostly on three errors. Of the 58 messages of these codes in its logs, 34 were
`FRS-PROP-0002`, 13 `FRS-EVAL-0013` and 11 `FRS-SRC-0002`. Each now carries the way out, and each
note stays away where it would mislead.

- **A cycle through a delay.** `y = a * x + b * y';` and `env = p * c + env' * (1 - c);` are
  recurrences written as in another language. The guidance finds the definitions of the cycle by
  name, at the top level and in every `with`/`letrec` block, and sorts each use of one by another
  into delayed (under `'`, `@`, `mem`, `prefix`, or the feedback side of a `~`) and immediate. When a
  use is delayed and the immediate uses alone close no cycle, a note says that a signal computed
  from its own past is written with `~`, and the help shows `y = x : *(a) : + ~ *(b);`, then the
  form with the previous value named, `y = x : (\(prev, x).(a * x + b * prev)) ~ _;`. Both rewrites
  were rendered by `faustprobe` and give the same samples. `v1 = x + a * (v1 - x);`,
  `y = y + y';` and `x = x;` need a value at its own sample: `~` would add a delay and change what
  they say, so they keep the generic help. A delay inside a library function is not seen, which
  only loses the note. On the bench, the 6 `compressor` cycles get the note; the 3 of `filter` (no
  delay) and the 4 of `pluck` (`x ~ dly` uses `x` at its own sample) keep the generic help.
- **An unresolved import.** Every name but `stdfaust.lib` gets a note that
  `import("stdfaust.lib");` gives every standard library under its prefix, and a first help when
  the name looks like one: `mathfaust.lib` is `maths.lib`, `ma.`; `mooreverb.lib` is `reverbs.lib`,
  `re.`; `std.dsp` is `stdfaust.lib`. The table is `stdfaust.lib` of the C++ reference, and the
  guidance reads the name only, never the file system, so it claims nothing about what the search
  path holds. When `stdfaust.lib` itself is missing, only the search-path help is true, and only it
  is given. It lives in `crates/compiler/src/import_guidance.rs`, applied by `CompilerError::import`.
- **The operator of a `:` mismatch.** The `<:`/`:>` hint now covers every pair of widths: a
  multiple of outputs adds one B per group (`A : (B, B)`, a stereo pair into a mono stage), and
  widths that do not divide get `(A, _) : B` (inputs left open) or `A : (B, !)` / `A : (B, _)`
  (outputs dropped or passed), with `si.bus`/`si.block` beyond one. 24 of the 34 mismatches were not
  about the operator at all: `_ : f, _ : g` and `a, b, c : ba.db2linear` are `,` binding more tightly
  than `:`, and the `:>` hint they got proposed summing three sliders. When a list is written before
  the `:` (the source composition, through `composition_origins`) and its last item alone fits B, a
  first help says so and shows `a, (b : c)`. A name bound to a list is not written there and gets
  nothing. A B with no input that is not a call may be a factor (`A * B`); a call with no input has
  more often been given an argument too many, and gets nothing.

The facts stay in `eval`, `propagate` and `parser`, and the three notes are guidance of `compiler`.
The `standard` text of all 58 bench messages was read again with `faustprobe`; each import gets
the note, and the 10 `mathfaust.lib`/`std.dsp` ones the library meant. The blind repairs
were not run again on this text.
