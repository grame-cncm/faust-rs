## BRA: two-pole feedback lost half of its adjoint

Commit date: 2026-09-05

Source commit: this commit

Found by the host-driven DDSP example (`ddsp_rad_host_block_resonator.dsp`):
the block gradient of `(target - fi.tf2(1, 0, 0, a1, a2, x))^2`, summed over
a block, was 56% of the central finite difference, while every one-pole
check passed. `rad` and `fad` disagreed on any recursion feeding back
`y[n-2]` (`mem`, `@(2)`, `fi.tf2`): 0.41 against 0.62 over a block of 8,
1.17 against 2.26 over 256.

Cause, read off the generated reverse loop of `x : + ~ (mem : *(-a2))`:
the tap is a chain `Delay1(Delay1(Proj(SYMREF)))`. The outer delay loads
its carry (stored by step n+1) into the adjoint of the inner delay, and the
inner delay's carry store is that adjoint. But a carry load is a plain read
of a struct field and both stores land in post-output --
`fBraCarry4 = ...; fBraCarry3 = fBraCarry4;` -- so the inner store read the
field the outer store had just overwritten: the recursion received the
adjoint of step n instead of step n+1, one step too early and scaled by the
pole. One-level feedback never showed it because its load is consumed by an
immediate temporary.

Fix (`module/bra.rs`): every carry load -- the pre-scan's, `Delay1`'s,
`Delay(c)`'s, `Prefix`'s -- is snapshotted into a stack temporary of the
immediate phase (`snapshot_bra_carry`, `fBraLoadN`) before the step's
stores. On the way, `Delay(c, Proj(SYMREF))` taps (`y@c` written with `@`)
are pre-seeded into the recursion's adjoint from their circular carry as
`Delay1` taps are, and the `Delay(c)` arm only stores for them
(`load_bra_delay_array_carry`, `bra_delay_array_slot`).

Tests: `rad_two_pole_feedback_bra_total_grad_matches_fd` (`rad_runtime.rs`,
block of 32 against central finite differences on the block loss, sliders
as seeds -- a literal seed is folded into the body); the host loop of
`ddsp_examples.rs` checks the block gradient of `fi.tf2` against finite
differences before training. `rad` now equals `fad` on the two-pole totals
at blocks 8, 64 and 256. No tracked golden changed (the corpus has no public
`rad` fixture with a two-sample feedback); the golden of the new fixture
`ddsp_rad_host_block_resonator.dsp` was generated with `golden-gen-rust`.

## BRA: the unary foreign functions have a backward rule

Commit date: 2026-09-05

Source commit: this commit

Found while bringing the RAD examples of the `DSP` directory up to date:
`rad_lms1.dsp`, a four-tap FIR followed by `ma.tanh` learned in the graph,
failed with `[FRS-SFIR-0004] signal FFun(..) not supported in BlockReverseAD
backward pass (B6)`. `ma.tanh` is a foreign function; the symbolic sweep has
had a rule for the unary hyperbolic families (`tanh`, `sinh`, `cosh`,
`atanh`, `asinh`, `acosh`, any precision variant) since the start, the
block sweep -- which the delayed taps of the FIR select -- had none, and
its postorder did not even walk the arguments of a foreign function.

arguments of an `FFun`, `collect_tape_needed_values` tapes the node's value
and its arguments, and `propagate_bra_ffun_adj` (`module/bra.rs`) applies
the symbolic table -- `tanh' = 1 - tanh^2` and `sinh' = sqrt(1 + sinh^2)`
from the node's own value, `cosh'`, `atanh'`, `asinh'`, `acosh'` from the
argument's -- rejecting any other foreign function with the same
diagnostic as before.

Tests in `rad_runtime.rs`: the five bounded families in one temporal body,
lane by lane against `fad` (`bra_unary_foreign_functions_match_fad_lane_by_lane`),
and the two-tap FIR + `tanh` loop learning its taps
(`in_graph_rad_learns_through_a_foreign_tanh`), both with an inline
`ffunction` so the test needs no library. `docs/rad-note-en.md` §3.7 and
§6.

## BRA: a recursion read only through a delay never ran inside a carrier

Commit date: 2026-09-05

Source commit: this commit

Found while switching `optimizers.lib` to the standard libraries: `pstate`'s
first-sample gate became `ba.time == 0`, i.e. `mem(counter) == 0`, and every
`rad` loop stopped learning (the parameter was reset to `init` at each
sample) while the `fad` loops and the old `counter == 1` gate were fine.
Reduced to `p = select2(mem(counter) == 0, prev, 0)`, `rad(p * x, p)`: the
generated code read the counter's state variable and never updated it.

Cause: a recursion read only through a delay emits the read of its state and
no body pass -- `resolve_recursion_carrier` deliberately leaves the update to
the global schedule, which lowers the projection node in dependency order
(delayed edges do not constrain the loop DAG, so C++ Faust also computes the
recursion at its projection). Two places are outside that schedule: the
nodes of a `BlockReverseAD` carrier, which the previsit skips as
`fixed_ad_internal_signals`, and every forward output of a program with
reverse-time outputs, which has no previsit at all (`process = (rad(p * x, p)
: !, _), (counter : mem)` never counted either). A group read at delay 0
does not have the problem: `Proj(SYMREC)` schedules its bodies on demand,
which is why the LCG noise inside the same losses kept running.

Fix (`module/state.rs`): `resolve_recursion_delay_ref`, the wrapper every
delayed read goes through, schedules the group at its first delayed read
when the schedule cannot reach it -- closed `SYMREC` group, not yet scheduled
in the clock context, projection node internal to a carrier or no previsit
(`scheduled_previsit`, false for programs with reverse-time outputs) -- by
lowering the projection node: the body pass lands in the current forward
phase and the store into the state in post-output, after the read. Never in
the reverse loop, where forward values are replayed from tapes. Programs the
schedule covers are untouched; no golden changed.

Tests: `in_graph_rad_runs_a_recursion_read_only_through_a_delay` (the reduced
loop learns `0.5`) and `delayed_recursion_read_next_to_a_public_gradient_is_scheduled`
(a counter next to a public gradient, a gated body) in `rad_runtime.rs`; the
`optimizers.lib` fixtures exercise `ba.time` under every loop from now on.

## BRA: seeds are leaves, `select2` has a backward rule, carries belong to the reverse loop

Commit date: 2026-09-05

Source commit: this commit

Found while adding a reverse-mode family to `optimizers.lib`, then by checking
block gradients against finite differences rather than against converging
fixtures. Four defects of the block sweep in `crates/transform/src/signal_fir`
(`block_reverse_ad.rs`, `module/bra.rs`, `module/build.rs`):

- `collect_bra_postorder` walked *through* the seeds: a loop whose seed is
  `clip(lo, hi, pstate(init, reset, prev))` -- a `select2` gate over the
  recursive state -- failed under `rad` as soon as the loss reached a
  recursion (an LCG noise, a filter) with `[FRS-SFIR-0004] signal
  Select2(..) not supported in BlockReverseAD backward pass (B6)`, while the
  same program under `fad`, or with the seed written as a bare projection,
  compiled. The block sweep saw the seed's own computation (the `select2`,
  the clamp, the optimizer's recursion) and tried to differentiate it, unlike
  the symbolic sweep, whose descent stops at any seed. The collector now
  takes the seed set, records a seed as a leaf, and the reverse walk skips
  it: its adjoint is the gradient lane. The tape planner uses the same stops.
- the backward pass had no rule for `Select2` at all. Added: the adjoint is
  routed to the branch taken at that sample (`then_bar = select2(c, y_bar,
  0)`, `else_bar = select2(c, 0, y_bar)`), with the condition replayed from
  its tape. Conditions are integers, which the tape planner used to skip
  on purpose (integer islands below a `FloatCast`); a `select2` condition
  is the one integer the sweep needs, so it gets a tape of its own type and
  `tape_store_var` now records the type.
- the carry of a recursion only landed on a *carrier root*:
  `var_slot_to_body_sig` was built from `body_sigs`, so `rad(y, c)` with
  `y = c : + ~ sin` was exact and `rad(y * y, c)`, `rad(2 * y, c)`,
  `rad(select2(t, y * y, ..), c)` -- any loss with the recursive output as
  an interior node, which is every loss -- kept the direct term of each
  sample only: 6.7 against 29.7 by finite differences over a block of 8 for
  `rad(y * y, c)`. The map is now built over the whole postorder, restricted
  to real-valued projections: an integer recursion in the body (the LCG
  noise of the corpus fixtures) has no temporal derivative, and a real carry
  added to it type-clashed with its body (`BinOp Float32 vs Int32` on every
  `rad_tbptt_*` fixture, caught by the first run).
- a carrier whose public projections are all gradients, `rad(loss, p) : !,
  _`, never ran its primal forward: no forward slice was opened (no forward
  output) and the reverse loop read a recursion it cannot recompute
  backwards (lanes `[8, 7, .., 1]` where `rad(loss, p)` gives `[6.7, 5.7,
  ..]`). `lower_sample_slices` now collects the carriers under the
  reverse-time outputs (`bra_groups_of_reverse_outputs`), opens the forward
  slice for them and runs `ensure_bra_forward_pass`, which lowers each body
  at the top level and plans its tapes; `decode_bra_carrier` factors the
  list decoding out of the `Proj` fast path.

The third fix exposed a fifth point, about where the sweep runs. A gradient
consumed inside the graph (`p_next = p - lr * (rad(loss(p), p) : !, _)` in
an adaptation recursion) is lowered in the *forward* loop, at the sample that
consumes it. There the sweep had always stored `Delay1` carries and, once the
carry landed on interior recursions, also loaded them: the adjoint recurrence
read at `n` what was stored at `n-1`, i.e. ran forward in time -- on `y[n] =
1 + p y[n-1]`, `loss = (y - 3)^2`, it returned -5, -7.5, -8.3 where the
direct term is -3, -3.75, -3.94 and `fad` gives -3, -5, -6.19: neither the
block-local gradient nor a derivative. `bra_sweep_is_causal` (the sweep is
not in the reverse loop) now gates every carry: in the forward loop the
horizon is the current sample, the past state of the body is held fixed, the
gradient is the direct term (the pseudo-linear-regression gradient of
adaptive IIR filtering -- what the `rad_tbptt_*` fixtures always computed,
their dead carry stores aside), and no carry is declared. Only the reverse
loop, which walks the block backwards, reads "the previous step" as the
adjoint of the next sample.

Tests: two structural tests in `transform`
(`bra_seed_computed_with_select2_is_a_leaf`,
`bra_select2_in_body_tapes_the_condition_and_compiles`); in `rad_runtime.rs`,
finite-difference checks of the block gradient for a `select2` inside
`c : +~sin`, for `rad(y * y, c)`, for `rad(c : +~sin, c) : !, _` and for a
seed `select2(t, a, b)` whose block gradient equals `FD_a + FD_b`;
`in_graph_rad_has_a_one_sample_horizon` (direct term against `fad`'s exact
derivative, frame by frame) and
`in_graph_rad_declares_no_carry_where_the_public_output_does` (on the C++
output); the corpus fixture `rad_tbptt_select2_pole.dsp` (a half-wave gain
in a one-pole's feedback, converging to silence) with its Rust golden. The
Rust goldens of `rad_tbptt_one_pole` and `rad_tbptt_two_poles` were
refreshed with `golden-gen-rust`: their in-graph sweeps lose the carry
fields they stored and never read, and the temporaries of the sample loop
are renumbered; the other snapshots are unchanged. The headers of those two
fixtures no longer describe a carry. `docs/rad-note-en.md` §4 states the
rules, §6 and §8 the tests and the sources.

Measured on the way (release `faustprobe`, 200 000 frames): with the
delayed taps of a 16-tap FIR passed as extra seeds -- the "temporal
firewall" that keeps the sweep symbolic -- `rad` is 3.6x smaller and 3x
faster than `fad` at 16 taps (1 050 vs 3 777 interpreter lines, 0.03 s vs
0.09 s) and 7x smaller, 10x faster at 64 (4 121 vs 28 891 lines, 0.14 s vs
1.45 s), for identical learning trajectories.

## FAD: scope the memo cache per recursion binder

Commit date: 2026-09-05

Source commit: this commit

Found while writing the optimizers tutorial: the smallest in-graph learning
loop, `loop(g) = g - lr * (fad(loss(g), g) : !, _)` with
`loss(g) = (g * x - t)^2`, gave a gradient different from the hand-written
`2 (g x - t) x` — twice as large on the second frame, an RMS gap of 0.056
over 1000 frames — whenever `x` was itself a recursion (`no.noise`, an LCG,
a sawtooth), and the exact gradient when `x` was an audio input or the seed
was written `clip(lo, hi, g)`, which is what every `optimizers.lib` loop
does. `fad_recursive_local_projection.dsp`, the reference fixture for the
pattern, is only compile-checked, and the recursive runtime tests
differentiate with respect to controls, so nothing caught it.

Cause, read off `--dump-sig-dag`: the seed `g` is the recursive input,
`delay1(proj(0, ref(1)))` in de Bruijn form, and the back-edge of a
single-slot noise recursion is spelled exactly the same inside its own body.
`ForwardADTransform` memoizes by `SigId`, and the memo was not scoped: with
`g` visited before `x` (`g * x`), the seed's dual — tangent `1.0` — was
cached at the outer scope and then served *inside* the noise body, so the
LCG state received a tangent of `1103515245`, `x` a tangent of ~0.5, and the
loss derivative an extra `(g - 0.7) dx` term. The existing guard only
covered the opposite direction (body entries discarded on exit, so they
cannot shadow the outer seed check), and its unit test visits the inner
recursion *before* the seed, which is why it passed.

Fix in `forward_ad.rs`, `(Rec)` arm: on entering a body, stash the outer
cache and start from its closed entries only (`de_bruijn_aperture == 0`,
memoized on the transformer — closed terms mean the same thing at every
depth); restore the outer cache on exit, which also drops the body entries
as before. Two tests pin the two directions at the arena level
(`outer_seed_does_not_leak_into_an_inner_rec_body` alongside the existing
`fad_seed_not_poisoned_by_inner_rec_back_edge`), and
`recursive_projection_seed_stays_a_leaf_inside_an_unrelated_recursion` in
`fad_recursive_runtime.rs` compares the `fad` gradient with the hand-written
one frame by frame through the interpreter (it failed before the fix at
frame 0: `2.9e-6` against `-4.6e-11`). Golden snapshots are unchanged: no
tracked fixture reads a recursion from a loss seeded on a bare recursive
projection. `docs/fad-debruijn-recursion-en.md` §6.5 and §9 describe the
scoped cache.

After the fix, `faustprobe` reports a zero difference lane for the three
excitation shapes that used to diverge, and the optimizers fixtures are
unchanged (their seeds were never bare projections).

Alongside, four documents for newcomers in `libraries/`:
`optimizers-overview-{en,fr}.md` (what `fad`/`rad` bring to differentiable
DSP, the organization of the library, the origin and choice of each
algorithm, measured behaviour, pitfalls) and
`optimizers-ddsp-tutorial-{en,fr}.md` (ten steps from a hand-written
gradient to the five-coefficient biquad). Every program in the tutorials was
run with `faustprobe` and the quoted numbers are those runs; the 17 code
blocks of each version pass `faust-rs --check` and are identical between the
two languages up to comments. Both documents have a section on `ondemand`
with `fad`: the optimizer clocked every 64 samples (312 steps to the exact
gain), the audio-rate gradient averaged and applied once per frame, and a
frame-rate spectral loss (`an.fft` on an 8-sample frame, `descend_1D` inside
the block) settling at the least-squares optimum 0.340. Two rules came out of
writing them: a frame operator with free `_` inputs must be given named
arguments or its inputs are duplicated at every use, and a body must receive
outer signals as explicit inputs.

`optimizers.lib` 0.6.0 packages the second pattern: `frame_sum`,
`frame_count`, `frame_mean` (an exact per-frame accumulator, reset the sample
after a firing) and `descend_1D_clocked` … `descend_5D_clocked`, which
compute the loss and `fad` at audio rate, average the gradient over the frame
and step inside an `ondemand` block, so the engine's state advances once per
frame. Two details found by testing: the parameter must read `init` until
the block has fired once (the block's held output is 0 before that, and a
2-D loop started from `(log 1000, 1)` otherwise ran its first frame at the
lower bound and diverged), and a reset shorter than a frame has to be
latched until the next firing. Fixture `opt_descend_clocked_gain.dsp`
(exact gain in a few frames) and a seventh runtime test;
`opt_all_functions.dsp` regenerated (68 Test entries, 113 outputs).
`docs/fad-rad-synthesis-{en,fr}.md` gain a section 10, "Learning at Frame
Rate with `ondemand`" (the former 10 and 11 become 11 and 12), with the
clocked gain and the frame-rate FFT loss as executable examples;
`docs/ondemand-note-{en,fr}.md` §6 replaces its `ad.fit_adam(...)` sketch
with the real `op.descend_1D` / `op.descend_1D_clocked` calls.

## optimizers.lib 0.5.0: loss-first loops, normalized and second-order engines, fixtures and tests

Commit date: 2026-09-05

Source commit: this commit

`libraries/optimizers.lib` was a FAD helper file with five copy-pasted loops
and five engines, an implicit instantaneous-MSE loss, an Adam without bias
correction (first steps `sqrt(1 - b2) / (1 - b1) = 3.16` times `lr`),
rectangular pole bounds that admit unstable filters, parameters that could
only start at `clip(0)`, and an `import("stdfaust.lib")` at the top. That
import resolves through `/usr/local/share/faust` (`compiler/src/paths.rs`),
which the tests may not depend on (AGENTS.md §3), so nothing in the workspace
exercised the library: no fixture, no test, no golden.

Version 0.5.0, documented to the Faust libraries convention
(<https://faustlibraries.grame.fr/contributing/>: `declare` header, section
banners, one block per public function with `Usage`/`Where`/`Test`/
`References`), prefix `op`, no import at all:

- **Loss-first loops** `descend_1D..5D(loss, engines..., bounds..., inits...,
  reset)`: one `fad` call over a scalar loss closed over the data, engines see
  `g = d(loss)/dp`. Losses `mse`, `pseudo_huber`, `logcosh`, `energy_loss`,
  `log_energy_loss`, regularizers `l2`, `l1s` — all smooth, since the `abs`
  rule is `NaN` at zero.
- **Least-squares loops** `lsq_1D..5D` (the old `optimize_ND` plus `init` and
  `reset`; `optimize_ND` kept as wrappers) with engines `lms`, `nlms`
  (sensitivity-normalized), `gn1`, and the original `sgd`/`adam`/`rmsprop`/
  `nadam`/`sign_sgd`. `adam` and `nadam` now bias-correct through
  `ema_bc(a, x) = ema(a, x) / ema(a, 1.0)` (`1.0 : smooth(a)` is exactly
  `1 - a^(n+1)`).
- **Gradient engines** `sgd_g`, `momentum_g`, `nesterov_g`, `adam_g`,
  `nadam_g`, `amsgrad_g`, `adabelief_g`, `rmsprop_g`, `adagrad_g`, `lion_g`,
  `sign_g`; conditioning `clip_g`, `softclip_g`, `gate_g`; schedules `lr_exp`,
  `lr_cos`, `warmup` (a learning rate is a signal); `polyak` readout.
- **Damped recursive Gauss-Newton** `lm_2D`, `lm_3D`: information matrix
  averaged with forgetting factor (bias corrected), Marquardt damping relative
  to its diagonal (unit-free), instantaneous innovation, gain `mu ~ 1 - a`.
  The averaged-innovation form was tried first and diverges — the same
  correction gets applied once per sample over the whole window.
- **Reparameterizations** `poles_from_reflection` (`a1 = k1 (1 + k2)`,
  `a2 = k2`: a bijection onto the stability triangle, so rectangular bounds
  on `k` are always stable), `reflection_from_poles`, `sigmoid_map`.
- **Newton solver** `newton_step`, `newton(N, F, y0)`, `F` and `F'` from one
  `fad`.

Measured with `faustprobe` before the change of API was settled (double
precision, `-I libraries`): resonant-filter identification with `lm_2D`
reaches `(1200.000000, 2.000000)` from `(1000, 1)` in 10 000 frames with a
single gain, where the per-parameter RMSProp of the synthesis note needs
`lr_f = 2.0`, `lr_q = 0.01`; NLMS on a 3-tap FIR converges at input levels
0.1, 1 and 10 alike while LMS is 100× too slow at 0.1 and clamps at 10;
`logcosh` keeps a gain within 1e-2 under ±20 spikes every 97 samples where
`mse` jitters by 0.2; the five-coefficient biquad started at `(a1, a2) =
(1.9, -0.5)` — inside the rectangle, outside the triangle — diverges to
`inf`, the reflection form converges from any start.

Tests. Seven fixtures `tests/corpus/opt_*.dsp` (LCG noise inline, stereo
residual output, `op = library("optimizers.lib")`, no standard library):
Adam gain, NLMS FIR at level 10, `lm_2D` pole + gain, `descend_5D` + Lion +
reflection biquad, `logcosh` under outliers, Newton cubic, and
`opt_all_functions.dsp`, generated from the `#### Test` entry of all 60
documented functions (95 outputs) so the documentation examples are compiled.
`crates/compiler/tests/optimizers_lib.rs` runs them through the interp fast
lane with `tests/corpus` and `libraries` as the only import paths and
requires the residual RMS to fall by 10× to 100× (f32 thresholds checked
against `faustprobe` runs in both precisions). `xtask golden`'s
`is_rust_golden_eligible` now skips any fixture naming a project-local

`docs/fad-rad-synthesis-{en,fr}.md` §4 now shows the biquad as

## Pin fmod's real nature against the C++ `%`/`fmod` conflation (f81491f8)

Commit date: 2026-09-05

Source commit: this commit

C++ Faust commit `f81491f84d92` (2026-09-04) fixed `fmod(int, int)` being
typed int: `SignalDispatch::xtendedOp` routed `XOp::Fmod` to the `Mod`
operation the `%` binop uses, whose nature rule is `x | y`. The WASM backend
then emitted `call $fmodf` on i32 operands, an invalid module that broke
every soundfile player (`so.loop`, `it.raise_modulo`); C++ hid it behind
implicit conversions, which is why the corpus stayed green.

Audit of faust-rs first. The bug cannot happen here, for two independent
reasons: `sigtype` has a dedicated `SigMatch::Fmod` rule with an explicit
`float_cast` (there is no shared operation to disambiguate), and the
promotion pass casts both `fmod` operands to real by primitive
(`promote_real_binary`), independently of the node's nature, after which the
retype makes the nature real anyway. Verified by mutation: with the
`float_cast` removed from the typing rule, FIR, C++ and WASM output were
unchanged and the `.wasm` modules still validated. The FIR checker would
NOT have caught it as an error had it happened: `FIR-FC03` treats all
numeric types as mutually compatible, `FIR-MA03` (integer-like argument to a
float math op) is a warning, and strict mode already fails on the ubiquitous
`FIR-M07` warnings, so it is not a usable gate. The WASM backend lowers
imported-call arguments without coercion, exactly like C++.

Two holes closed:

- `sigtype`: no unit test covered fmod's nature. Four added in `rules.rs`:
  `fmod(int, int)` is real, `remainder(int, int)` is real, `%` on two
  integers stays int, and the `so.loop` shape (int-seeded recursion wrapped
  by `fmod`) converges to real.
- `signal_prepare`: two tests in `tests/typing.rs` check that both `fmod`
  operands come out real after preparation with an explicit `FloatCast` on
  the `int()` operand, including inside a recursion body; and
  `verify_promotion_invariant` gains a clause refusing a prepared `fmod`,
  `remainder` or `atan2` whose result or operands are not real. This checker
  runs in production (`prepare_signals_for_fir_verified_with_options`).
- `tests/impulse-tests/dsp/math.dsp` receives the two lines from the C++
  commit (`fmod(int(_*9.2), 2.0)`, `fmod(int(_*9.2), int(2))`) and is again
  identical to the C++ file; `reference/math.ir` regenerated with the
  installed C++ Faust 2.87.11 (built after the fix), 76 → 78 outputs.

Mutation validation, per the plan/producer/checker methodology: removing the
`float_cast` from the `sigtype` rule fails exactly the two `fmod` tests;
replacing `promote_real_binary` by a neutral promotion for `fmod` fails the
two `signal_prepare` tests with the new invariant's message (`operands
Some(Int), Some(Int)`). Both mutations reverted.

Gates: `sigtype` 53/53, `transform --lib` 406/406, `compiler` 647/647;
`math.dsp` passes on all nine impulse lanes (cpp, c, interp, cranelift, wasm,
assemblyscript, rust, julia, cmajor); the 161 DSPs of `dsp/` + `dsp-rad/`
all compile through the widened invariant. Side note: the C++ oracle
preflight now classifies 39 DSPs as unsupported by the installed 2.87.11
(`ondemand`, `upsampling`, `downsampling`), the expected faust-rs-only
primitives, unrelated to this change.
