# 2026-09-05

## Pin fmod's real nature against the C++ `%`/`fmod` conflation (f81491f8)

Commit date: 2026-09-05

Source commit: this commit

C++ Faust commit `f81491f84d92` (2026-09-04) fixed `fmod(int, int)` being
typed int: `SignalDispatch::xtendedOp` routed `XOp::Fmod` to the `Mod`
operation the `%` binop uses, whose nature rule is `x | y`. The WASM backend
then emitted `call $fmodf` on i32 operands, an invalid module that broke
every soundfile player (`so.loop`, `it.raise_modulo`); C++ hid it behind
implicit conversions, which is why the corpus stayed green.

Audit of faust-rs first. The bug cannot happen here, for two independent
reasons: `sigtype` has a dedicated `SigMatch::Fmod` rule with an explicit
`float_cast` (there is no shared operation to disambiguate), and the
promotion pass casts both `fmod` operands to real by primitive
(`promote_real_binary`), independently of the node's nature, after which the
retype makes the nature real anyway. Verified by mutation: with the
`float_cast` removed from the typing rule, FIR, C++ and WASM output were
unchanged and the `.wasm` modules still validated. The FIR checker would
NOT have caught it as an error had it happened: `FIR-FC03` treats all
numeric types as mutually compatible, `FIR-MA03` (integer-like argument to a
float math op) is a warning, and strict mode already fails on the ubiquitous
`FIR-M07` warnings, so it is not a usable gate. The WASM backend lowers
imported-call arguments without coercion, exactly like C++.

Two holes closed:

- `sigtype`: no unit test covered fmod's nature. Four added in `rules.rs`:
  `fmod(int, int)` is real, `remainder(int, int)` is real, `%` on two
  integers stays int, and the `so.loop` shape (int-seeded recursion wrapped
  by `fmod`) converges to real.
- `signal_prepare`: two tests in `tests/typing.rs` check that both `fmod`
  operands come out real after preparation with an explicit `FloatCast` on
  the `int()` operand, including inside a recursion body; and
  `verify_promotion_invariant` gains a clause refusing a prepared `fmod`,
  `remainder` or `atan2` whose result or operands are not real. This checker
  runs in production (`prepare_signals_for_fir_verified_with_options`).
- `tests/impulse-tests/dsp/math.dsp` receives the two lines from the C++
  commit (`fmod(int(_*9.2), 2.0)`, `fmod(int(_*9.2), int(2))`) and is again
  identical to the C++ file; `reference/math.ir` regenerated with the
  installed C++ Faust 2.87.11 (built after the fix), 76 → 78 outputs.

Mutation validation, per the plan/producer/checker methodology: removing the
`float_cast` from the `sigtype` rule fails exactly the two `fmod` tests;
replacing `promote_real_binary` by a neutral promotion for `fmod` fails the
two `signal_prepare` tests with the new invariant's message (`operands
Some(Int), Some(Int)`). Both mutations reverted.

Gates: `sigtype` 53/53, `transform --lib` 406/406, `compiler` 647/647;
`math.dsp` passes on all nine impulse lanes (cpp, c, interp, cranelift, wasm,
assemblyscript, rust, julia, cmajor); the 161 DSPs of `dsp/` + `dsp-rad/`
all compile through the widened invariant. Side note: the C++ oracle
preflight now classifies 39 DSPs as unsupported by the installed 2.87.11
(`ondemand`, `upsampling`, `downsampling`), the expected faust-rs-only
primitives, unrelated to this change.
