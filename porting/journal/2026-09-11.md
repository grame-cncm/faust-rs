# 2026-09-11

## MEMOIZATION.md swept against the code since June

Commit date: 2026-09-11

Source commit: this commit

The roadmap's last content change was 2026-08-08, and it had drifted in both
directions: entries describing state that no longer exists, and eleven
memoization sites added since 2026-06-22 that it never mentioned. Every commit
in that range was read; what the sweep found is now in `porting/MEMOIZATION.md`.

**New entries.** Parser: the remote import cache (§2.1b), whose payload is the
final URL after redirects so that a redirect target cannot slip past the
duplicate and cycle detection, and the two process-wide `OnceLock`s holding the
lexer definition and the combined DFAs (§2.1c). Eval: the normal-form fast path
(§2.4c) and closure interning (§2.4d). Normalize: the table promotion cache and
its `None` sentinel, which is the identity value doubling as the `Rec` cycle
marker exactly as in §2.9 (§2.9b). Transform: CSE per execution scope (§2.12b),
straight-line scalar table-load reuse (§2.12c), FIR state keyed by clock
occurrence (§2.12d), the delay planner's dominance memo (§2.12e), the
block-reverse-AD tapes and the forward-output keys (§2.19), the clock
inference sweep (§2.20), and `Special`'s sequence summaries (§2.21). Propagate:
the canonical slot and UI identities (§2.16), the forward-AD memos (§2.17) and
the stateful-RAD linearity classifier (§2.18).

**Corrections.** §2.11 described `node_types` / `group_types` / `active_groups`,
deleted on 2026-03-19; the typing memo is now the annotator's own table, and the
fact worth recording is that the staging map is rebuilt wholesale at each of the
five schedule points, because every rewrite invalidates it. §2.12's flat
lowering cache is a scope stack since 2026-07-15. §2.15 still stated the
slot-environment restriction that 2026-08-30 removed, along with the
measurements of its removal.
§2.6's arity cache now lives on `BoxCompileOutput` and crosses a public API
boundary. Stale paths fixed in §2.2, §2.5, §2.7, §2.8, §2.10, §2.13.

**Two rules added.** Rule 6: the key names everything the value depends on — a
`SigId` means one thing inside a clock domain and another in its sibling, one
thing inside a recursion binder and another outside, one class at one de
Bruijn level and another at the next. Three separate bugs, all silently wrong
rather than slow. Rule 7: count the cost of the key itself, after a key computed
by a dump that prints a shared graph as a tree spent five minutes and ten
gigabytes before a single instruction was lowered.

**What the sweep says about the roadmap.** Of the seven changes that moved
compile time since 2026-08-06, three are not caches: two are better keys and one
is a better scope. §6 now records that, and the priority list now puts
hash-consed evaluator environments first (§3.7) — the last place where the port
pays a cost C++ does not, and the change that would retire §2.4c's exception
list.

Also noted, in §4 rather than §2: the interpreter FFI factory cache is keyed by
the `.fbc` header's SHA field, and the codegen layer writes an empty string
there, so distinct interpreter factories coalesce on the first insert. Not fixed
here.

## Interpreter FFI: a factory cache keyed by the empty string

Commit date: 2026-09-11

Source commit: this commit

Found while sweeping `porting/MEMOIZATION.md`. The interpreter FFI inserted
every factory under `factory.sha_key()`, and nothing ever set that field: the
codegen layer passes `""` with the comment "not computed at this layer", and the
`.fbc` reader defaults it to `""` when the header carries none. The cache is a
`HashMap<String, FactoryEntry>` whose `insert_or_acquire` coalesces on an equal
key, so the *second* factory created through the FFI was dropped and its
caller received the first one. A test writes the consequence down:
`createCInterpreterDSPFactoryFromString` for `process = _;` and for
`process = _, _;` returned the same pointer, a one-output factory for a program
with two. `getCInterpreterDSPFactoryFromSHAKey("")` returned whichever arrived
first. C++ is not exposed to this because its factory table is keyed by the
factory pointer and the SHA is only a lookup index; ours is keyed by the SHA.

The keys now follow the reference implementation. From source,
`source_factory_sha_key` is `sha1FromDSP` (`dsp_aux.cpp:216`): the uppercase
SHA-1 of the application name, the unexpanded source, and the quoted normalized
options, using the `reorganize_compilation_options` port the expansion path
already had. Two digests computed outside the code base pin that shape, so a key
libfaust computes for the same request finds the same entry. From bitcode,
`bitcode_factory_sha_key` is `generateSHA1(bitcode)` over the whole `.fbc` text,
as `readInterpreterDSPFactoryFromBitcodeAux` does, rather than the key the
header happens to carry. Both creation paths now consult the cache *before*
compiling and store the key on the factory they produce, which is what C++ does
and which makes a repeated identical request free instead of a compilation whose
result is thrown away.

The key deliberately carries no foreign-function fingerprint, where the
Cranelift key does: the interpreter resolves a foreign call by name at execution
time, so a re-registered address reaches a cached factory, and a missing
registration fails compilation, which is never cached.

Four tests in `crates/interp-ffi/src/factory.rs`:
`two_different_sources_get_two_cache_entries` (the bug),
`precision_and_option_order_decide_cache_identity` (`-double` separates,
argument order does not, the digest is 40 uppercase hex characters),
`a_bitcode_factory_is_keyed_by_the_digest_of_its_bitcode`, and
`a_source_key_is_the_digest_libfaust_computes`. The existing
`factory_cache_lifecycle_matches_reference_counted_cpp_contract` asserted that a
repeated identical creation returns one factory; it used to pass because every
key was empty and now passes because the keys are equal.

Nothing changes for the CLI: a factory built by the compiler and written to
`.fbc` still carries an empty header field, and `porting/MEMOIZATION.md` §4 no
longer describes this as an unrealized hazard.

Gates: fmt, clippy `-D warnings`, the workspace tests (111 suites), golden-check
202/202, interp-trace-check (5 snapshots), cli-parser, error-model,
ffi-boundary, structure and diagnostics-quality checks, and code-graphs after
refreshing the public API baseline for `set_sha_key`. Two failures
reproduce unchanged at the parent commit and are not from this change:
`libfaust-export-check` reports the dynamic library missing the
header-declared `setCCraneliftMemoryManager`, and the public API *index* under
`docs/code-graphs/` had drifted by three lines in the Cranelift layout section
(refreshed here; the gate checks eight artifacts and that is not one of them).
