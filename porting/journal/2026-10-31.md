# 2026-10-31

## diagnostics: report a failed `case` on its call

Commit date: 2026-10-31

Source commit: this commit

A `case` no rule matches was reported on the definition of the rules, and said
`no case rule matches arguments`. The rules are often right and the call wrong, and
the arguments were only in the trace. C++ cites them, with no location.

`PatternMatchFailed` now gets the application from the frame that refuses it, as
`TooManyArguments` does. The error is located on the name called, the message cites
`f(3)` with the arguments the rules saw, simplified, as `f(1 + 2)` reaches them, and
`...` stands for those after the one no rule takes. A new label marks the rules.

An application with no place of its own, like `m.k(5)` of a library, is labelled
`failing call` on its definition, with the role `CallSite`. That also applies to
`too many arguments`.

The mutants of the evaluation do not touch `case`, so this has no measure.
`a_case_failure_names_the_call_and_its_arguments` holds the behaviour.

## diagnostics: point an arity error at the definitions and the call

Commit date: 2026-10-31

Source commit: this commit

Of 191 arity mutants, 37 reported a line more than one away from the error. Two
causes account for 35 of them.

In 30, the composition reported is the right one and the width that is wrong is
written elsewhere: `capture : *(level)` of a `capture` that gained an output.
`add_operand_definition_labels` now labels the definitions of the operands, read
from the source of the composition: the names it composes and the functions it
calls, through groups and `with`, not their arguments, at most four, and only a
definition the file has once. Parameters are left out, or `x` in `f(x) = x : g`
would point at a top-level `x`.

`TooManyArguments` carried the function, and a primitive is one node for all its
uses: `attach(x, a, b)` in `vmeter` was reported on the `attach` of `null`. It now
gets the application from the `Appl` frame that refuses it, innermost first, which
gives the right definition. The message names the function, as C++ does, and counts
the parameters: `g(1, 2, 3, 4)` of a `g(x, y)` said `expected at most 0, got 2`, the
inputs of the result of `g`, and now says `too many arguments for `g`: expected at
most 2, got 4`.

Arity mutants with some line within one go from 80.6 % to 87.4 %, and from 85.9 % to
86.3 % over all kinds, against 73.7 % for C++. The first line reported hardly moves,
since a mismatch stays located where it is. Simulated lines read go from 47.8 to
46.3, and compiles stay at 3.3. Arity text grows from 1055 to 1119 characters.

The evaluation only read `file:line` headers, so it could not see a label in the
same file. `mutate.located` reads the source lines too, and the measures of the
previous commit were taken again with it: that is why compiles are 3.3 here and 3.54
in the entries below. C++ has no such lines and its figures do not change.

## diagnostics: leave out what the reader already has

Commit date: 2026-10-31

Source commit: this commit

Second step on the volume of text the evaluation in `faustprobe-diagnostics-eval`
measured. Nothing a tool reads goes away: the labels, the three scopes and the
binding trace stay in the JSON report as typed values, and `--error-verbosity debug`
prints the rest.

Human output starts on the diagnostic. `report_pipeline_failure` prints its
`... pipeline failed:` line only for an error with no diagnostics, and `faustprobe`
drops the summary line, which the C API keeps for hosts with a 4096-byte buffer. A
first line that names an option stays, since `--compare:` says which program failed.

Messages no longer carry `at node N`, which is still the debug fact `node_id`. The
`expr=` note repeated the symbol of an undefined name or the `A` and `B` of a
composition, on all the mutants measured, and is a debug fact too. `error originates
from` and `binding_trace=` are written only past the entry point. Of the scope notes
only `scope.visible` stays, and the note that restated the header of a composition
mismatch is gone.

`render_labels` prints one label per place and leaves out a definition or a call
site on the line of the error. That hid the `process` carets that followed every
undefined symbol. The filter reads the typed role and span.

`render_human_box_expr` falls back on `box_pp_bounded` for the shapes it has no form
for, so a function in an `A` or `B` reads `\(x1).((x1 * 0.5))`, not
`BOXSYMBOLIC(BOXSLOT(...`, and `fconstant` and `waveform` read as written. The
`declarations` fact of a redefined symbol uses it too, and its `declaration:` notes
are gone, since the labels show both clauses. Of 1122 mutants, none prints a box tag
or a node number, against 84 and 184 before.

Measured on the 2754 mutants both tools refuse: median text falls from 654 to 491
characters, 71 for C++, and the locations are unchanged. Simulated compiles stay at
3.54 and lines read at 54.8: this step moves no location.

The `bad_*` CLI transcripts were recorded again. The 68 others were already stale
for reasons unrelated to diagnostics and are left as they were.

## parser: syntax errors in the tokens of the language, and a fix for a missing `;`

Commit date: 2026-10-31

Source commit: this commit

The evaluation in `faustprobe-diagnostics-eval` showed that faust-rs prints eleven
times more text than C++ for syntax errors it locates no better. Four changes
address that, all on the error path.

A syntax error now reads `syntax error: unexpected `gain`, expected `;` or `[``
instead of up to sixty `Insert ENDDEF` lines. The list comes from the first token
of each repair, and is left out past six. `ParseOutput::errors` keeps the text of
lrpar, and the C ABI summary line is unchanged in shape.

A missing `;` gets a `maybe-incorrect` fix at the end of the previous statement,
when `;` is among the single-token repairs and a newline separates the two tokens.
It is not machine-applicable because `[` is a repair too.

Recovery from a missing `;` used to produce errors of its own. Each `;` is now
inserted and the text parsed again, and an error stays only if it stays there.
Positions are compared, not lines, since the end of input errs on the line of the
last real error. Past a further missing `;` only the first error of a parse counts.

The list of names in scope is summed up past twelve names, with the closest ones
first; `--error-format json` keeps all of them in the facts. `typo_library` text
goes from 9888 to 1518 characters (median).

The previous token came from the text, so a line ending in a comment had its `;`
placed in the comment, where it changes nothing, and the check then lost the
errors further down. It now comes from the lexer. The simulated repair found this,
and `a_missing_semicolon_is_inserted_before_a_comment` and
`the_errors_after_a_missing_semicolon_stay` hold it.

Measured on the 2754 mutants both tools refuse. Of the 344 missing `;`, the fix
gives a program that compiles for 337 and 7 have no fix, and they report 1.00 error
per run, against 1.29. Median text falls from 799 to 654 characters, 71 for C++.
Locations do not change: 80.6 % of first lines within one line. Simulated compiles
go from 3.51 to 3.54, within what two runs of one binary differ by, since lrpar
picks among equal repairs: the dropped cascades sometimes fell near a real error.
Lines read go from 55.3 to 54.8.

Error messages longer than 4096 bytes no longer arise from scope lists, so the
tests of the complete error buffers use a long symbol. `compile-budget-check`
cannot run on this Mac; a program that parses leaves `drop_cascaded_errors` on its
first test.

## diagnostics: a `with` that shadows a top-level name keeps the failing use

Commit date: 2026-10-31

Source commit: this commit

An undefined symbol was reported on the line of the enclosing definition instead
of its use when a `with` of that definition defined a name that also exists at
top level, usually in a library. `source_span_for_node_in_definition` looks for
the use between the start of the owner and the next top-level definition, and it
took the local site of that name for the next definition, so the use fell outside
the range. `reverb_tester` and `zita_rev1` show it; C++ gives the line of the use.

Names defined by `with` and `letrec` blocks under the owner are no longer
boundaries. If such a name is really defined at top level after the owner, the
range only ends later, and the use is still required to be the only one in it.

An expression of `faustprobe --eval` had the same cause, through the wrapper
environment: an undefined symbol is now located in it, as `<eval 0>:1:1` with the
expression as snippet, where it used to point at the generated wrapper.

On the 2754 mutants of the evaluation in `faustprobe-diagnostics-eval`, a misspelt
local name is within one line of the right one in 98.6 % of cases, against 95.6 %
before and 98.3 % for C++, and the cases only C++ gets right go from 9 to 0.

## eval: refuse an invalid route as C++ does

Commit date: 2026-10-31

Source commit: this commit

faust-rs accepted `route(2, 2, 1, 3, 2, 1, 5)`, whose five values are no list of
pairs, and silently dropped the last one. The evaluation of the two `faustprobe`
found it: C++ refuses this program, 2.84.3 and 2.91.0 alike.

`eval_route_value` now makes the checks of the `isBoxRoute` branch of `eval.cpp`,
with its two messages: sizes that are 0→1 boxes and an even number of routes
(`InvalidRouteShape`), then parameters that fold to numbers
(`InvalidRouteParameters`). As in C++, a pattern variable, a wire or a slot lets a
route through, since it is then a pattern of a `case`. A parameter whose arity is
unknown stays with propagation, a narrower rule than C++ kept so that nothing the
reference accepts can be refused. Programs already refused now get the C++ reason
at their definition, in place of `unsupported box node`.

41 forms of `route` have the same fate with faust-rs and with Faust 2.84.3 and
2.91.0. Of 967 programs of `tests/`, `examples/`, the C++ `examples/` and the
faustlibraries tests, none changes between accepted and refused, and the 2576
`*_test` definitions of faustlibraries still agree with the C++ `faustprobe`.

`compile-budget-check` was not run: it does not work on this machine. The check
propagates the parameters of each route once more, which by hand costs nothing
measurable on eight routes of 512 pairs (34 ms before and after) and 7 % on 256
distinct routes of 64 pairs (314 to 336 ms).

## ui: sort a group's items on their raw labels

Commit date: 2026-10-31

Source commit: this commit

Comparing the C++ port of faustprobe with the Rust tool on the Faust libraries
left four `spectral_level` tests whose bargraph values were the same under other
names. C++ sorts a group on the labels as written (`isBefore`,
`compiler/generator/uitree.cpp`), while Rust compared a key rebuilt from the
parsed `[n]` prefix. The rebuilt key lost the spaces `%2i` pads a number with, so
`[10]` came before `[ 2]`, and since `checkNullBargraphLabel` numbers unlabelled
bargraphs in that order, those bargraphs took other numbers. Widgets were listed
in another order for the same reason, which `carre_volterra`, `modulations` and
two Faust examples show.

The key is now the raw label, for widgets and groups, and
`ordering_key_from_label` is gone: that also settles labels with metadata before
the `[n]`, or a `[n]` that is not at the start. DIFF-BEH-015 said unlabelled
bargraphs always took the same number as in C++; it now records this case.

On the 611 programs of `tests/`, `examples/` and the C++ `examples/` that both
compilers accept, the interface tree matches Faust 2.90.21 on 609, against 605
before. The other two are the Rust-only relative groups of `rep_63` and `rep_64`.
Field names (`fHslider<n>`) still differ on programs that declare widgets out of
order; this change does not touch them. The 2576 `*_test` definitions of
faustlibraries now give the same result through both faustprobes (with
`FAUST_LLVM_RELOAD=1` on the C++ one), against 2572 before.
