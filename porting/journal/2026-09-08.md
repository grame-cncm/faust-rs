## faustprobe --in file: and --reset-per-block: the offline calibration

Commit date: 2026-09-08

Source commit: this commit

The `--train` loop of the previous entry ran on a synthetic excitation and
kept its state from block to block: enough for the two corpus examples, not
for the calibration a host such as faust-diff-fdn does, where the program
compares itself to a measured impulse response and every epoch replays the
whole response from a cleared instance. Two additions. `--in
file:PATH[:CH]` reads the excitation from a file: `.wav` (RIFF, PCM 8 to
32 bits, IEEE float 32 and 64, the extensible header) in the new
`crates/cranelift-ffi/src/probe/audio_file.rs`, `.f64` and `.f32` raw
little-endian mono; input `i` reads channel `i`, a mono file feeds every
input, `:CH` picks one channel for all, silence past the end. The file is
read once into an `Arc` in `InputMode::File`, so the sample function stays
a lookup. The samples are read at `--sr`: a WAV recorded at another rate
gets a warning on stderr, a raw file carries no rate and gets none.
`--reset-per-block` clears the instance before every block and restarts
the excitation at frame 0, so one block is one pass over the same response
and the loop is the offline calibration: `--block` the length of the
response, `--bra-tape` the next power of two.

Measured on faust-diff-fdn's `fdn_calibrate.dsp` (40 parameters, a 1 s
response at 16 kHz): `--sr 16000 --in file:target.f64 --block 16000
--bra-tape 16384 --reset-per-block --train ... --lr 0.03` reproduces the
Rust host's `log.csv` to the printed digits, the mean loss of block 1
`1.680490e-1` being the host's summed `2688.785` over 16 000 frames and
`t60_0` at `-0.109627` after 20 blocks in both, 20 epochs in 1.9 s. The
first run without `--sr` gave a loss ten times lower and another
trajectory: the program was running at 44 100 Hz over a 16 kHz response,
which is what the warning now says. Four unit tests on the reader (PCM 16
stereo and float 32 with the rate, PCM 24, a raw `.f64` by extension and
the unknown-extension error, non-WAV bytes); the extension is checked
before the file is read, so a missing file with the wrong extension names
the extension. Guide: the input table of section 4 and the
`--reset-per-block` paragraph of section 13.

## faustprobe --train and --fd-check: the host loop at the command line

Commit date: 2026-09-08

Source commit: this commit

The two `rad` examples whose loss and gradient lanes leave the graph
(`ddsp_rad_host_block_resonator.dsp`, `ddsp_rad_gru_amp_host.dsp`) could be
rendered by faustprobe but not driven: the tool set controls before the
render and reduced outputs after it, never the one from the other between
two blocks. `crates/cranelift-ffi/src/probe/train.rs` closes that loop with
the two operations a host has, `set_exact` and `compute_raw`: `train`
writes the controls, computes a block on one instance whose state carries
across blocks (truncated BPTT for a recurrent model), averages the loss and
gradient lanes, steps the controls by SGD or Adam and clamps them to their
range; `fd_check` compares every gradient lane, summed over a block from a
fresh instance at the initial values, with the central finite difference
of the loss lane. In the binary: `--train CONTROLS` (paths or unique
suffixes, in lane order), `--loss-lane`, `--grad-lane`, `--optimizer`,
`--lr`, `--blocks`, `--fd-check`, `--fd-step`, `--fd-tolerance`; one CSV
row per block thinned by `--every`, the trained values and the first and
last loss after; the check fails the command past the tolerance; `--sweep`,
`--reduce`, `--at`, `--set` and the impulse-test protocol are refused with
it.

Measured: the resonator's two lanes within 4e-6 of finite differences, and
`(-0.8, 0.5)` to `(-1.200000000, 0.720000000)` in 600 blocks of 256, the
block loss from 0.46 to 3e-28, in 0.6 s; the GRU's 27 lanes within 5e-6,
and 2 000 blocks of BPTT taking the mean block loss from 1.3e-2 to 2.0e-4
in a tenth of a second. Tests in `train.rs` on the two programs, with the
tolerances of `ddsp_examples.rs` (finite differences within 2 %, poles
within 0.02, loss down 30 dB and tenfold); they run on a 64 MiB thread like
every corpus test. Documented in the user guide (section 13) and in the
two examples' "With faustprobe" paragraphs of `ddsp-examples-{en,fr}.md`,
which said the day before that the loop was the host's alone.

## eval: a deep acyclic expression no longer aborts the process (issue #16)

Commit date: 2026-09-08

Source commit: this commit

Issue #16 (shakfu): `process = 1 + 1 + ... + 1`, two hundred thousand
times, killed the compiler with `SIGABRT` and no diagnostic. The chain is
acyclic, so it never pushes a `call_stack` frame and `max_depth` never sees
it; it recursed through `eval_value` until the 512 MiB stack of the CLI
worker ran out, between 150 000 and 200 000 levels. The C++ compiler reports
"stack overflow in eval" on the same input, because it watches the stack
address; the Rust port had replaced that with logical frame counts, and this
path had none. The proposed patch counted `eval_value` entries against the
existing `max_depth`, 32 768: correct in mechanism, but it would have
rejected the 50 000-level chain that both compilers accept (a chain costs
two entries per level), and a count calibrated on the CLI's 512 MiB cannot
protect an embedding host whose thread has 8 MiB, the case the issue
argues for.

Two changes in `crates/eval`, both in `loop_detector.rs`:

- `on_deep_stack(f)`, `stacker::maybe_grow` with a 256 KiB red zone and
  8 MiB segments: when the current stack has less than the red zone left,
  `f` runs on a heap-allocated segment. It wraps the four recursive entries
  of the evaluator, `eval_value` (after the cache lookup) and the three
  structural ones, `a2sb_value` and the two `apply` sites. This is the C++
  stack watch turned from an error into a continuation, the mechanism rustc
  uses for its own recursion; on wasm32 the crate compiles and the call
  runs in place. `remaining_stack` is a thread-local read and a pointer
  compare per call: the 295 reference examples compile in 26.3 s before
  and after, exit codes identical (7 failures on both sides, pre-existing).
- `enter_eval` / `leave_eval`, a keyless counter of `eval_value` nesting
  with its own budget, `nesting_max_depth`, default 400 000 entries
  (`FAUST_RS_DEFAULT_EVAL_NESTING_DEPTH`), separate from `max_depth`. Its
  role is no longer safety but resource: about 2 KiB of segments per entry,
  so at most about 800 MiB before the clean `FRS-EVAL-0099`, "stack
  overflow in eval (depth budget 400000)". Calibration by bisection on the
  environment variable: exactly two entries per level of a binary chain, so
  the budget is the 200 000 levels where the old evaluator aborted; the
  150 000-level chain it accepted still compiles (0.2 s, 470 MiB peak).

Measured with the CLI: 50 000 levels compile in 0.6 s (273 MiB), 150 000
compile, 200 000 and 300 000 report the diagnostic in 0.1 s. Tests: the
counter's unit tests; `on_deep_stack` recursing 40 000 kibibyte frames on a
256 KiB thread; a 5 000-level chain evaluated by `eval_box` on a 1 MiB
thread, and the same chain against a budget of 1 000 entries giving
`RecursionDepthExceeded`; in `crates/compiler`, the chain compiled to
signals on a 64 MiB thread, where the previous code aborted (checked by
building the probe on the previous commit: `boxes` at 64 MiB and `signals`
at 64 MiB both overflowed before, both pass now).

What remains for embedding hosts: the passes after eval still recurse on
the native stack. Measured in release on an 8 MiB thread, the whole
pipeline to signals handles 8 000 levels and overflows at 16 000
(`propagate::try_build_flat_box` and what follows, under 1 KiB per level);
in debug, 1 000 levels already overflow 8 MiB, which is why the compiler
test uses 64 MiB. The same `on_deep_stack` at the recursive entries of
`propagate` (and of the later passes, to be audited one by one) would close
that; it is a separate change. Gates: `eval` 56 + 73, `compiler` all
suites, fmt and clippy clean on both crates.

## Cranelift 0.117 to 0.135: the JIT emits islands inside blocks

Commit date: 2026-09-08

Source commit: this commit

The five Cranelift crates of `crates/codegen` (`codegen`, `frontend`, `jit`,
`module`, `native`) go from 0.117.2 (wasmtime 30, early 2025) to 0.135.1
(wasmtime 48, the latest stable; 0.136 is a release candidate). The API
changes met by the backend:

- `MemFlags` is now a handle into the function's deduplicated set of flag
  data; `load` and `store` take `impl Into<MemFlagsData>`, so the 24 sites
  pass `MemFlagsData::new()` where they passed `MemFlags::new()`.
- `global_value` is gone; the address of a data object is `symbol_value`.
- `FunctionBuilder::declare_var(ty)` allocates the `Variable` itself: the
  hand-rolled `next_var` counter is gone.
- Branch arguments are `BlockArg`s: the six `jump(header, &[v])` of the loops
  pass `BlockArg::Value(v)`.
- `FunctionBuilder::finalize` takes the target's frontend config,
  `jit.target_config()`.
- `iadd_imm` and `icmp_imm` are deprecated in favour of the explicit
  sign-extending `_s` forms, which are what the old ones did.

No change in the FIR lowering itself, and no warning left (`cargo clippy -p
codegen -p cranelift-ffi`). The lock file also moves the wasmtime internal
crates from 30.0.2 to 48.0.1 and picks up `hashbrown` 0.17, `foldhash` 0.2,
`memmap2` 0.9.11, `libm` 0.2.16.

The lowering-side workaround of the previous entry (`split_long_block`,
2048 CLIF instructions per straight-line block) is not kept: the reason it
existed, islands emitted only between basic blocks, is fixed since
wasmtime#13392 (cranelift 0.133). Checked by disabling the split before
dropping it: the 22 500-term program and the 44 000-statement oscillator-sync
demonstrator, 1.17 MB in one basic block, compile and give the same samples
with and without it.

Gates: `codegen` 369/369, `cranelift-ffi` all suites, the Cranelift impulse
lane 94/94 against the C++ references; the oscillator-sync check
(`faust-hasy/check.py`, eight cases against a numerical Fourier analysis)
unchanged to the last digit.
