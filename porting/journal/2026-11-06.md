## porting: the Mojo backend of grame-cncm/faust#1293, analysis and port plan

Commit date: 2026-11-06

Source commit: this commit

`porting/mojo-backend-port-analysis-and-plan-2026-11-06-en.md` reads the Mojo backend of the open
C++ pull request (head `05ac86fb1`, branched from `master-dev` at `fbd198a27`; the pinned
reference `8eebea429` has no Mojo backend). It works at the level of the generated text: the
contract the PR's `architecture/mojo` expects (struct `mydsp(FaustDsp)` with a `null_val` field,
snake-case lifecycle methods, `Some[FaustGui]` / `Some[FaustMeta]` callbacks, `S32`/`F64`/`Arr`/
`Ptr` types, `F32(x)` literals in single precision, `pow_unrolled[n]`). It also lists what not to
copy: a `snakeCase` rename that is not injective and is not checked, a reset writer that asserts a
cast shape, stream rewinding, global visitor state, and an explicit SIMD keyed on the names
`vindex` and `bargraph`. The `-gpu` path is not ported (2026-09-18 analysis, §1.3). The plan
follows the Julia emitter: M1 scalar emitter, M2 CLI, facade and lifecycle conformance, M3
compiled and run under a self-contained Mojo impulse runtime, M4 an optional text differential
against the PR's compiler, and M5 `-vec` (plain loops, then explicit SIMD as a FIR pass in its
own plan). Five decisions are open before M1 (§6), among them the Mojo toolchain and whether to
build the PR's compiler.

The same reading found that the PR rewrites the C++ Julia and JSFX type tables from `Int32` to
`S32`, which are not Julia or JSFX names. This is a C++-side remark to raise on the PR; it does
not touch faust-rs.
