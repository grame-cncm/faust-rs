## Stop building type warnings the caller discards

Commit date: 2026-07-28

Source commit: `25641ea4`

G7 built the potential-out-of-domain warning diagnostics unconditionally and
threw them away when `--warn` was absent. Rendering one warning is not free:
`type_warning_to_diagnostic` walks the definition graph through
`add_signal_source_labels` and dumps the offending Signal expression to a
string with `dump_sig_readable`. That is worth paying for when a reader will
see the result and pure waste otherwise.

`validate_signal_types` now takes `collect_warnings` and returns an empty
bundle before rendering anything when the caller does not want them. The
caller passes `self.semantic_warnings` and no longer rebuilds an empty bundle
after the fact.

Sized before fixing rather than after: 13 warning diagnostics across 60 corpus
files, and `--check` at roughly 148 ms per file in debug. The waste was real
but small, so this is a design correction — a producer should not do work its
caller has already declined — not a performance rescue. It is recorded that
way here so nobody later reads it as the fix for a measured slowdown.

Guarded by `a_disabled_warning_channel_builds_no_diagnostic_at_all`. Asserting
an empty bundle would not have caught the old behaviour, since a bundle built
and discarded is empty too; the test also requires that no source map was
attached, which only happens on the populated path. Verified by mutation:
removing the early return fails two cases, restoring it passes twelve.

`cargo clippy --workspace --all-targets -- -D warnings`;
`cargo test --workspace --all-targets`.

## Keep CompilerError under the Windows result_large_err threshold

Commit date: 2026-07-28

Source commit: `a676f1a0`

CI failed on Windows only, with 85 `clippy::result_large_err` errors against
`CompilerError`; Linux and macOS passed the same commit, and the vector
retention job was cancelled by fail-fast rather than failing on its own.

Measured rather than guessed. `CompilerError` was **120 bytes** on
aarch64-apple-darwin against the lint's 128-byte threshold — eight bytes of
margin. `PathBuf` is eight bytes wider on Windows (`OsString` there carries a
`is_known_utf8` flag beside its `Vec<u8>`), and the widest variant,
`Import(SourceReaderError, DiagnosticBundle)`, holds a `PathBuf` inline. That
put the enum at exactly 128 on Windows, which is where the lint fires. Nothing
platform-specific in the compiler was involved: the enum had been riding the
threshold, and Windows is simply the platform where it crosses.

Boxed the reader error: `Import(Box<SourceReaderError>, DiagnosticBundle)`.
`SourceReaderError` is 80 bytes and by far the widest payload, it is
constructed at exactly one site, and boxing it takes the enum to **104 bytes**
with no `PathBuf` left inline in any variant — so every platform now measures
the same 104 against a 128 threshold.

Added `compiler_error_stays_narrow_enough_for_every_platform`, which bounds the
enum at 112 bytes: below the lint threshold with room for the `PathBuf` width
difference, so the next variant that would only fail on a Windows runner fails
on any developer machine instead. The test documents that the fix for tripping
it is to box the payload, not to raise the budget.

Verified in both directions: with the boxing reverted the guard reports
`CompilerError grew to 120 bytes (budget 112)`; and `clippy.toml` with
`large-error-threshold = 104` reproduces the lint locally against the fixed
enum, confirming the measured size is the one clippy sees.

Note that CI last ran green 31 commits earlier (`f51d5000`), before the whole
error/diagnostics separation and G0-G8 series were pushed together, so the
commit that first put the enum on the threshold is somewhere in that range
rather than necessarily the tip.

## Publish the user-facing error model document

Commit date: 2026-07-28

Source commit: `db215f15`

Renamed `docs/diagnostics-codes-en.md` to `docs/faust-error-model-en.md` and
grew it from a code table into the user-facing description of the whole error
model, aimed at Faust programmers, tool authors, and the LLM agents that now
write a large share of Faust code.

The document compares each behaviour against the reference C++ compiler
(<https://faustdoc.grame.fr/manual/errors/>), explains the four independent axes
of a diagnostic (severity, category, stage, rendering verbosity), documents the
CLI stream contract and the JSON channel, and works through fourteen error
families with a real DSP, the C++ message, and the current faust-rs output side
by side. The former code table, its unreachable-code caveats, the retired-code
list, and the enforcement list are preserved as the reference section. All
in-source references to the old filename were updated, and
`docs/user-diagnostics-guide-en.md` now points at it as the full reference.

The comparison section is grounded in measurement rather than assertion: the two
Faust MCP servers in use today (`orlarey/faustcode`,
`grame-cncm/faustbrowser-mcp`) both compile through `libfaust-wasm`, and were
queried directly to record what an agent actually receives — one opaque C++
string per failure, with no location at all for a composition error.

Writing the examples surfaced three real defects, fixed here rather than
documented as-is:

- signal-typing errors carried facts but no `cause`/`rule`/`computed` notes and
  no help, so they read worse than every other family despite G7 requiring the
  opposite. `InferenceRule` now owns a `statement()` and a `help()` next to the
  check that enforces it, and the compiler renders them.
- a binary math-domain error reported the *numerator's* interval as the computed
  value, because `actual_interval()` returns the first operand. Added
  `InferenceError::actual_intervals()` and render every operand interval, so
  `_ % 0` now names `interval(0,0,0)` as well.
- the rename fix for a misspelled entry point ran backwards and emitted a no-op
  edit (`proces` → `proces`). A missing entry point is a misspelled
  *definition*, so the edit now renames it to the entry point (`proces` →
  `process`); a guard also drops any fix that would replace text with itself.
- structural and recursive-group typing failures are now categorized
  `compiler_bug` rather than `user_code`, since they are internal invariants.

## Plan consolidation of custom CLI parsers

Commit date: 2026-07-28

Source commit: `0054dcaf`

Added
`porting/cli-parser-consolidation-analysis-and-porting-plan-2026-07-28-en.md`
in response to the code-review concern about multiple custom CLI argument
parsers.

The analysis confirms that the production compiler already follows the desired
legacy-normalization-then-Clap model, while the main debt is concentrated in
the two impulse runners, the `xtask` dispatcher and its command-local parsers,
and several developer binaries/examples. It separately classifies FFI
`argc`/`argv`, already-received compiler options, data-format parsers, and the
dependency-free impulse architecture as non-process-CLI protocols that must
not be migrated blindly.

The C0-C4 plan covers semantic baselines, runner migration, a typed Clap
subcommand tree for `xtask`, secondary tools, and a CI policy check. It
preserves successful and legacy Faust invocations while proposing standard
Clap diagnostics and exit status for invalid command lines. The public mapping
is 1:1 for successful workflows, adapted for invalid CLI behavior, and
unchanged for the FFI argument protocol.

Documentation validation: reviewed all direct `std::env::args` consumers and
known `xtask` option loops; verified repository-relative paths and
`git diff --check`.
