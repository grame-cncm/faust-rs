## WP6 and W2: one deadline rule, zero disables it, a timeout is a diagnostic in JSON too (`FRS-COMP-0008`)

Commit date: 2026-10-10

Source commit: this commit

WP6 of the
[runaway-recursion plan](../eval-runaway-recursion-and-cycle-diagnostics-analysis-and-plan-2026-10-10-en.md),

## WP2: constant folding keeps its caches for the evaluation pass

Commit date: 2026-10-10

Source commit: this commit

Second work package of the
[runaway-recursion plan](../eval-runaway-recursion-and-cycle-diagnostics-analysis-and-plan-2026-10-10-en.md),
decision D3. Each fold of a pattern argument (C++ `isBoxNumeric`) validated,
typed, propagated and simplified the whole expression from empty caches,
where C++ 2.84.3 memoizes every step on the trees. A recursion whose
argument grows by one node per level was therefore quadratic.

- `propagate::FoldSession` keeps the arity cache, the propagation memo
  (results, free slots), the slot-environment and UI-path interners, the
  clock-domain table and the set of validated boxes from one fold to the
  next. `propagate::propagate_fold` uses it. It builds no UI program, and
  widgets get a placeholder control id (`FOLD_CONTROL_ID`, through
  `PropagateContext::control_id`): a fold only asks whether the outputs are
  numbers, and all callers use only that. A box with inputs is refused
  before propagation touches the caches. A failed propagation resets the
  session. The result memo's warm-up (1 024 calls) happens once per session
  instead of once per fold.
- `normalize::ConstSimplifyCache` and `try_simplify_const_cached` keep the
  simplification of the empty type context across calls, cleared after a
  division-by-zero unwind, which leaves in-progress sentinels.
- `eval::simplify::FoldCache` bundles both and is owned by `LoopDetector`.
  The three hot paths use it: the folds of `apply_pattern_matcher_value`
  (`box_simplification_in`, `simplify_dispatch_argument`), the matcher's own
  fold (`apply_pattern_matcher_internal`), and the patterns of rules,
  evaluated again at each application (`case::pattern_simplification`).
  Other callers keep a fresh cache per call.

Release, before / after / C++ 2.84.3: `g(n-1, x-1)` with `x` a slider at `n =
2000, 4000, 8000`: 7.9 s, 35 s, - / 0.05, 0.10, 0.19 s / 0.04, 0.08, 0.16 s.
`chain(hslider(...))`: 120 s timeout / `FRS-EVAL-0012` in 0.09 s / `stack
overflow in eval` in 0.11 s. Generated code is unchanged (`golden-check`).
Registry `DIFF-BEH-005`. Test: `folding_a_growing_argument_is_linear` in
`loop_detector.rs`, 2 000 levels within 60 s in debug (0.2 s now). The
compile-budget basket is not extended: its gate cannot measure on this machine
(calibration below its floor).

## WP4: the evaluator's catch-all cause is left to internal forms

Source commit: this commit

Fourth work package of the
[runaway-recursion plan](../eval-runaway-recursion-and-cycle-diagnostics-analysis-and-plan-2026-10-10-en.md).
Every `EvalError` variant without a diagnostic arm got "cause: evaluator
reached an unsupported or malformed intermediate form". WP3 gave
`LoopDetected` its own arm. Four other variants that a program, the API or a
run causes now have their own:

- `NotAConstantExpression`: the expression must fold to a number at compile

- `Cancelled`: the `--timeout` limit or the host, with help.

  required; the parser rejects both in source, so the box came from the API.

The catch-all now covers internal forms only (`Malformed*`,
`EmptyArgumentList`, `InternalError`) and says "internal". Registry
`DIFF-BEH-005` updated, with links to `DIFF-BEH-017`/`018`. Test:
`the_catch_all_cause_is_for_internal_forms_only` in `error.rs`.

## Parser: a definition is located at its name, even when the name is used earlier

Commit date: 2026-10-10

Source commit: this commit

Found while labelling the definitions of an evaluation cycle (WP3 of the
runaway-recursion plan). Identifiers are hash-consed, so the parser tells the
occurrences of a name apart by the origins it records. `set_def_prop_at_cursor`
located a definition at the first use of its name recorded since the name's
previous definition. When a name is used before it is defined, that use
belongs to another definition: in `a = b + 1; b = c * 2; c = a;`, `b` was
"defined" at 1:5 and `c` at 2:5, and every "definition site" label for them
pointed there.

The grammar now notes the occurrence it reads as a definition name (`DefName`
through `definition_name_from_token`, `RecName` through `note_definition_name`)
on a stack in `ParserCtx`. `set_def_prop_at_cursor` takes it when the
definition is complete. A definition nested in a `with` is pushed and popped
before the enclosing one. A definition that a syntax error turned into a
recovery statement leaves its entry behind. The search takes the newest entry
of the name being defined and drops those above it, so a leftover entry never
matches. The previous heuristic remains the fallback.

Tests: `crates/parser/tests/definition_locations.rs` (top level, `with`
block, after a syntax error).

## WP1 (#21): a recursion on a non-constant numeric-pattern argument is named (`FRS-EVAL-0012`)

Commit date: 2026-10-10

Source commit: this commit

First work package of the
[runaway-recursion plan](../eval-runaway-recursion-and-cycle-diagnostics-analysis-and-plan-2026-10-10-en.md).
`fi.bandpass(q, fc, fc)` with `q` a slider, and the minimal programs of the
plan, now report:

```text
error [FRS-EVAL-0012] recursion does not reach its base case: argument 2 is matched against the numbers 0 and 1, but is not a compile-time constant
  = note: computed: argument 2 is a signal that depends on `hslider("Q", 1, 0.5, 20, 0.01)`, matched against the rules (s, 0, Nh, fl, fu), (s, 1, Nh, fl, fu), (s, O, Nh, fl, fu)
```

before, `FRS-EVAL-0099 stack overflow in eval` with help about a missing base
case.

- `apply_pattern_matcher_value` folds the argument once
  (`simplify_dispatch_argument`) and records each dispatch on numeric

  `apply_pattern_matcher` now takes the folded argument; it has one caller.

- Code `FRS-EVAL-0012` (decision D1). Registry `DIFF-BEH-017`; codes

## Analysis and correction plan: runaway recursion and evaluation cycles (#21, #22)

Commit date: 2026-10-10

Source commit: this commit (analysis of `20669a61`; no source change)

Wrote the English
[analysis and correction plan](../eval-runaway-recursion-and-cycle-diagnostics-analysis-and-plan-2026-10-10-en.md)
for [#21](https://github.com/grame-cncm/faust-rs/issues/21) (a non-constant
filter order reports a depth-budget error) and
[#22](https://github.com/grame-cncm/faust-rs/issues/22) (an evaluation cycle
gets the catch-all "malformed intermediate form" cause). Eighteen minimal
programs and cost cases were compiled with C++ 2.84.3 (`8eebea429`), C++
2.90.6, and faust-rs.

Findings:

- #21 is a recursion whose argument, matched against numeric patterns, is a
  signal. Both compilers only report a stack overflow. The structural guard
  fires, and the evaluator never records the non-numeric dispatch that names
  the cause.
- Folding a pattern argument is not memoized across calls in faust-rs, where
  C++ 2.84.3 memoizes it at four levels. A growing argument makes the
  recursion quadratic. The simplest #21 programs then run into the 120 s
  timeout in release, and a valid program (`g(n-1, x-1)`, `n = 4000`) takes
  35 s, against 0.1 s in C++ 2.84.3.
- C++ `master-dev` regressed in the same way in `536ff8ca7`. Building the C++
  compiler before and after that commit, and with the memo clearing disabled,
  established the cause. Reported upstream as
  [grame-cncm/faust#1345](https://github.com/grame-cncm/faust/issues/1345),
  with a growth criterion proposed for its `tests/TESTING.md`.
- #22: the cycle is on the call stack when it is detected (`process → effect →
  cut → process`), but `LoopDetected` has no diagnostic arm.

The plan has six work packages (WP1 to WP6) and five decision points (D1 to
D5). A prototype of WP1 exists in the working tree, uncommitted. #16 is fixed
by `2d477161` but still open.

## Tutorial figures follow two library changes; the tutorial explains why they can

Commit date: 2026-10-10

Source commit: `8fb34c4507e24e3b059813d0692749da466c88f0`

Two tests of `crates/cranelift-ffi/tests/tutorial_examples.rs` failed against
faustlibraries `69cc662a` and passed with `9c421426` (2026-10-01). Bisected
over the library commits:

- `s13_2_a_rate_per_slider_learns_both`: `ff4c711d` realizes `tf1s`, hence
  `fi.lowpass(1, fc)`, as a trapezoidal integrator. The transfer function is
  the same, but the learned cutoff moves `fc` at every update, and the cutoff
  at 10 000 samples went from 2574.69 to 2574.73. The end point is unchanged.
- `s13_1_energy_gradient_rad_against_fad`: `b137daed` corrects
  `os.sawtooth` (`saw2ptr`: DC offset `f/SR`, transition sample), the
  program's input. The `drive` gradient went from 20.944 to 20.945, quoted
  20.95.

Both library changes are deliberate. The two figures are updated in the test
and in both tutorials. A new section 0.1, in English and French, explains to a
reader new to `fad`/`rad` why learning is sensitive to fine changes in the
libraries: the derivatives are those of the code as written, so a new
realization, a corrected signal, or a bound (whose derivative is zero beyond
it) moves a descent. It says what to compare first and how to find the
change. A pointer was added in 13.2, and the walls table got a row and a
completed cause. The test module header says what to do when an update of the
libraries fails a test.

## `--version` and the diagnostics JSON name the build's commit

Commit date: 2026-10-10

Source commit: `58bee35b6fc48ad1386ce7dd9628057efb1b797d`

[grame-cncm/faust-rs#20](https://github.com/grame-cncm/faust-rs/issues/20):
the workspace version only changes at a release, so the `0.8.0` tag and the
282 later commits of `main` all reported `faust-rs 0.8.0`, and a downstream
project could not check which commit a binary came from.

`crates/compiler/build.rs` records the full hash of `HEAD` and its committer
date (`FAUST_RS_COMMIT`, `FAUST_RS_COMMIT_DATE`), exposed as
`Compiler::commit()` and `Compiler::commit_date()`. It reports nothing outside a
Git checkout of this repository (a source archive, no `git`). It reruns when
`HEAD`, `packed-refs` or `refs/heads` change, and watches only existing paths,
since a missing one would rerun it on every build: an empty rebuild compiles
nothing. A commit or checkout recompiles `compiler` and its dependents.

- `--version` prints `faust-rs 0.8.0 (2199d069 2026-10-06)`, as `rustc` and
  `cargo` do. Without a commit, `faust-rs 0.8.0` as before.
- The diagnostics-v2 `compiler` block gains optional `commit` (full hash) and
  `commit_date`, present together; the schema declares them, with
  `dependentRequired`, and `assert_diagnostics_v2_shape` checks them.
- Generated code still names the package version only, so the output of a
  program does not change from one commit to the next.
- C++ Faust prints the commit on a second line, `Source commit: <hash>`, with
  `-modified` and `unknown`; the user chose the `rustc` form. Uncommitted
  changes are not reflected. Registry: `DIFF-CLI-013`.

The CLI transcript harness normalizes the commit on the `--version` line, and
`faustprobe`'s snapshot masks `commit`/`commit_date` like `target`. Only
`version.txt` and `compile_error_json.txt` were re-recorded. The 56 other
transcripts that differed already at `2199d069` (include-path order, generated
code) were left as they were.
