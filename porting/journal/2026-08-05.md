# 2026-08-05

## Guard lifecycle functions against leaking into backend output

Commit date: 2026-08-05

Source commit: this commit

The same mistake was made independently in the `c`, `rust` and `julia`
backends: each walks its `functions` block and emits whatever it does not
recognize, and none recognized `staticInit`, so each emitted it a second time
alongside the `classInit` it had already been rendered into. Not a cosmetic
duplicate — the `staticInit` body allocates a generator and fills a table using
locals that exist only inside `classInit` (lock guards, in Rust), so the stray
copy either fails to compile or writes somewhere it should not.

Three occurrences is a pattern, and `asc` and `cmajor` are still to come. Two
pieces instead of a fourth per-backend fix.

`backends::is_lifecycle_function` is the single list to consult, replacing three
hand-maintained `matches!` arms that had drifted apart. The doc comment records
why the list exists rather than just what is in it.

`crates/compiler/tests/lifecycle_leak_guard.rs` is what catches a backend that
forgets. It compiles one DSP whose table is filled at initialization — so the
module necessarily declares `staticInit` — through every backend, and asserts
the name never reaches the output. Backends that still refuse generated-table
sub-modules are skipped by detecting their own refusal message, so migrating one
brings it under the guard with no edit to the test.

A second test asserts the complement, because a backend that renders
`staticInit` nowhere at all would also pass the first: the table must actually
be written. That property has to hold across both emission shapes — a nested
backend calls `fill<Sub>(…)`, a flattened one inlines the loop — so the check is
that something assigns into the table, not that a particular call appears. The
first version counted occurrences of "fill" and failed on `julia`, which inlines
and never mentions the word; the count was a proxy for the property rather than
the property.

Verified by removing `staticInit` from the shared list and watching the guard
fail on `c`.

Commit date: 2026-08-05

Source commit: this commit

`subcontainer1.dsp` matches the C++ oracle under `-lang julia -double
--table-init runtime`, and the julia impulse gate stays at 93/93.

The reference corrected the plan. §5.9 listed `julia` under "native

teaching the emitter which tables moved, `promote_static_tables_to_struct`

knowledge. That is also the adaptation the Cmajor plan documents for the same
reason, so it should serve twice.

`staticInit` leaked through a catch-all function loop for the third time, after
`c` and `rust`. Three occurrences of one mistake is a pattern, not a
coincidence: a shared guard would be better than a fourth per-backend fix.

Two mistakes of mine, both caught by a warning I nearly dismissed. I applied a
fix believing I was patching `promote_static_tables_to_struct` when the
`str.replace` matched nothing at all — `cargo fmt` had reflowed the source — and
only noticed because the clippy warning survived instead of disappearing. That
warning was flagging a real latent defect: the promotion pass discarded
sub-modules instead of carrying them across. It normally runs after flattening,
where none are left, so nothing failed; it would have silently dropped a
generator the first time the order changed.


## Emit generated-table sub-containers from the rust backend (S4b, rust)

Commit date: 2026-08-05

Source commit: this commit

`-lang rust --table-init runtime` emits the upstream shape: a `mydspSIG0`
struct with its two methods, a `newmydspSIG0()` constructor, and a `class_init`
that allocates, initializes and fills. No destructor — the sub-container is a
local of `class_init` and drops on its own, which is why upstream skips
`delete` for this backend too. `subcontainer1.dsp` matches the C++ oracle.

Rust has no safe mutable static, so a runtime-filled table becomes
`std::sync::RwLock<[T;N]>`, as upstream does: `class_init` takes a write guard,
every body that reads a table takes a read guard, and table references name the
guard rather than the static. That last part is what made this backend bigger
than `cpp`, where a mutable static is free — the lock-aware reference has to
reach the value emitter, so the set of locked tables is computed once per module
and threaded through `emit_value` and its helper chain (29 call sites). Folded
tables under `--table-init const` are immutable and stay outside the set,
untouched.

Two things worth recording.

`staticInit` leaked as a free function through the catch-all loop, referencing
guards that only exist inside `class_init` — the same double-emission as in the
C backend, caught here by `rustc` rather than by reading the code.

And a mistake of my own, worth more than the bug: my first numeric comparison
failed at line 30000 with 44100 against 176400, and I nearly recorded it as a
table-refresh defect. The comparison was wrong, not the backend. The Rust
architecture is single-pass (`dsp.init(SAMPLE_RATE)` once) while the reference
`.ir` comes from the C++ four-pass oracle with a sample-rate sweep, which is
exactly why `Make.rust` compares the first 15000 frames with
`filesCompare -part`. I ran my own command before reading the harness contract.
Under the contract the backend matches.


## Migrate codebox to generated-table sub-modules (S4b, codebox)

Commit date: 2026-08-05

Source commit: this commit

`codebox` is the first backend to consume the S3 flattening pass. Its two
blockers are gone — its own static-table defect (`1f9b3ca3`) and the S2
scheduling hole (`e563451b`) — so the migration is what the plan predicted:
call `flatten_sub_modules_owned` with `StackLocals` before decoding, drop the
guard.

Validated numerically rather than structurally. The codebox evaluator runs the
emitted program, and the two `--table-init` modes are compared frame by frame
on the same source: `const` folds the generator into a literal table, `runtime`
inlines the generator and fills the table in `dspsetup`, and the outputs must
agree. Two fixtures, one constant and one whose carrier is read a sample late —
the shape that was silently producing zeros until this morning. The comparison
also asserts the signal is not all zeros, since two empty tables would agree
vacuously.

One emitter fix was needed: the flattened generator state arrives as
`DeclareVar` with no initialiser, and `let x : Int;` does not parse — the
grammar wants an initialiser on `let` just as it does on `@state`, which the
emitter already handled for the `@state` case only.

Line counts on a 65536-entry constant table: 65 572 folded against 42 filled.
Codebox is the backend where the sub-module form pays most, because it has no
array literal and folding costs one assignment per element — the opposite of
the intuition that a language this restricted would benefit least.


## Schedule table generators so their recursion carriers advance

Commit date: 2026-08-05

Source commit: this commit

Closes the S2 producer defect recorded in the previous entry. A generator whose
recursion carrier is read **only through a delay** produced a fill loop that
read the carrier and never advanced it, so every table entry kept the initial
value: `rdtable(64, int(ba.time * 2), …)` filled with zeros instead of
0, 2, 4, 6…

A generator is an ordinary 0-input program and needs the same dependency
scheduling as any other. `build_module` drives recursion-group emission through
`lower_scheduled_graph`, which no-ops when `scalar_schedule` is `None`, and
`build_generator_sub_module` passed `None` — so the group was only ever reached
through `lower_output_signal`, which lowers the delayed read without
materializing the group's update.

The fix runs the same `hgraph` gate the main pipeline runs, on the wrapper-free
branch since a generator carries no clock domains: `clk_env::annotate`,
`build_hgraph`, `analyze_scalar_scheduling_effects`, `orient_effect_conflicts`,
`schedule`. The scheduling strategy is threaded through `build_module` so a
generator is scheduled the same way as the program that owns it, rather than
silently defaulting.

Verified on the emitted code, not just the FIR: the fill body now reads

```cpp
for (int i0 = 0; i0 < count; ++i0) {
    int iRecCur10 = (iRec10 + 1);
    table[i0] = (2 * iRec10);
    iRec10 = iRecCur10;
}
```

and the compiled DSP outputs `0 2 4 6 8 10 12 14`. `subcontainer1.dsp` still
matches the C++ oracle sample-for-sample.

The new regression fixture is the shape none of the earlier ones had: a counter
consumed one sample late. It asserts the fill body contains at least one store,
since reading a carrier without writing it is exactly the defect, and it fails
as expected when the schedule is withheld again.


## Fix a dangling-clone bug in the flattening pass, and stop S4b on an S2 hole

Commit date: 2026-08-05

Source commit: this commit

Two real bugs, both found by trying to migrate `codebox` onto the flattening
pass rather than by any test written for it.

### `flatten_clone_body` discarded everything it cloned

Source and destination are the same store, which the cloner cannot borrow
twice. The version I shipped in S3 took the store out, cloned into the now-empty
store, then restored the source over it — discarding every node just written and
leaving the returned id dangling. It now clones into a scratch store, restores
the source, and re-interns the result through `FirStore::import_from`.

The S3 tests passed against that broken output. `match_fir` decodes a dangling
id as `Unknown`, and `verify_flattened` only looked for surviving sub-modules,
allocations and calls — so it walked straight past nodes that no longer existed.
`codebox` is what surfaced it, by refusing `statement Unknown`. `verify_flattened`
now reports any node that fails to decode, and reintroducing the bug makes the
S3 fixtures fail as they should have from the start.

### `codebox` also needed `staticInit` in `dspsetup`

Its setup emitter iterates lifecycle bodies by name and did not know
`staticInit`, so the flattened fill was dropped even once the clone was intact:
the table was declared and never written. Added, ordered first, since nothing
may read a table before it is filled.

### And then the actual blocker

With both fixed, the flattened output is structurally right — generator state as
locals, a count local, a real fill loop — but numerically wrong. On
`rdtable(64, int(ba.time * 2), …)` the loop body is
`itbl0mydspSIG0_cb[i] = imul(2, mydspSIG0_iRec10_cb);` with no update of
`mydspSIG0_iRec10_cb` anywhere, so all 64 entries would be 0 rather than
0, 2, 4, 6…

This is not a codebox or flattening problem: `-lang cpp --table-init runtime`
emits the same `table[i0] = (2 * iRec10);`. It is an S2 producer defect. A
generator whose recursion carrier is read **only through a delay** never gets
its carrier update emitted, because `build_module` drives recursion-group
emission through `lower_scheduled_graph`, which no-ops when `scalar_schedule` is
`None` — and `subcontainer.rs` passes `None`. The main pipeline builds that
schedule with the `hgraph` gate before calling `build_module`; the sub-module
lowering has to do the same. The identical DSP compiled as a main program is
correct, which is what made the difference visible.

It escaped S2 and S4a because the fixtures checked numerically read their
recursion directly (`os.osc`) or have no recursion at all (`subcontainer1`,
which is `ma.SR`). Both still match the C++ oracle.

So S4b stops here and the `codebox` guard goes back on. Migrating backends onto
a producer that can emit a silently wrong table would spread the defect instead
of containing it — the same reasoning that kept the guard on when codebox could
not emit static tables at all.


## Emit generated-table sub-containers from the c backend (S4a complete)

Commit date: 2026-08-05

Source commit: this commit

`-lang c --table-init runtime` now emits the reference C shape: a
`typedef struct` holding the generator's state, `calloc`/`free` allocation
helpers, the two entry points as `static` free functions taking the struct as
their first parameter, and a `classInit<Class>` that allocates, initializes,
fills and frees. `subcontainer1.dsp` matches the C++ oracle sample-for-sample
under `-lang c -double --table-init runtime`, as it already did for `cpp`.

The `dsp->` receiver seam I expected to have to build turned out to already
exist. Sub-module state is `AccessType::Struct`, which `emit_var_ref` renders
as `dsp->field`, and `dsp` is exactly what these free functions receive — so
the generator's body needed no rewriting at all. What the C backend actually
needed was smaller than the estimate: struct/helper emission, a `NewDsp` value
arm, and skipping `staticInit` in the catch-all function loop.

Emitted sizes against the C reference: `f01_osc_table` 4 011 vs 5 151 (77%),
`f03_sr_dependent` 3 830 vs 5 065 (75%), `f04_rwtable_seeded` 3 818 vs 5 053
(75%), `f08_nested_tables` 4 686 vs 5 022 (93%).

One assumption I got wrong and had to correct from the output rather than from
the code: I claimed the C backend emits only known DSP API functions by name
lookup, so `staticInit` could not leak. It has a catch-all loop after the named
ones, and `staticInit` was emitted a second time as
`static void staticInit(void** dsp, int sample_rate)` — a duplicate of the
`classInit` body with the wrong receiver type. Visible immediately in the
generated file, invisible in the reasoning.

Also adds `fir::subcontainer::flatten_sub_modules_owned` and `has_sub_modules`.
Backends receive `&FirStore` and cannot mutate it, so a backend that wants the
flattened form needs a variant that imports into its own store first. These
land now because S4b needs them, even though no backend consumes them yet.

### `codebox` is blocked, and the guard stays

Starting S4b on `codebox` — the one backend the plan assigns to the flattened
form — the wiring worked on the first try: the generator inlines, the module
emits, no sub-module error. But the output reads a table nobody declares. On
`rdtable(65536, 0.5, …)` the emitted program contains
`output0_cb = ftbl0mydspSIG0_cb[imod(iRec26_cb, 65536)];` with zero
declarations of that symbol and zero occurrences of the constant `0.5`.

Checked against the commit before this port, in `const` mode: same picture —
a read of `ftbl0_cb`, no declaration, no data. So `codebox` has never emitted
`static_decls`, independent of generated tables.

That makes removing its sub-module guard the wrong move: it would replace an
explicit refusal with a program that silently reads an unfilled table, which
is the exact failure mode this port exists to prevent and which rule FIR-SM01
forbids at the FIR level. The wiring is reverted, the guard stays, and the
static-table defect is filed as its own task. Once fixed, the migration is
five lines.


## Emit generated-table sub-containers from the cpp backend (S4a, cpp part)

Commit date: 2026-08-05

Source commit: this commit

`-lang cpp --table-init runtime` now emits the reference shape: a nested
`mydspSIG0` class holding the generator's state and its two entry points,
`new`/`delete` helpers, an uninitialized non-const file-scope table, and a
`classInit` that allocates, initializes, fills and releases the sub-container.
`c` still refuses with its S1 guard and is the next step — its sub-module state
needs the `dsp->` receiver seam, which is a different mechanism from C++'s bare
field access.

The result that matters: `subcontainer1.dsp` compiled with
`-lang cpp -double --table-init runtime` **matches the C++ oracle
sample-for-sample** under the impulse harness comparator. That fixture is the
canonical upstream test for sample-rate-dependent table content and has been a
`KNOWN_FAIL_all` entry for the whole project. Removing the entry waits for S7,
when `runtime` becomes the default.

Sizes against the reference, previously 330x and 124x too large:

| Fixture | Reference | faust-rs | ratio |
|---|---:|---:|---:|
| `f01_osc_table` | 4 301 | 3 818 | 88% |
| `f03_sr_dependent` | 4 285 | 3 650 | 85% |
| `f04_rwtable_seeded` | 4 253 | 3 632 | 85% |
| `f07_constant_content` | 3 175 | 2 992 | 94% |
| `f08_nested_tables` | 4 218 | 4 337 | 102% |
| `f12_two_generators` | 4 586 | 4 021 | 87% |

`f08` being *larger* than the reference is the interesting row: we emit two
filler classes and fill both tables, upstream emits one and leaves the inner
table zero (§2.4). The extra bytes are the defect not being reproduced.

Four emitter details were needed beyond the class itself, each found by diffing
against the frozen reference rather than by reasoning:

- Sub-container entry points are methods, so their explicit `dsp` receiver is
  stripped exactly as for the DSP API methods — otherwise the signature reads
  `void instanceInitmydspSIG0(void** dsp, int sample_rate)`.
- A sub-container handle is typed by the class it allocates: `mydspSIG0* sig0`,
  not the `void**` the FIR `Ptr(Obj)` would render to.
- `NewDsp` renders as the `new<Sub>()` helper call, not as `new <Sub>()`.
- A dropped void call is a statement, not a discarded value. The generic
  `(void)(...)` wrapper is wrong for it, and the call spelling differs per
  language — `sig0->fill…(…)` in C++ versus `fill…(sig0, …)` in C — so the
  shared statement emitter gained a `render_void_call` seam rather than a
  language-specific special case buried in it.

The S1 fail-closed test for `cpp` was replaced rather than deleted: it now
asserts the positive shape — nested class, both helpers, an uninitialized
non-const table, the four `classInit` statements in order, and that
`staticInit` never leaks out as a method of its own.


## Flatten generator sub-modules for non-nesting backends (S3)

Commit date: 2026-08-05

Source commit: this commit

`fir::subcontainer::flatten_sub_modules` inlines a table generator into the
program that calls it, replacing the allocate/init/fill triple with the
sub-module's own bodies. This is the port of the C++
`inlineSubcontainersFunCalls` + `DspRenamer` + `mergeSubContainers` trio, which
upstream applies for the backends that cannot express a nested container. Two
state policies: `StackLocals` demotes the generator's state to locals of the
initialization function (what a target with a `static classInit` needs, since a
static method has no instance to hold fields), `MergedStructFields` keeps it in
the DSP struct under a prefixed name (what `interp` and `wasm` need, their
`classInit` being instance-scoped). Names are prefixed either way: a sub-module
is lowered with its own fresh counters, so its `iRec0` has nothing to do with
the enclosing program's.

The pass reuses the inliner's hygienic clone engine instead of duplicating a
50-arm traversal. Two small generalizations were needed there:
`fun_arg_subst` went from `name -> name` to `name -> (name, AccessType)`, and a
`struct_subst` map was added. The reason is specific: `prepare_callee_body_for_inlining`
materializes every parameter into a stack temp, but a flattened `fill` must
write into the caller's *own* table, which lives in `Static` or `Struct`
storage — so the access class has to travel with the substituted name rather
than being assumed.

The tests run the real S2 producer and flatten its output rather than
hand-building a module. That mattered immediately: `verify_flattened` — written
as an independent check, not as a mirror of the pass — failed on the nested
fixture with "allocation of 'mydspSIG0SIG0' survived flattening". Two causes,
both mine. First, I resolved which sub-module a call belonged to via its
receiver object, but the clone engine hoists `NewDsp` out of its declaration
into a standalone statement, so the receiver map was never populated for the
nested case; resolving from the callee name instead is stable under cloning.
Second, splicing a sub-module's `instanceInit` can introduce a *new*
allocate/init/fill triple, for a generator nested one level deeper, so the
inlined statements have to go through the rewrite again.

S3 also exposed a defect in the S2 producer that the S2 tests had not: fill
bodies carried the DSP path's `output0 = outputs[0]` channel aliases, which
reference an `outputs` parameter that a `fill(dsp, count, table)` signature
does not have. It was invisible until flattening spliced those statements into
a function where the checker could see them. Fixed by not emitting the aliases
when lowering a fill module.

## Compile table generators into sub-modules (S2 producer)

Commit date: 2026-08-05

Source commit: this commit

The second half of S2: `--table-init runtime` now compiles every `SIGGEN`
payload into its own FIR sub-module whose `fill` computes the table content at
initialization time. `const` stays the effective default until S7, so nothing
observable changes for existing users yet.

The milestone is coverage, not size. The three programs that previously could
not be compiled at all — `subcontainer1.dsp` (`ma.SR` inside the generator), a
sample-rate-dependent `exp(-t/SR)` table, and an `ffunction` generator — now
lower successfully and stop at the S1 backend guard with `FRS-CGEN-CPP-0003`
instead of `FRS-SFIR-0004`. Those values do not exist at compile time; the only
way to express them is to compute them at init, which is what the sub-module
does.

Shape checks on the S0 fixtures: one sub-module per generator, one for two
reads of the same generator tree (`f11`), `mydspSIG0`/`mydspSIG1` for two
distinct ones (`f12`), three for the mixed-type probe (`f13`), and
`mydspSIG0SIG0` nested inside `mydspSIG0` for `f08` — matching the upstream
naming convention, nesting suffix included.

Mechanically the generator goes through the same `build_module` as the main
program, with an output sink redirecting the single output to `table[i0]` at the
sub-module's element type and no `FaustFloat` cast (C++ `compileSingleSignal`
pushes exactly that store). Recursion carriers, delay strategies, CSE and
scheduling are reused untouched. The result is lowered into its own `FirStore`
and imported through the `FirStore::import_from` added in S1. The parent emits
the C++ sequence — allocate the sub-container object as a stack local,
`instanceInit`, `fill` — with deallocation left to the backends, since it is
bound to how each language allocates and upstream itself skips it for Rust,
Julia and AssemblyScript.

Two bugs are worth recording; both were silent-wrong-answer shaped.

First, `assemble_sub_module` read its nested sub-modules from the caller's
`FillSpec`, which is always empty at that point, instead of from the recursive
lowering's own accumulator. Nested generators were dropped entirely.

The second is the instructive one. A sub-module's `instanceInit` was assembled
from constants + reset + clear, mirroring C++ `generateInstanceInitFun`. But a
sub-module has no `classInit`, so the fill call for a *nested* generated table —
which the recursive lowering had correctly placed in `static_init_statements` —
had nowhere to go and vanished. That yields an inner table declared and never
written, and an outer table computed from zeros: precisely the upstream 2.87.1
defect that §2.4 of the plan documents and that contract C5 exists to avoid. I
wrote the plan warning about this defect and then reproduced it anyway, which is
a fair argument for writing the checker before trusting the producer. Fixed by
prepending `static_init_statements` to the sub-module's `instanceInit`, and
locked by a new rule FIR-SM05 — verified by reintroducing the bug and watching
it fire:

```
error: sub-module 'mydspSIG0' owns nested generator 'mydspSIG0SIG0' but never
calls 'fillmydspSIG0SIG0' from 'instanceInitmydspSIG0'; the nested table would
be read uninitialized
```

FIR-SM01 also had to be reformulated. As first written it flagged any
uninitialized array read by `compute` with no fill call, and fired immediately
on ordinary delay lines (`iVec6`) — also uninitialized arrays, but zeroed by
`instanceClear` rather than filled. It now keys on the sub-module (every
declared sub-module must have its fill called): precise, producer-independent,
and still failing on the drop-the-call mutation.

## Adopt upstream table naming (S2 rename step)

Commit date: 2026-08-05

Source commit: `c093e424`

Naming-only step at the head of S2, deliberately separate from the semantic
change that follows so a later bisect can tell "renamed" from "changed".
Literal waveform tables become `{i|f}{module}Wave{j}` with a matching
`{name}_idx` cycling field; generated tables become `{i|f}tbl{k}`. Both counters
are allocation-ordered and shared across element types, matching C++
`getTypedNames`, where the `i`/`f` letter is a prefix rather than part of the
counter key.

Waveform output is now identical to the reference compiler — `fmydspWave0[3]`,
`imydspWave1[3]`, `fmydspWave0_idx` — the first place where the two compilers
agree character for character.

Generated tables match in form but not always in counter order: on
`f13_mixed_type_tables` upstream allocates `itbl0`(64), `ftbl1`(32), `itbl2`(16)
in program order while faust-rs allocates `ftbl0`(32), `itbl1`(64), `itbl2`(16).
Both compilers order the counter by allocation; what differs is when each one
first materializes a table during lowering. Stable across runs, no semantic
effect, recorded in plan §5.6 as a residual for S4a to note rather than a defect
to fix — closing it means aligning traversal order, a separate concern.

## Add the FIR sub-module node and its checker rules (S1)

Commit date: 2026-08-05

Source commit: this commit

S1 of the sub-module table-init plan: the FIR model now has somewhere to put a
table generator, and a checker that refuses the shapes which would silently
produce a zero-filled table. No producer yet — `faust-rs` emits byte-identical
output to the S0 baseline (`f01_osc_table` still 1 420 248 bytes), which is the
intended end state for this phase.

Added `FirMatch::SubModule` (tag `FIRST_SUBMODULE`) carrying name, element type,
its own state/static/global/function blocks, and nested sub-modules; `Module`
gains an eighth field `sub_modules`. `FirStore::import_from` wraps the existing
`TreeArena::clone_subtree_from`, which is what S2 needs to graft a generator
lowered in its own store into the parent one.

Four checker rules, each with a fixture that must fail when the rule is
disabled — verified by actually disabling them, not by assuming:

- SM01: a table declared without an initializer and read by `compute`, with no
  `fill` call in `staticInit`/`instanceConstants`. This is the rule that makes
  the upstream nesting defect impossible here.
- SM02: sub-module shape — exactly `instanceInit{name}` and `fill{name}`, all
  sections blocks, nested sub-modules recursively checked.
- SM03: `fill` signature (`count: Int32`, `table: Ptr(elem)`) and a body that
  writes only through its own `table` argument.
- SM04: sub-module name uniqueness across the whole nesting tree.

Two things went wrong and are worth recording.

The rule codes were first written as FIR-T01…T04, following the plan. They
collide: `FIR-T01`–`T04` are already the table-access rules (index type, store
element type, missing declaration) and `FIR-M06` is also taken. The mutation
tests still passed while the collision was live — they were matching a
pre-existing diagnostic, not the new one. Renamed to `FIR-SM01`…`SM04`, and the
plan updated to match. The lesson is the one the plan already states about
independent checks: a test that asserts on a shared identifier proves less than
it appears to.

`FirBuilder::module` takes `sub_modules: &[FirId]`, not a pre-built block, so
the ~100 existing call sites just append `&[]`. But the clone paths in
`fir::inliner` must clone the block's *items*, not the block node — passing the
cloned block would nest a block inside a block and break every consumer that
expects `sub_modules` to decode as a block of `SubModule`. Added
`clone_sub_modules` for that, after writing the bug first.

Every backend decoder now fails closed on a non-empty `sub_modules`, with its
own stable error code (`Unsupported`/`UnsupportedNode`/`CompilationFailed`
