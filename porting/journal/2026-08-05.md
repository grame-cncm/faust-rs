## Add the FIR sub-module node and its checker rules (S1)

Commit date: 2026-08-05

Source commit: this commit

S1 of the sub-module table-init plan: the FIR model now has somewhere to put a
table generator, and a checker that refuses the shapes which would silently
produce a zero-filled table. No producer yet — `faust-rs` emits byte-identical
output to the S0 baseline (`f01_osc_table` still 1 420 248 bytes), which is the
intended end state for this phase.

Added `FirMatch::SubModule` (tag `FIRST_SUBMODULE`) carrying name, element type,
its own state/static/global/function blocks, and nested sub-modules; `Module`
gains an eighth field `sub_modules`. `FirStore::import_from` wraps the existing
`TreeArena::clone_subtree_from`, which is what S2 needs to graft a generator
lowered in its own store into the parent one.

Four checker rules, each with a fixture that must fail when the rule is
disabled — verified by actually disabling them, not by assuming:

- SM01: a table declared without an initializer and read by `compute`, with no
  `fill` call in `staticInit`/`instanceConstants`. This is the rule that makes
  the upstream nesting defect impossible here.
- SM02: sub-module shape — exactly `instanceInit{name}` and `fill{name}`, all
  sections blocks, nested sub-modules recursively checked.
- SM03: `fill` signature (`count: Int32`, `table: Ptr(elem)`) and a body that
  writes only through its own `table` argument.
- SM04: sub-module name uniqueness across the whole nesting tree.

Two things went wrong and are worth recording.

The rule codes were first written as FIR-T01…T04, following the plan. They
collide: `FIR-T01`–`T04` are already the table-access rules (index type, store
element type, missing declaration) and `FIR-M06` is also taken. The mutation
tests still passed while the collision was live — they were matching a
pre-existing diagnostic, not the new one. Renamed to `FIR-SM01`…`SM04`, and the
plan updated to match. The lesson is the one the plan already states about
independent checks: a test that asserts on a shared identifier proves less than
it appears to.

`FirBuilder::module` takes `sub_modules: &[FirId]`, not a pre-built block, so
the ~100 existing call sites just append `&[]`. But the clone paths in
`fir::inliner` must clone the block's *items*, not the block node — passing the
cloned block would nest a block inside a block and break every consumer that
expects `sub_modules` to decode as a block of `SubModule`. Added
`clone_sub_modules` for that, after writing the bug first.

Every backend decoder now fails closed on a non-empty `sub_modules`, with its
own stable error code (`Unsupported`/`UnsupportedNode`/`CompilationFailed`
depending on what each enum already had) and a shared message pointing at
`--table-init const`. Three backends — cmajor, codebox, wasm — destructured
`FirMatch::Module` with `..` and would otherwise have compiled happily while
ignoring the field, emitting a table declaration that nothing fills. That is
the silent-wrong-answer failure this phase exists to prevent, so it gets an
explicit guard and a backend test rather than trust.

## Freeze the S0 baseline for SIGGEN table initialization

Commit date: 2026-08-05

Source commit: this commit

Ran S0 of the sub-module table-init plan: no code change, only the "before"
state frozen under `porting/generated/siggen-table-init-s0/` — thirteen
fixtures, their `faust 2.87.1` output in `ref/` (kept in full, it is the S4a
emission oracle), the current `faust-rs 0cb97dd7` output in `rs/`, and a
baseline document holding sizes, timings, structural counts and the impulse
measurement.

Three results changed the plan rather than just confirming it.

The impulse baseline is **93/93 on cpp, c and interp** — not the cpp 92/93,
c 87/93, interp 74/93 quoted by earlier porting documents and by the project
memory. Those figures are stale; nothing is failing today. The `93`
denominator survived only by coincidence: the corpus grew from 93 to 133
fixtures while 39 clock-domain DSPs (`ondemand_*`, `upsampling_*`,
`downsampling_*`, which upstream rejects with `undefined symbol : ondemand`
and which therefore have no C++ oracle) and `subcontainer1` were excluded,
landing back on 93 gated cases. Plan §8.2 layer 4 is restated from
"no regression against 92/93" to something exact: remove the
`KNOWN_FAIL_all := subcontainer1` line from `known.mk`, take the gate from 93
to 94 cases, and keep all three backends at 100%. There are no pre-existing
failures for a regression to hide behind.

Getting that number required stepping over the false-green trap already
recorded in memory. The first run of `make cpp && make c && make interp`
returned exit 0 in seconds with `Nothing to be done` — the `ir/` trees were
cached from an earlier session. The real measurement needed `ir/{cpp,c,interp}`
and `build/{cpp,c,interp}` removed first, keeping the expensive C++ oracle
cache in `reference/` and `build/ref/`. The evidence recorded is the surviving
`.ir` count rather than the exit code, since `Make.gcc`/`Make.interp` wrap each
comparison as `filesCompare … || (rm -f <ir>; false)`: 93 files means 93
comparisons passed.

Added a thirteenth fixture beyond the plan's twelve. §5.6 rule 1 — one `tbl`
counter shared by integer and real tables — had been inferred from
`getTypedNames` (`instructions_compiler.cpp:1040`) plus a same-type example,
which is not evidence. `f13_mixed_type_tables` produces `itbl0mydspSIG0`,
`ftbl1mydspSIG1`, `itbl2mydspSIG2`: the counter does advance across the type
change, so the `i`/`f` letter is a prefix and not part of the counter key.
Current output for the same program is `fTbl60`, `iTbl108`, `iTbl112` —
`SigId`-derived and unordered, the shape the S2 rename replaces.

Quantified the upstream nesting defect of plan §2.4 on `f08`: the reference
declares `static float ftbl0mydspSIG0SIG0[64]` and `static float
ftbl1mydspSIG0[64]` but emits only **one** filler class, and `classInit` fills
only the second. The inner table stays zero. faust-rs folds the same program
correctly to `{0.0f, 0.5f, 1.0f, 1.5f, …}`. `f08` is therefore a regression
guard, not a parity target — copying upstream there would copy a bug.

Sizes and timings re-measured slightly differently from the plan's figures
(330× rather than 333× on `os.osc`, 124.6× rather than 127× on the constant
table); the drift is the output path appearing in the metadata block. The
baseline document carries the re-measured values. Three `rs/` outputs exceed
32 KB and are stored head+tail with their full byte count inline — the elided
part is the folded literal list, whose size is the measurement.

## Specify SIGGEN table initialization through generated sub-modules

Commit date: 2026-08-05

Source commit: this commit

Asked to analyze replacing the compile-time table-generator interpreter
(`crates/transform/src/signal_fir/siggen.rs`) by the C++ reference mechanism:
compile the generator signal into its own sub-module whose `fill` function
computes the table content at initialization time (`signal2Container` /
`generateSigGen` / `generateStaticTable` upstream).

Probing the two compilers turned up more than the expected code-size argument.
`os.osc(440)` emits 4 261 bytes with `faust 2.87.1` and 1 420 238 with
`faust-rs 2cffc4a3` — a 333× ratio, because the 65536-entry table is folded
into a literal initializer list; the `rwtable` case is 22× and additionally
stores the content twice (static companion array plus per-instance copy). But
the decisive finding is functional: sample-rate-dependent and `ffunction`
generators cannot be folded at all and are rejected with `FRS-SFIR-0004`,
which is exactly what `tests/impulse-tests/dsp/subcontainer1.dsp` — the
canonical upstream test for this feature, and the impulse corpus's one
remaining transform error — exercises. UI widgets in table content are not a
gap: upstream's own type checker rejects them (`checkInit failed`), so neither
compiler has to model them.

One place where the current path is *better* than the reference: for a nested
generated table, upstream 2.87.1 declares the inner table
(`static float ftbl0mydspSIG0SIG0[64]`) but never emits its sub-container and
never fills it, leaving it zero. The interpreter folds the nested case
correctly today. The port must therefore be recursive rather than a literal
transcription of the C++ control flow, and that is written into the plan as a
tested requirement rather than left as an accident to be rediscovered.

Wrote `porting/siggen-subcontainer-table-init-port-plan-2026-08-05-en.md`:
baseline and evidence, the reference model with its two emission shapes
(nested container for the textual backends, `inlineSubcontainersFunCalls` +
`mergeSubContainers` for the flat ones), the FIR gap analysis, the target
design, invariants with their independent checkers and rejecting mutations,
phases S0-S7, the test plan, and risks. The FIR work is a `SubModule` node
plus an eighth `Module` field, a `staticInit` lifecycle function (the interp
backend already reserves the slot, `interp/mod.rs:320`), and sized
uninitialized tables expressed as `DeclareVar(Array)` — no new node kind
needed there, and `TreeArena::clone_subtree_from` already exists for importing
a child store's root.

Four decisions settled with the user over the session, each propagated through
the document rather than appended to it:

1. `cpp` and `c` emit the real nested class/struct, not the simpler
   `StackLocals` flattening. A `static classInit` stays valid because the
   sub-module object is a local of that function. §5.9.1 freezes the target
   text for both languages from reference probes, so the emitter is written
   against an oracle instead of toward one.
2. `--table-init const` is a permanent mode, not a transition scaffold. That
   keeps `siggen.rs`, `register_constant_table_init` and the 256-element
   unroll threshold as supported code — an earlier draft had them scheduled
   for deletion — and a mode matrix gates both paths on every migrated
   backend.
3. Generated tables take the upstream names: `{i|f}tbl{k}{Sub}` for read-only
   tables, `{i|f}tbl{k}` for writable ones (the suffix comes from
   `generateStaticTable`'s `vname += tablename` and is absent in
   `generateTable`), with one allocation-ordered counter shared by int and
   real tables. This lands as a standalone rename commit at the head of S2 so
   the naming diff never mixes with the semantic one, and it strengthens the
   emission-determinism invariant, since `k` is no longer `SigId`-derived.
4. No folded fast path in `runtime` mode: every `SIGGEN` becomes a sub-module,
   waveform and constant payloads included.

Decision 4 corrected a claim I had written into the first draft — that folding
constant and waveform generators produces "strictly smaller" code. Measuring
it disproved that: a constant generator with N = 65536 folds to 395 486 bytes
against the reference's 3 123 (127×, because `size` identical literals are
emitted where upstream emits `table[i1] = 0.5f;` in a loop), and a 5-value
waveform filling a 4096-entry table folds to 30 942 against 3 346. Folding
only wins when table length equals waveform length (2 178 against 3 083). The
subtler argument is that partial folding would skip upstream's counter
increments and renumber every later table in the same DSP, giving back exactly
the reference-diffability that decision 3 was taken to buy.

No code changed. Next step is S0: freeze reference and current outputs for the
plan's twelve fixtures under `porting/generated/`, and re-measure the impulse
baselines (cpp 92/93, c 87/93, interp 74/93 come from earlier documents and
should not be trusted as a starting point without re-running them).

## Record the precedence-aware-printing cross-backend analysis

Commit date: 2026-08-05

Source commit: this commit

While reviewing `cpp`'s already-shared `c_family` statement emission during
today's documentation sweep, asked whether other backends had a bigger
factoring opportunity than the small in-file helpers extracted so far.
Tracing what `c_family` shares — and what its own module doc says upstream's
`Text.hh` shares across every textual backend — led to
`crates/codegen/src/backends/textual.rs`: a faithful port of the C++
reference's precedence-aware infix printing (`TextInstVisitor::
{left,right}ArgNeedsParentheses`), explicitly written to be reusable, but
with exactly one caller (`cmajor`). `c_family` (shared by `c`/`cpp`), `rust`,
`julia`, `asc`, and `codebox` each still always fully parenthesize every
binary expression — the same defect class already found and fixed for
Cmajor, where it produced 111 levels of nesting on `bells.dsp` and made the
Cmajor compiler reject the output outright (fixed 2026-08-04, depth dropped
to 3).

Started a proof-of-concept port on `rust` per the user's choice, but stopped
before writing code: Rust routes integer arithmetic through `wrapping_*`
method calls rather than infix operators (for C-style overflow wrapping),
which has the same unbounded-nesting symptom but isn't fixable by
`textual.rs`'s precedence algorithm — the actual fix there is recognizing an
already-valid Rust postfix/method-call chain, a different problem. Rust also
interleaves explicit `as` casts into operand rendering before combining
operands, which changes what a precedence-aware rewrite needs to inspect.

Recorded the full analysis — evidence table, the Cmajor reference shape to
mirror, the Rust complication, and open questions about whether any
non-Cmajor backend has an active (not just latent) failure — in
`porting/textual-precedence-aware-printing-cross-backend-analysis-2026-08-05-en.md`,
and filed the scoped follow-up as task `task_37b2ce9f` rather than pushing
the `rust` change through incompletely.

## Add small-format `.fbc` read support to the interpreter serializer

Commit date: 2026-08-05

Source commit: this commit

`write_fbc` has always supported two `.fbc` text formats (normal and compact
"small"), matching the C++ interpreter and the original porting plan
(`porting/phases/faust-rust-interpreter-porting-en.md`: "Two modes exist in
C++: normal and small. The Rust port must support both."), but `read_fbc`
only ever implemented the normal-format grammar. Small-format output was
unreadable by the Rust reader; every production `write_fbc` call site already
passed `small=false`, so the gap was latent rather than user-visible.

Auditing the reader showed its block/instruction-level parsing (meta, UI,
code blocks) never validates header keywords by literal text — it discards
label tokens positionally — so the two formats already aligned token-for-token
there. Only the top-level file header (7 lines, previously gated by
`check_token` against normal-mode-only keywords) and one literal `label ==
"name"` check on the optional per-instruction name field needed a small-mode
branch. `read_fbc` now detects the format from the first header token
(`"interpreter_dsp_factory"` vs `"i"`) and reads the matching header grammar;
the name-field check became positional so it accepts both `"name"` and `"n"`.

Confirmed `interp-ffi::read_fbc_any`'s precision auto-detection (which only
checks whether the header line ends in `"double"`) already worked unmodified
for both formats, and that no `.fbc` fixtures in the tree depend on the
small format.

Validation: `cargo build -p codegen -p interp-ffi --lib`; `cargo test -p
codegen --lib` (333 passed, up from 331 — two new tests: a full small-format
write/read round trip, and a `name`-field round trip exercised in both

Added exhaustive white-box unit tests for the Cranelift backend's four pure
`FirMathOp` -> host-symbol lookup tables (`unary_math_symbol_f32/f64`,
`binary_math_symbol_f32/f64`) in `lowering.rs`. The test's expected-value
match has no wildcard arm, so adding a new `FirMathOp` variant fails to
compile here instead of silently falling through the `_ => None` arms in the
production tables; the guarantee was confirmed by temporarily adding a
fictitious variant and reverting.

Reviewed all non-test source files in the Cranelift backend (`api.rs`,
`core.rs`, `host.rs`, `jit_data.rs`, `subset.rs`, `lowering.rs`) for
documentation gaps. The backend was already extensively documented; filled
the handful of genuine gaps found: `find_module_and_compute` and
`fir_type_to_clif_type` in `core.rs`; the non-obvious `exp10`/`abs`/`rint`/
`remainder` host wrapper semantics in `host.rs`; the generic
`function_body_subset_gap_reason_from_decl` engine in `subset.rs`; and the
silent element-type-mismatch behavior of static-table serialization in
`jit_data.rs`.

Merged the two near-identical `FirType::Float32 | FirType::FaustFloat` and
`FirType::Float64` match arms in `ComputeLowering::lower_binop` into one,
since Cranelift's `fadd`/`fsub`/`fmul`/`fdiv`/`fcmp` are width-agnostic and
operate on whatever CLIF value type the already-coerced operands carry. Pure
refactor, no behavior change.

Validation: `cargo build -p codegen --lib`; `cargo test -p codegen --lib
backends::cranelift` (32 passed); `cargo clippy -p codegen --lib` clean for
the touched module.
