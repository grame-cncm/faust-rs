# 2026-08-06

## Three cmajor generated-table defects found by reading the output

Commit date: 2026-08-06

Source commit: this commit

Stéphane ran `faust-rs table2.dsp -lang cmajor --table-init runtime` and
noticed the emitted struct was misindented. Fixing the layout put the
surrounding lines in front of me, and two real bugs were sitting in them.

**Layout.** Struct members were emitted at the same indentation as the braces.
`emit_field_block` now takes an explicit indent, and the sub-module struct body
passes one level deeper than the enclosing declaration, matching the reference.

**Fill sizes.** Cmajor types array parameters by length, so the fill signature
needs the table's concrete size, which `collect_table_sizes` recovers from the
call site. It scanned `staticInit` only. A read-only table is filled from
`staticInit`, but a writable one is filled from `instanceConstants`, and a
nested generator's fill call sits inside its parent sub-module's
`instanceInit` — neither was reachable. Every `rwtable` generator therefore
missed and fell to the `unwrap_or(0)` default, emitting

    void fillmydspSIG0_0 (mydspSIG0& this, int32 count, int32[0]& table)

against a call site reading `fillmydspSIG0_10 (sig0, 10, itbl0)`. The scan now
covers the whole module, and — the part that matters more than the scan — a
missing size is an error instead of a zero. The `unwrap_or(0)` is what let a
name-and-signature mismatch reach the output at all.

**Generator constants.** `emit_sub_modules` destructured `SubModule` with `..`
and never emitted the sub-module's `static_decls` or `globals`, so the
`const int32[N] …Wave0` array a `waveform` generator reads was declared
nowhere and `cmaj` rejected the fill body with "Cannot find symbol". They now
go to processor scope, where the reference puts them: the constants are shared,
not per instance.

Full cmajor impulse lane: 87/87 under `--table-init runtime` and 87/87 under
the default `const` mode. `subcontainer1.dsp` — carried as `KNOWN_FAIL_all`
for the project's lifetime — matches the C++ oracle sample-for-sample through
Cmajor → C++ → binary.

Two things worth keeping. First, the size bug only ever fired on `rwtable`, and
the `rwtable` cases (`table1`, `table2`) are exactly the ones that were failing
in the lane — I had the evidence before the user's report and had not read it.
Second, `..` in a `FirMatch` destructure is silent about what it discards; both
dropped blocks here were fields I never named. A backend that ignores part of
a FIR node emits a program that is wrong in a way no FIR check sees, because
the FIR was right.
