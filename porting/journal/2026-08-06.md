# 2026-08-06

## Three cmajor generated-table defects found by reading the output

Commit date: 2026-08-06

Source commit: this commit

Stéphane ran `faust-rs table2.dsp -lang cmajor --table-init runtime` and
noticed the emitted struct was misindented. Fixing the layout put the
surrounding lines in front of me, and two real bugs were sitting in them.

**Layout.** Struct members were emitted at the same indentation as the braces.
`emit_field_block` now takes an explicit indent, and the sub-module struct body
passes one level deeper than the enclosing declaration, matching the reference.

**Fill sizes.** Cmajor types array parameters by length, so the fill signature
needs the table's concrete size, which `collect_table_sizes` recovers from the
call site. It scanned `staticInit` only. A read-only table is filled from
`staticInit`, but a writable one is filled from `instanceConstants`, and a
nested generator's fill call sits inside its parent sub-module's
`instanceInit` — neither was reachable. Every `rwtable` generator therefore
missed and fell to the `unwrap_or(0)` default, emitting

    void fillmydspSIG0_0 (mydspSIG0& this, int32 count, int32[0]& table)

against a call site reading `fillmydspSIG0_10 (sig0, 10, itbl0)`. The scan now
covers the whole module, and — the part that matters more than the scan — a
missing size is an error instead of a zero. The `unwrap_or(0)` is what let a
name-and-signature mismatch reach the output at all.

**Generator constants.** `emit_sub_modules` destructured `SubModule` with `..`
and never emitted the sub-module's `static_decls` or `globals`, so the
`const int32[N] …Wave0` array a `waveform` generator reads was declared
nowhere and `cmaj` rejected the fill body with "Cannot find symbol". They now
go to processor scope, where the reference puts them: the constants are shared,
not per instance.

Full cmajor impulse lane: 87/87 under `--table-init runtime` and 87/87 under
the default `const` mode. `subcontainer1.dsp` — carried as `KNOWN_FAIL_all`
for the project's lifetime — matches the C++ oracle sample-for-sample through
Cmajor → C++ → binary.

Two things worth keeping. First, the size bug only ever fired on `rwtable`, and
the `rwtable` cases (`table1`, `table2`) are exactly the ones that were failing
in the lane — I had the evidence before the user's report and had not read it.
Second, `..` in a `FirMatch` destructure is silent about what it discards; both
dropped blocks here were fields I never named. A backend that ignores part of
a FIR node emits a program that is wrong in a way no FIR check sees, because
the FIR was right.

Next: S5 (`interp`, `wasm`, `cranelift`), then S6 (vector) and S7 (flip the
default to `runtime`).

## S5: the three flat backends, and a false green that survived a full lane

Commit date: 2026-08-06

Source commit: this commit

`interp`, `wasm` and `cranelift` now emit generated tables, all flattened with
`MergedStructFields`. No backend refuses a sub-module any more. Each lane is
93/93 under `--table-init runtime` and 93/93 under `const`, and `subcontainer1`
— carried as `KNOWN_FAIL_all` for the project's lifetime — matches the C++
oracle on all three.

None of them keeps its table anywhere but `static_decls`, and for three
different reasons that happen to agree: interpreter static storage is already
per instance (`class_init` runs the static-init block on the instance's own
executor), while WASM linear memory and a Cranelift JIT data object are shared
across instances exactly as C++'s file-scope array is.

Four things worth recording.

**`classInit` was throwing away its sample rate in all three runtimes.** WASM
hardcoded an empty `classInit` body; the interpreter and Cranelift runtimes both
took a `sample_rate` and named it `_sample_rate`. That is survivable exactly as
long as no generator depends on the sample rate. `subcontainer1.dsp` does, and
filled its table from 0, reading back 1 — `fmin(192000, fmax(1, 0))`. The C++
interpreter has the same hole and can afford it, never having had a generator to
feed.

**`StoreTable(kStatic)` was in no flat backend's lowering subset.** Loads were
there; stores were not, because until now nothing ever wrote a static table. A
static table is addressed absolutely in WASM and through its own `GlobalValue`
in Cranelift, so neither could reuse the struct-relative store.

**A silent fallback hid that.** WASM's body emitter falls back to an empty
function when lowering fails, so the missing store first presented as all-zero
output — the precise failure mode this port exists to prevent — rather than as a
diagnostic. Adding the error-propagating probe that `compute` already had turned
it into `unsupported compute statement in WASM subset: StoreTable { …, access:
Static, … }`, which named the gap outright. The probe was worth more than the
fix it led to.

**The cranelift lane reported 93/93 in runtime mode while running in `const`
mode.** Both JIT backends build their compiler from `parse_ffi_compile_args`,
which had no `--table-init`, so the flag was accepted by the runner's CLI,
forwarded into argv, and dropped on the floor. The lane cannot detect this: all
93 gated DSPs pass in `const` mode too, so a silently-const run is
indistinguishable from a successful one. What exposed it was `subcontainer1` —
excluded from the lane precisely because it fails in `const` mode, and therefore
the only input whose behaviour differs between the two. The lesson is not "check
the flag"; it is that a gate whose two configurations produce identical results
cannot witness which one it ran. The distinguishing case has to be outside the
gate, and has to be checked by hand.

Also, tightening `lifecycle_leak_guard` — removing the now-dead "skip a backend
that refuses" path and adding `asc` and `cmajor`, which it had never covered —
immediately found `staticInit` leaking as an ordinary function in both. Neither
is ever called, so neither changed a single number; every impulse lane was green
straight through them. That is the whole argument for the guard.

## The asc lane reaches 93/93: a bug that needed five backends to become visible

Commit date: 2026-08-06

Source commit: this commit

`phaser_flanger.dsp` was the last assemblyscript failure, in both table-init
modes. The cause had nothing to do with generated tables: a Faust label may span
several source lines — `demos.lib:1647` has one — and asc lowers labels to `//`
comments, which end at the newline. The continuation was emitted as bare text:

    // ui button Noise (White or Pink - uses only Amplitude control on
    the left)

`asc` parsed the second line as code. Labels and metadata keys now go through
`one_line`, which collapses the break and the whitespace on either side of it
into the single space the break stands for. asc is the only backend that lowers
labels to comments, so nothing else was exposed.

The lane is now 93/93 under `--table-init runtime` and 93/93 under `const`.

What makes this one worth recording is how long it stayed invisible. The bug is
old and has nothing to do with this port, but the assemblyscript gate builds its
JSON companion through the `wasm` backend, which refused generated tables until
S5. So the lane could not run at all, and a plain syntax error in emitted code
sat there unobserved. Migrating `wasm` did not fix asc — it made asc *testable*,
and the first run immediately produced two findings: this one, and sub-module
classes dropping their own constants. A gate that cannot execute reports nothing,
and reporting nothing is indistinguishable from passing right up until someone
turns it on.

## S6: the vector path, and a measurement that chose the design

Commit date: 2026-08-06

Source commit: this commit

The plan left S6 with two acceptable outcomes: build the same sub-module in the
checked vector lowerer, or fail closed with a named `FRS-VEC-FALLBACK-…` reason.
Failing closed is far less work, and the plan sanctions it, so it was worth
being sure before rejecting it. 37 of the 133 corpus DSPs carry a generated
table, and 18 of those are certified in vector mode. Failing closed would
therefore have taken the certified count from 97 to 79 the moment S7 flips the
default — a 19% loss of vectorization to save a day of work. That decided it.

What the vector lowerer was doing was worse than "not implemented": it folded
every generator through the SIGGEN interpreter regardless of `--table-init`, so
the flag was honoured in scalar output and silently ignored in vector output.
It also inherited the interpreter's limits, which is why a sample-rate-dependent
generator dragged the whole program back to scalar.

`build_generator_sub_module` was a method on the scalar lowerer, unreachable
from the vector one. Extracting it to `module/subcontainer_compile.rs` went in
its own commit, with scalar output verified identical across the move, so the
S6 semantic diff would not be buried under a code move. The generator is
compiled in scalar mode even under `-vec` — it is a 0-input/1-output program
evaluated once at initialization, so there is nothing to vectorize, and a second
implementation is precisely how the two paths would drift apart.

Two things the vector module did not have. It had no `staticInit` at all, which
read-only generated tables need; it is now emitted only when there is something
to fill, so a module without a generated table keeps its exact previous shape.
And its final-module checker required a mutable table's initialization to cover
every cell element-wise — true of the folded shape, impossible for a single
`fill` call. That check was right to fire; the fix was to make the obligation
shape-dependent rather than to weaken it. A fill call must now name its table
*structurally* — the third argument has to be a load of that table — so a call
that names one table and writes another cannot pass as coverage for the first.
Three mutations confirm it still bites: a short count, a dropped fill, and a
fill aimed at the wrong table, rejected respectively by the new count check, by
FIR-SM01, and by the structural match.

The gate asked that the corpus keep its certified count. It does, and gains one:
97 under `const`, unchanged, with all 1552 certified mode/DSP pairs retained
across 16 modes; 98 under `runtime`, because `subcontainer1` can finally be
vectorized now that its generator no longer has to be foldable. cpp `-vec -lv 0`
and `-lv 1` impulse lanes are 93/93 in both modes.

Only S7 remains: flip the default, drop `KNOWN_FAIL_all := subcontainer1`, and
take the impulse gate from 93 to 94.

## S7: the default flips, and two gates that were already red

Commit date: 2026-08-06

Source commit: this commit

`--table-init runtime` is the default. `KNOWN_FAIL_all` is empty for the first
time in the project's life — `subcontainer1.dsp` had been sitting there since
the impulse harness was ported, because its table content depends on the sample
rate and the compile-time SIGGEN interpreter cannot evaluate that. Every lane
now gates 94 cases rather than 93: cpp, c, interp, wasm, cranelift, julia, rust
and assemblyscript all 94/94, cmajor 88/88. (94 of the corpus's 133 DSPs — the
C++ oracle cannot compile the 39 clock-domain fixtures, which
`build/ref/cpp-oracle-manifest.mk` excludes. Measure before that manifest exists
and every lane gates all 133 instead; I did, mid-session, and briefly believed
the gate had always been 132.)

`const` is qualified in the same runs rather than dropped: 93/94, the one
rejection being the expected `FRS-SFIR-0004` on `subcontainer1`, i.e. 93/93 with
it excluded. That is the mode working as specified, so `known.mk` now carries
`TABLE_INIT_CONST_UNFOLDABLE` and a const-mode run records it as an expected
outcome instead of a failure.

Vector certification improved rather than merely holding: 97 certified with 1
compile error became 98 certified with 0 errors across all 16 modes, and the
retention gate now covers 1568 mode/DSP pairs.

The size result is the one the whole port was for. A 65536-entry table becomes
a loop instead of 65536 literals: `grain3` goes from 2 840 039 bytes of C++ to
6 810, a 417× reduction, and its compile time from 0.17 s to 0.01 s. `table`
345×, `osc` 338×. The honest other side is that small tables grow — `table1`
2 956 → 4 598 bytes, because a sub-module costs more than eight literals. That
is a reason `const` stays available, not a reason to keep it as the default.

Two things worth recording, both about gates rather than about tables.

**Five transform tests and one codebox test failed on the flip, and every one
was right to.** They read `SignalFirOptions::default()` as meaning "folded" —
true when written, and silently a different assertion afterwards. Each now
names the mode it tests. The codebox one was more interesting: it pinned the
folded shape (`tbl[0] = 0;` per element), but its actual subject is a defect
where codebox read a table it never declared. So rather than re-pin it to
`const`, it now asserts the property in *both* modes — declared, and written
inside `dspsetup` before compute — keeping the literal-value checks only where
they mean something. A test tied to a default is a test that stops testing what
it was written for the moment the default moves.

**`cli-transcript-check` was already red before this commit**, and I nearly
recorded it as S7 fallout. The recorded `Module` line had no `sub_modules`
field, which S1 added the day before — so the transcripts had been stale for a
day and the gate had been failing unnoticed. I confirmed it by stashing the
whole S7 change and re-running on the pre-S7 tree: still 13 findings. Worth the
two minutes. Regenerating showed the accumulated drift honestly — `sub_modules`
on every FIR dump, plus `--table-init` and the `cmajor` language, neither of
which the recorded help had ever seen.

That is the second time in two days that turning a gate on revealed it had been
dark rather than green (the first was the assemblyscript lane). The pattern is
the same both times: a gate that cannot run, or that nobody runs, is
indistinguishable from a passing one until someone looks.

The port is complete: S0 through S7.

## Reviewing the finished port against its own plan

Commit date: 2026-08-06

Source commit: this commit

Stéphane asked me to check that the whole phase since `0cb97dd7` had actually
been done, and to look at the READMEs and rustdoc for the files it touched.
Thirty-three commits, S0 through S7. Reading the plan back against the code
found two obligations stated and not met, and one number I had reported wrongly.

**Invariant I2 had no independent check at all.** The plan assigns it to
FIR-SM03 — "`fill<Sub>` writes exactly `size` elements" — and FIR-SM03 exists,
so the row looked satisfied. It is not the same property: SM03 validates the
fill *signature*, that `count` is an `Int32` and `table` a pointer of the right
element type. Nothing anywhere compared the `count` a call site passes against
the length of the table it passes. FIR-SM01 proves a fill happens; between "a
fill happens" and "the table is full" sat an unchecked gap, and the failure it
admits is the quiet kind: pass `size - 1` and the last cell of a 65536-entry
table keeps whatever the target's uninitialized storage held. New rule FIR-SM06
closes it, reading the length from the table's own declaration so the producer
and the check do not share a source. The plan's own rejecting mutation turns it
red.

That is a specific kind of mistake worth naming: an obligation can be *marked*
satisfied because something with the right identifier exists. The check I wrote
in S1 and the check the plan asked for in §6 had the same name and different
subjects, and I never re-read the row against the implementation.

**The §8.1 fixture matrix was frozen at S0 and never executed by anything.** All
13 fixtures were used by hand throughout the port — I compiled them repeatedly
while debugging — and referenced from doc comments, which is exactly what made
them look covered. §5.10 requires both modes to carry the matrix, `const` being
permanent rather than a scaffold. They now run in CI: all 13 compile under
`runtime`, and exactly the three §2.3 fixtures are rejected under `const`.
Pinning *which* three matters in both directions — a fourth is a regression in
the folding path, a missing one means the compile-time interpreter grew a
capability the plan does not record.

**The gate is 94 cases, not 133, and I had said 133.**
`build/ref/cpp-oracle-manifest.mk` excludes the 39 clock-domain fixtures the C++
oracle cannot compile, leaving 94 of the corpus's 133 DSPs. That manifest is a
build artifact. It was absent for part of the S5–S7 session, so every lane I ran
gated all 133 instead — greener-looking, a genuine superset, and a different
test. Worse, when the discrepancy surfaced I resolved it the wrong way round: I
told Stéphane the gate had "never been 93" and that my earlier figures were
miscounts. They were not; the plan's "93 → 94" was right from the start, and my
correction was the error. Re-measured in the canonical state, every lane is
94/94 (cmajor 88/88, `const` 93/93).

Two lessons, and the second is the uncomfortable one. First: a gate whose size
depends on a build artifact will silently change size, and a lane that reports
"all green" over a different denominator is not the same evidence. Second: when
a measurement disagrees with a written plan, the plan is not automatically the
stale one. I assumed my fresh measurement beat the document and published a
correction on that basis, when the fresh measurement was the one taken in a
degraded environment. Checking *why* the numbers differed — two minutes of `ls
build/ref` — would have settled it before I said anything.

**Documentation.** `cargo doc` was already clean, but no README mentioned the
feature at all. `crates/fir/README.md` gained the sub-module section it never
had; `crates/codegen/README.md` gained the per-backend emission contract, with
the three obligations each of which was violated at least once during the port;
`crates/transform/README.md` documents `TableInitMode`;
`crates/impulse-runner/README.md` documents `--table-init`. And
`unsupported_sub_modules_message`, whose doc still promised a rejection no
backend performs any more, now records that it has had no caller since S5 and
why it is kept for the next backend.

One self-inflicted detour worth recording: FIR-SM06 appeared to break the cpp
lane, 75 of 133. It was my own `size - 1` mutant — reverted in the source,
never rebuilt into the binary. `grep -c MUTANT` returning 0 proves the file is
clean; it says nothing about what is in `target/release`.
