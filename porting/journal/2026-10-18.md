## Codegen factorization analysis

Commit date: 2026-10-18

Source commit: `2c91ac52` (analysis document and journal only; no code).

- **Question.** Which code in `crates/codegen` should be factored. The
  `c_family` core of 2026-07-05 covers only `c`/`cpp`, and `textual.rs` has a
  single caller (`cmajor`). Upstream instead shares one `TextInstVisitor` and
  one `Text.hh` across all its text backends.
- **Finding.** The other five textual backends (`rust`, `julia`, `cmajor`,
  `asc`, `codebox`) each re-implement the module decode, the lifecycle-stub
  decisions, every leaf (float/string literals, operator tokens, about ten
  math-name tables) and the whole statement walker. The three machine backends
  duplicate the object layout, the scalar math semantics and a FIR child walker.
  Twenty drifts between copies are listed. One is live and reproduced: the Rust
  backend spells an infinite literal `f64::INFINITYf32` for
  `process = _ * (1e30*1e30);`, which is not valid Rust. The interpreter
  constant-folds float `min`/`max` with semantics different from those it
  executes. Most others are latent: they are reachable only by FIR the
  production lowering does not originate, or through the box/signal API.
- **Proposal.** Four independent, output-identical restructurings:
  - R1, a module skeleton;
  - R2, a leaf layer (a Rust `Text.hh`);
  - R3, a structural walker trait (a Rust `TextInstVisitor`);
  - R4, layout, math and walker sharing in the machine backends.

  Plus quick wins Q1–Q4. Q1 is the error bridge: it drops `fir_node` for every
  backend but cpp. The other three are a shared precision enum, test fixtures
  and the c/cpp leftovers. Drift fixes land after each move, one commit each.
  Six decision points are left to the user.
- Document:
  [`porting/codegen-factorization-analysis-2026-10-18-en.md`](../codegen-factorization-analysis-2026-10-18-en.md).

Validation: none needed (documentation only). The findings were cross-checked
in source and marked V/S per row; the D1 reproduction used the release
`faust-rs` built at `d4f3f6a5`.

## FAD: zero tangents folded through the clock-domain wrappers

Commit date: 2026-10-18

Source commit: this commit (code, tests, plan and journal).

- **Finding.** On the faust-coopiano voice one `fad` seed cost six plain
  renders (993 ms against 155 ms), in the generated C++ as much as in the JIT.
  Not tangents moved to the audio rate: the note parameters' tangents are
  computed in their `ondemand` domains. But the twin held 3,097 tangents for a
  hammer seed that none of the 2,500 string parameters depends on, and 2,526
  of them are 0 at run time. The tangent of a block input no seed reaches
  (the key) was rebuilt by the `Clocked` rule as `Clocked(τ, 0)`: no rule, no
  later simplification and no test `is_literal_zero` saw a zero, every rule
  above it built full product terms, `augment_block` held the lane, and the
  sample-rate tangent code read it as an unknown.
- **Fix.** `signals::ad_rules::DerivativeZeroFolder` folds the literal zeros
  of each tangent as `ForwardADTransform::transform` returns it (`0 · x`,
  `x ± 0`, `0 / x`, `TempVar`/`PermVar`/`Clocked`/`Seq`/`ZeroPad`/`delay` of 0,
  `select2` of two zeros); the existing machinery then drops the lane and the
  `Seq` reads the literal. Placed in `signals` so the reverse-mode passes can
  share it; the signal simplifier cannot do it, as it runs after FAD has
  decided what to hold and treats `Clocked` as opaque. Only a zero leaves a
  wrapper: a held non-zero constant reads 0 before its first firing.
  `ZeroPad(0, h)` folds to 0, since a `ZeroPad` over a bare constant is
  refused by the lowering (`FRS-SFIR-0007`, caught by the `fad_beside_plain`
  matrix on the prototype).
- **Effect.** One seed: compile 26.1 → 15.3 s, compute 993 → 617 ms; three
  seeds: 31.9 → 19.6 s and 2.54 → 1.75 s; held values 6,194 → 3,674 (plain
  3,097). Primal bit-identical, tangents within 4.6e-15 relative. At key 60,
  without phantom partials, a seed costs one plain render (105 → 202 ms).
- **What remains** (plan §7): at key 40 the phantoms' domain, which fires
  every sample, takes 444 of the 617 ms, seven times its plain cost for 2.9
  times its operations. Its body is one sum expression over some 2,100 shared
  temporaries, all live until that statement: a FIR scheduling question, left
  to its own plan.

## `freeCMemory` releases the pointer arrays of every C API

Commit date: 2026-10-18

Source commit: this commit (parent `8c5a17bc`).

**Defect** (audit report §0, item 1). The C headers say that the null-terminated
arrays they return, `Signal*` from `CboxesToSignals*`/`CsimplifyToNormalForm2`
and `char**` from `getAll{Interpreter,Cranelift}DSPFactories`, are released
with `freeCMemory`. `libfaust-rs` exports `interp-ffi`'s `freeCMemory`
(`box-ffi` and `cranelift-ffi` gate theirs behind `standalone-capi-globals`),
and that one only did `CString::from_raw`: every array a host freed went
through the C-string path, which is undefined behaviour. `box-ffi`'s
array-aware version was never exported, and it looked the array up in the tree
context, so even it failed for an array freed after `destroyLibContext`.

**Fix.** `ffi-common` owns a process-global registry of the pointer arrays
handed to a host (`alloc_ptr_array`, `free_if_owned_ptr_array`) and the single
release routine `free_c_memory`: a registered array is released as the boxed
slice it is, anything else as a C string. The three adapters' `freeCMemory`
all call it, so which one is exported no longer matters. `tree-ffi` allocates
handle arrays through the registry instead of its context (they now outlive
`destroyLibContext`, as C++ `malloc`/`free` arrays do), and its unused
`free_context_or_c_string` is removed. Symbol ownership is unchanged: the
export baseline still matches.

**Tests.**
- `crates/cranelift-ffi/tests/free_c_memory.rs`, the regression test: it frees a
  `CboxesToSignals` array after `destroyLibContext` and a
  `getAllCInterpreterDSPFactories` array through `interp_ffi`'s `freeCMemory`
  (the exported one), and checks that neither stays registered. With the old
  body restored it aborts (SIGTRAP from the allocator).
- `ffi-common` and `tree-ffi` unit tests: registration, single release, empty
  arrays, survival across a context reset.
- `xtask libfaust-export-check` now builds and runs a C client
  (`free-c-memory.c`) of the same contract against `libfaust-rs`. It passes,
  but under the library's mimalloc the old defect is not observable from C, so
  it is an end-to-end check, not the regression test. The export check is not
  in CI.

**Validation.** `cargo fmt --all --check`, `cargo clippy --workspace
--all-targets -- -D warnings`, `cargo test --workspace --all-targets`,
`cargo doc` with `-D warnings`, the five structure gates,
`xtask libfaust-export-check`. No compilation-pipeline crate changed, so the
compile-budget gate was not run. `docs/code-graphs` regenerated (two new
`ffi-common` functions; the index also picks up the line shifts of the earlier

## compile-budget-check: no vector/scalar ratio, stale-baseline warning, baselines lowered

Commit date: 2026-10-18

Source commit: this commit (parent `1894ffea`).

**Failure.** CI run 39115097366 (job 117639737697) failed the compile budget on
`reverb_designer`: vector 4990 ms against a ratio allowance of
`9 × 304 ms + 2000 ms = 4736 ms`. Nothing regressed. Vector stood at ~832 units
against an 884-unit baseline. A local release A/B against `bf65d311` (last
green) measured scalar 270 → 173 ms and vector 3058 → 2758 ms: the October
front-end speedups (eval application memo, sigtype fixpoint memo, normalize,
`clk_env`) cut both, but the shared front end is a much larger share of scalar.

**Why the ratio is gone rather than raised.** Scalar and vector both contain the
whole front end, so any front-end speedup raises `vector / scalar`. The
allowance went 4× → 9× on 2026-08-06 (`7ca383df`, lexer DFA) for the same
reason and would have needed 12× now. It caught nothing the per-case
`vector_units_milli` check does not: calibration is front-end only, so a
vector-only regression always raises vector units. The absolute ceilings stay as
the catastrophic backstop.

**Stale baselines.** The audit behind this change found baselines far above
the measured cost, i.e. silent slack under a 40% tolerance:
`ja_smoothed_parameter` 3.3 units under 510, `dx7_alg5` 45 under 293,
`reverb_designer` scalar codegen 51 under 100. A case below 70% of its baseline
now prints a warning (a GitHub `::warning` annotation on Actions). It does not
fail.

**Baselines lowered.** Each to the largest value seen in green runs
38148527657, 38317887585 and 38374565145, plus for codegen the failing run
(ms / 6 ms calibration), and never above the old value. Those runs predate the
speedups, so the new values are upper bounds: no flake risk, still loose where
the speedups landed. Front end: `ja_smoothed_parameter` 510 → 3.5,
`dx7_alg5` 293 → 48, `parametric_eq` 105.5 → 85.3, `reverb_designer`
98.7 → 72.3, `spectral_level` 166.5 → 131.2, `vcf_wah_pedals` 80.5 → 67.8,
`virtual_analog_oscillators` 83 → 68.7 (`bells` kept). Codegen:
`cubic_distortion` 63/202 → 50/197.5, `spectral_level` 165.5/814 →
131.3/808.7, `reverb_designer` scalar 100.3 → 72 (vector kept at 884). Schema 2
→ 3, since a schema-2 file's ratio fields would otherwise be ignored silently.

**Follow-up.** The next green runs on current code will warn where these upper
bounds are still loose (expected: `reverb_designer` scalar codegen near the
70% line); lower them from those figures.
