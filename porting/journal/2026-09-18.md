## probe::engine: three types, three files, and what they wrote twice

Commit date: 2026-09-18

Source commit: this commit

Second step of `porting/faustprobe-restructuring-plan-2026-09-18-en.md`.
`probe/engine.rs` held `Factory`, `Probe` and `PolyProbe` in 1513 lines. It is
now `probe/engine/`: `factory.rs` (280), `probe.rs` (469), `poly_probe.rs`
(667), and `mod.rs` (125) with `RenderSpec`, the re-exports, and what the two
render loops share. Every public path stays: `probe::engine::Probe` and the
others are re-exported, no caller changed, and the API baseline moves by four
lines, none removed (`+fn ControlMap::writable`, three `use`).

What was written more than once:

- the compiler's `argv` (`-I DIR`, `-double`, the extra arguments) and the
  null check of the factory, in `compile_with_args` and
  `compile_from_string_with_args`: one `Factory::create`, given the call that
  differs;
- the resolution of a query into a writable control, with its three error
  messages, in `ControlMap::check_write`, `Probe::check_writable` and
  `Probe::set`: one `ControlMap::writable`. `set` keeps its own clamp: for a
  NaN `check_write` answers the control's initial value and `set` does not,
  and this is a refactoring;
- the two constructors of `PolyProbe`, the voices and the struct built twice:
  `voices_of` and `assemble`;
- in the two render loops, the length of a block shortened to the next
  scheduled event, and the hand-over of a computed block to the statistics and
  the caller: `next_block` and `push_block`.

And a second stray doc comment: `reset`'s first line ("Return the instance to
the state it had just after `init`") sat on `get_zone`.

Checked by the same harness, now 391 cases identical, the crate's 382 tests,
clippy, fmt, `code-graphs --check` after the bless. An 8-million-frame render
takes 0.21 s before and after. Six mutations of the factored code: `next_block`
ignoring the schedule (22 cases), the skip frame left out (189), `writable`
accepting a bargraph (1), one voice of allocation state whatever the bus (18),
`-double` not passed (124) are rejected; **the extra compiler arguments
dropped survived**: no case gave `--bra-tape` a value other than the default.
A hole in the harness, not in the code: two cases with `--bra-tape 64`, where
the tape is shorter than the block and the gradient is 283 instead of 476, and
the mutation is rejected (2 cases).

## faustprobe: the binary cut along its concerns, its duplications factored

Commit date: 2026-09-18

Source commit: this commit

Five phases and their leftovers landed in one day in `src/bin/faustprobe.rs`:
3545 lines, `run` alone 890 of them, `run_freqresp` 518, `run_train` 355,
`run_poly` 263. The house standard that `structure-check` enforces on two
other crates is 2000 lines a file and 200 a function. The size was a symptom:
the four modes had each grown their own copy of what they share. Plan:
`porting/faustprobe-restructuring-plan-2026-09-18-en.md`.

**Invariant: no output changes.** Not a message, not the order of two lines,
not which of two errors a faulty command line reports. The probe tests assert
on fragments, which is not enough for that, so the check was written first: a
harness (scratch, it cites absolute paths) runs 389 commands against a binary
and records exit status, stdout and stderr of each: every mode and format,
every entry of every refusal table, the failure paths, `--help`, and the 133
programs of `tests/impulse-tests/dsp` through the protocol. The numbers of
`--time` are masked and nothing else. Recorded with the binary of `4213cdfd`.
Run twice on that binary it did not agree with itself at first: the parser
lists the repair suggestions of a syntax error in an order that changes from
run to run, a defect of the front end reported apart; the harness sorts them.

The binary is now `src/bin/faustprobe/`, one module per concern (`cli`,
`setup`, `writes`, `report`, `failure`, `verify`, `render`, `poly`,
`freqresp`, `train`, `determinism`), which also removes the `#[path]` the
first sub-module had needed. First a mechanical cut by a script (items moved
with their doc comments, made `pub(crate)`, code untouched), 375 cases
identical; then the factoring, mode by mode, the harness after each:

- `report`: `Sink` (the rule "stdout when nothing else owns it" written once
  instead of four closures), `channel_lines`/`channels_json`,
  `print_controls`, `document`/`describe_program`/`print_json`, `TotalTiming`;
- `writes`: `Clamps` (the checked values of a sweep and "the clamps this point
  ran under", which the plain sweep and `--freqresp` each had), `applied`,
  `written`, `prime`;
- `failure`: `render_failure` (scalar and polyphonic renders fail by the same
  function) and one accumulator behind both failure contexts;
- `verify`: `Verification::prepare` and `judge`, 170 lines that lived in the
  middle of `run`;
- `cli::refuse` for the six refusal tables, `setup::compile_timed`,
  `assignments`, `sweep_axes`;
- each mode cut along its phases: `Plan::prepare` / `Run::render_point` / what
  is said; `Family::prepare` / `measure` / what is said; `run_train` as a
  sequence of `check_writes`, `grid_then_start`, `descend`, `summarize`.

After: the largest file 647 lines (3545), the longest function 116 (890). The
total grew, 3545 to 4333 lines: module headers, type definitions and
signatures outweigh the duplicated code that went. 389 cases identical, the
crate's 382 tests pass, clippy and fmt clean, `code-graphs --check` and
`structure-check` pass.

The harness earned its keep twice. Rewriting `--train` I parsed every `--set`
before checking any; the original did them one at a time, so of two faulty
`--set` it reports the first, and mine reported the malformed one. No case
covered it; one does now, and the order is restored. Ten mutations of the
shared helpers, each rejected: `rms` and `dc` swapped in a channel line (38
cases), a point's own clamps dropped (2), the last scheduled write not kept
(3), the sink inverted (63), `N renders` from three on (2), `refuse` naming
the last flag (1), the `--set` order above (1), the excitation validated
before `--compare`/`--ref` (1), a report-only width check made a gate (3), a
ringing note without its point (1).

Found and left as they are, the invariant forbidding otherwise:

- the doc comment of `reduce_channel` sat on `PointResponse`, 1000 lines from
  its function (moved back: a comment is not an output);
- `--set fb=1.5 --set fb=2 --at 3 fb=2.5` and a failure: the context lists
  `fb=2.5 fb=2`, the scheduled write having updated the first of two entries;
- `--freqresp --in impulse:5` words the missing input differently from a
  plain render (`the program has 2 input(s)` against `the program has 2
  inputs, channels 0 to 1`);
- a polyphonic CSV dump prints its header before `--in` is validated;
- `--train` checks its `--set` one at a time, the other modes parse all first.

## Security audit: rustls 0.23.45

Commit date: 2026-09-18

Source commit: this commit

The `Security audit` workflow failed on the push of `993da3f1` (run
35278054549). It runs on a push only when `Cargo.lock` changes, which the
`serde_json` dev-dependencies of the C ABI commit did, and otherwise on
Mondays; its last run, the scheduled one of 2026-09-14, passed. The cause is
not in the day's commits: RUSTSEC-2026-0285, published 2026-09-14, on
`rustls 0.23.43` (TLS 1.3 handshake messages accepted across encryption level
boundaries; patched in 0.23.45). `rustls` reaches the workspace through
`ureq`, which `compiler` takes under its optional `network-imports` feature
(`remote_fetch.rs`).

`cargo update -p rustls` moves two packages and nothing else: `rustls`
0.23.43 -> 0.23.45 and `rustls-webpki` 0.103.13 -> 0.103.15. Checked both
ways with the CI's own settings, `cargo audit --ignore RUSTSEC-2025-0141`:
exit 0 on the new lock file, `error: 1 vulnerability found!` on the old one.
The loopback transport tests pass against it
(`cargo test -p compiler --features network-imports --test
remote_fetch_transport`, 8 tests; without the feature that file runs none).

Left as it is: the job's visible error was not the advisory but
`Resource not accessible by integration`, raised when `rustsec/audit-check`
tries to publish its report as a check run; the workflow grants its token no
`checks: write`. It only shows when there is something to report, and it
hides what.
