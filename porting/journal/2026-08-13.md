## Add the missing `phaser_flanger` rounding-tolerance band for `make all-mem0`

Commit date: 2026-08-13
Source commit: this correction commit

- Root-caused a report that `tests/impulse-tests$ make all-mem0 -j 8` fails.
  `phaser_flanger.dsp`'s generated C++ diverges from the pinned C++ Faust
  oracle reference starting at frame 883 (delta 2e-6), growing through its
  LFO-modulated feedback delay chain to a few ×1e-4 within the mem0 lane's
  15000-frame prefix comparison — the same class of chaotic-feedback
  rounding sensitivity already covered for `vcf_wah_pedals`, `gate_compressor`,
  and `cubic_distortion` via `PRECISION_<dsp>` overrides in
  `tests/impulse-tests/known.mk`; `phaser_flanger` simply had no entry, so it
  ran under the default 2e-6 tolerance meant for bit-exact cases.
- Confirmed by bisection this is not a regression from any change made in
  this session: checked out the commit immediately before the session
  started (`f8d9f7b9`) in an isolated worktree, built its release binary,
  and reproduced byte-for-byte the identical divergence pattern.
- Confirmed by direct comparison that the divergence is entirely unrelated
  to `-mem0`: generated the ordinary (non-mem0) C++ output with the same
  reference-generating architecture (`impulsearch.cpp`) and compared it to
  the same reference file over the full 60000 frames. It diverges at the
  identical first sample (frame 883, output 1, delta 2e-6) as the mem0 lane,
  growing further from there to a true max of 1.419e-3 — `-mem0` only
  changes memory management, never arithmetic, so this is a general
  faust-rs/C++-Faust numeric characteristic of this DSP, not a mem0 defect.
- First fix attempt (`PRECISION_phaser_flanger := 1e-3`) was calibrated only
  from the mem0 lane's 15000-frame prefix (observed max 3.55e-4) and was

  `known.mk` table and were failing independently of mem0. Recalibrated to
  `1e-2` from the larger, authoritative full-range figure.

  `ir/cpp/phaser_flanger.ir` and `ir/c/phaser_flanger.ir` (full 60000-frame

## Fix `cargo test --release` failing while `cargo test` passes

Commit date: 2026-08-13
Source commit: this correction commit

- Root-caused a report that `cargo test --release` fails while plain
  `cargo test` is clean. `normalize::tests::normalize_add_term_debug_rejects_incoherent_de_bruijn_input`
  is a `#[should_panic]` test for a coherence check in
  `crates/normalize/src/normalize.rs:50` that is itself gated behind
  `#[cfg(debug_assertions)]`. `debug_assertions` is `true` by default for the
  `dev` profile (`cargo test`) and `false` by default for `release`
  (`cargo test --release`), so in a release build the whole check — panic
  included — is compiled out of the binary entirely; the test then fails
  because nothing panics.
- Not a logic bug: the check is an intentional debug-only sanity assertion,
  same category as `debug_assert!`. The test itself just didn't account for
  that. `crates/signals/tests/core_api.rs` already has the correct pattern
  three times over for the same situation — each of its "rejects bad input
  in debug" tests is marked `#[cfg(debug_assertions)]` itself, so it's
  excluded from release builds rather than failing there. Grepped the whole
  workspace for every file combining `should_panic` with
  `cfg(debug_assertions)`; `crates/normalize/src/normalize.rs` was the only
  one missing the guard.
- Fixed by adding `#[cfg(debug_assertions)]` above the test, matching
  `core_api.rs`'s established pattern.
- While validating, `cargo test --release --workspace` surfaced a second,

  `compiler::tests::machine_applicable_fixes::applying_a_machine_applicable_fix_removes_the_diagnostic_it_targets`

## Add alignment-aware `dsp_memory_manager` overloads to generated C++ `mem0`

Commit date: 2026-08-13
Source commit: this enrichment commit

- The pinned reference `dsp_memory_manager` (`architecture/faust/dsp/dsp.h`)
  only declares `allocate(size_t)` and `destroy(void*)`, unlike the Rust-only
  C ABI (`faust_memory_manager`), which already asks for alignment on
  allocation and hands size/alignment back on release. Generated C++ under
  `-mem0` now additionally recognizes `allocate(size_t, size_t)` and
  `destroy(void*, size_t, size_t)` and prefers them when the linked header
  declares them, while remaining a strict superset of the legacy contract.
- Every allocation/destruction call site (instance buffers, class tables, the
  DSP object, and generated table subcontainers) now routes through a new
  `faust_mem0_detail::{allocate,destroy}` shim emitted once per `-mem0`
  translation unit. It uses the classic `int`/`long`-tagged SFINAE overload
  pair to probe, at compile time, whether the static type of
  `dsp_memory_manager` declares the additive overloads; if not, it falls back
  to the legacy one-argument calls unchanged. The probe is against
  `dsp_memory_manager`'s static type, not the concrete manager subclass, so a
  manager that only overrides the legacy pair keeps compiling unmodified.
- The legacy overloads are documented as obsolete directly in the generated
  code (a comment inside `faust_mem0_detail`), kept only for source
  compatibility with hosts still built against the unextended upstream
  header.
- Also deduplicated `classDestroyChecked()` to call the already-shared
  `classDestroyTables()` helper instead of carrying its own copy of the
  reverse-order release loop.
- Enriched `tests/impulse-tests/archs/faust_mem0.h`'s `AuditCppMemoryManager`
  with the additive overloads, auditing that the returned address satisfies
  the requested alignment and that `destroy`'s size argument matches what was
  recorded at allocation.
- Added `mem0_generated_cpp_compiles_against_the_unextended_legacy_manager_header`,
  a new compile-and-run test defining `dsp_memory_manager` exactly as
  documented upstream (nothing else), proving the SFINAE fallback keeps
  generated code compiling and running against a host that has never heard of
  the extension. Extended the existing
  `mem0_generated_cpp_compiles_and_clone_is_independent` with a second
  `aligned_manager` that overrides the additive overloads directly and
  asserts the legacy ones are never reached, proving the richer path is
  actually preferred when available.
- Manually regenerated the real 33-buffer `karplus32.dsp` `-mem0` C++ output
  with the release binary and compiled/ran it end to end against the
  enriched `AuditCppMemoryManager` (`-std=c++17 -Wall -Wextra`, exit 0),
  beyond the small synthetic unit-test fixture.
- Documented the difference as `DIFF-API-005` in
  `faust-rs-vs-faust-cpp-differences-en.md`.
- Validation: the full `codegen` test suite (364 tests, +1 new), including
  all three mem0 C++ compile-and-run smoke tests; the `compiler` crate's
  pinned `mem0` C++ differential tests; `cargo fmt --all`. The full 94-DSP
  `all-mem0` corpus gate (`make -f Make.mem0 all-mem0`) was not rerun in this
  session — the unit-level SFINAE dispatch tests plus the manual
  full-scale `karplus32.dsp` check are the evidence for this change; rerunning
  that gate is a reasonable follow-up before the next `mem0` milestone.

## Compact `mem0` allocation-failure unwinding from O(N²) to O(N)

Commit date: 2026-08-13
Source commit: this correction commit

- Fixed quadratic code generation in the C and C++ `-mem0` backends: each
  allocation-failure branch re-emitted an explicit `destroy` call for every
  previously allocated field, so `memoryCreate()`/`create<Class>()` and the
  class-table allocation prefix grew as O(N²) in the number of buffers/tables.
  `karplus32.dsp` alone (33 instance buffers) produced roughly 4,700 lines for
  `memoryCreate()`.
- Every not-yet-allocated field is already `nullptr`/`NULL` (zeroed by the
  constructors in C++, by `memset` in C), and the failing field already holds
  its own possibly null/misaligned result, so a single reverse, null-guarded
  sweep releases exactly what was allocated so far. C++ reuses the existing
  `memoryDestroy()` from `memoryCreate()`'s failure path and factors
  class-table release into a new shared `classDestroyTables()` method. C adds
  `releaseInstance<Class>()` and `classDestroyTables<Class>()` helpers, the
  latter also reused by the pre-existing `classDestroyChecked<Class>`.
  Cranelift was unaffected: its ownership already runs through
  `ExternalAllocations`'s `Drop`, not generated per-field unwind text.
- Result on `karplus32.dsp`: generated C++ `-mem0` output shrank from 5,951 to
  1,599 lines (-73%) with identical transactional semantics.
- Validation: the full `codegen` test suite (363 tests), including the C and
  C++ compile-and-run smoke tests that inject an allocation failure at every
  index and assert a leak-free unwind under `-Wall -Wextra -Werror -pedantic`
  (C) and `-Wall -Wextra -Werror` (C++); the full `compiler` test suite,
  including the pinned `mem0` C++ differential tests.
