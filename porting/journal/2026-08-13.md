## M1: thread the typed `mem0` option

Commit date: 2026-08-13
Source commit: this implementation commit

- Added the shared `MemoryManagerMode::{None, Mem0}` codegen type with Rustdoc
  provenance to C++ `global.cpp`; it exposes one canonical `-mem0` spelling and
  deliberately has no speculative variants for `mem1`–`mem3`.
- Added the four CLI aliases and propagated the selected mode through
  `COptions`, `CppOptions`, `CraneliftOptions`, source mode, FIR fixture mode,
  and compilation-options metadata. Scalar C, C++, and Cranelift are the only
  accepted backend combinations; vector mode and non-codegen modes fail closed.
- Extended the dependency-light FFI argument parser with the same four aliases,
  explicit `mem1`–`mem3`, vector, and `-it` rejection. Cranelift source, file,
  signal, and box factory paths now pass the typed mode to JIT options.
- Canonicalized all aliases, including duplicates, to one `-mem0` token for
  Cranelift cache/serialization identity. Allocator pointers remain outside that
  identity.
- Recorded the newly reachable adapted CLI surface as `DIFF-CLI-010`. M1 only
  carries typed intent; allocation/layout behavior remains assigned to M2–M5.
- Validation: `cargo fmt --all`; all 31 `ffi-common` tests; the two new codegen
  option tests; three compiler CLI mem0 tests; the Cranelift cache-identity test;
  `cargo check -p compiler --all-targets`; and
  `cargo check -p cranelift-ffi --all-targets`; and focused Clippy with warnings
  denied all pass. One initial Cargo test invocation supplied several positional
  filters and was rejected by Cargo; the tests were rerun with valid per-filter
  commands and passed.
- `compile-budget-check` was run twice on M1 and found the same sole failure:
  `reverb_designer` vector at 984.750 then 1010.000 units versus the existing
  953.982 ceiling. A clean detached worktree at the unchanged M0 commit
  `fc8b5689` reproduced it at 995.250 units. M1 adds no lowering/emission work,
  so this is recorded as pre-existing measurement/baseline debt; the baseline
  was not changed.

## Plan the `-mem0` custom memory-manager port

Commit date: 2026-08-13
Source commit: this planning commit

- Analyzed the pinned Faust C++ `-mem`/`-mem0` contract, its generated C++
  lifecycle, memory-layout JSON, and `compute_cost` visitor. Recorded the
  reference weaknesses that the Rust port must not reproduce: heuristic object
  size, zero-sized static-table sentinels, empty `init`, shallow `clone`, global
  manager rebinding, unchecked allocation failure/alignment, incomplete type
  vocabulary, and defective conditional cost accounting.
- Defined one typed `Mem0Analysis` as the source of truth for generated C,
  generated C++, Cranelift JIT storage, manager descriptions, JSON
  `memory_layout`, and versioned `compute_cost`. Scope is deliberately limited
  to the four `mem0` aliases; `mem1`–`mem3` stay rejected.
- Specified an adapted, versioned plain-C manager ABI with alignment and opaque
  context, while preserving the legacy-compatible C++ manager surface. The
  plan includes transactional allocation, captured-manager destruction,
  poison/failure testing, exact target-ABI metadata, and deep clone behavior.
- Extended the design to Cranelift: external-buffer pointer slots in
  `StructLayoutPlan`, pointer-aware lowering, factory-owned writable static
  tables, managed class/instance allocation sets, functional C/C++ factory
  manager binding, cache and serialization rules, explicit wrapper-versus-JIT
  state ownership, and strict rejection of compute stubs in parity tests.
- Added a dedicated `tests/impulse-tests` strategy with `cpp-mem0`, `c-mem0`,
  `cranelift-mem0`, and `all-mem0` targets, self-contained DSP fixtures, a
  portable allocation trace, semantic JSON checks, and ordinary-versus-mem0
  plus optimized-versus-unoptimized runtime parity.
- This commit is planning/documentation only. No compiler behavior or public
  API is enabled yet; the document's whitespace check is clean.
