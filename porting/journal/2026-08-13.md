# 2026-08-13

## Plan the `-mem0` custom memory-manager port

Commit date: 2026-08-13
Source commit: this planning commit

- Analyzed the pinned Faust C++ `-mem`/`-mem0` contract, its generated C++
  lifecycle, memory-layout JSON, and `compute_cost` visitor. Recorded the
  reference weaknesses that the Rust port must not reproduce: heuristic object
  size, zero-sized static-table sentinels, empty `init`, shallow `clone`, global
  manager rebinding, unchecked allocation failure/alignment, incomplete type
  vocabulary, and defective conditional cost accounting.
- Defined one typed `Mem0Analysis` as the source of truth for generated C,
  generated C++, Cranelift JIT storage, manager descriptions, JSON
  `memory_layout`, and versioned `compute_cost`. Scope is deliberately limited
  to the four `mem0` aliases; `mem1`–`mem3` stay rejected.
- Specified an adapted, versioned plain-C manager ABI with alignment and opaque
  context, while preserving the legacy-compatible C++ manager surface. The
  plan includes transactional allocation, captured-manager destruction,
  poison/failure testing, exact target-ABI metadata, and deep clone behavior.
- Extended the design to Cranelift: external-buffer pointer slots in
  `StructLayoutPlan`, pointer-aware lowering, factory-owned writable static
  tables, managed class/instance allocation sets, functional C/C++ factory
  manager binding, cache and serialization rules, explicit wrapper-versus-JIT
  state ownership, and strict rejection of compute stubs in parity tests.
- Added a dedicated `tests/impulse-tests` strategy with `cpp-mem0`, `c-mem0`,
  `cranelift-mem0`, and `all-mem0` targets, self-contained DSP fixtures, a
  portable allocation trace, semantic JSON checks, and ordinary-versus-mem0
  plus optimized-versus-unoptimized runtime parity.
- This commit is planning/documentation only. No compiler behavior or public
  API is enabled yet; the document's whitespace check is clean.
