## `faustprobe` takes the `faust-rs` compiler options; the FFI constructors honor `-pn`, `-mcd`, `-dlt`, `-ct`

Commit date: 2026-09-25

Source commit: this commit

`faustprobe -pn pink_trombone_demo_test tests/demos_tests.dsp` was refused by
Clap (`-p` unknown), so one test of a library's test file could not be
probed. Forwarding it would not have been enough: the shared FFI argv parser
(`ffi_common::args::parse_ffi_compile_args`) skipped every option it did not
know, `-pn` included, and the Cranelift and Interpreter factories compiled
`process` without a word.

- `FfiCompileArgs` gains `process_name` (`-pn`/`--process-name`), `mcd`,
  `dlt` and `check_table` (`-ct 0|1`); a missing or malformed value is an
  error. The Cranelift `compiler_from_argv` and the interp `with_argv_options`
  apply them with the facade's `with_process_name`/`with_mcd`/`with_dlt`/
  `with_check_table`. They reach the factory cache key through the argv.
- `faustprobe` gets a `CompilerOptions` group, under the `faust-rs` long
  names: `--process-name`, `--vec`/`--vs`/`--lv`, `--scheduling-strategy`,
  `--mcd`, `--dlt`, `--check-table`, `--table-init`,
  `--table-init-sample-rate`. They go to the compiler through
  `compiler_args`, so FILE, the OTHER of `--compare`, the other width of
  `--check width` and the worker of `--check determinism` (forwarded
  explicitly) all see them. Refused: `--process-name` with `--eval` (the
  expressions are the program), all of them with `--nvoices` (the voices are
  compiled without them, as `--bra-tape` already was, now refused too).
  Left out: output options, `-mem`, `-ec`, `-os`.
- The single-dash spellings: `normalize_legacy_args` lived in the `faust-rs`
  binary (`crates/compiler/src/cli/args.rs`, under `main.rs`), out of reach of
  another binary; a first version of this change copied its table into
  faustprobe. It moved, unchanged, into the library as
  `compiler::normalize_legacy_args` (`src/legacy_args.rs`), re-exported where
  it was; faustprobe calls it before `Args::parse_from`. One public item added
  to the baseline, deliberately. `cli-parser-check` lists faustprobe's `main.rs`
  as a fourth normalized Clap entry point. `impulse_cranelift` keeps its own
  per-argument table: its long names (`--vectorize`, ...) differ.
- Registry: new DIFF-API-007 (the subset of compiler options the FFI
  constructors honor, the rest ignored where C++ applies or rejects them),
  DIFF-CLI-011 mentions the forwarded options.

Tests: `ffi-common` parses and refuses the new options;
`process_name_delay_and_table_options_reach_the_compiler` (cranelift-ffi)
shows each option changes the FIR of a program and its default spelled out
does not, and fails when `with_program_options` is not called;
`crates/cranelift-ffi/tests/compiler_options_probe.rs` renders `other` under
`-pn`/`--process-name`, passes `--check determinism` under `-pn` (fails when
the worker is not given the options), renders a delay loop bit-identically
under `-vec`, `-lv 1`, `-ss`, `-mcd`, `-dlt`, and checks the four refusals.
Docs: `docs/faustprobe-user-guide-en.md` section 3, the CLI-parser policy
allowlist. No compile-budget run: the pipeline crates are untouched apart
from the moved normalizer, and the gate cannot run on this Mac.

## Imports are looked up in the C++ order: the working directory, the last `-I` first, the source's directory last

Commit date: 2026-09-25

Source commit: this commit

`faust-rs -pn pink_trombone_demo_test tests/demos_tests.dsp`, run from a
faustlibraries checkout, failed with `undefined symbol pink_trombone_demo`:
it loaded the installed `demos.lib`, the C++ compiler the checkout's. The C++
`fopenSearch` (`compiler/parser/enrobage.cpp`) opens the name as given, relative
to the working directory, before walking `gImportDirList`; faust-rs never tried
it for `import` and tried it last for `library`/`component`. Checking the rest
of the order against `compiler/global.cpp` found two more differences, both
aligned with the user's agreement:

- several `-I`: C++ inserts each at the front of `gImportDirList`, so the last
  one is searched first (`-I a -I b` finds `b/x.lib`); faust-rs searched them in
  the given order. The CLI (`run_main`) and the shared FFI argv parser
  (`ffi_common::args::parse_ffi_compile_args`, used by faustprobe and the
  Cranelift and interp factories) now reverse them; `impulse_cranelift` emits
  its priority list backwards to keep it. Search paths passed through the Rust
  API keep their order.
- the main file's directory: C++ pushes `gMasterDirectory` after
  `FAUST_LIB_PATH` and the installed libraries; faust-rs put it first, so a
  library next to the source shadowed an installed one of the same name from
  any working directory. `paths::build_import_search_paths` now puts it last.

The two resolvers (`SourceReader::resolve_import_from` for `import`, eval's
`candidate_loaded_source_paths` for `library`/`component`) had drifted apart;
they now share `parser::import_candidates` (the name as given, then the search
paths, then the importing file's directory), a new public function. The name as
given is the bare relative path, which `exists()` resolves against the working
directory and which also matches a virtual source registered under a bare name
(the in-memory library bundles of the Wasm artifact). Eval's loaded-source cache
is consulted only up to the first candidate that exists, so a later candidate
already cached cannot shadow it.

Tests: `crates/compiler/tests/import_search_order.rs` (six scenarios for each of
`import` and `library`, every expected value replayed with C++ faust 2.89.2),
`import_dir_probe.rs` updated (without `-I` the installed `analyzers.lib` wins
over the one next to the program, which wins when run from its directory), the
path-order unit tests and the two argv parser tests updated.
`docs/user-cli-guide-en.md` states the order. No registry entry: the three
differences were unrecorded and are now closed. Compile budget: one relative
`exists()` per import; not measured (the gate cannot run on this Mac).
