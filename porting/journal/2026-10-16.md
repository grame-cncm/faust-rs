## WASM speed, W4 study: the cold arms cost nothing; counter method corrected

Commit date: 2026-10-16

Source commit: this commit (parent `e0327d1f`).

Study only; no code change. Recorded in section 8 of
[`wasm-compute-speed-analysis-and-plan-2026-10-16-en.md`](../wasm-compute-speed-analysis-and-plan-2026-10-16-en.md).

- **Measurement error found.** Earlier instruction and cycle counts subtracted
  a 0-block run from an N-block run. That difference carries a fixed cost
  (about 30,000 instructions per sample over 1,000 blocks of the light body),
  and the cost grows with function size. The cold `if` arms looked expensive
  for that reason alone.
- **Steady state.** Measured as the slope between two run lengths, the arms
  are free. Removing them, replacing them with a call, or outlining them into
  functions (live-ins as arguments or through memory) all stay within 1 %:
  89,800 instructions and 28,300 cycles per sample for W1. W4 is dropped.
  Wall-clock figures were steady-state measurements and stand.
- **W1 re-measured by slope.** Instructions: voice −12 %, light body −21 %,
  imaged body −35 %, bank −37 %. Cycles move about as the wall clock does.
- **What remains.** The light body (W1) runs 1.11 times em++'s instructions
  but about 1.45 times its cycles. The mix is almost the same: equal FP work,
  spills and stores, plus 2,300 loads (C3) and 4,800 immediate moves. Data
  locality and frame size match. An instruction-fetch or layout effect is
  suspected (W6, hardware counters).
- **Layout prototype (W5).** A throwaway patch put small fields first and
  static tables last, with identical outputs. Voice instructions drop 34 %,
  the bodies' 3 %. Decision D4 is open, since the layout would no longer
  follow Faust C++'s declaration order.

## WASM: constant struct addresses in the memarg offset (W1)

Commit date: 2026-10-16

Source commit: this commit (parent `88dc9776`).

W1 of
[`wasm-compute-speed-analysis-and-plan-2026-10-16-en.md`](../wasm-compute-speed-analysis-and-plan-2026-10-16-en.md),

- **Constant addresses.** `K + i * size` goes into `offset=` over

  the value the former code computed, so with `-ct 0` an out-of-table index

  instructions than `offset=K`, with cycles within noise.

  layout, the exports and `get`/`setParamValue` are unchanged, so no registry
  entry is needed.

## WASM `compute` speed: analysis and plan

Commit date: 2026-10-16

Source commit: this commit (parent `8886a772`).

Point 14 of faust-coopiano's `faust-rs-issues/RAPPORT.md`: `-lang wasm` code
runs 1.3 to 1.8 times slower than faust-rs's C++ compiled by `em++ -O3`.
Analysis only, recorded in
[`wasm-compute-speed-analysis-and-plan-2026-10-16-en.md`](../wasm-compute-speed-analysis-and-plan-2026-10-16-en.md).

- `wasm-opt -O3` gains nothing on the light body and loses 8 % on a
  resonator bank.
- The main cause is the address form. Each struct access is
  `dsp + K + i * size` in separate i32 instructions. TurboFan value-numbers
  every `dsp + K` and spills it. Faust C++ emits absolute addresses when the
  memory is internal. A WAT rewrite that folds `K` into `offset=` cuts cycles
  per sample by 23 % on the voice, 27 % on the light body and 45 % on the
  imaged body (93–102 % of a core down to 52–53 %, em++ 49 %). Outputs stay
  bit-identical.
- The FIR reads every recursion state at the top of the sample loop, and V8
  does not move loads. Moving them to their first use takes 18 % more off a
  400-mode bank, which then beats Faust C++ wasm and em++. It gains little
  on coopiano. Forwarding stored values gains 2 to 3 %.
- The light body keeps a 1.35x gap. The rarely-taken `if` arms (control
  change, gated blocks) cost faust-rs 10k to 13k cycles per sample and em++
  at most 2k. Without them, W1 matches em++. Branch hints do not help in
  V8 12.4. The cause is open (W4).
- Plan: W1 address form, then W2 sinking with an independent alias checker,
  W3 forwarding, W4 investigation. D1 (absolute or `dsp`-relative base),
  D2 (wasm emitter or FIR pass) and D3 (scope) wait for the user.

## Normalized sums join the terms that depend on state last (upstream `d4d51e5ed`)

Commit date: 2026-10-16

Source commit: this commit (parent `354e208`).

faust-coopiano found that `1 - c - o` (a rate-limited damper openness) is
normalized as `(1 - o) - c`, where Faust 2.90.10 builds `(1 - c) - o`, hoists
`1 - c` and lets the follower reach 0 exactly (faust-coopiano
`faust-rs-issues/RAPPORT.md`, point 15). It is not a faust-rs divergence: the
pinned reference (`8eebea429`, 2.84.3) prints the same normal form as
faust-rs. Upstream changed it after the reference, in commit `d4d51e5ed`
(Yann Orlarey, 2026-08-09), with a fifth "audio-recursive" order. The user
chose to port it, as `gApplyMemo` was ported before it. Plan:
`porting/aterm-late-state-join-port-plan-2026-10-16-en.md`; registry:
DIFF-BEH-023.

- **`tlib`.** `TreeArena::contains_recursion`, the `kContainsRec` bit of C++
  tlib, is computed when a node is interned: a `SYMREC`, `SYMREF`,
  `DEBRUIJNREC` or `DEBRUIJNREF` node occurs in the tree. `SYMREF` is
  included because faust-rs writes a self-reference as
  `proj(i, SYMREF(var))`.
  - The four tags are interned when the arena is created, so later tag ids
    shift by four; nothing depends on their values (the corpus differential
    shows no other change).
  - One byte per node; this adds one line to the public-API baseline and
    MEMOIZATION §2.25.
- **`normalize`.** `state_order` gives 3 to a term that some state reaches
  and `sig_order` otherwise.
  - `Aterm::normalized_tree` folds orders 2 and 1 onto the constants as
    before, then joins the state terms last as the right operand (negative,
    then positive), so `{slow, state}` keeps `slow + state`.
  - `Mterm::complexity` weighs a state factor `1 + 3`, as upstream's uncapped
    `sigOrder` does. The commit message does not say so, but upstream's
    `mterm::complexity` reads it.
  - The grouping of products keeps `sig_order`, upstream's cap at 3.
  - The pair pruning of `greatest_divisor` stays exact: every common factor
    still weighs more than 0, and the property test now includes a state
    factor.
- **Tests.**

  - `tlib`: the bit on each tag and its propagation.

    `fSlow0 = 1.0f - fHslider0`, and the interpreter follower reaches 0
    exactly at optimization levels 0 and max.
  - Both mutations are caught: no state order (three tests), and the state
    terms joining on the left (two).

## Diagnostics: reserved words, unary minus, and arity errors located at the program's composition

Commit date: 2026-10-16

Source commit: this commit (parent `06ad235`).

Points 7 to 9 of faust-coopiano's `faust-rs-issues/RAPPORT.md`: three
rejections whose diagnostics did not say why, or pointed elsewhere.

- **Reserved words** (`crates/parser/src/lib.rs`). `f(x) = x * rad with {
  rad = 2.0; }` failed with lrpar repair sequences only. The parse error now
  says when the unexpected token, or the word just before it (the parser took
  `rad` for its primitive and expected `(`), is a word faust-rs reserves
  while Faust C++ accepts it as an identifier: `fad`, `rad`, `cinput(s)`,
  `coutput(s)` (both C++ compilers accept them), and `ondemand`,
  `upsampling`, `downsampling` (reserved by the C++ reference branch too,
  accepted by the 2.90 releases, checked with 2.90.10), and proposes a
  rename. Making them contextual keywords would let C++ programs compile; it
  is a grammar and compatibility decision, not taken here.
- **Unary minus**. The grammar's unary minus takes a name or a number, in C++
  too. `-max(1, 2)` and `exp(-sin(0.5))` now get the rule and `0 - max(...)`
  (and why `-(max(...))` is not it: a partial application). `exp(-L.g(2, k))`
  reads `((0 - L).g)(2, k)` and failed with "access requires a captured
  closure value" and no position: `eval_guidance` recognizes the unary-minus
  box under the failing access and states the rule; `eval_error_node` now
  returns the node of `ExpectedClosureValue`, and the grammar records the
  `-` token's span on the unary minus (`ParseState::unary_minus_from_token`,
  a sibling of the `*_from_token` builders the grammar actions call; one new
  public-API baseline line), so the error points at the `-`.
- **Arity errors**. A composition built by evaluation has no position, and
  `maybe_add_source_label` fell back to its first located descendant: for
  `bad = pair : +, pair : +` the `(1, 2)` of `pair` on another line, for
  `m(1) : …` the `(_, _)` in `m`'s body. Picking only descendants located at
  a single place, as the report suggested, would not have helped: both are
  written once. The evaluator now records, for every `:`, `,`, `<:`, `:>`,
  `~` box it builds, the source composition it was evaluated from
  (`LoopDetector::record_composition_origin`, `None` once two sources build
  the same box), handed out as `EvalStats::composition_origins` (remapped
  through `a2sb` like `def_names`). Propagation errors use it first: the
  composition the program writes is labelled `failing composition`; a box
  with two origins, or whose origin the sources write at several places,
  gets the program's call instead of a guessed line.
- Registry: DIFF-SRC-001/002 (`fad`/`rad` reserved) and DIFF-BEH-005.
- Tests (`crates/compiler/tests/diagnostic_hints.rs`): reserved words at the
  word and after it, the reference-branch wording for `ondemand`, no note on
  an unrelated error; unary minus before a primitive, valid minus forms still
  parsing; the access hint located at the `-`; arity errors located at the
  faulty `:` for both reproducers; and no composition blamed for a box with
  two origins (the same text twice, and an alias). Mutations rejected: no
  origin lookup, the first origin kept instead of none, no previous-word
  check.

Validation: generated C++ and diagnostics byte-identical over the scalar

## Small integral real powers are inline products on every backend (DIFF-BEH-022)

Commit date: 2026-10-16

Source commit: this commit (parent `8cb6431`).

Normalization writes `x*x` as `pow(x, 2)`, as C++ does, and `emit_pow`
lowered every real power to a `pow`/`powf` call: a libm call per square in
the Cranelift JIT and the interpreter, and textual code slower than C++.
faust-coopiano's `faust-rs-issues/RAPPORT.md` point 4: 256 squares ran at
29× real time under faustprobe against 135× written as products, and its
voice had 391 `pow(x, 2)` per sample before a workaround. C++
`powprim.hh::generateCode` expands a literal integral exponent from 0 to 8
into a `<Klass>_faustpower<n>_f` helper computing `((x·x)·x)…`, on the
backends where `gNeedManualPow` holds, and keeps `pow` elsewhere (Interp,
WASM, JSFX, Codebox, Cmajor, JAX), which cannot all call a local function.

- `crates/transform/src/signal_fir/leaf_emit.rs`: `emit_pow` writes that
  product inline for a real result, on every backend and in scalar and
  vector code (both lowerers share the emitter). The base is one FIR value
  used in every factor, so FIR common-subexpression materialization binds a
  non-trivial base to one temporary, evaluated once as the helper's argument
  is. An integer base is converted first, as for `pow`. Integer results keep
  their inline product (DIFF-BEH-020); a negative integer literal, which C++
  expands to the base itself, keeps `pow`.
- A helper on every backend was considered, as asked, and set aside: four
  backends cannot call a local function (sub-containers are flattened for
  interp, wasm, jsfx and codebox for that reason) and Cranelift would need
  internal calls, where the inline product needs nothing from any backend.
- `porting/faust-rs-vs-faust-cpp-differences-en.md`: DIFF-BEH-022.
- Tests (`crates/compiler/tests/real_pow_expansion.rs`): products in scalar
  and vector code, float and double, verified FIR and a certified vector
  plan; a foreign-function base evaluated once; non-integral, larger,
  negative and non-literal exponents keep `pow`; interpreter results equal to
  the left-associated products bit for bit at optimization levels 0 and
  max. Mutations rejected: no expansion, a right-associated product,
  exponents −8 to 9 accepted.

Measurements: r09a (256 squares) under faustprobe 29× → 133× real time,
equal to the hand-written products (129×).

Validation:

- every backend reachable through `-lang` (c, cpp, rust, julia, wasm,
  wast, interp, cranelift, cmajor, codebox, asc, fir) compiles the test
  programs with the exit status of the base binary;
- corpus differential (base `8cb6431`, every `.dsp` under `tests/` and
  `examples/`): no change in exit status or diagnostics; 106 programs
  differ in scalar mode, 105 with `-vec`, 106 with `-double`, and in each
  the base output had `pow` calls with a small integral literal exponent
  (3 200 in scalar mode), none of which remain, while every other `pow`
  call is unchanged;

## Long sums: greatest_divisor scans only the pairs that can share a divisor

Commit date: 2026-10-16

`:>` builds the left-nested sum `((x0 + x1) + x2) + …`, and `simplify`

Commit date: 2026-10-16

Source commit: this commit (parent `13040c0`).

After the `gApplyMemo` port, what remained of the coopiano voice's
evaluation was the `(expr, env)` eval cache (`porting/MEMOIZATION.md`
§2.4b): 10.05 M entries of 128 bytes, its rehash from 2^23 to 2^24 buckets
being the 4.3 GB transient peak at the end of evaluation. An entry is the
32-byte key and an `EvalValue`, which was 96 bytes because
`EvalValue::PatternMatcher` held its `PatternMatcherValue` inline, although
the cache only ever stores boxes and closures.

  `PatternMatcher(Box<PatternMatcherValue>)`. `EvalValue` is 40 bytes (the

  store and source-context pointers, and a store freed during the pass (an

  whose layers would hit stale entries. `last_pinned` makes the insertion
  path one pointer comparison unless the store changes. The
  `FAUST_EVAL_APPLY_PROFILE` line now also prints the number of pinned

## eval: pattern matchers are persistent values (`DIFF-GAP-018` closed)

Commit date: 2026-10-16

Source commit: this commit (parent `d854350`).

A `case` function passed as an argument and applied more than once to
different arguments kept the pattern-variable bindings of its first
application: `h(p) = p(2), p(3); process = h(case { (x) => x + 1; });` failed
with `FRS-EVAL-0099` (C++: `3, 4`), and with a later rule binding no
variable, `f = case { (x) => x + 1; (3) => 100; }; process = h(f), f(3);`
silently gave `3, 100, 4` (C++: `3, 4, 4`). `apply_pattern_matcher` bound
the variables in place into the matcher's rule environments, which every
copy of the matcher shares (a `boxPatternMatcher` handle, a matcher bound to
a parameter); C++ pushes a new layer per binding
(`E[r->r] = pushValueDef(assoc->id, Z1, E[r->r])`,
`compiler/patternmatcher/patternmatcher.cpp`).

- `crates/eval/src/pattern_matcher.rs`: a binding pushes a child layer and
  replaces the rule's slot with it, one layer per rule and argument rather
  than per binding (equivalent: the nonlinearity lookup reads the new layer
  first and still stops at the rule's barrier). Mapping `1:1` in behaviour.
- `crates/eval/src/lib.rs`, `eval_case_value`: one barrier layer for every
  rule, as C++ `listn(len(rules), pushEnvBarrier(env))`; nothing writes into
  it any more.
- The apply memo's restriction to unshared matchers is lifted:
  `PatternMatcherValue::fresh_env` is no longer cleared on a stored handle
  or on a read from an environment, a copy of a matcher in its initial state
  being the same function as the fresh one. Measured to matter: no change on
  the 134 DSPs of `tests/impulse-tests/dsp` and `tests/compile-budget/dsp`
  nor on the coopiano voice, but a `case` passed to itself through an
  overlapping recursion, `fibk(k, n) = k(k, n-1) + k(k, n-2)`, which only
  evaluates since the fix, goes from exponential (release, `n = 27` 2.2 s;
  the reference `8eebea429`, without `gApplyMemo`, 50.8 s at `n = 25`) to
  linear (C++ 2.90.8 likewise). `porting/MEMOIZATION.md` §2.4e and §2.4b
  updated; the eval cache still does not keep matchers.
- Cost (release binaries before and after, best of five): compile-budget
  basket by hand within noise (worst 1.05 on an 11 ms case; the gate itself
  refuses on this machine, calibration under its 4 ms floor); coopiano voice
  identical memo counters, time and maximum resident set, generated C++
  byte-identical, 76 392 environment layers before and 76 357 after; over
  the 134 corpus DSPs 30 751 layers before and 38 186 after, with the same
  eval-cache entries.
- Tests (`crates/eval/src/apply.rs`):
  `a_shared_matcher_does_not_answer_for_a_fresh_one` now asserts `p(3) = 4`;
  `a_shared_matcher_keeps_its_applications_apart` (five programs, values
  from C++ `8eebea429` and 2.90.8: a `case` passed as an argument, nonlinear
  rules, a partially applied shared matcher, an outer definition named like
  a pattern variable); `a_case_handle_passed_through_a_recursion_is_memoized`
  (`fibk(fibk, 40)` under the 60 s budget); and the structural
  `applying_a_matcher_leaves_its_rule_environments_untouched`. Mutations

  `fresh_env` cleared on a stored handle (`fibk` times out).
- `DIFF-GAP-018` removed from `porting/faust-rs-vs-faust-cpp-differences-en.md`
  §9.

## eval: port of the C++ application memo (`gApplyMemo`)

Commit date: 2026-10-16

Source commit: this commit (parent `bf65d31`).

A call inside the body of a lambda was evaluated again at every application of
the lambda, so `f_i(m) = f_{i-1}(m) : \(x).(x + 0.5 * f_{i-1}(m))` cost `2^D`,
and a `case` recursion with overlapping calls (`fib`, `ma.chebychev`) grew like
Fibonacci. Both were found porting the coopiano piano to Faust
(`faust-coopiano/faust-rs-issues/RAPPORT.md`, items 1, 2 and 13), whose voice
spent 12.8 s and 11 GB of resident memory in evaluation. The cause: every
application evaluates its body in a new environment layer, which the
`(expr, env)` eval cache has never seen. Upstream Faust fixed the same cost
with `gApplyMemo` (`6789c5da8`, #1290), absent from the reference branch
`8eebea429`.

- `crates/eval/src/apply.rs`: `beta_reduce` memoizes one beta-reduction of an
  abstraction closure, keyed by the `abstr`, the identity of the captured
  environment and the evaluated argument; the head of
  `apply_pattern_matcher_value` memoizes a fresh matcher applied to its full
  argument list, keyed by the `case`, the environment it was evaluated in and
  the arguments. Only successful box and closure results are stored. Mapping
  `adapted` (C++ keys on the hash-consed closure or `boxPatternMatcher` tree and
  the whole argument list): rationale, the treatment of box functions and the
  lifetime are in `porting/MEMOIZATION.md` §2.4e.
- A matcher is fresh (`PatternMatcherValue::fresh_env`) until it is stored as a
  `boxPatternMatcher` handle or read from an environment. A shared matcher
  keeps the bindings of its earlier applications, because pattern variables
  are bound in place into its rule environments; that defect predates the memo
  and is recorded as `DIFF-GAP-018`; the memo is kept off shared matchers so it
  does not spread it.
- `LoopDetector::pinned_environments` keeps alive every environment store an
  apply-memo key points to, so its address cannot be reused within the pass.
- The automaton cache holds `Rc<Automaton>`, shared with every matcher,
  instead of a deep copy per `case` evaluation, lookup and handle read.
- `FAUST_EVAL_APPLY_PROFILE=1` prints the memo's probes and hits per kind and
  the sizes of the memo, of the eval cache and of the environment store.
- Measured (release, Apple M5): `r01_eval_call_reuse.sh` lambda column 67 ms
  to 0.10 ms at `D = 14`; `fib(22)` 194 ms to 0.19 ms; the coopiano voice
  evaluation 12.8 s to 2.0 s, maximum resident set 11.1 GB to 4.5 GB, whole
  compilation 22.9 s to 12.1 s, generated C++ byte-identical. Three
  compilations of the voice at once now take 14.8 s each with 0.6 s of system
  time (`faust-rs` to C++; the report measured 216 s each and 126 s of system
  time through `faustprobe` before). The rest of the
  voice's evaluation is the eval cache itself, 10 M entries of about
  128 bytes.
- Documentation corrected: `MEMOIZATION.md` §2.4c and §3.7 said C++
  hash-conses its environments. Its layers are `unique` (`pushNewLayer`); its
  cross-level hits come from `evalIdDef`, which evaluates a bound value under
  the empty environment, and from `gApplyMemo`. §3.7 is reframed as bound
  values evaluated under a canonical environment.
- Tests: four in `crates/eval/src/apply.rs`, each under a 60 s budget, with
  five mutations rejected (memo off for abstractions or for matchers, the
  environment dropped from either key, a stored handle kept fresh).
- Compile-budget basket, release binaries before and after, best of five: no
  case slower beyond noise (worst 1.03 on an 8 ms case); `dx7_alg5` `--check`
  124 ms to 76 ms, `reverb_designer` 186 ms to 136 ms. The
  `compile-budget-check` gate itself refuses on this machine (calibration
  `karplus.dsp` 3 ms, under its 4 ms floor), as it did before this change; the
  comparison was done by hand for that reason.
- Validation: fmt, clippy `-D warnings`, the workspace tests (3219 passed),
  the five structure gates and `golden-check` (292 cases) pass.
