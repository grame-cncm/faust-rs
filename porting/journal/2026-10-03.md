## `adaptive_fad` taught: tutorial §11.5 and DDSP example 15

Commit date: 2026-10-03

Source commit: this commit

The two examples of
`porting/adaptive-fad-teaching-examples-proposal-2026-10-03-en.md`, with the
tutorial section placed at §11.5 in review, next to the clocked loops the
operator builds on.

- Tutorial §11.5, "Learning the sliders of an existing program", EN and FR.
  It uses a two-slider program (a low-pass cutoff and a gain) and has three
  programs:
  - the controls read with `cinputs` and `cinput`;
  - `adaptive_fad` with one Adam rate: the cutoff moves 3 Hz in 70 000
    samples while the gain overshoots to 1.63;
  - a rate per slider, 1 % of its range read from `cinput`, which reaches
    2500 Hz and 1.2 with a residual of 2.4e-8 rms.

  Three tests (`s11_5_*` in `crates/cranelift-ffi/tests/tutorial_examples.rs`)
  pin the quoted figures, and the program count goes from 33 to 36. The
  intro, "Going further" and the "Common walls" table follow; the new row of
  the table covers a slider stuck at its bound by a function that is not
  differentiable at its default.
- DDSP example 15, `tests/corpus/ddsp_fad_adaptive_pedal.dsp`: an ordinary
  six-slider drive pedal under an `hgroup` learns its hidden setting from the
  same program under named literal modulations. Adam steps at 1 % of each
  slider's range every 512 samples. All six sliders come within 1e-4 in
  200 000 samples, with a residual of 2e-7 rms, at about 130x real time. Two
  choices make it identifiable: the envelope separates drive from level, and
  `fi.peak_eq_rm` replaces `fi.peak_eq`, whose `abs` of the gain is not
  differentiable at 0 dB. The test `fad_adaptive_pedal_learns_its_six_sliders_without_being_rewritten`
  checks it in f32 (residual 7.1e-7). `ddsp-examples-{en,fr}.md` (title,
  table, paragraphs) and `libraries/README.md` now count fifteen programs.

## `rad`: a read-only table read in a temporal body no longer refused

Commit date: 2026-10-03

Source commit: this commit

`rad(os.osc(110) * g, g)` failed with `FRS-SFIR-0004 signal RdTbl(..) not
supported in BlockReverseAD backward pass (B6)`. The phase recursion of
`os.osc` routes the body to the `BlockReverseAD` fallback, and that sweep had
no `RdTbl` arm, although `docs/rad-note-en.md` §3.6 lists read-only tables as
supported. It surfaced in the `adaptive_fad` proposal (finding F2): an
`adaptive_rad` loss whose excitation is `os.osc` did not compile.

- `propagate_bra_adj` (`crates/transform/src/signal_fir/module/bra.rs`) now
  handles `RdTbl`. The contents of a read-only table (a `Waveform`, or a
  write-once `WrTbl(_, _, nil, nil)`) are constant and receive nothing. The
  read index is an integer after signal promotion and is a gradient boundary,
  like the existing int→real `FloatCast` rule: no real adjoint enters integer
  arithmetic. A writable table is refused, as by the symbolic sweep. A
  non-integer index is refused too; it is not reachable after promotion.
- Parity: FAD's tangent through an integer index is zero, and the symbolic
  sweep stops at the `int_cast` that produced the index, so the three agree.
  On `os.osc(f) * g`, `rad` and `fad` give the same `d/dg` sample for sample
  and both give `d/df = 0`.
- Tests (`crates/compiler/tests/block_reverse_ad.rs`). Both fail without the
  rule, with the original error.
  - `fir_bra_readonly_table_read_on_the_primal_path` covers a `waveform` and
    a generated table read at an integer phase recursion.
  - `fir_bra_seed_in_a_table_index_has_zero_gradient` checks a seed reaching
    the table only through `int(x * 3)`.
- Docs: `docs/rad-note-en.md` §3.6 and `docs/rad-usage-en.md` say how the
  integer index behaves in both sweeps. The proposal's F2 is marked fixed.

Observed, not changed: the BRA sweep forwards an adjoint through `IntCast`
unchanged. The note's table (§3.5), the symbolic sweep and FAD all give it a
zero contribution. The new `RdTbl` arm does not depend on that rule, since it
never hands its index an adjoint. The discrepancy is recorded here for a
separate decision.

## Proposal: two teaching examples for `adaptive_fad`

Commit date: 2026-10-03

Source commit: this commit

`porting/adaptive-fad-teaching-examples-proposal-2026-10-03-en.md` proposes
how to teach `optimizers.lib`'s `adaptive_fad` / `adaptive_rad` (a whole
program learning its own sliders through `cinputs`, `cinput` and the `"*"`
modulation), which neither the tutorial nor the DDSP example set covers yet.
Every figure in it was measured with `faustprobe` on `control-inputs-wildcard`
rebased on `main-dev`.

- Simple: a new tutorial §13 on a two-slider program (low-pass cutoff and
  gain), in three programs: reading the controls with `cinput`; one Adam rate
  for both, where the cutoff barely moves and the gain overshoots to 1.63;
  one rate per slider read from its range, which reaches 2500 Hz and 1.2 with
  a residual of 2.4e-8 rms.
- Ambitious: DDSP example 15, an ordinary six-slider drive pedal that learns
  its hidden setting from the same program under named literal modulations.
  All six sliders come within 1e-5 in 200 000 samples at 126x real time;
  `adaptive_rad` drifts on it, since the four filters are recursive.
- Findings: `fi.peak_eq` is not differentiable at its 0 dB default (`abs` of
  the gain), so the slider jumps to its bound; `rad` refuses the read-only
  table of `os.osc` (FRS-SFIR-0004 in the block reverse sweep), contrary to
  `docs/rad-note-en.md` §3.6, which is being fixed next.

The documentation, the fixture and the tests are not part of this commit;
the proposal lists their deliverables and pass criteria.
