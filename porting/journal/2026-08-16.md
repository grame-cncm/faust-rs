## faust-probe: three limits found by using it on a real synthesis job

Commit date: 2026-08-16

Source commit: this commit

Implementing a plucked-string synth and measuring it end to end with
`faust-probe` turned up three limits, none of which shows up on a toy DSP.

**`--at` could not be combined with `--sweep`.** The check was a blanket ban,
justified by "a schedule would replay identically per point while the swept
value changed underneath — representable, but almost certainly not what the
caller meant". For a triggered instrument that is exactly what the caller means:
strike the note once per point and see how the result moves with the swept
parameter. Measuring attack level against pitch is the canonical case, and it was
unreachable — the pluck happened to start in its own struck state, so the
measurement was possible only by luck.

The genuine conflict is narrower: a schedule that writes a control the sweep is
also driving, where the scheduled write silently wins and the reported axis value
is not what the render used. That is now the error, named to the offending
control, and `Schedule::param_paths` exists to detect it.

**`--sweep` required `--format json`.** The reason given was that CSV "describes
a single render and would concatenate them into something unreadable". True of
the per-frame dump, but a sweep has an obvious tabular form: one row per point,
the swept values then what each render reduced to. That is now what
`--sweep --format csv` emits, with the frame dump suppressed, so

```
faust-probe --sweep freq=55,110,220 --reduce peak dsp.dsp
freq,peak_out0
55,0.550540865
110,0.554010880
220,0.558590684
```

replaces a JSON document whose shape had to be discovered before anything could
read it. `--format ir` still refuses, since a `.ir` file is one render by
definition. The reduction itself was factored into `reduce_channel` so the JSON
and CSV paths cannot report different numbers for the same window.

**`--quiet` wrote nothing to stdout.** Statistics went to stderr, which is right
while the CSV dump owns stdout, but `--quiet` exists to print statistics *instead
of* the dump — so `faust-probe --quiet … > out.txt` produced an empty file. This
cost a measurement during the session: `2>/dev/null`, added to hide compilation
noise, silently discarded the result. With `--quiet` the statistics now go to
stdout; without it they stay on stderr.

**Check.** Two tests on `param_paths`, one with a mixed schedule and one empty.
`cargo test -p cranelift-ffi` (148), `cargo fmt --check` and `cargo clippy` are
green. The JSON sweep output and the plain CSV dump are unchanged, verified by
rendering both before and after.

## `--dump-sig-dag`: print the signal graph as a DAG instead of a tree

Commit date: 2026-08-16

Source commit: this commit

`dump_sig` and its variants print a *tree*. The arena is hash-consed, so a shared
subgraph is a single node, but printing re-expands it at every path that reaches
it. On `fi.tf2` the effect is mild — the single recursion is named three times
under the numerator — and it is easy to assume the rest of the library behaves
the same way. It does not: the cost is the number of *paths*, which grows
exponentially with filter order.

Measured on `--dump-sig` output size versus the new dump, one output each:

| expression | tree | DAG | ratio |
|---|---:|---:|---:|
| `fi.tf2(…)` | 1.3 kB | 740 B | 1.7× |
| `fi.lowpass(3, 1000)` | 18 kB | 2.0 kB | 9.2× |
| `fi.lowpass(6, 1000)` | 164 kB | 3.0 kB | 53.9× |
| `fi.highpass(8, 1000)` | 569 kB | 4.0 kB | 141× |
| `ve.diodeLadder(1000, 0.5)` | 800 kB | 5.2 kB | 154× |
| `re.mono_freeverb(…)` | 1.6 MB | 6.0 kB | 273× |
| `fi.bandpass(4, 500, 2000)` | 2.3 MB | 6.5 kB | 358× |

A 2.3 MB dump for one fourth-order bandpass is not a readable artifact, and the
trend across orders 3/6/8 shows it is not a plateau.

**Change.** New `signals::dump_sig_dag(arena, roots, controls)` walks the graph in
post-order, gives each interior node a dense index and prints it exactly once:

```text
n0 = SIGINPUT(int(0))
n1 = DEBRUIJNREF(int(1))
n2 = SIGPROJ(int(0), n1)
n3 = SIGDELAY1(n2)
…
n11 = SIGPROJ(int(0), n10)
n12 = SIGBINOP(op=mul (*), n11, float_bits(0x3fd3333333333333))
n13 = SIGDELAY(n11, int(1))
n16 = SIGDELAY(n11, int(2))
[0] = n18
```

Beyond size, this makes node identity *syntactic*. A consumer reading the tree
dump cannot distinguish two occurrences of one node from two structurally equal
but distinct ones without re-deriving hash-consing on its side; with indices the
question is textual. That was a real cost downstream: an external analyzer over
this dump had to compare the *analyses* of the recursions it found, because it
could not deduplicate the terms themselves.

Design points worth recording. All roots share one numbering, so structure common
to two outputs is printed once instead of once per output — the tree dump repeats
it. Atomic leaves (`int`, `float_bits`, `sym`, `str`, `nil`) stay inline; binding
them would roughly double the line count and they carry no sharing worth naming.
Numbering is a dense post-order counter rather than the arena `SigId`, which is
allocation-ordered and would leak unrelated compilation history into the output.
The traversal is iterative for the same reason the existing dump is: a deep left
spine must not recurse.

The control-range annotation added earlier today applies here too, so
`--dump-sig-dag` carries the declared `init`/`min`/`max`/`step` of slider-like
controls exactly as `--dump-sig` does.

**Check.** Three tests: sharing printed once, numbering shared across roots, and
a root that is itself an atomic leaf inlined into the marker rather than left
dangling. `cargo test -p signals -p compiler --all-targets` (676 tests), `cargo fmt --check`
and `cargo clippy` are green, and the tree dumps are untouched, so their differential assertions still
hold.

**Not done.** `--dump-sig` keeps its tree output rather than switching to the DAG
form. The two answer different questions — a tree is what you want when reading
one small expression, a DAG when reading a real library function or feeding a
tool — and the tree dumps remain the reference for structural differential
checks. Deciding whether the DAG form should become the default is a separate
call, and it should be made after something actually consumes it.

## `--dump-sig` now resolves the declared range of slider-like controls

Commit date: 2026-08-16

Source commit: this commit

A signal node stores only a stable `ui::ControlId`: `hslider("d", 100, 0, 2000, 1)`
lowers to `SIGHSLIDER(int(0))`, and the declared `init`/`min`/`max`/`step` live in
the UI registry that `propagate` publishes as `SignalCompileOutput::ui`. That split
is right for the compiler, but it makes the dump unusable for any analysis over the
exported graph: a consumer cannot tell a slider bounded to `0..15` from one bounded
to `0..100`, and those two index a 16-entry table very differently.

The gap showed up while feeding `--dump-sig` output into an external range checker.
Every table read whose index came from a control had to be reported as *not proven*,
not because the program was unsafe — the backend clamps it, `std::min<int>(…, 15)`,
from the compiler's own interval analysis — but because the information the clamp is
derived from never reaches the dump.

**Change.** New `signals::dump_sig_annotated(arena, root, &UiProgram)`. It behaves
exactly like `dump_sig_readable` except on `SIGVSLIDER`, `SIGHSLIDER`, `SIGNUMENTRY`,
`SIGVBARGRAPH` and `SIGHBARGRAPH`, where the control's `ControlRange` is resolved and
spliced in after the id child:

```
SIGHSLIDER(int(0), init=0.0, min=0.0, max=100.0, step=1.0)
SIGVBARGRAPH(int(0), init=0.0, min=-1.0, max=1.0, step=0.0, SIGINPUT(int(0)))
```

Controls with no range — `SIGBUTTON`, `SIGCHECKBOX` — are left exactly as before,
since `ControlSpec::range` is `None` for them. Numbers are formatted with `{:?}`,
the shortest round-tripping form for `f64`, so the annotation is readable and
lossless at once. `--dump-sig` is switched to the new function; `&out.ui` was
already in scope at that call site.

**Why not change `dump_sig` / `dump_sig_readable`.** The obvious move is to make the
existing dumps carry the ranges. They cannot, and the reason is dependency direction
rather than output stability: `dump_sig_readable` is called from
`normalize::normalform` and `normalize::mterm`, and from `compiler::error_mapping`
when attaching a `signal_expr` debug fact to a diagnostic. None of those own a
`UiProgram`, and none would gain anything from one; threading a control registry
into `normalize` to serve a dump would be invasive for no benefit there. So
`dump_node_iter` takes an `Option<&ui::UiProgram>`, the two existing entry points
pass `None`, and their output stays byte-identical. That also leaves them fit for
their documented job — deterministic structural dumps for differential checks —
which is a secondary benefit, not the motive.

**Check.** `annotated_dump_resolves_control_ranges` asserts both directions on one
graph: the range resolved on an `HSlider`, a `Button` untouched, and
`dump_sig_readable` unchanged on the same term. `cargo test -p signals` (21),
`-p normalize`, and `eval_cpp_micro_differential` — which asserts on
`dump_sig_readable` fragments — are green, as are `cargo fmt --check` and
`cargo clippy`.

**Not done.** Soundfile controls are untouched: `SIGSOUNDFILE` carries a
`ControlId` too, but its metadata is not a `ControlRange` and no consumer asked for
it yet. The dump also still exposes controls only where they are *used*; a program
declaring a control it never reads shows nothing, which is correct for graph
analysis but means the dump is not a substitute for the UI listing.
