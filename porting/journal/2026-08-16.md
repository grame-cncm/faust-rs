# 2026-08-16

## `--dump-sig` now resolves the declared range of slider-like controls

Commit date: 2026-08-16

Source commit: this commit

A signal node stores only a stable `ui::ControlId`: `hslider("d", 100, 0, 2000, 1)`
lowers to `SIGHSLIDER(int(0))`, and the declared `init`/`min`/`max`/`step` live in
the UI registry that `propagate` publishes as `SignalCompileOutput::ui`. That split
is right for the compiler, but it makes the dump unusable for any analysis over the
exported graph: a consumer cannot tell a slider bounded to `0..15` from one bounded
to `0..100`, and those two index a 16-entry table very differently.

The gap showed up while feeding `--dump-sig` output into an external range checker.
Every table read whose index came from a control had to be reported as *not proven*,
not because the program was unsafe — the backend clamps it, `std::min<int>(…, 15)`,
from the compiler's own interval analysis — but because the information the clamp is
derived from never reaches the dump.

**Change.** New `signals::dump_sig_annotated(arena, root, &UiProgram)`. It behaves
exactly like `dump_sig_readable` except on `SIGVSLIDER`, `SIGHSLIDER`, `SIGNUMENTRY`,
`SIGVBARGRAPH` and `SIGHBARGRAPH`, where the control's `ControlRange` is resolved and
spliced in after the id child:

```
SIGHSLIDER(int(0), init=0.0, min=0.0, max=100.0, step=1.0)
SIGVBARGRAPH(int(0), init=0.0, min=-1.0, max=1.0, step=0.0, SIGINPUT(int(0)))
```

Controls with no range — `SIGBUTTON`, `SIGCHECKBOX` — are left exactly as before,
since `ControlSpec::range` is `None` for them. Numbers are formatted with `{:?}`,
the shortest round-tripping form for `f64`, so the annotation is readable and
lossless at once. `--dump-sig` is switched to the new function; `&out.ui` was
already in scope at that call site.

**Why not change `dump_sig` / `dump_sig_readable`.** The obvious move is to make the
existing dumps carry the ranges. They cannot, and the reason is dependency direction
rather than output stability: `dump_sig_readable` is called from
`normalize::normalform` and `normalize::mterm`, and from `compiler::error_mapping`
when attaching a `signal_expr` debug fact to a diagnostic. None of those own a
`UiProgram`, and none would gain anything from one; threading a control registry
into `normalize` to serve a dump would be invasive for no benefit there. So
`dump_node_iter` takes an `Option<&ui::UiProgram>`, the two existing entry points
pass `None`, and their output stays byte-identical. That also leaves them fit for
their documented job — deterministic structural dumps for differential checks —
which is a secondary benefit, not the motive.

**Check.** `annotated_dump_resolves_control_ranges` asserts both directions on one
graph: the range resolved on an `HSlider`, a `Button` untouched, and
`dump_sig_readable` unchanged on the same term. `cargo test -p signals` (21),
`-p normalize`, and `eval_cpp_micro_differential` — which asserts on
`dump_sig_readable` fragments — are green, as are `cargo fmt --check` and
`cargo clippy`.

**Not done.** Soundfile controls are untouched: `SIGSOUNDFILE` carries a
`ControlId` too, but its metadata is not a `ControlRange` and no consumer asked for
it yet. The dump also still exposes controls only where they are *used*; a program
declaring a control it never reads shows nothing, which is correct for graph
analysis but means the dump is not a substitute for the UI listing.
