## Classify unavailable C++ impulse oracles automatically

Commit date: 2026-07-31

Source commit: this commit

The impulse harness now preflights every selected DSP with the configured C++
Faust compiler before generating reference responses. It writes a cached,
configuration-sensitive manifest of supported and rejected DSPs, retains one
diagnostic log per C++ rejection, and filters only those unavailable-oracle
cases from every ordinary differential backend target. This is deliberately
separate from `KNOWN_FAIL_*`: a rejected C++ oracle such as
`ondemand_09_nested_feedback` cannot be compared, but is not evidence of a
faust-rs failure.

`make reference-report` exposes the current classification. The regular
backend, scheduling, vector, and execution-option targets ensure the reference
preflight happens before they plan their prerequisite graph, so they cannot
fail later merely because `reference/<dsp>.ir` was impossible to produce.

Validation: two-DSP fixture (`APF` supported, `ondemand_09_nested_feedback`
rejected by C++ Faust 2.87.3); native supported-oracle build; backend dry-run
proving the rejected DSP is absent from its plan.

## Define a generated-code optimization roadmap for Signal-to-FIR

Commit date: 2026-07-31

Source commit: this commit

Added a general Signal-to-FIR optimization roadmap that inventories the
existing variability placement, structural CSE, state-aware load reuse, delay
strategies, scheduling, and checked vector lowering before identifying the
next opportunities. The roadmap separates transformation legality,
profitability, and numerical/ABI policy, and recommends an observation-first
sequence: generated-code metrics, a common FIR effect/location vocabulary,
cost- and lifetime-aware materialization, local memory value numbering,
short-state register promotion, costed loop alternatives, and finally layout
and filter-specialized lowering.

The document uses the BPF old-state snapshot as a motivating cross-backend
example, explains why `RESTRICT` cannot replace common-FIR
reasoning, and defines semantic, structural, runtime, and compilation-cost
gates for every phase. Primary Faust, LLVM, Halide, SPEC, benchmark-statistics,
and workload-characterization references anchor the recommendations.

The performance section is corpus-independent. It separates mechanism,
application, and deployment claims; defines operating points and eligibility;
characterizes workloads with deterministic Signal/FIR feature vectors; and
requires stratification, redundancy and influence analysis before freezing a
manifest. It distinguishes broad sentinels, parameterized mechanism families,
and representative applications without combining their scores by default.
The primary measure is time per frame, compared through paired log-ratios. When
a single score is justified, the plan defines a family-balanced weighted
geometric mean, its effective weighted corpus size, confidence interval, and
mandatory tail/family diagnostics; a known deployment mix instead uses its
actual total-time ratio. A quantitative tooling and repetition guide separates
`faustbench` timing from counters, compiler remarks, disassembly, static CPU
models, cache simulation, and whole-command timing.

The roadmap now also defines a recursive compiler-improvement loop around that
measurement contract. Each evaluation epoch freezes its corpus, weights,
targets, budgets, semantic gates, minimum detectable effect, and stopping rule;
development mechanism families drive candidate search, while independent
application and shadow sets check generalization. The loop separates automated
measurement and profitability search from reviewed legality-changing compiler
work, evaluates a constrained Pareto vector rather than one opaque score, and
records every candidate in a replayable append-only ledger. Its "fixed point"
is deliberately empirical: no distinguishable admissible improvement was
found within a named search neighborhood and budget, not a claim of universal
compiler optimality. Phased L0–L4 automation starts with manifests and replay,
then bounded parameter/plan search, and permits generated transformations or
learned policies only after correctness and anti-overfitting controls are
established.

The closed-loop section now also budgets the experiment itself. It gives a
parameterized timed-kernel cost model, derives the 50-second per-workload lower
bound for a two-revision `faustbench -run 5` comparison, and shows that a
91-workload confirmation with five outer pairs already consumes about 6 hours
19 minutes before build and cooldown overhead. A staged semantic preflight,
mechanism screening, qualification, full confirmation, and attribution funnel
keeps broad candidate search affordable. The plan distinguishes faust-rs
candidate/parent measurements from C++ semantic-oracle and external-reference
measurements, constrains parallel timing to isolated workers, estimates both
machine and calendar budgets, and requires those estimates to be replaced by
observed L0/L1 throughput before a real epoch is frozen.

Validation: primary literature and tool-reference review; `faustbench` timing
source inspection at C++ reference `8eebea429` and arithmetic cross-check;
Markdown link and whitespace/diff review. Documentation-only change, so runtime
and compilation gates were not run.

## Make generated-code benchmarks statistically auditable

Commit date: 2026-07-31

Source commit: this commit

`make bench` now alternates C++ Faust and faust-rs execution order across the
DSP corpus, retains `inf`/`nan`, and distinguishes unsupported C++ primitives,
per-compiler failures, dual failures, and non-finite measurements. Only finite
positive pairs enter a new aggregate CSV containing the geometric-mean delta,
median delta, win/loss counts, and regressions above the configured warning
threshold. The per-DSP CSV keeps its original five columns and appends the run
order.

A self-contained synthetic harness test locks the alternating order, explicit
statuses, and aggregate calculations. The benchmark documentation now
describes the comparability policy and all output artifacts. It distinguishes
the quick default pass from the normal performance workflow, whose recommended
command is `make bench BENCH_OPTIONS="-double -run 5 -bs 512"`.

Validation: `make -C tests/impulse-tests bench-self-test`; focused real
`faustbench` smoke test; formatting and workspace quality gates.

## Clarify Rust execution-option methods in generated output

Commit date: 2026-07-31

Source commit: this commit

Rust output now places a short comment immediately before `impl FaustDsp for
mydsp` only when `-ec` and/or `-os` produce `control()` or `frame()`. It
explains that the trait deliberately retains the legacy block `compute`
contract, while those options expose `control()` and `frame()` as public
inherent methods. The execution-options integration test asserts both the
generated comment and its absence from classic output.

Validation: `cargo fmt --all`; targeted execution-options test; workspace
clippy; workspace tests.

## Omit empty FBC-to-C++ else branches

Commit date: 2026-07-31

Source commit: this commit

The FBC-to-C++ generator previously emitted `else {}` when an `If` false
branch contained only `Return`. It now renders branches independently and
omits an empty branch; when only the false branch has statements, it emits the
equivalent inverted condition.

Validation: `cargo fmt --all`; `cargo test -p codegen fbc_to_cpp::tests`;
`cargo clippy -p codegen --all-targets -- -D warnings`; and
`--dump-cpp-from-fbc tests/corpus/FOO.fbc` with no emitted `} else {`.
