# 2026-08-07

## Text backends print the compiler version and compile options in their headers

Commit date: 2026-08-07

Source commit: this commit

Every text-emitting backend now opens its generated file the way C++ Faust
does: a `Code generated with Faust <version> (...)` line followed by
`Compilation options: <opts>`, both readable straight off the source without
consulting the tool that produced it.

Two backends had nothing to build on. `c` had no header comment block at
all — its `emit_c_header` went straight to the include guard — and `codebox`
and `asc` printed a bare `"Code generated with faust-rs"` with no options
line. `rust`, `julia` and `cmajor` had an options line, but it was a string
literal (`"-lang rust"`) fixed at compile time, identical whether the run used
`-single` or `-double`.

The version comes from a new `codegen::VERSION` constant
(`env!("CARGO_PKG_VERSION")`), so it tracks the workspace version without the
`codegen` crate depending on `compiler` for it. The options string is real
per-invocation text: each backend's `Options` struct gained a
`compile_options: Option<String>` field, and the CLI now fills it with
`compile_options_json_string(Some(cli_lang_name(lang)), cli.double)` — the
same helper already used for the JSON companion's `compile_options` key, so
the header and the JSON sidecar agree by construction rather than by two
call sites happening to match. Callers that don't supply one (mostly tests,
and the library facade paths that predate this) fall back to a value derived
from whatever precision field the options struct already carries, so the
fallback isn't just `"-lang X"` with the precision silently dropped.

Adding the field broke every call site that built one of these `Options`
structs as a literal without `..Default::default()` — about a dozen across
`compiler`'s CLI, its test crates, and `xtask`. Most already used the spread
and needed nothing; the ones that didn't (`RustOptions`, `JuliaOptions`,
`CmajorOptions`, one `CodeboxOptions` construction site missing it, two
`COptions` sites) got the field added explicitly or the spread added,
whichever the call site already looked like.

One test's assumption stopped being an assumption: `codebox_backend.rs`'s
`double_precision_only_changes_literal_spelling` asserted that `-single` vs
`-double` output was identical after normalizing the `0.5f`/`0.5` literal
spelling — true before this change, false now that the header's compilation
options line also says `-single` or `-double`. The test normalizes both
differences now instead of asserting away the second one.

The version bump to 0.6.0 (workspace `Cargo.toml`) is otherwise unrelated to
the header work except that it's the number the new header line prints — it
was requested alongside the header change, not derived from it.

Verified against the CLI directly for all seven backends
(`cpp`/`c`/`rust`/`julia`/`cmajor`/`asc`/`codebox`), including `-double`
propagating into the rust header's options line. Full workspace `cargo test`
is green.

## `interp` was missing from the sweep, and the options line was a subset — both fixed, amended into the same commit

Commit date: 2026-08-07

Source commit: this commit

Stéphane asked to check `interp` specifically and verify against the real
Faust C++ source. Reading the vendored checkout at `/Users/letz/faust`
answered both halves at once: `interpreter_dsp_aux.hh`'s `write()` uses the
same `FAUSTVERSION` macro every other backend uses (nothing interp-specific),
and `interpreter_code_container.cpp:218` calls
`gGlobal->printCompilationOptions(compile_options)` — the identical function
`code_container.cpp` and `julia_code_container.cpp` call — to build the real
options string, not a placeholder.

Two gaps, once compared against that. `interp`'s own `FAUST_VERSION` constant
(`crates/codegen/src/backends/interp/serial.rs`) was a second, independently-
bumped literal (`"2.85.0-rust"`, tracking the vendored C++ oracle version
across `git log -S` history, not faust-rs's own release) — asked and
confirmed with Stéphane before touching it, since C++ has exactly one version
concept and keeping two here was a real divergence, not a deliberate one.
It's now `pub const FAUST_VERSION: &str = crate::VERSION;` — an alias, not a
second source of truth. And `compile_options` on the interp factory was
hardcoded to `""` at the only production call site
(`generate_interp_module`, commented "not set at this layer") and never
filled in downstream — every `.fbc` dump had an empty `compile_options` line
regardless of flags.

The second finding reopened the other seven backends' fix from earlier today:
their options line was `-lang X -single`/`-double`, a partial subset by the
CLI helper's own doc comment. C++'s `printCompilationOptions` prints far
more — `-mcd`, `-cn`/`-scn`/`-pn` when non-default, `-vec -lv -vs`, `-ss`,
and more that faust-rs has no flag for at all. `compile_options_full_string`
(`crates/compiler/src/cli/runner.rs`) mirrors the parts faust-rs actually
implements — every flag, `-mcd` included, appears only when it differs from
its default, which is a deliberate departure from C++ (which prints `-mcd`
and precision unconditionally): Stéphane asked for `-mcd` to stay silent at
its default rather than mirror that part of C++'s behavior, so the line
reads as "what this run changed," precision being the one exception since it
has no meaningful "unset" state. Plus `-table-init`/`-dlt`, which have no
C++ counterpart but are faust-rs's own codegen-affecting flags and belong
in the same line for the same reason. It replaces
`compile_options_json_string` at every CLI call site (source mode, fixture
mode, the shared JSON-companion emitter) so the header and the JSON sidecar
keep agreeing by construction; the lighter helper stays for the paths with no
`CliArgs` to draw from (`interp-ffi`'s C API, the ASC service facade).

That richer line broke two things it had no business breaking, both from the
same mistaken assumption: that the options-line echo says something about
whether the backend's *body* honors a flag. `backend_class_name_contract.rs`
infers "this backend supports `--class-name`" from whether custom output
contains the requested name — and now every backend's header contains `-cn
custom_name` whether or not the body does anything with it, so `codebox`
(flat, no class, never used `-cn`) started reading as passing when it
shouldn't. And three facade-vs-CLI byte-parity tests (rust, asc, cmajor)
compared full output including the header, but a facade call with
`Options::default()` has no `CliArgs` to build the full string from and
correctly falls back to a bare `-lang X -single`. Both are fixed the same
way: strip the options-echo line before comparing, so the tests check what
they were actually written to check.

Bench-verified again after the fix: all eight backends
(`cpp`/`c`/`rust`/`julia`/`cmajor`/`asc`/`codebox`/`interp`) print the same
`-mcd 16 -table-init runtime -ss 0 -single` by default, and `-cn Foo -mcd 8
... -vec -lv 0 -vs 32 ...` reflects real flags when passed. Amended into the
same commit as the earlier sweep (`fa966cb8`, previously `5fcdeb09`, not yet
pushed) rather than stacked as a second commit, since this is the same change
finished rather than a new one — Stéphane's call, not a default. Full
workspace `cargo test --no-fail-fast` is green.

## `-mcd` was unconditional after all — a magic `16` fixed, then centralized properly

Commit date: 2026-08-07

Source commit: this commit

Stéphane caught that `compile_options_full_string` still had
`if cli.mcd != 16 { ... }` — a bare literal duplicating `-mcd`'s
`default_value_t = 16` in `CliArgs` (`args.rs`), exactly the kind of drift
this whole change was supposed to prevent. First pass fixed only `-mcd`
(and, while at it, made `-ss`/`-table-init` conditional the same way —
they'd stayed unconditional from the first sweep, which was inconsistent
once `-mcd` wasn't). Stéphane then asked to centralize the defaults for
*all* the options rather than accept a second literal.

The first attempt at that was wrong and worth recording: `#[derive(Default)]`
alongside `#[derive(Parser)]` looks like it would reuse each field's
`default_value_t`, but it does not — it fills every field with its type's
plain `Default::default()`. `CliArgs::default().mcd` came out `0`, not `16`.
A unit test comparing the derived value against `CliArgs::try_parse_from(["faust-rs"])`
caught it before it shipped: silently wrong, and dangerous specifically
because it looks like the fix that was asked for. The `Default` derive was
reverted.

The actual fix is `cli_defaults()` (`args.rs`): re-parse an empty argument
list through the same `clap::Parser` derive that parses the real command
line, and read the resolved defaults back off the result. That is the only
way to get "what clap decided" without a second copy of the value — clap's
own attribute stays the one and only place a default is spelled out. A
pinning test (`cli_defaults_matches_documented_flag_defaults`) locks the
values this now depends on (`mcd: 16`, `dlt: u32::MAX`, `process_name:
"process"`, `scheduling_strategy: 0`, `table_init: Runtime`), so a future
change to one of those defaults is a visible diff in that test rather than a
silent shift in what the header omits.

`-cn`/`-scn`'s "mydsp"/"dsp" comparison couldn't use `cli_defaults()` the
same way — `CliArgs.class_name` defaults to `None` (unset), not to the
string `"mydsp"`; the "mydsp" convention lives one layer down, applied by
every backend's own `Options::default()` in `codegen`. Comparing against
`cli_defaults().class_name` would have made `-cn mydsp` print `-cn mydsp`
even though that's a no-op, the opposite of the fix. Two new constants,
`codegen::DEFAULT_CLASS_NAME`/`DEFAULT_SUPER_CLASS_NAME`, are now what both
`compile_options_full_string` and (documented, not yet retrofitted) every
backend's `Options::default()` should read from — the eight backends still
each spell `"mydsp"`/`"dsp"` locally, which is real remaining duplication,
just not the duplication that was asked about today.

Full workspace `cargo test --no-fail-fast` green; amended into the same
commit again, still unpushed.

## CI's `Lint and test` job was failing on `main` — a missing `faustlibraries/old` on the path, not a code bug

Commit date: 2026-08-07

Source commit: this commit

Stéphane linked a failing CI run
(`grame-cncm/faust-rs/actions/runs/31201726968`) after pushing the commit
above. `Lint and test` failed its `Test` step on all three OSes:
`eval_memo_scope.rs`'s two tests (added the day before, `4b22f857`, unrelated
to anything in this session) panicked compiling `spectral_tilt.dsp` —
"library could not resolve source file `oscillator.lib`".

First hypothesis was that the test's `compile()` helper bypasses
`FAUST_LIB_PATH` with a hardcoded `/usr/local/share/faust` fallback — plausible,
wrong. `merge_import_search_paths` (`crates/compiler/src/paths.rs`) reads
`FAUST_LIB_PATH` unconditionally regardless of what the caller passes, so
CI's `FAUST_LIB_PATH=$GITHUB_WORKSPACE/faustlibraries` should have been in
the search list either way.

The actual cause needed cloning the pinned `faustlibraries` commit
(`ecf2fdc23814...`) to look at directly: `oscillator.lib`, `filter.lib`,
`effect.lib` don't exist at its root — Faust renamed them
(`oscillators.lib`, `filters.lib`) and relocated `sawtooth_demo`,
`spectral_tilt_demo`, `spectral_level_demo` into `demos.lib`, `bypass1` into
`basics.lib`, years ago. They compile locally only because a real Faust
install's `/usr/local/share/faust` still ships the deprecated names as
compatibility shims (confirmed: `oscillator.lib` there opens with "WARNING:
Deprecated Library!! ... removed in August 2017") — a plain `faustlibraries`
git checkout, which is exactly what CI uses instead of a system install, has
no such shims. Not a `-rs` bug; the CI environment and a real dev machine
disagree about what's on the library path, and this is apparently the first
test to compile a corpus DSP that needs one of the deprecated names since
that gap opened.

First fix attempt edited `spectral_tilt.dsp` itself to import the current
names directly. Verified semantically identical against the deprecated
originals (same author, same UI labels, same implementation, just moved
files) and it passed against the pinned checkout — then reverted, on finding
the *actual* established fix already sitting in the same file: the
`vector_retention` job's `FAUST_LIB_PATH` already reads
`faustlibraries:faustlibraries/dx7:faustlibraries/old`, with a comment
explaining that `old/` is exactly for "historical DSPs that import legacy
names." `lint_and_test`'s own `FAUST_LIB_PATH` (added earlier, separately)
just never got that same treatment. `faustlibraries/old` does contain
`oscillator.lib`/`filter.lib`/`effect.lib` at the pinned commit — confirmed,
and confirmed the unmodified `spectral_tilt.dsp` compiles clean once that
directory is on the path. Editing a checked-in corpus fixture to route
around a CI path gap would have been the wrong layer to fix it at, and this
makes that concrete: the project had already chosen "add `old/` to the
path" as the answer, once, for the identical problem.

`lint_and_test` runs a matrix (`ubuntu-latest`/`macos-latest`/`windows-latest`);
`vector_retention` is Ubuntu-only and hardcodes `:` as the path separator,
which breaks `std::env::split_paths` on Windows. The fix uses a GitHub
Actions ternary (`matrix.os == 'windows-latest' && ';' || ':'`) to pick the
right one per runner.

Verified against the exact pinned `faustlibraries` checkout with both
`:`-joined (Ubuntu/macOS-shaped) and repo-relative path layouts, reproducing
CI's directory structure rather than trusting the local system install not
to mask the gap again. Full workspace `cargo test --no-fail-fast` and
`cargo clippy -- -D warnings` are green.

## Two more CI-only findings after the FAUST_LIB_PATH fix: a checker false positive and a threshold two commits already knew about

Commit date: 2026-08-07

Source commit: this commit

The `FAUST_LIB_PATH` fix above unblocked `Test`, but the pushed run
(`.../runs/31204857907/job/92953584754`) still failed at
`Structure check (Ubuntu)`, which runs four `xtask` commands as one
sequential shell step: `cli-parser-check`, `error-model-check`,
`ffi-boundary-check`, `structure-check`. `error-model-check` failed first,
so the step aborted there (bash `-e`) and the other three had never actually
run on CI — including `structure-check`, which turned out to have its own,
independent, already-red finding underneath.

**`error-model-check`'s finding was a false positive.** It flagged
`crates/eval/src/loop_detector.rs: legacy 'errors' import path detected` —
but the file has no `use errors::...` anywhere. The checker's `"errors::"`
pattern is a plain `.contains()`, and line 184's doc comment references
`` `diagnostic_errors::diverging_recursive_case_reports_eval_error_instead_of_aborting` ``
— a real test-module path from crates/eval's own diagnostics tests, unrelated
to the legacy top-level `errors` crate this check exists to keep out, but
containing `errors::` as a substring of a longer, legitimate identifier.
`contains_legacy_errors_import` (`crates/xtask/src/error_model_check.rs`)
now requires the character immediately before `errors::` to not be an
identifier character, so `diagnostic_errors::`/`user_errors::`/similar no
longer trip it while a real `use errors::Foo` (preceded by whitespace or
nothing) still does. A new test pins both directions. This is exactly the
"prefixed identifier" class of false positive a substring check invites, and
worth watching for on the other four patterns in the same function too —
`IntoDiagnostic`, `DiagnosticSeverity` and the rest just haven't collided
with a legitimate longer name yet.

**`structure-check`'s finding was real, from unrelated prior work.**
`signal_fir/vector/lower/signal.rs` — a single `impl PureVectorLowerer` kept
intact by design, per its own module doc — crossed the 2200-line review
threshold (to 2332) during yesterday's S6 generated-table work, a session
this one has no context for. That threshold's own doc comment already
anticipated this moment and had an opinion about it: it was raised once
before, from 2000 to 2200, with an explicit note to *prefer splitting the
file next time rather than raising the number again*. Stéphane's call, not a
default: asked, and the answer was to raise it again — to 2400, with margin
this time — rather than have this session attempt a structural split of a
numerically-sensitive vector-lowering path it doesn't have the S6 context
for. The threshold's doc comment is updated to say plainly that this is the
second time, and that splitting should win by default if it happens again.

Every `xtask` structure/policy check plus the full test suite, clippy, and
`cargo fmt --check` all run clean locally after both fixes — the same
sequence `Structure check (Ubuntu)` runs, run individually rather than
trusting the first green result.

## `examples-compare` gains `--per-symbol`, for corpora with no `process`

Commit date: 2026-08-07

Source commit: this commit

Stéphane asked for `examples-compare` to be able to compile
`faustlibraries/tests/*.dsp` — 50 files, each a flat list of independent
one-liners exercising one library function per line
(`db2linear_test = ba.db2linear(-6);`, `linear2db_test =
ba.linear2db(0.5);`, ...), never combined into a `process`. The existing
tool compiles one whole file per case; every one of these 50 files would
just fail outright with no `process` to compile, which answers nothing about
whether the 1110 individual definitions inside them actually work.

`-pn <name>` — Faust's flag for selecting a definition other than `process`
as the entry point, which faust-rs already implements identically to C++ —
is the right primitive; `examples-compare` just never had a reason to use it
before every case in a file had the same intended entry point. `--per-symbol`
scans each file for top-level `<name><suffix>` definitions (`--symbol-suffix`,
default `_test`, matching this corpus's own naming convention) and compiles
each one as its own case via `-pn`, turning "does this file compile" into
"does every case in it compile" — which is what these files are actually for.

The scan is deliberately line-based, not a Faust parse: unindented lines
whose left-hand side is a bare identifier (rejects `foo_test(x) = ...` —
`-pn` needs a fully-applied signal expression, a function can't stand alone
as `process`) ending in the suffix, skipping comments and `==`. Parsing the
corpus correctly is exactly the thing being tested, so the scanner that finds
cases can't depend on either compiler already working.

The files also import from their parent directory (`basics.lib` etc. live in
`faustlibraries/`, not `faustlibraries/tests/`), which the existing one-`-I`-
per-file design couldn't express, so `measure` now takes any number of
`-I` dirs and `--extra-include` (repeatable) supplies the rest.

Verified against the real corpus, not just the unit tests for the scanner:
`--per-symbol --filter basics_tests` finds all 89 cases in that one file and
compiles all 89 with both compilers; the full 50-file, 1110-case run (~8.5
minutes, `--extra-include` pointed at the faustlibraries checkout) finds 893
cases both compilers accept, 216 faust-rs rejects that C++ accepts, 0 the
other way — the gap report this was built for — and faust-rs 4x faster in
aggregate (65.6s vs 259.4s) despite `dx7_tests.dsp`'s FM-algorithm cases
alone costing C++ ~6s each. Per-symbol mode also defaults `--repeats` to 1
rather than the whole-file default of 3: hundreds of small, fast cases don't
need noise-averaging the way a handful of large files do, and tripling an
850-plus-case run for no benefit would just be slow. Full workspace
`cargo test`, `cargo clippy -p xtask -- -D warnings`, and `cli-parser-check`
are clean.
