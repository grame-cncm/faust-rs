## impulse-tests: the carillon against an ordinary CPU program

Commit date: 2026-11-07

Source commit: this commit

The carillon's CPU baseline was the GPU's own batch code run on the CPU, which is 4 to 5 times
slower there than ordinary instances of `pm.standardBell`: its voice-interleaved layout keeps each
voice's state N elements apart, and each mode is a call of its own. `bench` now also times
`cpu_faust_block_ns`, one scalar `refdsp` instance per bell (50 modes per `compute`) on 1, 4 and
10 threads with the same panned mix, and `gpu_vs_cpu` is against the fastest of those runs.

Measured (Apple M5, 256 frames, 48 kHz): GPU 0.62 / 0.64 / 0.84 / 2.0 ms at 1 / 37 / 256 / 1,024
bells; ordinary CPU on 4 threads 0.05 / 0.15 / 0.97 / 3.88 ms (one thread: 0.013 / 0.47 / 3.47 /
13.7 ms, which `faustbench-llvm` confirms: 0.44 ms for 37 distinct bells). The GPU now wins from
about 220 bells (11,000 modes), by ×1.15 at 256 and ×1.9 at 1,024, where the first measurement
reported ×5.7 and ×9.7. The two tunes (37 bells) take 0.47 ms on one core, 9 % of the budget,
against 43 to 46 % for the GPU in real time.

The same check on the banks of `porting/faust-gpu-audio-synthesis-2026-11-07-en.md` §5, with
`faustbench-llvm` and the bank written as one program: 1,024 modes take 0.18 ms on one core,
less than the GPU's 0.22 ms; 4,096 take 1.25 ms (GPU 0.38 ms, threads one instance at a time
1.06 ms). The partials are less affected (1,024 in 0.53 ms on one core). The synthesis now states
which baseline each figure uses: §1, §2.3, §3, §4, the modal section (renamed "a fit only at very
large scale") and the carillon section, whose lessons gain "the baseline must be the program a CPU
user would write".

## porting: audio on the GPU with Faust, a synthesis

Commit date: 2026-11-07

Source commit: this commit

`porting/faust-gpu-audio-synthesis-2026-11-07-en.md` draws the conclusions of the GPU batch plan:
the GPU is worth it for thousands of independent instances of one program (×2 to ×5 against the
CPU threads, ×7 to ×18 against one core), with blocks of 128 to 256 frames and tens of
milliseconds of latency, and not for one instance, ordinary polyphony, small blocks or `f64`. Three
measurements were added for it: one reverb instance on the GPU (30 to 100 times slower than one
CPU core), an additive bank of sine partials (GPU ahead from 4,096 partials, ×4.1 at 65,536) and a
modal bank of two-pole resonators (ahead from 1,024 modes, ×2.7 to ×2.8 beyond). It goes through
additive and modal synthesis, reverberation, physical models, polyphony, granular synthesis,
filter banks, spatialisation, spectral processing and offline learning, with a decision guide;
the main caveat is that the CPU baseline does not use SIMD across voices.

## fir: the independent checker of the voice layout (G3.3)

Commit date: 2026-11-07

Source commit: this commit

G3.3 of `porting/mojo-gpu-batch-g3-voice-layout-design-2026-11-07-en.md` (outcome §8).
`fir::batch::check::check_voice_layout` accepts a layout only if it is its source with the
per-voice state laid out as designed: it reads the classification from the output and checks its
semantics on the source (who touches what), recomputes every base from the source declarations
without reading the producer's report, walks source and output in lockstep across the two stores,
and checks the signatures and the control table. It shares nothing with the producer but the FIR
matcher. `layout_voices` now fails closed on it. Eight producer mutations (overlapping bases, a
short length, a dropped stride, a dropped voice, a shared field moved into an arena, an access
left behind, the voice on `staticInit`, an uncast store) are each rejected under the expected
rule; over the corpus the checker accepts all 132 laid-out programs, at most 9 ms per program for
producer and checker together.

## fir: `fir::batch::layout_voices`, per-voice state as a structure of arrays (G3.2)

Commit date: 2026-11-07

Source commit: this commit

G3.2 of `porting/mojo-gpu-batch-g3-voice-layout-design-2026-11-07-en.md` (outcome §7). The new
module `crates/fir/src/batch/` rewrites a flattened module so one instance structure serves N
voices: every `Struct` field of the instance lifecycle or a control moves into one arena per
element type, element k of voice v at `(base + k) * N + v`; the arenas become `Struct` pointer
fields beside `fVoices`; the four instance functions gain `voice: Int32` after `dsp`; fields
touched by `staticInit` alone (an inlined generator's working state) stay shared, as do `Static`
tables; the control bases are declared as the `Static` table `fVoiceControls`. The rewrite is
generic (any other node is rebuilt from its arena kind), and stores of another type are cast to
the arena type, because the FIR verifier types a `StoreTable` where it did not type the
producer's `StoreVar` of a `Float32` constant into a `FaustFloat` field. 14 unit tests. Over the
133 impulse programs (a temporary driver, the corpus needing the local libraries): 132 laid out,
`sound` refused, no new verifier error; `osc` drops from 256 KB to six elements per voice, its
table shared. Not wired into any backend, so no output changes and no compile cost; the
compile-budget gate cannot run on this machine. The public API gains the 12 items of the pass,
which the Mojo emitter will call in G3.5.

## porting: G3 design, per-voice state as a structure of arrays

Commit date: 2026-11-07

Source commit: this commit

`porting/mojo-gpu-batch-g3-voice-layout-design-2026-11-07-en.md` designs G3 of the GPU batch plan.
A synthetic `freeverb`-like kernel (16 feedback combs on 2,048-float lines per voice) on the M5
measured the two layouts before any compiler work: one structure per voice collapses past 1,024
voices (47.6 ms at 4,096), the structure of arrays stays flat (1.5 ms), ×31; ×39 at 16,384. The
design: a backend-neutral FIR-to-FIR pass `fir::batch::layout_voices` that moves every `Struct`
field into one arena per element type, element k of voice v at `(base + k) * N + v`, adds a
`voice` argument to the four instance lifecycle functions, leaves the `Static` tables shared (the
fix G2 named for `osc`), and refuses what it does not handle; an independent checker that
recomputes the layout and walks source and output in lockstep, with seven rejecting mutations; a
CPU differential against N scalar runs; then the Mojo batch emission, kept only if the real
large-state programs gain at least ×2. Four decisions are open: run-time or compile-time voice
count, per-voice or shared controls (UI nodes name their zone), a CLI option or an emitter option,
and where the differential runs.

G3, the structure-of-arrays layout; sharing the tables is the fix for `osc`.

## codegen, compiler: `-lang mojo`, the Mojo backend of grame-cncm/faust#1293

Commit date: 2026-11-07

Source commit: this commit

M1 to M3 of `porting/mojo-backend-port-analysis-and-plan-2026-11-06-en.md`. The emitter
`crates/codegen/src/backends/mojo/` writes the contract of the pull request's `architecture/mojo`
(pinned at `05ac86fb1`): struct `mydsp(FaustDsp)` with a `null_val` zone, snake-case lifecycle
methods, `Some[FaustGui]`/`Some[FaustMeta]` callbacks, C++ `snakeCase` names, with a rename
collision refused (`FRS-CGEN-MOJO-0004`). It departs from upstream where Mojo semantics differ
from C: typed literals, and `faust_idiv`/`faust_irem`/`faust_fmod`/`faust_round` helpers, since
Mojo `//`, `%` and `mod` floor and `round` rounds half to even. `-lang mojo` is wired through the
CLI, the `Compiler` facade, `CompilerError::CodegenMojo` and the capability row (`-vec` as plain
loops; `-ec`/`-os` refused), with a lifecycle conformance test. DIFF-BACK-010 records the
differences.

The impulse lane is opt-in (`make mojo`, `mojo-vec0`, `mojo-vec1`, `MOJO=` naming the
toolchain): a self-contained runtime in `tests/impulse-tests/archs/impulsemojo.mojo`. Scalar:
131/131 in 54 s, clock-domain programs included. The `-vec` lanes passed 91/91 on the
oracle-admitted set; their rerun on the 131 programs was still running at commit time.

The full run found a Mojo `1.1.0.dev2026090705` compiler hang: field accesses through the
receiver inside nested loops never finish compiling (`upsampling_04` to `_09` sat for eight
hours), at `-O0` as at `-O3`. The same accesses through a local reference compile at once, so a
generated method whose body has a loop takes its receiver as `self` and opens with
`ref dsp = self`; loops keep the C++ `for ... in range` form (test
`methods_with_loops_alias_their_receiver`). This also explains the ten-minute `-vec` builds
seen earlier. A first workaround, nested counted loops written as `while`, cured two levels of
nesting and not three, and was dropped. The defect is to be reported to modular/modular once
checked on the current nightly.

M4 (text differential against the pull request's compiler, run once by hand): the same method
set on 91/91 programs; field types differ on 59 from faust-rs's FIR layout (DIFF-BEH-009).
