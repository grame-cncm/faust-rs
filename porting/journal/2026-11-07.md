## porting: G3 design, per-voice state as a structure of arrays

Commit date: 2026-11-07

Source commit: this commit

`porting/mojo-gpu-batch-g3-voice-layout-design-2026-11-07-en.md` designs G3 of the GPU batch plan.
A synthetic `freeverb`-like kernel (16 feedback combs on 2,048-float lines per voice) on the M5
measured the two layouts before any compiler work: one structure per voice collapses past 1,024
voices (47.6 ms at 4,096), the structure of arrays stays flat (1.5 ms), ×31; ×39 at 16,384. The
design: a backend-neutral FIR-to-FIR pass `fir::batch::layout_voices` that moves every `Struct`
field into one arena per element type, element k of voice v at `(base + k) * N + v`, adds a
`voice` argument to the four instance lifecycle functions, leaves the `Static` tables shared (the
fix G2 named for `osc`), and refuses what it does not handle; an independent checker that
recomputes the layout and walks source and output in lockstep, with seven rejecting mutations; a
CPU differential against N scalar runs; then the Mojo batch emission, kept only if the real
large-state programs gain at least ×2. Four decisions are open: run-time or compile-time voice
count, per-voice or shared controls (UI nodes name their zone), a CLI option or an emitter option,
and where the differential runs.

## impulse-tests: `make mojo-gpu-bench`, the GPU cost model (G2)

Commit date: 2026-11-07

Source commit: this commit

G2 of `porting/mojo-gpu-batch-of-voices-plan-2026-11-07-en.md`. `archs/benchmojogpu.mojo` times one
block of N voices on the GPU (full, launch, copies, empty kernel; median of 100 blocks after 20
warm-up blocks) against the same voices on 1, 4 and 10 CPU threads; `make mojo-gpu-bench` sweeps
five programs over 64–65,536 voices and 64–512 frames. The probe of the morning was cold: with
warm-up, 1,024 `APF` voices take 215 µs a block, not 336; every block pays a floor of about 215 µs.
The GPU beats the best CPU threading only for `APF` (32 bytes of state), from 1,024 voices, by up
to ×3.6 (×13.7 against one core). `osc`, `freeverb`, `zita_rev1` and `karplus32` (150–480 KB of
state, tables or delay lines) never win, and the large-state ones degrade faster than the voice
count grows (`freeverb` ×16 in time for ×4 in voices at 4,096): the kernel reading
array-of-structures state far beyond the device caches. That is the condition the plan set for
G3, the structure-of-arrays layout; sharing the tables is the fix for `osc`.

## impulse-tests: `make mojo-gpu`, many voices per program on the GPU (G1)

Commit date: 2026-11-07

Source commit: this commit

G1 of `porting/mojo-gpu-batch-of-voices-plan-2026-11-07-en.md`, on Mojo `1.3.0.dev2026110705` with
`modular` `26.8.0.dev2026110705` (decision of the day). `archs/runimpulsemojogpu.mojo` runs 64
voices of each program on the Apple M5, one GPU thread per voice calling the unchanged scalar
`compute`; `make mojo-gpu` (opt-in) builds it in `-single`. Even voices get the impulse, odd ones
silence; the harness fails unless the voices are bit-identical by class, voices 0 and 1 match the
same `f32` program on the CPU within 1e-4 × max(1, peak), and no voice is silent where the CPU is
not. The oracle is the host running the identical text, because the CPU lane in `-single` itself
passes only 85 of 132 programs against the `f64` C++ references; `make mojo` keeps that check in
`-double` (132/132, rerun on 1.3 after the `Make.mojo` change).

Result: 131/131 (`sound` and `math`, which needs `f64`, are `KNOWN_FAIL_mojo-gpu`). Eight programs
drift apart from a rounding-level start amplified by feedback and run without the tolerance check
(`MOJO_GPU_DRIFT`); the GPU math functions were measured and are not the cause.

The silent failure of the morning probe (`freeverb`, `karplus32` writing nothing) was not the
state size: the channel pointer tables were in the thread's private memory, and a pointer to
private memory passed to a `compute` that is not inlined loses its writes on Metal, without error.
The harness keeps the tables in device memory; the generated text did not change.

## porting: many voices of a faust-rs Mojo program on a GPU, measurements and plan

Commit date: 2026-11-07

Source commit: this commit

`porting/mojo-gpu-batch-of-voices-plan-2026-11-07-en.md` measures, on the Apple M5 through Metal,
the two ways of putting a Faust program on a GPU. The `-gpu` path of grame-cncm/faust#1293 (one
kernel per stage of the loop graph of one instance) runs and matches the references on 6 of 8
programs, and is 270 to 2,600 times slower than the CPU: `APF` runs on one GPU thread. The batch
form of the September analysis (§3.3), N instance structures on the device and one thread per
voice running the ordinary `compute`, was probed by hand around faust-rs scalar Mojo output,
unchanged: `APF` agrees with the CPU to 1e-6 and is 15 times one CPU core at 16,384 voices, within
30 % of the real-time budget. `freeverb` and `karplus32`, with 150 and 480 KB of state per voice,
build and launch without error and write nothing; that is undiagnosed, and the timings of those
two are not reported. The plan: G1 a per-voice correctness lane with no silent failure, G2 a cost
model against all performance cores, G3 a structure-of-arrays FIR pass only if G2 calls for it,
G4 a real-time polyphonic runner.

## codegen, compiler: `-lang mojo`, the Mojo backend of grame-cncm/faust#1293

Commit date: 2026-11-07

Source commit: this commit

M1 to M3 of `porting/mojo-backend-port-analysis-and-plan-2026-11-06-en.md`. The emitter
`crates/codegen/src/backends/mojo/` writes the contract of the pull request's `architecture/mojo`
(pinned at `05ac86fb1`): struct `mydsp(FaustDsp)` with a `null_val` zone, snake-case lifecycle
methods, `Some[FaustGui]`/`Some[FaustMeta]` callbacks, C++ `snakeCase` names, with a rename
collision refused (`FRS-CGEN-MOJO-0004`). It departs from upstream where Mojo semantics differ
from C: typed literals, and `faust_idiv`/`faust_irem`/`faust_fmod`/`faust_round` helpers, since
Mojo `//`, `%` and `mod` floor and `round` rounds half to even. `-lang mojo` is wired through the
CLI, the `Compiler` facade, `CompilerError::CodegenMojo` and the capability row (`-vec` as plain
loops; `-ec`/`-os` refused), with a lifecycle conformance test. DIFF-BACK-010 records the
differences.

The impulse lane is opt-in (`make mojo`, `mojo-vec0`, `mojo-vec1`, `MOJO=` naming the
toolchain): a self-contained runtime in `tests/impulse-tests/archs/impulsemojo.mojo`. Scalar:
131/131 in 54 s, clock-domain programs included. The `-vec` lanes passed 91/91 on the
oracle-admitted set; their rerun on the 131 programs was still running at commit time.

The full run found a Mojo `1.1.0.dev2026090705` compiler hang: field accesses through the
receiver inside nested loops never finish compiling (`upsampling_04` to `_09` sat for eight
hours), at `-O0` as at `-O3`. The same accesses through a local reference compile at once, so a
generated method whose body has a loop takes its receiver as `self` and opens with
`ref dsp = self`; loops keep the C++ `for ... in range` form (test
`methods_with_loops_alias_their_receiver`). This also explains the ten-minute `-vec` builds
seen earlier. A first workaround, nested counted loops written as `while`, cured two levels of
nesting and not three, and was dropped. The defect is to be reported to modular/modular once
checked on the current nightly.

M4 (text differential against the pull request's compiler, run once by hand): the same method
set on 91/91 programs; field types differ on 59 from faust-rs's FIR layout (DIFF-BEH-009).
